# S15 — Foundation 基础平台系统设计

- 状态：设计建议（2026-11-06）。推荐方案已写成 [ADR-051](../adr/ADR-051-foundation-platform.md)、[ADR-052](../adr/ADR-052-org-account-authz-center.md)、[ADR-053](../adr/ADR-053-foundation-common-services.md)，见 [ADR-029](../adr/ADR-029-design-rulings.md) 第 69 条。**排期：2026-11-06 负责人选定方案 C**，Foundation 整体放在 M4 之后的 F 阶段，M3 业务系统按第 19.2 节的过渡约定自建最小权限（第 19 节）。
- 范围：在 [S9](S9-平台基座与企业接入.md) 能力地图、[ADR-015](../adr/ADR-015-identity-tenant-rbac.md)、[ADR-026](../adr/ADR-026-foundation.md) 的基础上，把 Foundation 定义为两部分：**Java 工程化底座**（父工程、依赖清单、starter、规范与模板）和**通用企业中台**（组织架构、用户权限、子系统与菜单与授权模式、模块与功能级微前端、公共服务），成为 Tioka 与客户业务系统（第一个是合同场景的 `lease-biz`）共用的基础。
- 对标：若依（RuoYi-Vue / RuoYi-Vue-Plus）的系统管理能力、IAM 联邦与 SCIM、AgentCore 的身份与工作区、Keycloak。
- 约束：单企业独立部署，不引入 `tenant_id`（ADR-029 第 60 条）；Java 17；前端 Vue 3 + Element Plus；本文只写设计，不含代码与脚本。

## 1. 结论

0. **Foundation = Java 工程化底座 + 通用企业中台**（2026-11-06 负责人明确）。底座是一组按版本发布的父工程、依赖清单、starter、测试基座、规则集与工程模板，从现有 `tioka-dependencies`、`tioka-framework` 抽出（第 5 节）；中台是独立部署的服务，管组织、用户、子系统、模块、功能、授权模式、菜单、数据范围和公共服务，门户作为微前端基座加载各子系统（第 6 节）。
1. **Foundation 中台做成独立部署的系统**，有自己的服务、库和管理台，不再是 Tioka 的一个模块。Tioka 和业务系统都是它的「子系统」（下文的「应用」即子系统）。原因是合同场景已经确定要新建独立部署的业务系统（M3-04），它同样需要用户、组织、角色、菜单、区域数据权限、字典和日志；不独立出来，就会在 Tioka 和业务系统里各做一套，以后每多一个业务系统再做一套。
2. **认证交给 Keycloak，Foundation 做主数据和授权**。Keycloak 已经是 FND-05 的验收 IdP，也是 Tioka 与业务系统共用的登录域（ADR-029 第 57 条）。登录协议、MFA、LDAP/AD 联邦、SAML、IM 扫码登录都用 Keycloak 现成能力配置出来；Foundation 不重写协议，只管「人、组织、账号、应用、角色、菜单、数据范围」。
3. **组织与人员以 Foundation 为准**（客户有 HR、IM 通讯录或 AD 时，由 Foundation 同步进来再分发），账号由 Foundation 推送到 Keycloak。各应用只读 Foundation 的投影，不各自维护用户表。
4. **权限分两层**：Foundation 管「应用级」的菜单、按钮权限码、角色和数据范围（若依那一套，加上可自定义的数据维度，如区域、门店）；应用内部的资源级权限（Tioka 的空间成员、资源 ACL、Cedar 策略、数据集策略）仍在应用里，但可以引用 Foundation 的组织、岗位、角色和维度值作为主体或属性。
5. **令牌里不放权限**。令牌只带身份；应用按「用户 + 应用」向 Foundation 取授权快照（角色、权限码、菜单、数据范围、版本号），缓存在本地，收到变更事件后失效。这样权限变更即时生效，令牌也不会膨胀。
6. **接入靠 SDK**：后端一个 Spring Boot starter，前端一个 Vue 包，覆盖登录、权限注解、数据范围条件、按钮指令、菜单路由、字典组件、组织人员选择器、审计上报。非 Java 应用照 OpenAPI 与事件契约接入。
7. **公共服务按「业务系统真用得上」筛选**：字典、参数、审计与登录日志、消息中心与公告、文件、工作日历、编号规则。若依的代码生成、定时任务中心、服务监控、多租户不做（第 7 节逐项说明）。
8. **授权模式按子系统选择**：集中、分级、混合、自管四种；另有组织分级管理员和按子系统、模块、功能的功能开关（第 6.2 节）。
9. **微前端**：门户为基座，推荐无界（wujie）承载 Vue 3 + Vite 子应用；菜单项声明加载方式，子应用可独立运行（第 6.3 节）。
10. **排期**：后端约 122、前端约 45 人天（含底座、子系统目录、微前端与两次迁移）。负责人选定方案 C：Foundation 放在 M4 之后的 F 阶段（约 W70–W80，按 3 后端 + 1 前端约 11 周）；M3 业务系统按过渡约定自建最小权限，M1〜M4 周次不变（第 19 节）。

## 2. 为什么现在要独立出来

| 现状 | 问题 |
| --- | --- |
| 用户、角色、组、成员都在 Tioka `system` 模块（M0-02、M1-01） | 只服务 Tioka。业务系统 `lease-biz` 要按区域控制谁能看哪些合同（M3-04 BIZ-08），目前只能自己再做一套用户角色和区域授权 |
| 组织同步（FND-09）、SAML/LDAP（FND-10）排在 M4 | 合同场景在 M3 上线影子期，法务、经办人的部门与区域要靠手工维护，两边各维护一次 |
| ADR-026 的外部身份映射、离职处理只针对 Tioka | 员工离职后，Tioka 吊销了令牌，业务系统还能登录 |
| 管理后台（HCI-03）是 Tioka 内的页面 | 业务系统管理员要学两套界面；客户运维要在多个系统里开通同一个人 |
| 客户后续还会有租金结构化、执行预警等业务系统（ADR-029 第 50 条后续场景） | 每个系统重复做一遍基础功能，权限口径不一致，审计无法汇总 |

## 3. 定位与边界

### 3.1 做什么

- 统一登录与单点登录（由 Keycloak 承担协议，Foundation 承担配置与管理）。
- 组织、人员、岗位、职级、账号的主数据与同步。
- 应用注册、客户端与服务账号。
- 权限中心：菜单、权限码、角色、授权、数据范围与自定义数据维度、授权快照。
- 公共服务：字典、参数、消息与公告、文件、审计与登录日志、工作日历、编号规则。
- Java 工程化底座：父工程、依赖清单、starter、测试基座、规则集、工程模板与 CI 模板（第 5 节）。
- 子系统、模块、功能目录与授权模式、功能开关、分级管理（第 6.1、6.2 节）。
- 微前端基座与子应用接入规范（第 6.3 节）。
- 接入 SDK 与契约：后端 starter、前端包、OpenAPI、事件。
- 门户：应用启动台、个人中心、统一消息与待办入口。

### 3.2 不做什么

| 不做 | 由谁承担 |
| --- | --- |
| 登录协议实现（OIDC、SAML、LDAP 绑定、TOTP） | Keycloak |
| 应用内的资源级权限（某个 Agent 谁能编辑、某份合同谁经办） | 各应用（Tioka 的 ResourceGuard 与 ACL，业务系统自己的业务规则） |
| 工具调用策略、数据集行列策略 | Tioka 的 GOV-07（Cedar）、ADR-040（CEL） |
| 业务审批流 | 业务系统自身或后续单独选型；Tioka 的人工审批仍在 Orchestration |
| 指标监控与告警 | GOV-08（OpenTelemetry、Prometheus）、GOV-13 |
| 多租户 | 不做（ADR-029 第 60 条）；集团多公司用组织树表达 |
| 代码生成 | 不做（团队用 Cursor） |

### 3.3 与 Keycloak 的分工

| 事项 | Keycloak | Foundation |
| --- | --- | --- |
| 账号的登录凭证（本地密码、TOTP） | 保存与校验 | 发起创建、停用、重置，不保存密码 |
| 登录方式（OIDC、SAML、LDAP、IM 扫码） | 协议实现与身份代理 | 管理界面封装常用配置，复杂配置引导到 Keycloak 控制台 |
| 会话与令牌 | 签发、刷新、吊销 | 触发吊销（离职、停用、强制下线），展示在线会话 |
| 用户、组织、岗位 | 只保留登录所需的最小用户记录 | 主数据 |
| 角色、菜单、数据范围 | 不存 | 主数据，生成授权快照 |
| 客户端（应用） | 实际的 OIDC 客户端 | 应用登记，自动开通与轮换客户端密钥 |
| 登录事件 | 产生 | 采集、留存、查询 |

一句话：**Keycloak 回答「你是谁」，Foundation 回答「你在组织里是谁、在每个应用里能做什么」**。

## 4. 总体架构

```
                         ┌────────────── 客户侧来源 ──────────────┐
                         │ HR 接口 / 飞书通讯录 / 钉钉 / 企微 / AD │
                         └──────────────┬─────────────────────────┘
                                        │ 同步（拉取 / SCIM 推送）
┌──────────────┐  管理接口   ┌──────────▼──────────┐   事件（RocketMQ / Webhook）
│   Keycloak   │◀───────────│   Foundation 服务    │──────────────┐
│ 登录与令牌    │  登录事件   │ 主数据·权限中心·公共服务│              │
└──────┬───────┘───────────▶└──────────┬──────────┘              │
       │ OIDC                    授权快照 / 字典 / 消息 API         │
       │                                │                         │
┌──────▼───────────────────────────────▼─────────────────────────▼──┐
│ 接入应用：Tioka（api / worker）· lease-biz · 后续业务系统 · 门户与管理台 │
│ 后端 starter：令牌校验、授权快照缓存、权限注解、数据范围、审计上报          │
│ 前端包：登录跳转、菜单路由、按钮指令、字典组件、组织人员选择器              │
└───────────────────────────────────────────────────────────────────┘
```

| 组件 | 说明 |
| --- | --- |
| Foundation 服务 | 一个 Spring Boot 应用，独立 PostgreSQL 库（可与 Tioka 共用实例、不同库）、共用 Redis 与 RocketMQ（键与主题加前缀 `fdn`）；多实例无状态，同步与对账任务靠 Redis 锁单实例执行 |
| Foundation 管理台 | Vue 3 + Element Plus 单页，自身也是一个接入应用，走同一套 SDK |
| 门户 | 与管理台同一前端工程的另一个入口：应用启动台、个人中心、消息与待办 |
| Keycloak | 一个 realm（默认名 `enterprise`），Foundation 用服务账号调它的管理接口；数据库可与 Foundation 共用实例 |
| 后端 starter | 供 Java 应用引用，版本与 Foundation 服务的接口版本对齐 |
| 前端包 | 供 Vue 应用引用，Tioka 前端与业务系统前端共用 |

**技术栈与 Tioka 一致**：Java 17、Spring Boot 3、MyBatis-Plus、PostgreSQL、Redis、RocketMQ、Flyway、Vue 3、Element Plus。同一团队维护，CI 与部署脚本可复用。

**代码位置（推荐）**：单独仓库 `tioka-foundation`，与 `lease-biz` 一样和 Tioka 只通过接口与事件交互。备选是放在 Tioka 仓库里的独立 Maven 工程（第 20 节）。

## 5. Java 工程化底座

Foundation 的第一部分是工程化底座：Tioka、Foundation 中台本身、业务系统以及以后的子系统，都从同一套父工程、依赖清单、starter 和规范起步。它不是一个运行的服务，而是一组按版本发布的 Maven 构件、工程模板和规则集。

### 5.1 现状

Tioka 根目录已有 `tioka-dependencies`（版本清单）与 `tioka-framework`（错误码与统一返回、ID、Jackson、请求上下文、持久层基类与空间过滤、`Principal` 与权限注解、领域事件、trace 上下文）。这些代码大部分是通用的，但和 Tioka 绑在一起：包名、配置前缀是 `tioka`，`Principal` 带空间概念，没有单独发布，业务系统无法直接引用。

### 5.2 构件划分

| 构件 | 内容 | 来源 |
| --- | --- | --- |
| `foundation-dependencies` | 统一版本清单：Spring Boot、MyBatis-Plus、Redisson、RocketMQ、Hutool、MapStruct、springdoc、Testcontainers、ArchUnit 等 | 由 `tioka-dependencies` 抽出 |
| `foundation-parent` | 父工程：Java 17、编译参数、`-parameters`、代码格式与静态检查插件、`flatten`、版本号规则、发布到私有仓库 | 新建 |
| `foundation-starter-core` | 错误码体系与统一返回、业务异常、ID（ULID）、Jackson 约定、时间统一 UTC、请求上下文 | 由 `tioka-framework` 的 error、id、jackson、context 抽出 |
| `foundation-starter-web` | 全局异常处理、接口约定（分页、排序、过滤参数）、`Idempotency-Key` 处理、OpenAPI 生成、请求日志与脱敏 | 新建，吸收 Tioka 各 Controller 的共性 |
| `foundation-starter-security` | OIDC 资源服务、当前用户、权限注解、授权快照客户端、数据范围条件、`@PublicApi` 白名单、服务账号调用 | 由 `tioka-framework` 的 security 抽出通用部分；第 12.2 节的 SDK 即此构件 |
| `foundation-starter-data` | MyBatis-Plus 配置、基类 DO（审计字段、乐观锁、逻辑删除约定）、只追加与不可变快照基类、Flyway 约定（号段、命名）、多数据源可选 | 由 `tioka-framework` 的 persistence 抽出；空间过滤留在 Tioka |
| `foundation-starter-mq` | RocketMQ 封装、领域事件、outbox 表与中继、消费幂等表、死信处理约定 | 由 Tioka 的 messaging 与 M2-01 outbox 设计抽出 |
| `foundation-starter-cache` | Redis 与 Redisson、键前缀、分布式锁、限流 | 新建 |
| `foundation-starter-observability` | OpenTelemetry、Micrometer、日志格式与 traceId 透传、健康检查 | 由 trace 抽出，对齐 GOV-08 |
| `foundation-starter-audit` | 操作审计注解、异步上报、本地落盘重试 | 新建，对接第 13 节审计服务 |
| `foundation-starter-client` | 中台客户端：字典、参数、组织查询、消息与待办、文件、编号 | 新建，第 12.2 节其余能力 |
| `foundation-test` | 测试基座：Testcontainers（PostgreSQL、Redis、RocketMQ、Keycloak）、测试数据构造、通用 ArchUnit 规则集 | 由 Tioka 的闸门基座抽出 |

各 starter 只依赖 core，彼此不互相依赖（audit 依赖 security 取当前用户除外），应用按需引用。配置前缀统一为 `foundation.*`。

### 5.3 工程规范

- **模块分层**：每个业务模块拆 `-api`（对外契约、DTO、事件）与 `-biz`（实现），编译期只允许依赖其他模块的 `-api`，与 Tioka 现行规则一致（`module-dependencies.md`）。
- **包结构**：`api`（Controller）、`application`、`domain`、`infrastructure`，与 Tioka 现有 `system` 模块一致。
- **规则集**：ArchUnit 规则随 `foundation-test` 发布：Controller 必须声明权限或 `@PublicApi`、禁止在请求线程同步调外部系统、禁止 `tenant_id`（第 60 条）、权限码只能引用常量目录、跨模块只依赖 `-api`。各项目引用后自动生效，豁免需登记。
- **工程模板**：提供一个模板工程（不是代码生成器），含父工程、示例模块、权限清单文件、Flyway 目录、CI 流水线、Dockerfile、Helm 片段与接入自检。新子系统从模板复制起步。
- **CI 模板**：编译、单元测试、集成测试（Testcontainers）、ArchUnit、依赖漏洞扫描、OpenAPI 契约比对、权限清单校验、镜像构建。
- **版本**：底座按语义化版本发布；破坏性变更只在主版本；每个版本附升级说明。各项目锁定版本，升级单独提交。

### 5.4 Tioka 的迁移

Tioka 改为以 `foundation-parent` 为父工程、导入 `foundation-dependencies`，`tioka-framework` 只保留 Tioka 特有部分（空间与归属过滤、`Principal` 的空间字段、Runtime 执行器等），其余换成对应 starter。迁移按 starter 逐个进行，每步保持 G0〜G3 闸门通过；包名变化用一次性重构完成，不保留兼容层。

## 6. 子系统、授权模式与微前端

Foundation 的第二部分是企业中台：组织架构、用户权限（第 8〜11 节）、公共服务（第 13 节），以及本节的「子系统 → 模块 → 功能」目录、授权模式和微前端。**本文后续提到的「应用」即子系统**。

### 6.1 子系统、模块与功能目录

| 层级 | 说明 | 例子 |
| --- | --- | --- |
| 子系统 | 独立部署、独立登录客户端的系统 | Tioka、合同业务系统、Foundation 管理台 |
| 模块 | 子系统内的业务板块，对应一个一级菜单或一个微前端子应用 | Tioka 的「模型中枢」「知识」「工作流」；业务系统的「合同」「要点库」 |
| 功能 | 一个可授权的页面或能力，对应一个菜单项 | 「供应商管理」「合同台账」 |
| 操作 | 功能内的按钮或接口，对应权限码 | `contract:submit`、`model:credential:admin` |

目录由子系统的权限清单声明（第 11.1 节）：清单里除菜单与权限码外，还声明模块、功能、每个功能的前端加载方式（第 6.3 节）。管理台按子系统 → 模块 → 功能 → 操作展示一棵树，授权时可以整模块勾选。

**功能开关**：管理员可以按子系统、模块、功能停用（例如某客户不买「工作流」模块）。停用的功能从所有人的快照中剔除，菜单不显示，接口由 starter 直接返回 403，不需要各子系统自己判断。

### 6.2 授权模式

不同子系统对「权限由谁管」的要求不同，每个子系统登记时选择一种授权模式：

| 模式 | Foundation 管什么 | 子系统管什么 | 适用 |
| --- | --- | --- | --- |
| 集中授权 | 角色、菜单、权限码、数据范围全部 | 只执行（starter 校验） | 新建的业务系统，如合同业务系统 |
| 分级授权 | 同上，但该子系统的角色与授权交给「子系统管理员」维护，系统管理员只指定子系统管理员 | 只执行 | 子系统较多、各业务线自己管人的企业 |
| 混合授权 | 菜单、功能、权限码与系统级角色 | 资源级权限（谁能编辑哪个 Agent、哪个知识库） | Tioka |
| 自管授权 | 只提供身份、组织与单点登录 | 全部授权自己管；Foundation 只登记入口与菜单链接 | 外购系统、遗留系统 |

另外支持**组织分级管理员**：可以把某个组织单元子树的人员维护与授权交给该单位的管理员，他只能看到并授予自己被授权范围内的角色，不能把高于自己的权限授给别人。

自管授权的子系统可以在以后改为集中授权：Foundation 提供「从子系统导入现有角色与用户角色」的一次性导入，导入结果先预览再生效。

### 6.3 微前端

门户（Foundation 前端）作为**基座应用**，各子系统的前端以**子应用**方式按模块或功能加载，用户在一个门户里使用所有子系统，同时每个子系统仍可单独访问。

| 项 | 设计 |
| --- | --- |
| 框架 | 推荐无界（wujie）：用 iframe 承载 JS 沙箱、Web Component 承载 DOM，对 Vite 构建的 Vue 3 子应用无需改造构建配置，样式与全局变量天然隔离，子应用可保活 |
| 加载粒度 | 菜单项声明加载方式：内置路由（门户自身页面）、子应用（指定子应用入口与子路由）、iframe（第三方页面）、外链（新窗口）。一个子系统通常注册为一个子应用，模块与功能是子应用内的路由；对体量大的模块（如 Tioka 的工作流画布）可以单独注册为一个子应用 |
| 登录状态 | 基座完成登录；子应用通过前端包取令牌，不再各自跳转登录；单独访问子应用时前端包自行走单点登录 |
| 菜单与路由 | 菜单只来自授权快照；基座路由与子应用路由同步，刷新与深链可直达子应用的具体页面 |
| 通信 | 只允许经前端包提供的通信接口：基座向子应用下发用户、主题、语言；子应用向基座发「打开某功能」「更新待办数」「显示通知」等事件。事件名与载荷在前端包中统一定义，不允许子应用直接访问基座全局对象 |
| 共享依赖 | 不强制共享 Vue 与 Element Plus 实例（隔离优先）；公共组件（组织人员选择器、字典组件、合同模型确认组件 `@tioka/ontology-confirm`）以 npm 包形式发布、各子应用自行引入 |
| 统一外观 | 前端包提供主题变量与布局规范；子应用在基座内运行时隐藏自身外层布局 |
| 子应用要求 | 可独立运行；使用前端包；配置可被基座加载的公共路径；不在全局写持久状态；按接入自检（第 12.1 节）增加「基座内加载、深链、保活切换」三项 |
| Tioka 前端 | 管理与构建类页面（模型中枢、Agent、Flow、知识、审计）作为子应用挂入门户；对话界面同时保留独立入口，供只用对话的员工直接访问 |
| 降级 | 子应用加载失败时显示错误页与「在新窗口打开」按钮，不影响基座与其他子应用 |

## 7. 与若依的对标

若依是国内企业后台最常见的基座，客户运维人员普遍熟悉它的菜单结构。Foundation 的管理台菜单按若依的习惯组织，降低学习成本；能力上按下表取舍。

| 若依能力 | Foundation 处理 | 说明 |
| --- | --- | --- |
| 用户管理 | 采纳并拆分 | 拆成「人员」（组织里的人）与「账号」（登录身份），一人可有多账号来源、可兼职多部门 |
| 部门管理 | 采纳并扩展 | 组织单元分集团、公司、部门三类，支持多公司 |
| 岗位管理 | 采纳 | 增加职级；岗位可作为授权对象 |
| 角色管理 | 采纳并扩展 | 角色属于某个应用或全局；授权对象可以是人员、部门、岗位 |
| 菜单管理 | 改造 | 菜单与按钮权限码由应用随版本提交「权限清单」导入，管理台只调整显示与排序，不手工新增权限码，避免代码与配置漂移 |
| 数据权限（全部、自定义、本部门、本部门及以下、本人） | 采纳并扩展 | 五档保留，增加自定义数据维度（区域、门店、项目等），见第 11.4 节 |
| 字典管理 | 采纳 | 增加应用归属、版本与变更事件 |
| 参数设置 | 采纳 | 增加敏感参数（只写不读）与变更审计 |
| 通知公告 | 采纳 | 并入消息中心 |
| 操作日志、登录日志 | 采纳并集中 | 各应用经 SDK 上报，Foundation 集中查询；Tioka 的 GOV-02 审计仍在 Tioka，只把管理类操作镜像过来 |
| 在线用户、强退 | 采纳 | 数据来自 Keycloak 会话 |
| 客户端管理（多端认证） | 采纳 | 即应用注册与 OIDC 客户端 |
| 三方登录（JustAuth） | 改为 Keycloak 身份代理 | 飞书、钉钉、企微扫码作为 Keycloak 的身份提供方 |
| 对象存储（OSS） | 采纳（P2） | 文件服务，后端用 MinIO 或客户 OSS |
| 短信、邮件 | 采纳 | 消息中心的渠道，接口沿用 ADR-029 第 56 条的 `NotificationChannel` |
| 多租户 | 不做 | ADR-029 第 60 条 |
| 定时任务（Quartz、XXL-Job、SnailJob） | 不做中心化调度 | Foundation 自身的同步、对账任务内置；各应用用各自调度（Tioka 已有 scheduler 角色） |
| 代码生成 | 不做 | 团队用 Cursor |
| 服务监控、缓存监控、Admin 监控 | 不做 | 走 GOV-08 的 Prometheus 与 Grafana |
| 工作流（Flowable、Warm-Flow） | 不做 | 见第 3.2 节 |
| 数据脱敏、字段加密、接口加密 | 部分采纳 | 敏感字段加密复用 FND-08 的 `CredentialCipher` 思路，在 Foundation 内独立一份主密钥；接口加密依赖 TLS，不另做 |
| 幂等、限流、分布式锁 | 作为 SDK 约定 | 写接口要求 `Idempotency-Key`（与 M3-04 一致），不单独做组件 |
| 国际化 | 预留 | 菜单与字典带多语言名字段，界面先只做中文 |

## 8. 领域模型

### 8.1 组织与人员

| 实体 | 关键字段（说明） | 规则 |
| --- | --- | --- |
| 组织单元 | 编码、名称、类型（集团 / 公司 / 部门）、上级、排序、负责人、状态、来源与外部 ID、生效时间 | 编码全局唯一；树深不超过 10 层；停用前要求下级与在岗人员已迁出 |
| 岗位 | 编码、名称、所属组织单元（可空表示全局岗位）、状态 | 可作为角色授予对象 |
| 职级 | 编码、名称、序列、等级 | 只做属性，供数据规则与策略引用 |
| 人员 | 工号、姓名、手机、邮箱、类型（员工 / 外包 / 数字员工）、状态（在职 / 停用 / 离职）、来源与外部 ID | 工号唯一；手机、邮箱加密存储，列表脱敏显示 |
| 任职 | 人员、组织单元、岗位、是否主任职、开始与结束日期 | 一人恰有一个主任职；兼职用多条任职表达 |
| 汇报关系 | 人员、直属上级 | 可由同步来源提供，也可按组织负责人推导 |

**数字员工**：人员类型增加「数字员工」，对应 Tioka 的已发布 Agent（ADR-032 岗位授权书）。它出现在组织树里，可以有岗位、可以被选为待办处理人，**没有登录账号**，权限仍由 Tioka 按授权书与负责人权限求交集（ADR-032、ADR-039）。人员档案由 Tioka 在 Agent 上岗与下岗时经接口维护，负责人字段必填。

### 8.2 账号与身份

| 实体 | 关键字段 | 规则 |
| --- | --- | --- |
| 账号 | 登录名、关联人员、Keycloak 用户 ID、状态（正常 / 锁定 / 停用）、类型（个人 / 应急管理员）、最近登录 | 一个人员最多一个个人账号；应急管理员不关联人员，默认停用，启用需双人操作并审计 |
| 外部身份 | 来源（飞书 open_id 与 union_id、钉钉 userId、企微 userId、AD objectGUID、SCIM externalId）、外部 ID、关联人员、关联方式、关联时间 | 继承 ADR-026：按工号或已验证邮箱自动关联，或由本人用该来源登录后确认；**不允许仅凭姓名匹配** |
| 服务账号 | 名称、所属应用、Keycloak 客户端、可用的权限码、状态、负责人、过期时间 | 只用 client credentials 流程；负责人离职时进入交接待办 |

Tioka 的个人与空间 API Key（FND-06）仍在 Tioka，因为它绑定空间；它的所有人引用 Foundation 账号。

### 8.3 应用与权限

| 实体 | 关键字段 | 规则 |
| --- | --- | --- |
| 应用 | 编码、名称、图标、访问地址、Keycloak 客户端、回调地址、负责人、状态、权限清单版本 | 编码不可改；Foundation 管理台与门户本身也登记为应用 |
| 权限清单 | 应用、版本、内容哈希、导入时间、导入人 | 每个应用版本发布时提交一次；同哈希不重复导入 |
| 菜单 | 应用、编码、名称、类型（目录 / 菜单 / 按钮）、上级、路由路径、组件标识、图标、排序、是否显示、权限码 | 来自权限清单；管理台只能改名称、图标、排序、显示 |
| 权限码 | 应用、编码（`资源:动作`，与 M1-01 的权限点格式一致）、说明、风险级别 | 来自权限清单；高风险权限码授予时需二次确认并审计 |
| 角色 | 编码、名称、范围（全局 / 某应用）、内置标志、权限码集合、数据范围、互斥角色 | 内置角色不可删；全局角色只含 Foundation 自身的权限码 |
| 授权 | 角色、授予对象（人员 / 组织单元 / 岗位）、是否含下级组织、生效与失效时间、来源（手工 / 规则 / 同步） | 同步与规则产生的授权不覆盖手工授权（延续 ADR-026） |

### 8.4 数据权限

| 实体 | 关键字段 | 规则 |
| --- | --- | --- |
| 数据维度 | 应用（可空表示全局）、编码（如 `region`、`store`）、名称、值来源（字典 / 组织树 / 应用上报的值列表）、是否层级 | 维度由应用的权限清单声明或管理员新建 |
| 维度值 | 维度、值编码、名称、上级 | 应用上报的值列表经接口增量维护 |
| 角色数据范围 | 角色、部门范围（全部 / 本部门 / 本部门及以下 / 本人 / 自定义部门）、各维度的取值集合（含「全部」） | 一个角色可同时限定部门范围与多个维度，之间取交集 |
| 人员维度授予 | 人员、维度、取值集合、来源 | 用于「某人额外负责华东区」这类不走角色的授予 |

### 8.5 公共数据

字典（类型与项）、参数、消息、公告、文件元数据、工作日历、编号规则、审计记录、登录日志、同步任务与同步日志，见第 13 节。

## 9. 认证与单点登录

### 9.1 登录方式

| 方式 | 实现 | 优先级 |
| --- | --- | --- |
| 账号密码 | Keycloak 本地凭证；密码策略、失败锁定、过期由 Foundation 管理台设置后下发到 realm | P0 |
| 企业 IdP（OIDC） | Keycloak 身份代理到客户 IdP（Entra ID、Okta、客户自建） | P0（配置） |
| LDAP / AD | Keycloak 用户联邦，只做认证；人员数据由 Foundation 同步 | P1 |
| SAML 2.0 | Keycloak 身份代理 | P1（配置） |
| 飞书、企微、钉钉扫码 | Keycloak 身份代理（OAuth 类提供方），首次登录按 8.2 规则关联人员 | P1 |
| TOTP 二次验证 | Keycloak 必需动作；可按角色强制（如系统管理员、安全管理员） | P1 |
| CAS | 有客户需要时用 Keycloak 社区扩展或网关，不在本期 | — |

这样 FND-10（SAML、LDAP）从「编码」变成「配置 + 验收」，原 M4 的工作量明显减少。

### 9.2 登录流程

1. 用户访问任一应用，前端包发现未登录，跳到 Keycloak 授权页（授权码 + PKCE）。
2. Keycloak 完成认证（本地、代理或联邦），签发令牌。令牌里有：Keycloak 用户 ID、Foundation 账号 ID、人员 ID、工号、姓名、主组织单元编码。**不带角色和权限**。
3. 应用后端用 starter 校验令牌，按「人员 + 应用」取授权快照（第 11.3 节）。Tioka 延续 FND-05 的做法，把 OIDC 令牌换成自己的 `tka_` 令牌，`Principal` 的角色与权限来自快照。
4. 已登录的用户打开另一个应用时直接单点登录。

**关联失败**：外部身份无法关联到人员时，Keycloak 首次登录流程停在「请联系管理员」页，同时在 Foundation 生成一条待处理关联，管理员确认后用户重新登录即可。不自动建人员。

### 9.3 会话与注销

- 会话时长、空闲超时由 Foundation 设置后下发到 realm；默认空闲 30 分钟、最长 10 小时，可按等保要求调整。
- 单点注销：Keycloak 后端通道注销通知各应用；Tioka 收到后吊销对应 `tka_` 令牌。
- 强制下线：管理台在线用户页操作，Foundation 调 Keycloak 吊销会话，并发出 `fdn.account.sessions_revoked` 事件，应用据此吊销自己的本地令牌。

### 9.4 应急管理员

Foundation 与 Keycloak 各保留一个应急账号，默认停用。启用需要两名系统管理员先后确认，或在服务器上执行运维命令；启用、每次登录、停用都写审计并发通知。延续 ADR-026「本地账号只保留应急管理员，生产可关闭」。

## 10. 组织与账号同步

### 10.1 来源

| 来源 | 方式 | 优先级 |
| --- | --- | --- |
| Foundation 本地维护 | 管理台录入、Excel 导入 | P0 |
| 飞书通讯录 | 定时全量 + 事件订阅增量 | P1 |
| LDAP / AD | 定时拉取（变更号或时间戳增量） | P1 |
| SCIM 2.0（Entra ID、Okta、Keycloak 推送） | Foundation 作为 SCIM 服务方 | P2 |
| 钉钉、企微、客户 HR 接口 | 按同步来源 SPI 补实现，可由交付或客户二开 | 按需 |

同步来源 SPI 是 ADR-026 `OrgDirectoryAdapter` 的落点，插件包加载规则沿用 FND-12 插件宿主的约定（签名、版本、隔离类加载器），Foundation 内置一个精简宿主。

### 10.2 同步引擎

- **一个部署只有一个权威来源**负责组织树与人员主信息（可选「本地」）。其他来源只补外部身份关联，不改人员主信息，避免两个来源互相覆盖。
- **字段映射**：每个来源配置字段映射（外部字段 → 人员、组织单元、岗位字段），可设默认值与转换（如部门编码前缀）。
- **预演差异**：每次同步先算差异（新增、修改、停用、移动），差异量超过阈值时暂停，等管理员确认。默认阈值：一次停用人员超过 5% 或超过 50 人、删除组织单元超过 10 个。
- **幂等**：按「来源 + 外部 ID」合并；外部为准，但被标记为「本地锁定」的字段不被覆盖（如手工修正的显示名）。
- **记录**：每次同步一条任务记录，含差异摘要、耗时、失败条目，可下载明细。

### 10.3 入职、调岗、离职

| 事件 | Foundation 动作 | 发出的事件 | 应用的反应（示例） |
| --- | --- | --- | --- |
| 入职 | 建人员、任职；按「组织或岗位 → 角色」规则授予角色；按配置开账号并推送到 Keycloak | `fdn.person.created`、`fdn.authz.changed` | Tioka 按规则加入对应空间（ADR-026 组映射改为引用 Foundation 组织单元与岗位） |
| 调岗 | 改任职；规则授权重算，手工授权保留 | `fdn.person.updated`、`fdn.authz.changed` | 应用失效授权快照缓存 |
| 停用、离职 | 账号停用、Keycloak 会话吊销、服务账号与负责事项进入交接待办 | `fdn.person.disabled`、`fdn.account.sessions_revoked` | Tioka：吊销令牌与代用户令牌、取消进行中的 Turn、资产转交（ADR-026）、所负责的数字员工暂停（TRU-03）；业务系统：待办转交 |

## 11. 权限中心

### 11.1 权限清单

每个应用在仓库里维护一份权限清单文件（菜单树、按钮、权限码、数据维度声明、内置角色建议），随应用版本发布时由 CI 或启动时调用 Foundation 导入。导入规则：

- 新增的权限码与菜单直接生效，默认不授予任何角色（内置角色建议除外）。
- 清单里消失的权限码标为「已下线」，保留 90 天后清理；已下线的权限码从快照中剔除。
- 同一应用的清单版本只能前进，回滚应用版本时重新导入旧清单视为新版本，审计里可见。

Tioka 的权限点目录（M1-01 `Permissions` 常量）就是 Tioka 应用的权限清单来源，导出成清单文件即可，不改格式。

### 11.2 角色与授权

- **系统级角色**由 Foundation 内置：系统管理员、安全管理员、审计管理员（三员，第 15 节）、组织管理员、应用管理员。
- **应用级角色**由各应用的清单建议、管理员在 Foundation 维护，例如 Tioka 的「模型管理员」「审计查看」，业务系统的「法务」「经办人」「区域负责人」。
- 授予对象可以是人员、组织单元（可含下级）、岗位。有效角色 = 直接授予 ∪ 所在组织单元授予 ∪ 岗位授予，过滤掉过期与互斥冲突的授予。
- **Tioka 空间角色不搬**：`workspace_admin`、`builder`、`member`、`viewer` 绑定空间，仍由 Tioka 的空间成员表管理；ADR-026 的「组 → 空间角色」规则改为以 Foundation 的组织单元、岗位或应用角色为条件。Tioka 的 `tenant_admin`（界面「系统管理员」）改为 Foundation 中 Tioka 应用的一个应用级角色。

### 11.3 授权快照

| 项 | 说明 |
| --- | --- |
| 粒度 | 一个人员在一个应用里一份快照 |
| 内容 | 有效角色、权限码集合、可见菜单树、部门范围（展开后的组织单元编码集合或「全部」）、各数据维度的取值集合、人员属性（主组织单元、岗位、职级）、快照版本号 |
| 计算 | 授权、任职、组织树、角色定义、清单任一变化时，增量重算受影响人员；全量重算由每日对账任务兜底 |
| 获取 | 应用以服务账号调用快照接口；starter 在本地 Redis 缓存，键含版本号 |
| 失效 | Foundation 发 `fdn.authz.changed`（含人员与应用、新版本号）；starter 收到后删除缓存。事件丢失时依靠缓存 TTL（默认 5 分钟）兜底 |
| 故障 | Foundation 不可用时，starter 使用未过期缓存；缓存过期且无法获取时**拒绝**而不是放行（延续 S9 第 11 节「降级拒绝」） |

### 11.4 数据权限

**部门范围五档**沿用若依：全部、自定义部门、本部门、本部门及以下、本人。**自定义维度**解决部门树表达不了的范围，例如合同场景的区域、门店：

- 维度在应用清单里声明（如业务系统声明 `region`，值来源为「应用上报」），业务系统通过接口维护区域列表。
- 角色上配置维度取值（「华东区负责人」→ `region ∈ {华东}`），也可以直接授予给人员。
- 快照里给出每个维度的最终取值集合。多个角色之间取并集；同一角色内部门范围与各维度之间取交集。

**执行在应用里**。starter 提供两种用法：

1. 数据范围注解 + 持久层条件生成：应用在查询方法上声明「本查询的部门字段、维度字段对应哪一列」，starter 按快照生成过滤条件拼进 MyBatis-Plus 查询。和 Tioka 现有的空间行级过滤（FND-03）并存，互不替代。
2. 直接读取快照里的取值集合，自己判断（适合复杂业务规则）。

**与 Tioka 已有设计的关系**：

- GOV-07（Cedar）的 principal 属性增加「组织单元、岗位、职级、各维度取值」，来自快照；策略可以写「只有华东区的经办人能调用某工具」。
- ADR-040 数据集策略（CEL）里的主体属性同样取自快照；M3-03 的 `acl_principals`（业务系统在确认事件里带区域与经办人）可以直接写 Foundation 的维度值编码，两边口径一致。
- 这两处都是「多一个属性来源」，不改 ADR-025、ADR-040 的执行位置。

## 12. 应用接入

### 12.1 接入步骤

1. 在 Foundation 登记应用：编码、名称、地址、负责人；系统自动在 Keycloak 开通 OIDC 客户端与服务账号。
2. 应用后端引入 starter，配置 Foundation 地址、应用编码、服务账号；前端引入前端包。
3. 应用提交权限清单（菜单、权限码、维度）。
4. 管理员在 Foundation 配置应用角色与授权。
5. 应用订阅事件（人员停用、授权变更、字典变更）。
6. 跑接入自检：登录、菜单、按钮、数据范围、单点注销、离职联动六项（管理台提供自检页，逐项给出结果）。

### 12.2 后端 starter 能力

| 能力 | 说明 |
| --- | --- |
| 令牌校验 | 校验 Keycloak 签发的令牌，解析出账号、人员、主组织单元 |
| 当前用户 | 线程内可取当前人员、应用角色、权限码、数据范围；后台任务恢复身份时取快照的指定版本 |
| 权限注解 | 方法上声明所需权限码；不满足返回 403 并上报审计 |
| 数据范围 | 见第 11.4 节 |
| 审计上报 | 管理类与业务关键写操作经注解上报，异步批量投递，Foundation 不可用时本地落盘重试 |
| 字典与参数 | 本地缓存，按变更事件刷新 |
| 消息 | 发送站内信与通知、登记待办 |
| 组织查询 | 按编码查组织单元、人员、上下级，带本地缓存 |

### 12.3 前端包能力

登录跳转与令牌刷新；按快照菜单生成路由；按钮权限指令；字典标签与下拉组件；组织单元树、人员选择器（支持按组织、岗位、角色筛选）；统一的个人菜单（个人中心、切换应用、注销）；401 与 403 页面。

### 12.4 非 Java 应用

照 Foundation 的 OpenAPI 与事件契约接入；令牌校验用任意标准 OIDC 库；事件可选 Webhook（HMAC 签名，与 CON-07a 一致）。

### 14.2 事件

| 事件 | 含义 | 主要订阅方 |
| --- | --- | --- |
| `fdn.org.changed` | 组织单元新增、修改、移动、停用 | 各应用的组织缓存 |
| `fdn.person.created` / `updated` / `disabled` | 人员变化 | Tioka（空间规则、离职处理）、业务系统 |
| `fdn.account.sessions_revoked` | 某账号会话被吊销 | 各应用吊销本地令牌 |

事件经 outbox 投递到 RocketMQ 主题 `fdn-events`，并可同时投 Webhook；事件体只带 ID、版本与变化类型，订阅方需要详情时回查接口，避免敏感字段在消息里扩散。

## 15. 安全与合规

国内私有化项目常要求等保二级或三级，Foundation 按三级的常见检查项设计默认值，客户可调整。

| 项 | 默认 |
| --- | --- |
| 三员分立 | 系统管理员（组织、账号、应用、角色）、安全管理员（密码与会话策略、登录方式、授权审核）、审计管理员（只读日志与审计）三个内置角色互斥，同一人不能兼任；部署时可关闭此约束（小团队） |
| 密码策略 | 最少 8 位、三类字符、90 天过期、不得与近 5 次重复；连续失败 5 次锁定 15 分钟 |
| 会话 | 空闲 30 分钟、最长 10 小时、同一账号并发会话上限可配 |
| 高风险授权 | 授予带高风险权限码的角色需安全管理员复核后生效（P1，复核走 Foundation 内置的简单复核，不依赖 Tioka 审批台） |
| 敏感字段 | 手机、邮箱、证件号加密存储，列表脱敏；主密钥来自 `SecretStoreAdapter`，生产缺少主密钥时启动失败（与 ADR-026 一致） |
| 日志留存 | 审计与登录日志在线保留不少于 180 天，超期归档到对象存储；审计记录按 GOV-09 的哈希链方式封印（Foundation 自己一条链） |
| 传输 | 全部 HTTPS；服务间调用用服务账号令牌，不用固定密钥 |
| 出网 | Foundation 只访问配置过的同步来源与渠道，地址白名单沿用 FND-07 的规则 |

## 16. 部署与运维

| 项 | 设计 |
| --- | --- |
| 形态 | Foundation 服务、管理台与门户静态资源、Keycloak 三个部署单元；中间件与 Tioka 共用（不同库、不同前缀） |
| 小部署 | Docker Compose 一套起：PostgreSQL、Redis、RocketMQ、MinIO、Keycloak、Foundation、Tioka |
| 生产 | Helm：Foundation 至少 2 副本；Keycloak 至少 2 副本，会话缓存用其内置分布式缓存 |
| 启动顺序 | Keycloak → Foundation（初始化 realm、内置应用与角色）→ 各应用 |
| 初始化 | 首次启动建 realm、Foundation 与门户两个应用、三员角色、应急管理员（停用状态，生成一次性启用口令写入启动日志，延续 FND-02 的随机初始密码思路） |
| 数据库变更 | Flyway；迁移号段独立，不占 Tioka 号段 |
| 备份 | Foundation 库、Keycloak 库纳入 Tioka 的备份方案（`ops/HA与备份.md`）；恢复演练要求两库时间点一致，再跑一次账号对账 |
| 空气隔离 | 镜像、Keycloak 主题、前端资源全部进离线包（FND-11） |
| 可用性 | Foundation 不在请求热路径上：应用靠快照缓存运行，Foundation 短时不可用不影响已登录用户；Keycloak 不可用时新登录失败，已有会话在令牌有效期内可用 |

## 20. 备选方案汇总

| 决策 | 推荐 | 备选与不选的原因 |
| --- | --- | --- |
| Foundation 的形态 | 独立部署的基础平台 | ① 留在 Tioka `system` 模块，业务系统各自做：重复建设、离职不联动；② 直接引入若依 Vue-Plus 作为基座：技术栈相近，但自带多租户、Sa-Token 会话、定时任务与代码生成等用不上的部分，与 ADR-029 第 60 条和 Tioka 的 Spring Security 体系冲突，裁剪成本不低于新建 |
| 认证 | Keycloak 负责协议，Foundation 负责管理 | ① 用 Spring Authorization Server 自建认证中心：少一个组件，但 SAML、LDAP 联邦、IM 代理、MFA 都要自己做，工作量多约 30 人天；② 不用中心化认证，各应用本地登录：不能单点登录 |
| 组织主数据 | Foundation 为准，推送到 Keycloak | 以 Keycloak 为准、Foundation 读 Keycloak：Keycloak 的组模型表达不了岗位、兼职、职级与数据维度 |
| 账号进入 Keycloak 的方式 | Foundation 调管理接口推送，每日对账 | Keycloak 用户存储扩展回读 Foundation：实时一致，但要在 Keycloak 里部署自写扩展，升级 Keycloak 时有兼容风险 |
| 权限传递 | 令牌只带身份，应用取授权快照 | 权限放进令牌：实现简单，但令牌变大、权限变更要等令牌过期 |
| 数据权限执行位置 | 应用内，starter 生成条件 | 由 Foundation 提供统一查询代理：侵入业务查询，性能与耦合都不可接受 |
| 菜单来源 | 应用提交清单导入 | 管理台手工维护（若依做法）：代码与配置容易漂移，权限码拼错只能上线后发现 |
| 代码位置 | 单独仓库 | Tioka 仓库内独立 Maven 工程：共用 CI 更方便，但版本节奏与 Tioka 绑在一起，客户只要 Foundation 时也要拉整个 Tioka |
| 排期 | 方案 C（负责人已选） | 方案 A 加人、方案 B 延长 M3，见第 19.1 节 |
| 微前端框架 | 无界（wujie） | ① qiankun：生态最大，但对 Vite 构建的子应用需要额外插件与改造，ESM 支持不好；② Module Federation：共享依赖、加载快，但隔离弱，要求子应用构建工具与版本对齐，适合同团队的组件共享而非子系统集成；③ 纯 iframe：隔离最好，但路由同步、弹窗遮罩、保活与通信体验差 |
| 底座形态 | 一组按版本发布的构件 + 工程模板 | ① 只出文档规范、各项目复制代码：很快漂移；② 代码生成器（若依做法）：生成的代码之后无法随底座升级，团队已用 Cursor |
| 授权模式 | 按子系统四选一 | 只支持集中授权：Tioka 的资源级权限与外购系统都无法纳入 |
| 定时任务中心 | 不做 | 引入 XXL-Job 一类调度中心：Tioka 已有 scheduler 角色与 Redis 锁，再加一套调度中心增加运维面 |
