## 1. GOV-07 工具调用策略引擎（6 人天，BE-A，W30–W31）

### 1.1 改动清单

| 模块 | 组件 | 改动 |
| --- | --- | --- |
| governance-api | `PolicyApi` | 新增。一个求值方法：输入「主体、动作、资源、上下文」，返回结果（ALLOW / DENY / ESCALATE）、命中的策略 `@id` 列表、各策略的模式（DRYRUN / ENFORCE）、是否发生求值错误 |
| governance-biz | `CedarSchemaProvider` | 新增。从工具注册表与授权书动作类别生成 Cedar 的实体类型与动作组：每个工具是一个动作，动作类别是动作组 |

| governance-biz | `PolicyEvaluator` | 新增。按第 1.3 节的两遍求值实现；只有本类依赖 `cedar-java`（ArchUnit 规则 `cedarOnlyInGovernance`） |
| governance-biz | `PolicyCache` | 新增。按空间缓存已解析的策略集与版本号；收到策略变更事件或 60 秒到期后重建 |
| governance-biz | 管理接口 | 新增。策略列表与详情、导入（Cedar 文本）、切换模式、停用；空间级策略编辑界面在 M4，M3 只提供接口与导入 |

| framework | 错误码 | `POLICY_DENIED` 40340 → 403；`POLICY_EVAL_FAILED` 40341 → 403 |

### 1.2 Cedar 映射

| 要素 | 取值 | 来源 |
| --- | --- | --- |
| principal | 用户或服务账号；属性：角色列表、部门编码 | Principal（M1 FND-04） |
| action | 工具名；所属动作组为授权书的动作类别 | 工具注册表、授权书 |
| resource | 工具实体；属性优先取变更单汇总（金额、记录数、对象类型），其次取工具声明的可策略化参数字段 | ADR-033 第 8 步 |
| context | Agent ID、Agent 版本、空间、来源（web / im / orch / flow / eval）、时间、当日累计金额与记录数、当前自治等级、委派链、深度、`onBehalfOf` | ADR-032、ADR-039、ADR-029 第 46 条 |

### 1.3 求值规则

- RBAC 已在第 3 步执行，策略只能收紧：策略集里只有一条系统内置的全放行基线，其余全部是 `forbid`。导入或编译出的 `permit` 策略在保存时被拒绝。
- 每条 `forbid` 带 `@effect` 注解，取值 DENY 或 ESCALATE；没有注解按 DENY。
- 两遍求值：第一遍「基线 + 全部 DENY 组」，命中即 DENY；否则第二遍「基线 + 全部 ESCALATE 组」，命中即 ESCALATE；都没命中即 ALLOW。
- 参与求值的策略：系统级 + 当前空间 + 当前 Agent 版本的授权书策略（`source = charter:{agentVersionId}`），以及委派链上祖先的禁区策略（MAS-02）。
- 求值超时（默认 20 毫秒）或出错：ENFORCE 模式下按 DENY 处理并写审计（原因 `policy_error`）；DRYRUN 模式下按 ALLOW 处理并告警。

### 1.4 DRYRUN 与 ENFORCE

- 模式按策略设置。DRYRUN 的策略命中时，结果仍按 ALLOW 返回，审计里记「本应拒绝」或「本应转审批」与策略 `@id`，供管理员评估误拦率。
- 授权书编译出的策略一律 ENFORCE（ADR-032）；空间导入的策略默认 DRYRUN。
- 切换模式需要权限点 `gov:policy:admin`，写审计。

### 1.5 缓存与跨实例刷新

- 策略增删、模式切换、授权书发布都经 outbox 发 `tioka.gov.policy_changed.v1`（带空间与新版本号）；各实例收到后让该空间的缓存失效。缓存另有 60 秒到期兜底。
- 求值时把使用的策略集版本号写进审计，出问题能还原当时生效的策略。

### 1.6 本地库与备选方案（开工前置 Q3）

`cedar-java` 通过 JNI 调用 Rust 实现的本地库。W24 内在目标架构上做一次验证构建：

| 情况 | 做法 | 工期影响 |
| --- | --- | --- |
| 目标架构有官方构建 | 直接使用 | 无 |
| 没有官方构建 | 在 CI 中为该架构从源码构建本地库，随镜像发布 | GOV-07 +2 人天 |
| 源码构建也不可行 | Cedar 以独立进程（HTTP 求值服务）部署在同一 Pod，`PolicyEvaluator` 改为远程调用，超时与失败规则不变 | GOV-07 +3 人天，Helm 多一个容器 |

`PolicyApi` 的接口在三种情况下都不变，调用方无感知。

| `tioka.policy.enabled` | true | 关闭后第 9 步直接 ALLOW，仅用于故障时的紧急开关，切换写审计 |
| `tioka.policy.eval-timeout-ms` | 20 | 单次求值超时 |

## 3. TRU-02 有效权限、授权书编译、当日累计、四眼（6 人天，BE-A，W34–W35）

### 3.1 授权书编译

- `CharterCompiler` 在 Agent 版本发布时运行，对每个动作类别生成：单次金额超额 → ESCALATE；单 Run 记录数超额 → ESCALATE；当日累计金额或记录数超额 → ESCALATE（读 context 中的当日累计）；参数范围之外 → DENY；禁区工具 → DENY（禁区策略按委派链编写，供 MAS-02 让祖先禁区生效）。
- 策略 `@id` 规则：`charter:{agentVersionId}:{动作类别}:{规则名}`；审计与档案页按它聚合。
- 新版本发布时写入新的一组策略；旧版本的策略保留，钉旧版本的会话与编排工单仍按旧授权书执行；版本归档时一并停用。

### 3.2 有效权限

- DELEGATED：发起人权限 ∩ 授权书 ∩ 空间策略；SERVICE：服务账号角色 ∩ 授权书 ∩ 空间策略，且编排场景再与经办人权限求交（`onBehalfOf`，ADR-029 第 44 条）。
- 发起人权限每个 Turn 开始与每次工具调用前重新加载，缓存 60 秒（沿用 M1）。

### 3.3 当日累计

- Redis 计数键按（Agent、动作类别、日期）组织，`commit` 成功后加上变更单汇总，撤销后扣回（TRU-07）。
- 日期按空间时区切分（默认 Asia/Shanghai，存储仍为 UTC）。
- Redis 数据丢失时，从当天 `trust_action` 中 APPLIED 且未撤销的记录重算；重算期间该 Agent 的超额判断按「已用满」处理（宁可多转审批）。

### 3.4 四眼

- 动作类别 `fourEyes = true` 时，审批台与飞书卡片的可审批人列表去掉 Turn 发起人与编排工单请求人；审批提交接口在服务端再校验一次，违规时拒绝并写审计。

### 3.5 测试

| 用例 | 断言 |
| --- | --- |
| `CharterCompilerTest` | 每类规则生成对应策略；`@id` 符合规则；禁区策略含委派链条件 |
| `CharterEnforceIT#overLimitEscalates` | 单次 8 万、额度 5 万 → ESCALATE，审批卡片带变更单 |
| `CharterEnforceIT#outOfScopeDenied` | 客户等级 A 不在范围 → DENY，审计记策略 `@id` |
| `CharterEnforceIT#dailyAccumulation` | 当日累计第 3 笔超限转审批；撤销第 1 笔后第 3 笔可自动执行 |
| `CharterEnforceIT#pinnedVersionKeepsOldCharter` | 新版本收紧额度后，钉旧版本的会话仍按旧额度 |
| `FourEyesIT` | 发起人不在可审批人列表；伪造提交被拒 |
| `DailyCounterRebuildIT` | 清空 Redis 后计数从 `trust_action` 重算一致 |

## 4. TRU-03 负责人失效与交接（3 人天，BE-A，W43）

- 状态机按 ADR-032「负责人与生命周期」：ACTIVE、SUSPENDED、HANDOVER。复核逾期触发在 M4（TRU-04），M3 只处理用户禁用与成员移除。
- 事件来源：M2 的身份事件桥接（ID-BR）发出的用户禁用、空间成员移除事件；消费者幂等。
- SUSPENDED 的效果：新建 thread 与 Turn 返回 `AGENT_SUSPENDED`（42301 → 423）；运行中的 Turn 在下一步开始前取消；编排决定记为 UNAVAILABLE；IM 中 @它回复「该助手暂停服务，联系 {部门}」。
- 交接：空间管理员指定新负责人 → HANDOVER；新负责人在档案页确认授权书 → ACTIVE。状态变化写 `trust_charter_event`，经 NTF-01 通知负责人与空间管理员。
- 测试：`OwnerLifecycleIT`（禁用负责人后新 Turn 返回 423、运行中 Turn 被取消、编排决定 UNAVAILABLE；交接确认后恢复；重复事件只处理一次）。

## 5. TRU-07 撤销（11 人天，BE-B，W44–W46）

流程、状态与连带效果以 ADR-033「撤销」为准。施工补充：

### 5.1 改动清单

| 模块 | 组件 | 改动 |
| --- | --- | --- |
| trust（connector-biz 内的 `trust` 包） | 撤销接口 | 撤销范围为 Turn、编排 Run 或单个动作；权限：Turn 发起人、工单请求人、Agent 负责人、批准过该动作的审批人、有 `trust:undo` 的空间管理员 |
| trust | 撤销服务 | 事务内选出范围内 APPLIED 且未过撤销期的动作，按序号倒序标 COMPENSATING 并写 outbox 补偿消息；IRREVERSIBLE 的列入「无法撤销」清单；返回两份清单 |
| trust | 补偿消费者 `trust-compensator` | 按撤销范围 ID 分区，保证同组顺序；调用工具的补偿钩子（幂等键为动作 ID 加 `:undo`）；成功 → COMPENSATED、扣回当日累计、发 `tioka.trust.action_undone.v1`；失败重试 3 次后 → COMPENSATION_FAILED，停止该组后续补偿，生成给负责人的编排人审 |
| connector-biz | 飞书回答卡片 | Turn 结束且有未过撤销期的可撤销动作时显示「撤销本次」按钮，按钮值用 CON-03 的 HMAC 签名，接收人限定为可撤销人 |
| runtime-biz | 轨迹与审批台 | `change_set` item 的状态徽标增加 COMPENSATING、COMPENSATED、COMPENSATION_FAILED |
| eval（EVO-01） | 负向反馈 | 消费撤销事件写一条负向反馈，该 Turn 进入待标注 |

### 5.2 撤销期

- 按动作类别配置，存于授权书的动作类别扩展字段（V202 增加空间级默认值），默认 24 小时；过期后接口返回 `UNDO_WINDOW_CLOSED`，按钮消失。

### 5.3 并发

- 同一范围的撤销请求用数据库行锁串行；第二次撤销返回第一次的结果。
- 撤销进行中的范围，新的 `commit` 不受影响（撤销只针对已提交动作）。

### 5.4 测试

| 用例 | 断言 |
| --- | --- |
| `UndoIT#fiveStepsRestored` | 5 步写操作撤销后，FakeErp 状态与执行前快照完全一致，补偿按倒序执行 |
| `UndoIT#compensationFailureStops` | 第 3 步补偿失败：后两步不再补偿，生成人审，审计可查 |
| `UndoIT#irreversibleListed` | 范围内含 IRREVERSIBLE 动作：列入清单并生成人审，其他动作照常补偿 |
| `UndoIT#windowClosed` | 超过撤销期返回 `UNDO_WINDOW_CLOSED` |
| `UndoIT#idempotentDoubleClick` | 同一范围连续撤销两次，只补偿一次 |
| `UndoDualInstanceIT` | 两个实例同时收到撤销请求，只有一个生效 |
| `UndoCardIT` | 飞书卡片「撤销本次」按钮签名错误被拒；非可撤销人点击被拒 |

## 6. TRU-08 爆炸半径与撤销熔断（4 人天，BE-B，W46–W47）

- 单 Run 累计：Redis 按（编排 Run 或 Turn、动作类别）累计变更单汇总；加上本次超过授权书的 `perRunRecords` 或单次金额时，第 11 步把判定至少提到 REQUIRE_APPROVAL。Run 结束后计数过期。
- 熔断：同一 Agent 1 小时内被撤销 3 次，或补偿失败 1 次，全部动作类别降到 L1，并通知负责人。阈值空间可配置，配置变化写审计。
- 测试：`BlastRadiusIT`（单 Run 内第 N 步累计超限后转审批）；`UndoCircuitBreakerIT`（第 3 次撤销后全部类别为 L1；1 小时窗口滑动正确）。

## 7. TRU-09 自治等级（6 人天，BE-A，W42–W43）

- 等级、判定表、观察期、事后抽检以 ADR-034 为准；`trust_autonomy` 等表随 V203 建立（影子相关表在 M4）。
- **默认审批策略切换**：M3 起默认审批策略由 `agent-config` 改为 `autonomy`（ADR-029 第 38 条）。Agent 版本的 `toolPolicies` 只能收紧：`approve`、`deny` 照办，`auto` 不能越过等级。切换以空间开关控制，默认开启；升级手册写明。
- **初始等级**：所有动作类别 L1；负责人可在授权书上限内手动调高，写审计。自动晋级（TRU-12）在 M4。
- **估算变更单**：`estimated = true` 的变更单在判定表中不能自动提交到 L3 以上（ADR-033）。
- **观察期**：新版本发布后 7 天内 L3、L4 按 L2 执行。EVO-06 回归门禁在 M4，M3 不提前结束观察期。
- **事后抽检**：L3、L4 自动执行的动作按 10% 抽样生成「抽检」审批主体，在审批台按注册表渲染（M2 约束 F27）；抽检驳回等同一次撤销请求，交给负责人确认是否执行撤销。
- 测试：`AutonomyGateTableTest`（ADR-034 判定表逐行）；`AutonomyPolicyIT#toolPolicyOnlyTightens`；`AutonomyPolicyIT#observationPeriod`；`PostHocSamplingIT`。

## 8. TRU-10 自动降级与通知（4 人天，BE-B，W47–W48）

- 消费 `tioka.trust.action_undone.v1`：该 Agent 该动作类别降一级（最低 L1）；消费补偿失败事件或 TRU-08 熔断：全部类别降到 L1。
- 每次变化写 `trust_autonomy_event`（原等级、新等级、原因、关联动作）并经 NTF-01 给负责人发卡片；Web 端在档案页显示。
- 降级后的恢复：M3 只允许负责人手动调回（不超过授权书上限，写审计）；自动晋级在 M4。
- 测试：`AutoDemotionIT`（一次撤销触发降一级并收到通知；补偿失败降到 L1；重复事件只降一次）。

## 10. 闸门 G3 追加用例

`gate/G3CharterGateIT`（双实例、Keycloak、开启鉴权）：
1. Agent 授权书：动作类别 `ar.writeoff` 单次 5 万、客户等级限 C、D；禁区含 `biz.erp.deleteCustomer`。
2. 单次 3 万 → 自动执行（等级 L2、可逆）；单次 8 万 → 转审批，审批卡片带变更单；客户等级 A → 拒绝，审计记策略 `@id`；调禁区工具 → 拒绝。
3. 发起人不在可审批人列表中（四眼）。
4. 空间导入一条 DRYRUN 策略，命中后调用照常执行且审计有「本应拒绝」。
5. 禁用该 Agent 的负责人 → 新 Turn 返回 423，编排决定为 UNAVAILABLE。

`gate/G3UndoAutonomyGateIT`：
1. Agent 在 L2 下经编排 Run 执行 5 步写操作（FakeErp）。
2. 请求人撤销该 Run → FakeErp 与执行前快照完全一致；`trust_action` 全部 COMPENSATED；当日累计扣回。
3. 该动作类别降为 L1，负责人收到降级通知；下一次同类调用转审批。
4. 1 小时内再撤销两次 → 全部类别为 L1。
5. 注入补偿失败 → 停止后续补偿、生成人审、全部类别 L1。

## 12. 完成标准

- 任何写工具调用都经过第 7、9、10、11 步，审计能看到动作类别、命中的策略 `@id`、等级与判定结果。
- 没有一条路径能让 Agent 越过授权书执行写操作：禁区与范围外拒绝，超额转审批，四眼生效。
- 撤销一次 5 步写操作后外部系统完全复原；补偿失败与无法撤销的动作都会生成人审，不静默。
- 撤销与熔断会降级并通知负责人；降级后同类调用按新等级判定。
- 第 10 节两个闸门用例在 CI 上绿；ops 文档写明 Cedar 本地库的架构要求、默认审批策略切换与回退方式。
