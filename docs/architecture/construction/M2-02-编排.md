## 0. 总览

```text

   ├─ later → orch_timer(LATER)

```

## ORC-05 规则引擎：CEL 条件、动作、版本、灰度（P1，8 人天，先做）

### 规则版本内容（`orch_rule_version`）

| 字段 | 说明 |
| --- | --- |
| `event_type` | 精确匹配，或以 `.*` 结尾的前缀匹配（如 `feishu.message.*`） |
| `condition_cel` | CEL 表达式，变量只有 `event`（信封：`source`、`type`、`subjectKey`、`hops`）与 `attrs`（`map<string,string>`）；不得访问 `body` |
| `actions_json` | 动作数组，见下 |
| `concurrency` | `serial` / `merge` / `parallel` |
| `accept_mode` | `off` / `observe`（默认）/ `auto` |
| `tell` | `always` / `needed`（默认）/ `never` |
| `emits_json` | 回执允许派生的事件类型白名单 |
| `service_account_id` | 执行身份（Mandate 的执行面） |

动作（`actions_json`，M2 支持三种）：

```json
[
  {"type": "agent",  "agentVersionId": "av_…", "maxSteps": 30, "maxDuration": "2h", "prompt": "处理以下事件：{{event.body}}"},
```

## ORC-03 接入、决定、归单、派工（P0，12 人天）

### `OrchApi.ingest`

```java
@Transactional
public EventAck ingest(EventEnvelope e) {
    validate(e);                                           // source/type/idempotencyKey 必填；attrs 键值长度上限
    if (e.hops() > props.maxHops()) return filtered(e, "hops_exceeded");     // ORC-07
    Optional<String> existing = events.findIdByIdem(tenant, e.idempotencyKey());
    if (existing.isPresent()) return EventAck.duplicate(existing.get());
    String eventId = events.insert(e, STORED, strengthOf(e));            // 唯一键冲突 → 回读，返回 DUPLICATE
    List<Rule> rules = rules.activeFor(e.type());                         // 暂停的规则 → decision UNAVAILABLE
    if (rules.isEmpty()) { events.markFiltered(eventId); return EventAck.filtered(eventId); }
    for (Rule r : rules) decide(eventId, e, r);                           // 每条规则独立，互不影响
    return EventAck.stored(eventId);
}
```

**强度**（ADR-020 修订第 2 条）：`attrs["tioka.addressed"] == "true"`（由 Connector 在 @ 机器人、指派给机器人时设置）或审批答复产生的事件 → `EXPLICIT`；其他 → `INFERRED`；`attrs["tioka.actor_is_bot"] == "true"` 一律 `INFERRED`。

**决定**：

| 条件 | decision |
| --- | --- |
| CEL 为假 | IGNORE（只在 `tioka.orch.record-ignored=true` 时落库，默认不落，避免噪声） |
| 规则 `accept_mode=off` | IGNORE |
| `accept_mode=observe` 且 INFERRED | WOULD_ACCEPT（不建 Run） |
| `accept_mode=observe` 且 EXPLICIT，或 `auto` | ACCEPT |
| 工单已存在且其 Mandate 已撤销 | STOP |
| 服务账号被禁用或配额 `scope_type=rule` 超限 | UNAVAILABLE |

**跟进订阅**（修订第 8 条）：`attrs["tioka.external_thread"]` 命中 `orch_subscription` 且未过期 → 直接归到该工单，`via=FOLLOWUP`，强度视为 EXPLICIT。

**归单与并发**（ACCEPT 后，同一事务）：

```text
wi = SELECT … FROM orch_work_item WHERE rule_id=? AND subject_key=? FOR UPDATE；不存在则 INSERT（唯一键冲突时重读）
新工单：INSERT orch_mandate(ACTIVE, strength, via, requester…, scope_json=服务账号角色与工具快照)
switch concurrency:
  serial:   wi.active_run_id 为空 → 建 Run；否则建 Run(PENDING) 排队（派工器按创建顺序逐个派）
  merge:    wi.active_run_id 为空 → 建 Run；否则把 eventId 追加到 wi.pending_events_json，不建 Run
            （活动 Run 结束时若 pending 非空，用合并后的事件列表建下一个 Run）
  parallel: 直接建 Run
建 Run：INSERT orch_run(PENDING, input_json, run_as_json=服务账号身份)；publish tioka.orch.run_created.v1
fact：event_received、decision、run_created
```

### 派工器（消费者 `orch-dispatcher`）

```text
handle(run_created):
  run = SELECT … FOR UPDATE；status != PENDING → 返回（幂等）
  serial 且工单有其他非终态 Run 在前 → 返回（前一个结束时会重新发布 run_created）
  复验 Mandate（修订第 3 条）：ACTIVE、规则版本未 RETIRED、服务账号有效且仍有动作所需权限
     失败 → mandate REVOKED(reason)，run FAILED(MANDATE_INVALID)，工单关闭，fact
  action = 规则版本 actions[0]（admission 已在决定阶段处理）
  agent：thread = runtime.createThread(origin=orch, originRef=runId, metadata={workItemId, ruleVersionId})
         （同一工单复用 thread：wi 上记录 thread_id，后续 Run 在同一 thread 上开新 Turn，保留上下文）
         turn = runtime.startTurn(thread, clientMsgId=runId + ":" + attempt, input=渲染后的 prompt,
                                  options={maxSteps, maxDuration, toolAllowList=服务账号可用工具 + "orch.receipt"})
  flow： flowPublicationApi.invoke(origin=orch, …)（Flow 执行结束发 tioka.flow.run_finished.v1，回执由 Flow 输出映射）
  run → DISPATCHED，记录 thread_id、current_turn_id；fact dispatched
  全部以 PrincipalHolder.runAs(服务账号) 执行
```

### Turn 结果回写（消费者 `orch-turn-watcher`）

订阅 `tioka.runtime.turn_finished.v1`（payload：`turnId, threadId, status, origin, originRef, errorCode`），只处理 `origin=orch`：

| Turn 结果 | Run |
| --- | --- |
| 开始执行（`turn_started`） | DISPATCHED → RUNNING |
| COMPLETED 且有回执 | 按回执处理（下节） |
| COMPLETED 无回执 | 视为 `resolve`，`outcome=DONE`，并写 fact `missing_receipt` 告警 |
| FAILED | 若本 Turn 有已执行的 `WRITE`/`EXTERNAL_SEND` 工具 → `UNCERTAIN`（只能人工判定）；否则 `attempt < 3` 时重建 Turn 重试，否则 FAILED |
| CANCELLED | CANCELLED |
| Run 已终态（迟到结果） | 只记 fact `late_result`，不改状态 |

Run 进入终态后：工单 `active_run_id` 清空；serial 有排队 Run → 重新发布其 `run_created`；merge 有 pending 事件 → 建下一个 Run。

### `orch.receipt` 工具（回执）

内置工具，仅 `origin=orch` 的 Turn 可见。参数 schema（`docs/contracts/events/orch-receipt-v1.json`）：

```json
{
  "outcome": "DONE | NOTHING | FAILED | CANCELLED",
  "summary": "string ≤ 2000",
  "data": {},
  "actions": [
    {"kind": "notice", "text": "…", "to": "requester | owner | channel"},
    {"kind": "ask", "key": "confirm-refund", "title": "…", "form": [{"name": "approve", "type": "boolean"}], "assignee": {"roles": ["workspace_admin"]}, "timeout": "PT24H", "onTimeout": {"default": {"approve": false}} },
    {"kind": "later", "key": "followup", "at": "2026-11-06T09:00:00+08:00", "input": "…"},
    {"kind": "emit", "type": "tioka.custom.refund_requested.v1", "subjectKey": "…", "attrs": {}, "body": {}}
  ]
}
```

处理（消费者在 Turn 完成后处理，**整体校验，单事务生效**，修订第 4 条）：

1. JSON Schema 校验 + 语义校验：`FAILED` 只允许 `notice`；`emit.type` 必须在 `emits_json` 白名单内（不在的移入 `rejected`，记 fact，不影响结局）；`ask.timeout` ≤ 7 天；`later.at` 在未来且 ≤ 90 天。
2. 校验失败 → **回执重写**（修订第 5 条）：`rewrite_count < 2` 时在同一 thread 开新 Turn，输入为「回执不合法：{错误列表}，请重新调用 orch.receipt」，Run 保持 RUNNING；第 3 次仍失败 → 保留业务结局（按 Turn 状态），回执作废，发通知卡片说明，fact `receipt_invalid`。
3. 生效：
   - `notice` → 按 `tell` 策略：`never` 不发；`needed` 只在 `FAILED` 或有 `ask`/有结果摘要时发；`always` 都发。经 IM 发（`tioka.connector.im_send_requested.v1`）。
   - `ask` → ORC-04。
   - `later` → `orch_timer` upsert（`work_item_id, timer_key`）。
   - `emit` → `OrchApi.ingest`（hops+1，`source=orch`, idempotencyKey=`{runId}:{序号}`）。
   - 无 `ask` 时 Run → SUCCEEDED（`DONE`/`NOTHING`）或 FAILED/CANCELLED。

## ORC-04 人审挂起与续跑（P0，6 人天）

```text
回执含 ask：
  同工单同 key 且有 PENDING 审批 → 复用，不重发（修订第 6 条）
  否则 INSERT runtime_approval(subject_type='orch_run', subject_id=runId, kind='card',
                               card_json={title, form, summary, key}, assignee_json, expires_at=now()+timeout,
                               workspace_id=规则所在空间)
  Run → WAITING_ATTENTION；fact attention_opened
  投递：审批台（M2-04）+ IM 卡片（M2-03，消费 tioka.runtime.approval_requested.v1 中 subject_type=orch_run 的）

OrchApprovalHandler implements ApprovalSubjectHandler（subjectType = "orch_run"）：
  onDecided(a)：
    run = FOR UPDATE；status != WAITING_ATTENTION → 返回
    Mandate 复验（失败 → STOP）
    APPROVED/REJECTED：在同一 thread 开新 Turn，input = 「人工答复：{answer JSON}，备注：{comment}」，

             ；都没有 → Run FAILED(ATTENTION_TIMEOUT)
```

## ORC-06 定时与延时（P1，5 人天）

```text
OrchTimerPoller（每实例，每 5 秒）：
  BEGIN
  rows = SELECT * FROM orch_timer WHERE status='ACTIVE' AND next_fire_at <= now()
         ORDER BY next_fire_at LIMIT 100 FOR UPDATE SKIP LOCKED
  for t in rows:
     fire(t)：OrchApi.ingest(EventEnvelope(source='timer', type=t.target.eventType 或 'orch.later',
              idempotencyKey = t.id + ':' + t.next_fire_at, subjectKey = t.target.subjectKey, attrs = t.target.attrs, …))
     LATER → status='DONE'
     CRON  → next_fire_at = 按 misfire 策略计算：
              LATEST_ONLY：只触发一次（本次），下次 = cron.next(now, tz)
              ALL：逐个补触发直到追上（单次最多 100 个，剩余下一轮）
              SKIP：不触发错过的，下次 = cron.next(now, tz)
  COMMIT
```

cron 解析用 Spring `CronExpression`（6 段，秒级），时区用规则声明的 IANA 名称。管理端：`GET/POST/DELETE /api/orch/timers`（`orch:write`），CRON 定时器由规则版本的 `schedule` 字段在发布时创建/更新，退役时删除。

测试：`OrchTimerIT#survivesRestart`（34 号验收：关闭上下文再启动，到期仍触发）、`#noDoubleFireAcrossInstances`、`#misfirePolicies`、`#laterSameKeyReschedules`。

## RT-09 长任务与心跳（P1，5 人天）

### 要点

1. **心跳与时长解耦**：租约续期（RT-01）与 Turn 时长无关，2 小时 Turn 只要执行实例活着就不会被回收。补充：续期线程池与业务线程池隔离，GC 暂停超过 `lease-ttl` 的风险用 `lease-ttl=30s` 覆盖；新增指标 `tioka_turn_lease_renew_lag_seconds`。
2. **时长上限**：`TurnOptions` 新增 `maxDuration`（默认 30 分钟；`origin=orch|job` 上限 4 小时，其他 1 小时）。超时 → 当前步结束后以 `FAILED(TURN_TIMEOUT)` 结束，并写 `status{kind:"max_duration_reached"}`。
3. **长工具不占 worker**（ADR-029 第 16 条）：工具可返回「已受理」：

```java
// runtime-api spi
record ToolResult(boolean ok, String content, PendingJob pending) {    // pending 非空即异步
    public record PendingJob(String jobType, String jobId, Duration timeout) {}
}
```

   `AgentLoop` 遇到 pending 结果：写 `tool_result{ok:true, pending:{jobType, jobId}}` 占位 → Turn → `WAITING_CHILD` → 释放锁与 worker。作业完成方发布 `tioka.runtime.child_finished.v1 {turnId, callId, ok, output}`；消费者 `runtime-child-router` 写真正的 `tool_result`（同 callId，content 带 `resolves=占位 item seq`）并把 Turn 置 QUEUED。超时由 `ChildTimeoutSweeper` 写失败结果并唤醒。M2 第一个使用者：Flow 发布调用工具（Flow 运行超过 30 秒时转为异步）。
4. **前端**：`turn.waiting` 事件带 `reason=child`，对话页显示「后台任务进行中」与已等待时长。

### 测试

`LongTurnIT#twoHourTurnNotReclaimed`（用可控时钟 `Clock` 注入 + 缩短的 `lease-ttl`：模拟 2 小时内 720 次续期均成功，回收器从不触发）、`#maxDurationStops`、`AsyncToolIT#waitingChildResumes`、`#childTimeout`。

## 完成标准

- Run 自动执行到终态；审批后原 Run 继续（G2）。
- 规则变更不改代码；重启后定时不丢。
- 2 小时任务不被误回收。
- 编排状态机契约测试（随机步进 + 穷举）通过。
