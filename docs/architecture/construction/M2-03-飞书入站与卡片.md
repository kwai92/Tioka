## 0. 本节确定的几件事

| 事项 | 结论 |
| --- | --- |
| 接入方式 | 飞书「事件订阅 v2.0」HTTP 回调（不用长连接），一个绑定一个应用；回调地址 `POST /api/connector/im/feishu/{bindingId}/events` |
| 鉴权 | 只靠飞书签名与加密（`@PublicApi`）；不接受任何 Tioka 令牌 |
| 应答 | 3 秒内应答 200；业务全部异步（经 outbox） |
| 身份 | 飞书用户按 `open_id` 映射到 Tioka 用户；未绑定不执行任何操作，只回绑定链接 |
| 群聊 | 只响应 @机器人；私聊全部响应 |
| 卡片按钮 | 回调 `card.action.trigger`（同一事件订阅地址），按钮 value 内带 HMAC 签名 |
| 代用户令牌 | 加密存库；访问令牌过期前 5 分钟自动刷新；用户未授权时工具返回授权链接 |

## CON-02 飞书事件订阅入站（P0，10 人天）

### 回调处理（同步部分，目标 < 200ms）

```text
POST /api/connector/im/feishu/{bindingId}/events
1. binding = 缓存读取；不存在或停用 → 404
2. 若配置了 encrypt_key：
     验签：X-Lark-Request-Timestamp、X-Lark-Request-Nonce、X-Lark-Signature
           sig = hex(sha256(timestamp + nonce + encryptKey + rawBody))；不等 → 401
           |now - timestamp| > 300s → 401（防重放）
     解密：body = {"encrypt": base64}；key = sha256(encryptKey)；前 16 字节为 IV；AES-256-CBC/PKCS7
3. type == "url_verification" → 校验 token == verification_token → 返回 {"challenge": …}
4. schema "2.0"：eventId = header.event_id；eventType = header.event_type；校验 header.token
5. INSERT im_inbound_dedupe ON CONFLICT DO NOTHING；冲突 → 直接 200
6. 只处理：im.message.receive_v1、card.action.trigger、im.chat.member.bot.added_v1；其他 → 200 忽略
7. card.action.trigger → 交给 CardActionService（同步，见 CON-03，需在 3 秒内返回卡片）
8. 其余：同一事务写 outbox tioka.connector.im_inbound.v1 {bindingId, eventType, event}；返回 200
```

`im_inbound_dedupe` 每天清理 7 天前的行。

### 消息处理（消费者 `im-inbound`）

```text
handle(im_message_receive):
  msg = event.message；sender = event.sender.sender_id.open_id
  if sender_type != "user": 忽略（机器人消息）
  群聊（chat_type=group）且 mentions 中没有本应用机器人 → 若 orch_enabled 则作为推断事件投编排，否则忽略
  user = identity.resolve(binding, sender)
     未绑定：
        identity_match=email → 调飞书 contact/v3/users/{open_id} 取 email，按 auth_user.email 匹配；成功则写映射
        仍未绑定 → 回复「请先绑定 Tioka 账号」卡片，按钮链接 {tioka.public-url}/connect/feishu?b={bindingId}&s={签名 state}；结束
  user 不是 binding.workspace 成员 → 回复「无权使用」；结束
  text = 解析 content（text：去掉 @_user_N 占位；post：拼接文本段；图片与文件：M2 回复「暂不支持」）
  principal = loader.load(user, binding.workspace)        // 以发消息的人的身份执行（ADR-015）
  runAs(principal):
     key = (bindingId, chat_id, thread_id 或 root_id 或 '')
     conv = im_conversation_map[key] 或 新建 Chat 会话（agent = binding.default_agent_id，title = 群名/私聊对象）并写映射
     turn = chatService.send(conv, text, clientMsgId = "feishu:" + message_id, origin = "im")
  answerCardRenderer.start(binding, msg, turn)              // 先回复一张「思考中」卡片
  if orch_enabled：OrchApi.ingest(source="feishu", type="feishu.message.received",
                                  idempotencyKey=message_id, subjectKey=chat_id + ":" + thread_id,
                                  attrs={tioka.addressed: 是否 @机器人 或 私聊, tioka.external_thread: chat_id:thread_id,
                                         tioka.actor_is_bot: "false", chat_type, sender_user_id: user}, body=原消息)
```

会话归属：群聊话题对应的 Chat 会话 `owner_id` = 第一个发言的用户；同一话题其他成员发言时以各自身份 `startTurn`，但会话归属不变（`im_conversation_map.owner_user_id` 记录归属；ChatService 对 `origin=im` 放宽 owner 校验为「该映射存在且发送者是空间成员」）。

### 回答卡片（流式）

```text
AnswerCardRenderer.start：
  ref = feishu.reply(message_id, card("思考中…"))；保存 im_outbound_ref(purpose=answer, ref_type=turn, ref_id=turnId)
  订阅该 thread 的 Runtime 事件（复用 StreamPump，作为服务端订阅者）
  每收到 item.delta / item.completed：累积文本；节流 1 秒执行一次 PATCH /open-apis/im/v1/messages/{id}
     （内容 hash 未变则跳过；PATCH 返回 230020 频控 → 下次再更新）
  turn.completed：最终渲染（正文 + 引用列表 + 「在 Tioka 中打开」按钮）
  turn.failed / cancelled：渲染错误说明
  turn.waiting(approval)：正文后追加「等待审批」，审批卡片由 ApprovalCardService 另发
  订阅最长 30 分钟；实例重启丢失订阅时，由 Turn 结束事件 tioka.runtime.turn_finished.v1 的消费者 im-answer-finalizer 补一次最终渲染
```

卡片用飞书卡片 JSON 2.0；正文 Markdown 截断到 8000 字，超出附「查看全文」链接。

### 身份绑定流程

`GET {public-url}/connect/feishu?b&s` → 前端页（需登录 Tioka）→ 后端 `GET /api/connector/im/feishu/{bindingId}/oauth/authorize`（构造飞书 OAuth 授权链接，state 写 Redis 10 分钟，含当前 userId）→ 飞书回调 `GET /api/connector/im/feishu/oauth/callback?code&state`（`@PublicApi`）→ 换 `user_access_token` 得 `open_id` → 写 `sys_external_identity`；同时把令牌交给 `UserTokenVault`（FND-08，一次授权两用）。

## CON-03 卡片回调 → 审批提交（P0，6 人天）

### 审批卡片下发（消费者 `im-approval-cards`）

订阅 `tioka.runtime.approval_requested.v1`：

| subject_type | 发给谁 | 发到哪里 |
| --- | --- | --- |
| `turn`（工具审批） | Turn 发起人（assignee 为空时）或 assignee 用户 | Turn 来自 IM → 原会话（回复原消息）；否则私聊有映射的审批人 |
| `orch_run`（编排人审） | assignee 用户；assignee 为角色时展开为空间内该角色成员 | 私聊每个有映射的审批人；工单有外部会话订阅时同时发到该会话 |
| `flow_node_run` | 同上 | 私聊 |

卡片内容：标题、摘要、参数或表单（飞书卡片表单容器）、「批准」「拒绝」按钮、「在 Tioka 中处理」链接。每张卡片写 `im_outbound_ref(purpose=approval, ref_id=approvalId)`。

### 按钮签名

```text
value = {"a": approvalId, "d": "approve"|"reject", "r": 接收人 open_id, "e": 过期 epoch 秒, "s": sig}
sig   = base64url(HMAC-SHA256(card_sign_key, a + "|" + d + "|" + r + "|" + e))[0:22]
```

### 回调处理（同步，3 秒内）

```text
CardActionService.handle(card.action.trigger)：
  v = action.value；校验 sig（常量时间比较）、e 未过期 → 否则返回 toast「卡片已失效」
  operator = event.operator.open_id；operator != v.r → 返回 toast「这张卡片不是发给你的」
  user = identity.resolve(operator)；未绑定 → toast + 绑定链接
  answer = 表单值（action.form_value），kind=tool 时可能包含修改后的参数 JSON
  runAs(loader.load(user, approval.workspace)):
     runtimeApi.decideApproval(a, new ApprovalDecision(d == approve, answer, "via feishu"))
       — 权限与 assignee 校验在 decideApproval 内完成（RT-07），失败 → toast 原因
       — 已被处理：返回 toast「已由 {某人} 处理」并刷新卡片
  返回：{"toast": {...}, "card": 已处理状态卡片}     // 直接在回调响应中更新本卡片
```

### 多端同步

消费者 `im-approval-cards` 同时订阅 `tioka.runtime.approval_decided.v1`：查 `im_outbound_ref(ref_type=approval, ref_id)`，把所有已发出的同一审批卡片 PATCH 为「已由某人批准/拒绝 · 时间」。Web 审批台处理后飞书端同步；飞书端处理后 Web 通过 SSE `approval.decided` 同步（ADR-021）。

## FND-08 代用户 OAuth 令牌保管（P1，6 人天）

### 迁移 V141

```sql
CREATE TABLE sys_user_credential (
    id VARCHAR(32) PRIMARY KEY, tenant_id VARCHAR(64) NOT NULL DEFAULT 'default',
    user_id VARCHAR(64) NOT NULL, provider VARCHAR(64) NOT NULL,           -- feishu:{appId}
    access_token_enc TEXT NOT NULL, refresh_token_enc TEXT,
    access_expires_at TIMESTAMPTZ NOT NULL, refresh_expires_at TIMESTAMPTZ,
    scopes VARCHAR(1024), key_version INT NOT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'ACTIVE',                           -- ACTIVE / REVOKED / REFRESH_FAILED
    create_at TIMESTAMPTZ NOT NULL DEFAULT now(), update_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (tenant_id, user_id, provider));
```

### 加密

- `CredentialCipher`：AES-256-GCM，96 位随机 IV，密文格式 `v{keyVersion}:{base64(iv|ciphertext|tag)}`；AAD = `userId|provider`（防止密文被挪到别的用户行）。
- 主密钥来自 `SecretStore`（现有 `LocalSecretStore`，键 `tioka.master-key.v{n}`），部署时由环境变量 `TIOKA_MASTER_KEY` 初始化；轮换：新增 `v{n+1}`，后台任务逐行重加密，旧版本保留到全部完成。

### 接口

```java
// connector-api
public interface UserTokenVault {
    /** 返回有效访问令牌（必要时刷新）；用户未授权或刷新失败 → empty。 */
    Optional<String> accessToken(String userId, String provider);
    /** 构造授权链接（用户未授权时由工具返回给模型/用户）。 */
    String authorizeUrl(String userId, String provider, String returnTo);
    void revoke(String userId, String provider);
}
```

- 刷新：访问令牌剩余 < 5 分钟时刷新；同一用户同一 provider 刷新用 Redis 锁 `cred:refresh:{userId}:{provider}`（防止并发刷新导致旧 refresh_token 失效）。飞书刷新：`POST /open-apis/authen/v2/oauth/token`（`grant_type=refresh_token`），刷新令牌轮换后同事务写回。
- 刷新失败（`invalid_grant`）→ `REFRESH_FAILED`，下次访问返回 empty。
- 读取审计：每次 `accessToken` 不写审计（太频繁），使用令牌的工具调用已经写审计（CON-01）；授权、撤销写审计。

### 工具中的用法

飞书文档工具（`feishu.doc.read`，ADR-021）：

```java
Optional<String> token = vault.accessToken(principal.userId(), provider);
if (token.isEmpty())
    return ToolResult.fail("需要授权访问你的飞书文档，请打开链接完成授权：" + vault.authorizeUrl(…));
// 不静默改用应用身份（ADR-021）
```

用户在「个人设置 → 已连接的应用」可查看与撤销（`GET/DELETE /api/connector/credentials`，仅本人）。

## 完成标准

- 在飞书里 @Agent 发起对话，答案流式更新到卡片（G2 `FeishuChatGateIT`）。
- 点卡片审批后 Run 续跑，Web 与飞书状态一致（G2 `FeishuApprovalGateIT`）。
- Agent 以用户身份读飞书文档；用户未授权时得到授权链接。
