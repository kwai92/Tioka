### 选择逻辑

```java
Resolution resolve(ModelCallContext ctx) {
    if (ctx.turnId() != null) {
        Optional<Freeze> f = freezes.find(ctx.sessionId(), ctx.turnId());     // model_turn_freeze
        if (f.isPresent()) return Resolution.of(f.get().bindingId(), chainAfter(f.get()), "frozen");
    }
    RoutingPlan plan = plans.resolve(ctx.routingPlanId(), ctx.purpose());    // 指定 → 用 purpose 默认方案
    String primary = switch (plan.type()) {
        case HARD -> plan.hardBindingId();
        case PRIMARY_FALLBACK -> plan.primaryBindingId();
        case DIFFICULTY -> throw notImplemented("ADR-024");                    // ENG-03 已下线
    };
    if (ctx.turnId() != null) freezes.insertIfAbsent(ctx.sessionId(), ctx.turnId(), primary, plan.type().name());
    // insertIfAbsent：INSERT … ON CONFLICT DO NOTHING，然后重新读；并发两步时以先写者为准
    return Resolution.of(primary, plan.fallbackChain(), plan.type().name());
}
```

- 冻结键 `(sessionId, turnId)`：同一 Turn 内所有步共用一个 binding；新消息 = 新 Turn = 重新选择（34 号验收）。
- Flow 节点：`sessionId=flowRunId, turnId=nodeRunId`；嵌入、rerank 不冻结（`turnId=null`）。
- `ModelRouterService` 的内存 `lastRoutes` 删除；查询「上次选了哪个模型」改查 `model_turn_freeze`。
- `ModelRouterApi.select` 删除，`ModelRouterController` 的调试接口改为 `GET /api/model/freezes?sessionId=`。

测试：`TurnFreezeIT#sameTurnSameBinding`（3 步工具任务 3 次调用同一 binding）、`#newTurnReselects`（中途把方案主模型改掉，下一个 Turn 用新模型）、`#concurrentFreezeSingleWinner`。

## MH-02 自动故障接力（P0，4 人天）

### 可切换的错误

| 错误 | 重试同一 binding | 切换下一个 |
| --- | --- | --- |
| 连接失败、超时（连接 10s、首字节 60s、流空闲 60s） | 是（2 次） | 是 |
| HTTP 429 | 是（按 `Retry-After`，最长 10s） | 是 |
| HTTP 5xx | 是 | 是 |
| HTTP 400（参数、上下文超长）、401、403、404 | 否 | 否：抛 `MODEL_ERROR`（新错误码 50201，HTTP 502）带上游消息 |
| 内容安全拦截（`finish_reason=content_filter`） | 否 | 否 |

### 流式中途失败（ADR-029 第 2 条）

```text
chat(…, onDelta):
  emitted = false
  包装 onDelta：首次调用置 emitted = true
  try 当前 binding
  catch 可切换错误:
     if emitted: onDelta.accept(StreamDelta.discard())      // Runtime 收到后发 item.discarded，清掉预占 seq
     freezes.recordFailover(sessionId, turnId, nextBinding, reason)   // failover_count + 1
     timeline：写 FailoverEvent（已有 model-api/FailoverEvent），Runtime 收到后写 status item {kind:"model_failover", from, to, reason}
     用下一个 binding 从头重跑本次调用
  链耗尽：抛 MODEL_UNAVAILABLE（新错误码 50301，HTTP 503），Turn → FAILED
```

`failover-max`（默认 2）限制单次调用最多切换次数；冻结记录更新后，同一 Turn 后续步直接使用新 binding。

测试：模型桩支持剧本指令 `fail: {status: 503, after_chars: 0|20}`。`FailoverIT#beforeFirstDelta`（无 discarded，结果来自备用）、`#midStream`（收到 discarded，最终文本只来自备用、无重复）、`#nonRetryable400NoFailover`、`#chainExhausted503`。

## MH-03 重试、退避、冷却、限流（P1，4 人天）

- 重试：指数退避 `500ms × 2^n`，抖动 ±20%，最多 2 次；总预算不超过 `retry-budget`（默认 20s）。
- 冷却：同一 binding 在 60 秒窗口内失败 ≥ 5 次 → Redis `mh:cooldown:{bindingId}` 置 60 秒；冷却期间 `resolve` 跳过它（直接用链上下一个），主 binding 冷却期间新 Turn 的冻结写入备用。
- 限流（令牌桶，Redis Lua，按 binding）：

| 键 | 含义 |
| --- | --- |
| `mh:rl:{bindingId}:rpm` | 请求数桶，容量 = `rpm_limit`，每秒补充 `rpm_limit / 60` |
| `mh:rl:{bindingId}:tpm` | token 桶，容量 = `tpm_limit`；请求前按 `估算 = 输入字符数 / 3 + max_tokens` 预扣，调用后按实际用量补差 |

`acquire` 拿不到时按 Lua 返回的等待毫秒数睡眠后重试，总等待超过 `rate-limit-max-wait`（默认 10s）抛 `RATE_LIMITED`（429）。「限流触发时排队而非报错」（34 号验收）即指这 10 秒的排队。

```yaml
tioka:
  model:
    retry: { max-attempts: 2, base-delay: 500ms, budget: 20s }
    failover-max: 2
    cooldown: { failures: 5, window: 60s, duration: 60s }
    rate-limit-max-wait: 10s
    timeouts: { connect: 10s, first-byte: 60s, stream-idle: 60s }
```

测试：`TokenBucketIT`（Lua 正确性，并发 50 个请求在 `rpm_limit=60` 下第 2 秒起平滑放行）、`CooldownIT`。

## MH-05 用量统一上报（P0，3 人天）

- 每次 `chat`、`embed`、`rerank` 结束（成功、失败、每一次 failover 尝试）都写一条 `model_usage`：`status` = `SUCCESS` / `ERROR` / `FAILOVER`。
- `cost_micros = prompt × input_price / 1e6 + completion × output_price / 1e6`（四舍五入）。
- 写入方式：`UsageRecorder` 放入内存队列，后台线程每 1 秒或满 200 条批量 `INSERT`；进程退出前 flush（`SmartLifecycle.stop`）。丢失窗口 ≤ 1 秒，可接受（计费以 `model_usage` 为准，配额以 Redis 为准，两者每小时对账一次，见 GOV-03）。
- `cost_event` 表已在 V102 删除；`CostTimelineService` 改为查询 `model_usage`，接口 `GET /api/runtime/cost` 保持路径不变、字段改为下表。

| 字段 | 来源 |
| --- | --- |
| `turnId`、`step`、`modelRef`、`promptTokens`、`completionTokens`、`costMicros`、`latencyMs`、`status` | `model_usage` |

测试：`UsageIT#everyCallRecorded`（Chat、Flow LLM、嵌入各一次，均有记录且 purpose 正确）、`#failoverRecordedTwice`。

## GOV-03 配额生效（P0，6 人天）

### 指标与卡点（ADR-017、ADR-029 第 7 条）

| metric | scope_type | 卡点 | 检查 | 计数 |
| --- | --- | --- | --- | --- |
| `tokens_month` | workspace、agent、user | `ModelGateway` 第 2 步 | `used < limit`，否则 `QUOTA_EXCEEDED` | 第 7 步 `INCRBY` 实际 token |
| `concurrent_turns` | workspace、user | `TurnRunner` 获取租约前 | 占位成功才执行，否则 Turn 保持 QUEUED 并在 5 秒后重新投递 | 有序集合 |
| `tool_rpm` | tool、workspace | `ToolGateway`（CON-01） | 令牌桶 | — |

### Redis 结构

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `q:tok:{scopeType}:{scopeId}:{yyyyMM}` | String 计数 | `INCRBY`；TTL 40 天 |
| `q:lim:{scopeType}:{scopeId}:{metric}` | String | 上限缓存，TTL 60s，未命中读 `gov_quota`；没有配置 = 不限 |
| `q:cc:{scopeType}:{scopeId}` | ZSet，member = turnId，score = 过期时间戳 | 占位前先 `ZREMRANGEBYSCORE … -inf now` 清理过期；Turn 终态或进入 WAITING_* 时 `ZREM`；续租时更新 score |

并发占位用 Lua 一次完成「清理过期 → 比较 `ZCARD` 与上限 → `ZADD`」，同时检查 workspace 和 user 两个 scope，任一失败则全部回滚。

### 落库与对账

`QuotaFlusher`（每 60 秒）：把本月 Redis 计数写回 `gov_quota.used_value`（`window_start` = 月初）。`QuotaReconciler`（每小时）：用 `SUM(model_usage)` 校正 Redis 计数（取两者较大值，避免少算）。Redis 丢失时从 `gov_quota.used_value` 恢复。

### REST

| 方法与路径 | 权限 | 说明 |
| --- | --- | --- |
| `GET /api/system/quotas?scopeType&scopeId` | `quota:read` | `[{metric, limit, used, windowStart}]`，`used` 取 Redis 实时值 |
| `PUT /api/system/quotas/{scopeType}/{scopeId}/{metric}` | `quota:admin` | `{limit}`；`limit=null` 删除即不限 |

现有 `QuotaService`、`QuotaController`（`/workspaces/{id}/limits`）改为上述实现与路径，旧路径删除。

测试：`QuotaIT#tokensExceededRejectsNext`（34 号验收：超配额请求被拒；ADR-029 第 7 条：单次可超、下一次被拒）、`#concurrentLimitQueues`（上限 2，发 3 个 Turn，第 3 个等前一个结束后才执行）、`#waitingApprovalReleasesSlot`、`#redisLossRecoversFromDb`。
