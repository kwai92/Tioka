## 2. DOC-01 文档层（5 人天）

> **2026-11-06 修订（ADR-029 第 71 条）**：本节与第 3 节的解析按 [ADR-060](../adr/ADR-060-document-parsing-service.md) 输出契约 `tioka.parse/v1` 核心子集（PRS-00，BE-A，+2.5 人天，与 DOC-01 / DOC-02 同期）：`DocxParser` 必须渲染自动编号（POI 段落文字不含编号，否则 `ClauseTreeBuilder` 对自动编号合同失效）、按单元格输出表格（含合并单元格）、采纳修订并把批注分离为 `COMMENT`；`ImageParser` 与 OCR 经「模型引擎」适配器调用 `qwen-vl-ocr`（Q6）。契约类型放 `docparse-api`，实现仍在 `ontology-biz`，M4 迁入解析服务（PRS-01）。

### 解析流程

```text
ingest(fileRef)
 1. 下载原文件 → 计算 SHA-256 → 查 doc_document（同哈希同解析器版本 READY 则直接返回 docId）
 2. 写对象存储，doc_document = PARSING
 3. 解析器产出「行」序列：{page, text, bbox?, kind, tableRef?, source}
    - PDF：逐页取文字层；字符密度 < 阈值（缺省 50 字/页，或乱码率 > 20%）的页加入 OCR 队列
    - 图片：每张一页，全部 OCR
 4. OCR 页（DOC-02）回来后与文字层合并
 5. UnitSegmenter：行 → 单元；ClauseTreeBuilder：单元 → 条款树
 6. 批量写 doc_page / doc_unit / doc_clause（一个事务），doc_document = READY
```

### 切分规则

- **段落**：Word 以段落为单元；PDF 以版面块为单元，跨页的段落在下一页开头没有编号且上一页末行不以句号结尾时合并。
- **标题**：命中条款编号正则（`^第[一二三四五六七八九十百零〇\d]+条`、`^\d+(\.\d+){0,3}\s`、`^[（(][一二三四五六七八九十\d]+[)）]`）的行。
- **表格**：一个单元格一个单元，`table_ref` 记行列；合并单元格取左上角坐标。费用表、递增表常在表里，必须按单元格切，不能把整表拼成一段。
- **签章区**：「甲方（盖章）」「签订日期」之后的块标 `SIGN`。
- **空白填写位**：`【\s*】`、`_{3,}`、`（\s*）` 内为空、单独的 `/` 等，标 `BLANK_FIELD` 并在所属条款上标 `BLANK`。这是取值状态「空白」的来源，不能丢。
- **所在部分**：遇到「定义」「专用条款」「通用条款」「附件」标题时切换 `section`，之后的单元继承。

## 3. DOC-02 OCR 与合并（4 人天）

### 改动清单

| 模块 | 文件 | 改动 |
| --- | --- | --- |
| model-api | `capability/OcrRequest.java`、`OcrResult.java` | 新能力：输入图片（页渲染为 PNG，200 DPI），输出行、框、置信度 |
| model-biz | `gateway/ModelGateway` | 增加 `ocr(OcrRequest, CallContext)`，与 `chat` 同样走配额、用量、审计、数据标签路由（DAT-03） |
| model-biz | `provider/bailian/BailianOcrAdapter` | 百炼 OCR / 视觉模型；路由计划里配置主备 |
| ontology-biz | `application/doc/OcrMerger` | 文字层与 OCR 合并 |

### 合并规则

1. 页只有 OCR：直接用 OCR 行。
2. 页两者都有：按 bbox 的 IoU（≥ 0.5）配对；配对上的行用文字层（文字层没有识别错误），OCR 独有的行（如图片里的印章文字、手写日期）追加，`source = MERGED`。
3. OCR 行置信度 < 0.8 的，写入单元 `ocr_conf`。@model.build 抽到这些单元上的值时，置信度上限取 `ocr_conf`，低于 0.8 的取值状态直接置「待复核」，原因「OCR 低置信」。

### 并发与成本

页渲染在本机完成，OCR 调用每份文档并发 4、全局并发按路由计划 QPS。按每天约 10 份、每份 30 页、扫描件占一半估算，每天约 150 页 OCR，成本可以忽略；容量瓶颈在抽取步骤，不在 OCR。

| --- | --- |

### 输出阶段

在 ADR-016 的循环里，「若无 toolCalls: Turn → COMPLETED」之前插入：

```text
若 AgentSpec.output != null 且 mode = FINAL:
    payload = 解析最后一条 assistant 内容（SCHEMA / JSON 模式）或 emit_output 的参数（TOOL 模式）
    for round in 0..maxRepair:
        errs = SchemaApi.validate(ref, payload) + SchemaApi.checkEvidence(...)
        若 errs 为空: 写 data item(valid=true)，Turn → COMPLETED，结束
        若 round == maxRepair: 写 data item(valid=false, errors=errs)，Turn → COMPLETED(reason=output_invalid)，结束
        追加 tool_result（errors 的 JSON Pointer + 原因清单），再调一次模型，payload = 新输出
```

`mode = TOOL` 时，`emit_output` 作为普通工具注册，每次调用在 `prepare` 阶段走同样的校验，失败作为 tool\_result 返回给模型，由模型自己修；Turn 结束时汇总所有有效的 `data` item。

### 路径语法

```text
path     := root ('.' seg)*
```


## 9. ONT-04 `rule.evaluate`（4 人天）

### 改动清单

| 模块 | 文件 | 改动 |
| --- | --- | --- |
| ontology-api | `rule/RuleSpec.java`、`RuleResult.java` | `RuleSpec(ruleId, applies, requires, check, onBlank, params)`；`RuleResult(conclusion, touched[], params{name,value,configVersion}, error?)` |
| ontology-biz | `application/rule/RuleEvaluator` | CEL 编译缓存（按 `ruleId + 表达式哈希`）、三值求值 |
| ontology-biz | `domain/cel/ModelValueProvider` | 把 `model_json` 暴露为 CEL 变量 `m`，每个叶子是 `optional<值>`，同时记录访问过的路径 |

### 求值

```text
evaluate(rule, model, cfg):
  touched = []
  if rule.applies != null and eval(applies) is false: return NOT_APPLICABLE
  for p in rule.requires:
      s = status(p)
      if s == 未知: return MISSING
      if s == 不适用: return NOT_APPLICABLE
      if s == 空白: return rule.onBlank
  r = eval(check)                 # optional<bool>
  if r is none: return MISSING    # check 中访问到未知值
  return r ? SATISFIED : NOT_SATISFIED
  （每个返回都带上 touched：路径、值、状态、来源）
```

- 「待复核」状态的取值按已知值参与计算，但结论附 `needsReview = true`，Finding 在业务系统里提示「依赖待复核取值」。
- 求值超时 50 ms，超时与表达式错误返回 `error`，结论记「缺失」并告警，不让审查整体失败。
- 阈值 `cfg` 由调用方传入（审查场景来自业务系统的阈值配置，带 `configVersion`）。

### 测试

`RuleEvaluatorTest` 表驱动，至少 24 行：适用 / 不适用 × 已知 / 未知 / 空白 / 不适用 × 满足 / 不满足，加超时、表达式错误、待复核传递。

```yaml
      type: map
```

## 14. FLW-08 Flow 并行 map 节点（4 人天）

- DSL：`type: map`、`items`（表达式，结果为数组）、`concurrency`（缺省 4，上限 32）、`body`（单个节点或子图）、`onItemError: FAIL | SKIP | COLLECT`（缺省 COLLECT，失败项收集进结果的 `errors`）。

## 15. NTF-01〜02 通知渠道（5 人天）

### SPI

通知是 ADR-026 九类适配器中的「通知」一类，这里给出它的接口（ADR-029 第 56 条）：

```java
public interface NotificationChannel {
    String channel();                                  // feishu / email / dingtalk / wecom / sms / custom:{name}
    ChannelCapabilities capabilities();                // interactive、supportsUpdate、maxLength、supportsAttachment
    DeliveryRef send(Recipient to, Notice notice);
    default void update(DeliveryRef ref, Notice notice) { throw new UnsupportedOperationException(); }
}

public record Notice(
    String noticeKey,             // 业务幂等键，如 lease-review:{runId}:ready
    String title,
    List<Block> blocks,           // 段落、键值对、列表；与 ImMessage 同一套块模型
    List<Action> actions,         // 按钮：OPEN_URL（深链）或 CALLBACK（卡片回调，进 CON-03）
    DataLabel label) {}
```

- `NotificationService.notify(notice, recipients, channels)`：按 `dedup_key` 去重写 `ntf_delivery`，经 outbox 异步发送；失败按 1、5、30 分钟重试 3 次，之后 FAILED 并告警。
- 去向许可（ADR-040）：发送前检查 `notice.label` 是否允许发往该渠道。合同场景的通知只含合同号、门店、结论计数和深链，标签为 INTERNAL，不放合同原文。
- 可逆性：`notify` 是 IRREVERSIBLE（ADR-033），但只给本组织员工发、内容为 INTERNAL 的通知，按授权书配置可以免审批（M3-04 的授权书里配置）。

### 两个实现（第一期）

| 渠道 | 实现 | 要点 |
| --- | --- | --- |
| 飞书 | `FeishuNotificationChannel`，内部复用 M2-03 的 `FeishuImChannelAdapter.send/update` | 卡片按钮用 `open_url`（深链，不带令牌）；审查结论更新后用 `update` 改卡片状态（如「已处理」） |
| 邮件 | `SmtpNotificationChannel`（Spring Mail） | HTML 模板 + 纯文本备份；按钮渲染为链接；`Message-ID` 记为 `external_ref` |

收件人解析：`Recipient` 为 Tioka 用户 ID 或业务系统给的员工号，经 FND-09 的外部身份映射找到飞书 `open_id` 与邮箱；找不到时降级为只发邮件并在 `ntf_delivery.last_error` 记 `RECIPIENT_UNMAPPED`。

### 测试

`NotificationServiceIT#dedup`、`#retryThenFail`、`#labelDenied`（CONFIDENTIAL 通知发往邮件被拒）；`FeishuNotificationChannelIT` 用 M2-03 的飞书桩。

## 16. CON-07a 最小业务连接器（5 人天）

ADR-029 第 42 条把 CON-07 延后到 M4 之后。合同场景需要的只是其中一小部分，所以拆出 CON-07a 在 M3 做（第 55 条），其余部分（OpenAPI 上传界面、任意业务系统接入）仍按原计划。
