## BAS-23 底座依赖清单与父工程（P0，2 人天）

### 目标与范围

建立 `tioka-foundation` 仓库的 Maven 底座部分：`foundation-dependencies`（统一版本清单）与 `foundation-parent`（父工程），可从私有仓库发布，供 Tioka、Foundation 服务本身与后续业务系统引用。本项不含任何 starter（BAS-24）、不含服务代码（BAS-01）。

### 关键设计

仓库根为 aggregator（`packaging=pom`），`foundation-dependencies` 与 `foundation-parent` 是两个独立可发布构件。

```text
tioka-foundation/                 # 仓库根（aggregator，packaging=pom，模块在后续工作项追加）
├── pom.xml
├── foundation-dependencies/
│   └── pom.xml                   # dependencyManagement：版本清单（不引入依赖）
├── foundation-parent/
│   └── pom.xml                   # 父工程：编译参数、格式与静态检查、flatten、enforcer、发布
├── foundation-starter-*/         # BAS-24 追加
├── foundation-test/              # BAS-01 建骨架，BAS-24 充实
└── foundation-server/ foundation-ui/   # BAS-01 追加
```

| 构件 | 职责 | 来源 |
| --- | --- | --- |
| `foundation-dependencies` | 只做 `dependencyManagement`：Spring Boot 3.2.x、MyBatis-Plus、Redisson、RocketMQ client、Hutool、MapStruct、springdoc、Testcontainers、ArchUnit、`ulid-creator`；Flyway/Testcontainers/Lettuce 由 Spring Boot BOM 管理，不另写版本 | 由 `tioka-dependencies` 抽出 |
| `foundation-parent` | `parent` 关系：Java 17、`-parameters`、代码格式与静态检查插件、`flatten-maven-plugin`、`maven-enforcer-plugin`（Java 版本 + 依赖收敛）、`revision` 版本占位、`distributionManagement` | 新建 |

发布流程：版本按语义化（BAS-23 首版 `0.1.0-SNAPSHOT`），破坏性变更只进主版本，每版附升级说明（S15 §5.3）；发布到私有 Maven 仓库，凭据经 `~/.m2/settings.xml` 的环境变量注入，不入库。

```xml
<!-- foundation-parent/pom.xml（片断） -->
<project>
  <groupId>com.foundation</groupId>
  <artifactId>foundation-parent</artifactId>
  <version>${revision}</version>
  <packaging>pom</packaging>
  <properties>
    <revision>0.1.0-SNAPSHOT</revision>
    <maven.compiler.release>17</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>
  <dependencyManagement>
    <dependencies>
      <dependency>
        <groupId>com.foundation</groupId>
        <artifactId>foundation-dependencies</artifactId>
        <version>${revision}</version>
        <type>pom</type>
        <scope>import</scope>
      </dependency>
    </dependencies>
  </dependencyManagement>
  <build>
    <plugins>
      <plugin><artifactId>maven-compiler-plugin</artifactId>
        <configuration><parameters>true</parameters></configuration></plugin>
      <plugin><artifactId>flatten-maven-plugin</artifactId></plugin>
      <plugin><artifactId>maven-enforcer-plugin</artifactId></plugin>
    </plugins>
  </build>
  <distributionManagement>
    <repository><id>foundation-private</id><url>${env.FOUNDATION_REPO_URL}</url></repository>
  </distributionManagement>
</project>
```

### 表结构与迁移

无数据库变更（纯构建构件）。Foundation 的迁移号段自 V1 起，留给 BAS-01（见下节）。

### 配置项

无运行时 `foundation.*` 配置。发布相关：私有仓库 URL 与凭据经环境变量/`settings.xml`，不写入仓库文件。

### 测试

| 用例 | 断言 |
| --- | --- |
| 构建自检 | 空本地仓库下 `mvn -q -U clean verify` 通过 |
| `ExampleBuildIT`（示例工程） | 只引 `foundation-parent`（间接导入 `foundation-dependencies`）即可 `mvn compile` |

### 完成标准

- [ ] `foundation-dependencies`、`foundation-parent` 可发布到私有仓库（对 [F-00](F-00-F阶段实施计划.md) R2 负责）
- [ ] 示例工程只引父工程即可编译（PF-00a 验收）

## BAS-01 工程骨架与闸门基座（P0，4 人天）

### 目标与范围

建立 Foundation 服务的 Maven 多模块骨架、独立库与 Flyway 基线、Keycloak 管理接口连接、CI 流水线、GF 闸门基座（Keycloak 与 PostgreSQL 容器），冒烟用例 `GfSmokeIT` 通过（对 [F-00](F-00-F阶段实施计划.md) R3 负责）。本项不含中台业务功能与 starter 实现。

### 关键设计

**Maven 多模块划分**（`foundation-server` + 各领域 `-api/-biz` + `foundation-ui`；starter 在 BAS-24 追加）：

```text
tioka-foundation/
├── pom.xml
├── foundation-server/                          # 装配：依赖各 -biz，只做装配与少量门面
│   ├── pom.xml
│   └── src/main/java/com/foundation/server/FoundationApplication.java
│   └── src/main/resources/
│       ├── application.yml
│       └── db/migration/                       # Flyway：Foundation 库自 V1 起
├── foundation-common/                          # 通用公共域（本项先建空骨架，BAS-09 填充）
│   ├── foundation-common-api/                  # 契约、DTO、事件（只含对外类型）
│   └── foundation-common-biz/                  # 实现
├── foundation-ui/                              # Vue 3 + Element Plus（管理台 + 门户，BAS-FE 填充）
└── foundation-test/                            # Testcontainers 基座 + ArchUnit 规则集（BAS-24 充实）
```

**包与分层**：包根 `com.foundation.<domain>`，`*-biz` 固定五层，与 [00-施工总纲](00-施工总纲.md) §2.1 一致。

```text
com.foundation.<domain>
├── api/             # Controller 与请求/响应 record，只做校验与权限注解
├── application/     # 应用服务，事务边界（@Transactional）
├── domain/          # 领域对象与纯逻辑，不依赖 Spring
├── infrastructure/  # Repository、mapper/、persistence/*DO、外部客户端
└── config/          # *AutoConfiguration、@ConfigurationProperties（prefix = foundation.<域>）
```

**服务形态**：一个 Spring Boot 应用，独立 PostgreSQL 库（可与 Tioka 共用实例、不同库），共用 Redis 与 RocketMQ（键与主题加 `fdn` 前缀）；多实例无状态，同步与对账任务靠 Redis 锁单实例执行（S15 §4）。生产至少 2 副本（S15 §16）。

**Flyway**：迁移目录在 `foundation-server/src/main/resources/db/migration`，命名 `V{n}__{desc}.sql`；Foundation 库自 V1 起，独立历史表，与 Tioka 号段（V220〜V269、V270+）互不占用（S15 §16、F-00 §5 约定 1）。Keycloak 库由 Keycloak 自管，Foundation 不迁移。

**Keycloak 管理接口连接**：Foundation 以服务账号经 `client_credentials` 调 Keycloak Admin REST API（S15 §4、ADR-051 第 2 条）；连接与超时用 `@ConfigurationProperties`（`foundation.keycloak.*`）。首次初始化（建 realm、内置应用、三员角色、停用状态应急管理员）在 BAS-04、BAS-21 落地，本项只做连接与连通性校验。

```java
// com.foundation.keycloak.KeycloakAdminClient（接口）
public interface KeycloakAdminClient {
    String realm();                                   // 默认 enterprise（ADR-051 第 2 条：共用一个 realm）
    boolean ping();                                   // 取 access_token 并读 realm 表示连通
    String accessToken();                             // client_credentials，内部缓存至过期前
}
```

**CI**：本项先建最小可跑流水线（编译 + 单元 + 集成 Testcontainers + ArchUnit + 闸门），完整模板在 BAS-25。

**闸门基座**：`foundation-test` 提供 Testcontainers 单例容器基类，容器为 PostgreSQL 16（pgvector）、Redis 7、RocketMQ、Keycloak（`quay.io/keycloak/keycloak:24.0`，`dasniko/testcontainers-keycloak:3.3.0`）并导入 `foundation-realm.json`（S15 §14.1 的接入自检与 GF 闸门共用）。

## BAS-09 字典与参数（P0，3 人天）

### 目标与范围

实现公共服务中的字典与参数（S15 §13）：字典类型/项、参数键值，归属全局或某应用；变更经 outbox 发 `fdn.dict.changed`、`fdn.param.changed`；参数支持敏感值只写不读、加密存储，每次修改记旧值与新值摘要。starter 的本地缓存刷新由 BAS-08 实现，本项只保证事件发出与查询接口（对 [F-00](F-00-F阶段实施计划.md) R4 负责）。

### 关键设计

模块落在 `foundation-common-api` / `foundation-common-biz`，包 `com.foundation.common.dict`、`com.foundation.common.param`。

```java
// foundation-common-api：contract
public interface DictApi {
    List<DictItemView> items(String appCode, String typeCode);       // 供 starter / 前端查询
    void upsertType(DictTypeCmd cmd);
    void upsertItem(DictItemCmd cmd);
}
public interface ParamApi {
    String value(String appCode, String key);                        // 明文读；secret=true 时抛 FORBIDDEN
    String valueFor(key, ...);                                       // 内部（服务间）：可读密文解密值
    void set(ParamCmd cmd);                                          // 写；记录旧值与新值摘要
}
```

**归属与作用域**：`app_code` 为 `NULL` 表示全局项，非空表示归属该应用（子系统编码，见 BAS-04）。查询时「应用项优先于全局项」。

**ID 前缀**（Foundation 沿用 [00-施工总纲](00-施工总纲.md) §2.2 的 ULID 生成器，前缀为 Foundation 自有集合，与 Tioka 前缀在不同库、互不冲突）：

| 前缀 | 用途 |
| --- | --- |
| `dt` | 字典类型 |
| `di` | 字典项 |
| `pm` | 参数 |
| `ph` | 参数变更历史 |
| `evt` | outbox 事件（`fdn_outbox.id`） |

后续工作项的前缀（组织 `org`、人员 `per`、账号 `acc`、应用 `app`、角色 `rol`、快照 `snp` 等）在各自施工设计登记。

**敏感参数**：`secret=true` 时 `param_value` 存信封加密密文（AES-256-GCM，主密钥来自 `SecretStoreAdapter`，ADR-026）；对外读接口一律拒绝并返回掩码，仅服务间内部接口可解密；每次修改写 `fdn_param_history`，只记旧值与新值的 SHA-256 摘要，不记旧明文。

**变更事件**：字典/参数写操作经 `fdn_outbox` → RocketMQ 主题 `fdn-events`（可同时投 Webhook，HMAC 签名），事件体只带 ID、版本、变化类型（S15 §14.2）。事件名固定为 `fdn.dict.changed`、`fdn.param.changed`。

**REST（摘要）**：`POST/PUT/DELETE /api/foundation/dict-types`、`/dict-items`、`/params`（写接口要求 `Idempotency-Key`，S15 §14.1）；`GET /api/foundation/dict/{type}?app=`、`GET /api/foundation/param/{key}?app=` 供 starter 与前端使用。

### 表结构与迁移

```sql
-- V2__dict_param.sql
CREATE TABLE fdn_dict_type (
    id         VARCHAR(32)  PRIMARY KEY,             -- dt_{ulid}
    code       VARCHAR(64)  NOT NULL,
    name       VARCHAR(128) NOT NULL,
    app_code   VARCHAR(64),                          -- NULL=全局；否则归属应用
    status     VARCHAR(16)  NOT NULL DEFAULT 'ENABLED',
    create_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    update_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    create_by  VARCHAR(64)  NOT NULL DEFAULT 'system',
    update_by  VARCHAR(64)  NOT NULL DEFAULT 'system'
);
-- 全局项与归属项分别唯一（PostgreSQL 中 NULL 互不相等，故拆两个部分唯一索引）
CREATE UNIQUE INDEX uq_dict_type_global ON fdn_dict_type (code) WHERE app_code IS NULL;
CREATE UNIQUE INDEX uq_dict_type_app    ON fdn_dict_type (app_code, code) WHERE app_code IS NOT NULL;

CREATE TABLE fdn_dict_item (
    id         VARCHAR(32)  PRIMARY KEY,             -- di_{ulid}
    type_id    VARCHAR(32)  NOT NULL REFERENCES fdn_dict_type(id),
    code       VARCHAR(64)  NOT NULL,
    label      VARCHAR(128) NOT NULL,
    sort_no    INT          NOT NULL DEFAULT 0,
    status     VARCHAR(16)  NOT NULL DEFAULT 'ENABLED',
    style_tag  VARCHAR(32),                          -- 样式标签（S15 §13）
    ext_json   JSONB,
    create_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    update_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),
    UNIQUE (type_id, code)
);
CREATE INDEX idx_dict_item_type ON fdn_dict_item (type_id, sort_no);

CREATE TABLE fdn_param (
    id           VARCHAR(32)  PRIMARY KEY,           -- pm_{ulid}
    app_code     VARCHAR(64),                        -- NULL=全局
    param_key    VARCHAR(128) NOT NULL,
    param_value  TEXT,                               -- secret=true 时存 AES-256-GCM 密文
    secret       BOOLEAN      NOT NULL DEFAULT FALSE,
    description  VARCHAR(255),
    update_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
    update_by    VARCHAR(64)  NOT NULL DEFAULT 'system'
);
CREATE UNIQUE INDEX uq_param_global ON fdn_param (param_key) WHERE app_code IS NULL;
CREATE UNIQUE INDEX uq_param_app    ON fdn_param (app_code, param_key) WHERE app_code IS NOT NULL;

-- 每次修改记旧值与新值摘要（S15 §13）；只存摘要，不存旧明文
CREATE TABLE fdn_param_history (
    id          VARCHAR(32)  PRIMARY KEY,            -- ph_{ulid}
    param_id    VARCHAR(32)  NOT NULL REFERENCES fdn_param(id),
    old_digest  VARCHAR(128),                        -- 旧值 SHA-256（首次为空）
    new_digest  VARCHAR(128) NOT NULL,
    changed_by  VARCHAR(64)  NOT NULL,
    changed_at  TIMESTAMPTZ  NOT NULL DEFAULT now()
);
CREATE INDEX idx_param_history ON fdn_param_history (param_id, changed_at DESC);
```

## BAS-24 底座 starter 抽取（含 `foundation-test` 与规则集）（P0，8 人天）

### 目标与范围

从 `tioka-framework`、`tioka-dependencies` 抽出按能力拆分的九类 starter 与 `foundation-test`，并把 ArchUnit 规则集作为构件发布，各项目引用后自动生效（S15 §5.2、§5.3）。本项交付「库」，不含中台服务功能。

### 关键设计

**构件划分（逐条展开，取自 S15 §5.2）**：

| 构件 | 抽取边界（内容） | 来源 | 依赖 | 关键类 / 接口 | 配置前缀 |
| --- | --- | --- | --- | --- | --- |
| `foundation-starter-core` | 错误码体系与统一返回、业务异常、ID（ULID）、Jackson 约定、时间统一 UTC、请求上下文 | `tioka-framework` 的 error、id、jackson、context | 无 | `ErrorCode`、`BizException`、`ApiResponse`、`Ids`/`IdPrefix`、`RequestContext` | `foundation.core.*` |
| `foundation-starter-web` | 全局异常处理、接口约定（分页/排序/过滤参数）、`Idempotency-Key` 处理、OpenAPI 生成、请求日志与脱敏 | 新建，吸收 Tioka 各 Controller 共性 | core | `GlobalExceptionHandler`、`PageQuery`、`IdempotencyFilter`、`OpenApiConfig`、`RequestLogFilter` | `foundation.web.*` |
| `foundation-starter-security` | OIDC 资源服务、当前用户、权限注解、授权快照客户端、数据范围条件、`@PublicApi` 白名单、服务账号调用（即 S15 §12.2 的 SDK） | `tioka-framework` 的 security 抽通用部分 | core | `TokenVerifier`、`CurrentUser`、`@RequirePermission`、`@PublicApi`、`AuthzSnapshotClient`、`DataScopeProvider` | `foundation.security.*` |
| `foundation-starter-data` | MyBatis-Plus 配置、基类 DO（审计字段、乐观锁、逻辑删除约定）、只追加与不可变快照基类、Flyway 约定（号段与命名）、多数据源可选 | `tioka-framework` 的 persistence；**空间过滤留在 Tioka** | core | `BaseDO`、`MutableRecordDO`、`AppendOnlyDO`、`ImmutableSnapshotDO`、`FlywayNaming` | `foundation.data.*` |
| `foundation-starter-mq` | RocketMQ 封装、领域事件、outbox 表与中继、消费幂等表、死信处理约定 | Tioka 的 messaging 与 M2-01 outbox 设计 | core | `MqTemplate`、`DomainEvent`、`Outbox`、`OutboxRelay`、`IdempotentConsumer` | `foundation.mq.*` |
| `foundation-starter-cache` | Redis 与 Redisson、键前缀、分布式锁、限流 | 新建 | core | `RedisConfig`、`KeyPrefix`、`DistributedLock`、`RateLimiter` | `foundation.cache.*` |
| `foundation-starter-observability` | OpenTelemetry、Micrometer、日志格式与 traceId 透传、健康检查（对齐 GOV-08） | 由 trace 抽出 | core | `OtelConfig`、`TraceIdFilter`、`HealthConfig` | `foundation.observability.*` |
| `foundation-starter-audit` | 操作审计注解、异步上报、本地落盘重试（对接 S15 §13 审计服务） | 新建 | core、security | `@Audited`、`AuditReporter`、`AuditLocalFallback` | `foundation.audit.*` |
| `foundation-starter-client` | 中台客户端：字典、参数、组织查询、消息与待办、文件、编号 | 新建，S15 §12.2 其余能力 | core | `DictClient`、`ParamClient`、`OrgClient`、`MessageClient`、`FileClient`、`SeqClient` | `foundation.client.*` |
| `foundation-test` | Testcontainers（PostgreSQL、Redis、RocketMQ、Keycloak）、测试数据构造、通用 ArchUnit 规则集 | Tioka 闸门基座 | 无（测试作用域） | `FoundationContainers`、`TestFixtures`、`FoundationArchRules` | `foundation.test.*` |

**依赖约束**：各 starter 只依赖 core，彼此不互相依赖（`audit` 依赖 `security` 取当前用户为例外）；应用按需引用（S15 §5.2）。`foundation-test` 不进生产依赖。

**starter 模块结构**（以 core 为例）：

```text
foundation-starter-core/
├── pom.xml
└── src/main/
    ├── java/com/foundation/starter/core/
    │   ├── error/       # ErrorCode, BizException, ApiResponse
    │   ├── id/          # Ids（ULID 生成与解析）, IdPrefix
    │   ├── json/        # Jackson 约定（WRITE_DATES_AS_TIMESTAMPS=false 等）
    │   ├── time/        # UTC 约定（DO LocalDateTime、API Instant）
    │   ├── context/     # RequestContext（traceId、appCode）
    │   └── config/CoreAutoConfiguration.java + CoreProperties.java
    └── resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
```

**ArchUnit 规则集（S15 §5.3）**：随 `foundation-test` 发布，各项目引用后自动生效，豁免需登记（`foundation-arch-exemptions.md`，逐条注明理由与到期版本）。

| 规则 | 守护的设计 | 实现 |
| --- | --- | --- |
| `controllersDeclarePermissionOrPublicApi` | `@RestController` 的 public 方法必须带 `@RequirePermission` 或 `@PublicApi` | 复用 Tioka ENG-10 的 `controllersMustDeclarePermission` |
| `noSyncExternalCallInRequestThread` | 禁止在请求线程同步调外部系统 | 新写 |
| `noTenantId` | 禁止 `tenant_id` / `sys_tenant` / DO·迁移·API 出现租户字段（ADR-029 第 60 条） | 新写（字段名与列名双向检查） |
| `permissionCodesFromCatalog` | 权限码只能引用常量目录 | 复用 Tioka `permissionLiteralsFromCatalog` |
| `modulesDependOnlyOnApi` | 跨模块编译期只依赖对方 `-api` | 复用 Tioka `serverDependsOnlyOnApi` 的泛化版 |
| `noNewObjectMapper` | 只用注入的 `ObjectMapper` | 复用 Tioka 同名规则 |
| `doTimeFieldsAreLocalDateTime` | DO 时间字段只用 `LocalDateTime` | 复用 Tioka 同名规则 |
| `noSynchronizedOrReentrantLock` | 应用代码禁止 `synchronized`/`ReentrantLock` 做业务互斥 | 复用 Tioka ENG-10 |

规则一次性写全；尚未满足处用 `FreezingArchRule.freeze(...)` 冻结现存违例（库存于各项目 `src/test/resources/archunit_store/`），新违例立即失败，库存只能减少（M0 ENG-10 约定）。

### 表结构与迁移

starter 为库，无自身迁移脚本。`foundation-starter-mq` 的 outbox 表结构约定与 BAS-01 的 `V1__foundation_schema.sql` 中 `fdn_outbox` 一致（服务侧建表，starter 只读写）；`foundation-starter-audit` 的本地落盘重试在应用进程本地目录，不入库。

## BAS-26 Tioka 切换到底座（P0，3 人天）

### 目标与范围

Tioka 改为以 `foundation-parent` 为父工程、导入 `foundation-dependencies`，逐个 starter 替换通用部分，`tioka-framework` 只保留 Tioka 特有部分（空间与归属过滤、`Principal` 的空间字段、Runtime 执行器等），迁移按 starter 进行、每步保持 G0〜G3 闸门通过，包名变化一次性重构、不保留兼容层（S15 §5.4）。本项只切「底座依赖形态」，不含中台接线（在 BAS-20）。

### 关键设计

- **父工程与清单**：Tioka 根 `pom.xml` 的 `parent` 改为 `foundation-parent`，`tioka-dependencies` 退化为对 `foundation-dependencies` 的导入（或直接移除）。
- **逐个 starter 替换**（顺序自下而上；每步跑 G0〜G3）：

| 步 | 替换 | Tioka 侧动作 | 闸门 |
| --- | --- | --- | --- |
| 1 | core | `com.tioka.framework.{error,id,jackson,context}` → `com.foundation.starter.core.*` | G0〜G3 |
| 2 | data | persistence 基类换成 starter；**空间过滤留在 `tioka-framework`** | G0〜G3 |
| 3 | web | 统一异常处理、分页、`Idempotency-Key` 换 starter | G0〜G3 |
| 4 | cache | Redis/Redisson、锁、限流换 starter | G0〜G3 |
| 5 | mq | 消息封装、outbox 换 starter（复用 Tioka 既有 `sys_outbox` 约定） | G0〜G3 |
| 6 | observability | trace 换 starter，对齐 GOV-08 | G0〜G3 |
| 7 | security | 通用部分（`TokenVerifier`、`@RequirePermission`、`@PublicApi`）换 starter；**授权快照接线留 BAS-20**，本步保留 Tioka 本地实现 | G0〜G3 |
| 8 | audit | `@Audited`、上报换 starter；Tioka 的哈希链与归档（GOV-09、OBS-10）**原样保留**（F-00 §5 约定 5） | G0〜G3 |
| 9 | client | 引入 `foundation-starter-client`（依赖中台就绪，实际接线在 BAS-20/BAS-28）；本步只引接口、留桩 | — |

- **包名重构**：一次性把对应包改到 `com.foundation.starter.*`，不保留兼容层（S15 §5.4）。
