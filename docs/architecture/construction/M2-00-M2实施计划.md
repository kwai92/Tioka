## 1. 结论

M2 的五份施工设计（M2-01〜M2-05）技术内容够写代码，但和 M1 开工前一样，排期层面不能直接用：

1. **人天与分工对不上，前端有一半工作没有名字**。总纲表写后端 100、前端 36 人天；各节实际相加后端 94、前端 18。前端多出的 18 人天没有对应任何工作，而编排控制台、死信运维、飞书接入配置、飞书账号绑定页这些界面在设计里都没有。本次列为 FE-15〜FE-20，共 14 人天。
2. **G2 只有分段骨架**。34 号计划的 G2 要求「中途重启不丢任务、多 worker 不重复领取」和一条完整链路，现有 4 个骨架都不覆盖；RocketMQ、飞书开放平台桩、实例重启也没人排进闸门环境。本次新增 ENG-04c、G2-E2E 两个工作项和 2 个闸门用例。
3. **和 2026-11-06 合入的 ADR-041〜043 有冲突或缺少衔接**。最直接的两处：RT-09 把「Flow 发布为工具时转异步」当作第一个使用者，而 ADR-043 把这件事放到 M4 之后（FLW-18）；编排规则的 `flow` 动作会建在 M3 要重写的旧 Flow 引擎上。本次按第 65 条处理，并列出 F17〜F28 作为 M2 的实现约束，不增加人天。
4. **核算后放得下**。M2 后端 123、前端 37 人天（BE-A 41、BE-B 40、BE-C 42、FE 37，每人 10 周容量 50），余量约 18%，比 M1 宽松，不需要延长 M2。但这意味着 W20–W23 后端全部在 M2，34 号计划说的「M3 在 M2 后半段并行启动」，后端实际做不到，见第 10 节。

`G2EndToEndGateIT` 的步骤：飞书桩向实例 1 推送一条 @机器人消息 → 规则（`auto`，`agent` 动作）接单 → Turn 在实例 2 执行 → 回执提出 `ask` → 飞书桩收到审批卡片 → 重启实例 2 → 飞书桩向实例 1 回调「批准」→ Run 在存活实例上续跑 → 回执 `notice` 发回飞书桩（结果回写）。断言：只有 1 个工单、1 个 Run、审批卡片只发 1 次、最终消息只发 1 次，Web 审批台上该审批显示「已由某人批准」。

ENG-04c 提供的闸门基座：

| 能力 | 说明 |
| --- | --- |
| RocketMQ | 闸门 profile 使用真实 Broker（容器），不用 in-memory 模式 |
| 飞书开放平台桩 | 独立 HTTP 服务：按飞书规则签名、加密事件并推送到实例；记录发送、更新消息与卡片的请求供断言；可模拟卡片按钮回调、频控错误码、令牌刷新 |
| 实例重启 | 闸门支持按名称停止、启动某个实例（同进程内关闭并重建应用上下文，夜间任务另跑一次多进程版本） |

## 10. 与 M3 的衔接

34 号计划写「M3 在 M2 后半段并行启动」，ADR-041 也按「M3 前段 W20–W27」排了版本框架和模型中枢。按本文排期，M2 的工作需要 3 名后端干满 W14–W23（负载 80%〜84%，余量都留给 G2 回归），因此：

- **后端**：M3 的后端工作实际从 W24 起步，比日历上的 W20 晚 4 周。M3 的 W20–W48 一直是按日历写的，从没按人力核算过（34 号计划多处写「M3 施工设计编写时核算」）。这 4 周是否要补，在写 M3-00（M3 实施计划）时一并算清，本文不改 M3 周次。
- **前端**：前端负载 37/50，W21 起有余量，可以先做 M3 的 FE-07（统一历史与对比组件）。
- **能提前给 M3 的东西**：M2 结束时，outbox（M3 撤销、数据源增量同步依赖）、`WAITING_CHILD`（RT-12 依赖）、`CredentialCipher`（ADR-042 依赖）、FLW-03（FLW-09 依赖）都已就绪，M3 前段没有被 M2 卡住的前置。

如果负责人希望 M3 后端严格按 W20 起步，可选做法是把 TRU-05、TRU-06（后端 15、前端 5，P1，不阻塞 G2）挪到 M3 前段，让 BE-B 在 W19 后转去做 ADR-041、ADR-042 的模型中枢项。总工作量不变，只是换了顺序；代价是 M2 不再交付「写工具的预演与变更单」。本文默认不这样做。
