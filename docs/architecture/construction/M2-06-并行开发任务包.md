## 1. 结论

1. **M2 的代码在 main 上还没开始，但本机已经有两批没推上来的改动，必须先处理，否则一开就全面冲突。** main（`329e5af`）上没有 V130 以后的迁移，没有 RocketMQ 客户端代码，四个 G2 闸门骨架仍是 `@Disabled`，编排模块仍是 M0 的旧表。本机仓库里：
   - `feat/m2-mgr-expert-sess` 上有一个未推送的提交 `e4344f5 feat(ORC-02): M2 event envelope and payload contracts`，即 M2-00 要求 W14 先合的事件契约 PR（信封去掉 `tenantId`、加 `replayOf` / `traceparent`、11 个事件 payload schema、`EnvelopeContractTest`）。
   - 本机 `main` 工作区有约 240 个文件未提交的「名词对齐与编码规约」改动（`docs/superpowers/specs/2026-11-07-*` 七份设计都标「已完成」，新增 47-GL、48-CS 与两条 `.cursor/rules`），基线还停在 PR #24（`5e30924`），没有 PR #27、#28。它改了全部业务模块（Runtime 的 Session → Thread、注解 SQL 迁到 XML、删除死代码等），其中 `V127__rename_tenant_admin_to_system_admin` 与 main 上 PR #27 的 `V127__m1_audit_request_id` **撞号**；`RuntimeMqTopics`、`OrchestrationMqTopics` 被它和 `e4344f5` 同时改动。
2. **所以 M2 的并行分两段：先串行打地基（第 0 波，W14 前 3 天），再按模块边界扇出。** 地基是四个包：名词对齐入库 → 事件契约 → 后端骨架、前端骨架。骨架把所有泳道都要碰的东西（依赖、配置键、跨模块端口接口、注册表、ArchUnit 规则占位、前端路由与导航）一次放好，之后各包只在自己的目录里写。
3. **能并行的上限由依赖链决定，不由 Cursor 数量决定。** 主链 ORC-02 → ORC-05 → ORC-03 → ORC-04 → CON-03 → G2-E2E 仍是串行的；并行能带来的是：主链之外的 P1 项不再排队（HCI-06b、OBS-04a 的大部分、TRU-05 的契约与 FakeErp、ORC-03 的回写半边可以提前到主链旁边做），每名开发者同时带 1 条主链会话 + 1 条旁路会话。按第 5 节的拆法，P0 功能冻结有机会从 W21 提前到 W20 左右，但本文**不改计划周**，按第 76 条⑤在 G2 通过时记录实际偏移。
4. **建议并发度：每名后端最多 2 个写代码的 Cursor 会话，前端 2 个，全队同时最多 8 个开着的 PR。** 再多，瓶颈会变成人工评审与 rebase，而不是写代码。
5. **两处设计层面的冲突，本文顺带定掉**（第 77 条）：
   - V143 里有 `DROP TABLE flow_run` 并重建，M2-00 写「HCI-05b 先合者带入」。HCI-05b 在 W15–W16 合入时会把旧 Flow 引擎正在用的 `flow_run` 删掉，而 FLW-03 要到 W20–W21 才改引擎，中间五周 Flow 运行全部坏掉。**拆为 V143（审批台、轨迹所需列，随 HCI-05b）与 V146（`flow_run`、`flow_node_run` 重建，随 FLW-03）**。
   - 名词对齐的三个迁移：`V128`（Runtime Thread 改名）、`V129`（`flow_publication` 改名）保留原号；**撞号的 tenant_admin 改名迁移改为 V136**（M2 段预留号，`out-of-order` 已开启）。
6. **M3 能不能和 M2 并发：依赖上约 165 后端人天可以，人手上要看 Cursor 的实测速度。** 推荐在 W16、W18 检查点量出实际人天与估算之比，按公式拉入 M3 的活，合同主链前段优先（第 8 节）。比为 0.7 时 M3 约提前 3 周，0.6 时约提前 4 周。速度未实测前只做原来 26 人天的无条件档。计划周不预先改。

## 3. 并行规则（所有任务包都遵守）

### 3.1 一包一分支一工作树一 PR

- 每个任务包对应一个分支 `feat/{工作项ID}-{英文短名}`，一个 git worktree（建议放在仓库外的 `../tioka-wt/{包号}`），一个 Cursor 会话，一个 PR。一个 Cursor 会话不跨包。
- 分支基于最新 `origin/main`；每天开工前 rebase 一次；依赖的包合入后当天 rebase。
- PR 规模：不含测试的改动尽量不超过约 600 行；超过时按包内的「子包」拆成连续 PR。
- PR 标题以 `[工作项ID]` 开头。描述固定写五项：做了什么、验收用例（红 → 绿的证据）、迁移号、持有的热点锁、越界申请（没有写「无」）。
- Cursor 只开 PR，不合并。合并由该包负责人评审后执行；涉及热点锁的 PR 另需锁表里下一位持有人看一眼。

### 3.2 契约先行

- 跨模块的东西先合接口，再并行实现：`-api` 模块的接口与 DTO、`docs/contracts/events` 的事件 schema、`docs/contracts/db` 的建表、前端 fixtures。实现方只依赖 `-api`，不依赖对方的 `-biz`。
- 第 0 波的 PK-00b（事件）、PK-00c（端口接口）、PK-00d（前端路由与 fixtures）就是 M2 的契约 PR。之后新增事件或改端口签名，单独开一个小契约 PR，标题 `[CONTRACT]`，三名后端都评审，合入后各包 rebase。
- 包内也可以契约先行：标了「a 子包为契约」的包，a 子包当天合入，b、c 子包按契约并行。

### 3.3 热点文件与串行锁

下列文件或目录被多个包改动。规则是：**同一把锁同一时间只有一个未合入的 PR 持有**；按表中顺序轮转；持有者在 PR 描述写「持有 K1」，合入即释放。没轮到的包要改这些文件，先用接口或扩展点绕开，绕不开就等。

### 3.4 测试与闸门

- 每个包先写验收用例（红），再实现到绿；PR 里贴红绿证据（CI 链接或本地输出）。
- 本地只跑本包相关模块与本包的 IT；`-Pgate` 全量交给 CI。一台笔记本上不要同时跑两个 `-Pgate`（Keycloak + Broker + 双实例内存不够）。
- G2 闸门用例由「转绿」的那个包去掉 `@Disabled`（第 7 节）；G0、G1 用例任一变红，当天修复优先于新功能（M2-00 第 7.3 节）。
- 需要 MQ 的 IT 打 `@Tag("mq")`；其余 IT 用 `tioka.messaging.mode=in-memory`（M2-01）。

### 3.5 本地多工作树

- 每个工作树单独的应用端口（`SERVER_PORT`）；Docker Compose 的 PG、Redis、RocketMQ、Jaeger 共用一套。
- Testcontainers 各自起容器，不开 reuse，避免两个会话共用一个库互相污染。
- 改了迁移的包在本地用全新的库验证一次（不要在已经跑过别的分支迁移的库上验证）。

## 8. M3 与 M2 并发

### 8.1 结论

- **从依赖上看，M3 有约 130 后端人天（约 30%）完全不依赖 M2 的产出，另有约 35 人天只依赖 M2 前半段就合入的项。** 也就是说，技术上约 165 人天的 M3 可以和 M2 同时做（第 8.2 节）。
- **卡住并发的不是依赖，是人。** M2 已经排了 3 名后端 133.5 / 150 人天，余量约 16 人天，这部分要留给 G2 回归。负责人此前两次选择不加人。所以 M3 能并发多少，取决于用 Cursor 之后**实测**的速度，不能按假设的倍数提前排进计划。
- **推荐方案 B「按实测速度开 M3 前置泳道」**：W16、W18 两个检查点量出 M2 已合入任务包的实际人天与估算之比，按第 8.4 节的公式算出空出的人天，再按第 8.3 节的固定顺序从 M3 拉活。顺序以合同主链前段为先。
- **压缩幅度**：实测比为 0.7 时约拉入 40 人天，M3 提前约 3 周（G3 约 W54）；比为 0.6 时约 55 人天，提前约 4 周。M4、F 同步平移。如果这个速度在 M3 里也保持，按第 76 条⑤重算容量后还能再缩，但下限受影子期（50 份真实合同、法务复核）和业务系统联调这些日历事项约束。本文不改计划周，实际偏移在 G2、G3 通过时记录。

### 8.4 能拉多少（检查点公式）

- 在 W16 与 W18 的周检查点各算一次。**实测比 r** = 已合入 main 且 CI 绿的 M2 任务包的实际人天之和 ÷ 这些包在 M2-00 的估算之和。实际人天由各人在 PR 描述里填写，评审时核对。
- **可拉入人天** = 150 × 剩余周数 ÷ 10 − M2 剩余估算 × r − 15。150 是 3 人 × 10 周 × 5 天，15 是留给 G2 回归的余量，不得挪用。结果小于 0 时不拉。
- 参考值（按全程同一个 r 算）：

| r | 可拉入人天 | 约等于 M3 前移 |
| --- | --- | --- |
| 1.0 | 约 1，只做第一档里不占人天的部分 | 0 |
| 0.8 | 约 28 | 约 2 周 |
| 0.7 | 约 41 | 约 3 周 |
| 0.6 | 约 55 | 约 4 周 |
| 0.5 | 约 68 | 约 5 周 |

  M3 前移周数按 M3 每周有效产出 12.75 人天换算，而且只有拉入的是第二、三档（关键路径上的项）时才成立。
- **评审带宽**：拉 M3 的会话算在每人 2 个会话以内，不另开第 3 个。全队开着的 PR 上限从 8 放到 10，多出来的 2 个只给 M3 的 PR。M3 的 PR 只要负责人一人评审，不进 G2 必需检查。

### 8.5 约束与退出

1. **锁**：第 3.3 节的 8 把锁对 M3 的 PR 同样有效。GOV-07、RT-12、RT-10 在 W22 TRU-05 合入前不开工。MH-08 W17 前不改 `DefaultModelGateway`。
2. **迁移**：只用 M3-00 第 9 节登记的号（V150〜V219）。拉入的项在 M2 期间合入 main，新表可以建，但不改 M2 正在改的表。
3. **不接线**：一律以特性开关关闭或未接线的方式合入，不改变 M2 的任何行为，G0〜G2 必须保持绿。
4. **退出**：任一周检查点主链落后，或 G0〜G2 有用例变红一天内修不好，当天停止所有 M3 会话（开着的 M3 PR 可以先放着），等追平后再按公式重算。
5. **记账**：拉入并合入的项在 M3-00 第 5 节标「M2 期间完成」。W24 开工盘点时，M3 周计划按第 76 条⑤整体平移，34 号计划同步修订。本文不预先改周次。
