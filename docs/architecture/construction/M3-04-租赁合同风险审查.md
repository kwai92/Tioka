## 0. 系统边界

```text
┌──────────── 业务系统 lease-biz（新建，独立部署，权威） ────────────┐
│ 合同与文件 · 模型确认版本 · 审查要点库 · 阈值 · 修订案例 · 正反例       │
│ 审查轮次与结论 · 法务处置 · 租约状态（派生，只读展示）                   │
│ 前端：合同工作台、确认页（嵌 @tioka/ontology-confirm）、结论处理页     │
└───────▲──────────────────────────────┬─────────────────────────────┘
        │ OpenAPI（biz.lease.* 工具）     │ 事件（HTTP 或 RocketMQ）
        │ 服务账号 + X-Tioka-On-Behalf-Of │ lease.contract.submitted / contract.model.confirmed / lease.review.feedback
┌───────┴──────────────────────────────▼─────────────────────────────┐
│ Tioka                                                              │
│ 连接器 biz.lease（CON-07a） → 编排规则 → 审查主管 Agent                │
│ 文档层 · @model.build · 模型投影 · rule.evaluate · 折叠（租赁领域包）   │
│ 复核员 / 判断员 / 质检员（agent.delegate）· 通知（飞书 + 邮件）          │
└────────────────────────────────────────────────────────────────────┘
```

- **业务系统独立部署**，有自己的 PostgreSQL 库，不是 Tioka 的模块。同一个团队写，但代码在单独的仓库或单独的 Maven 工程里，和 Tioka 只通过 OpenAPI 与事件交互。这样「业务系统是权威」在部署上也成立，以后换成客户自己的业务系统时 Tioka 不用改。
- 业务系统和 Tioka 共用同一个 Keycloak realm：法务登录一次两边都能用；Tioka 调业务系统用服务账号 `svc-tioka-lease`。
- 业务系统技术栈建议与 Tioka 一致（Java 17、Spring Boot、Vue 3），便于同一团队维护。

## 1. 租赁领域包

### LSE-01 模型定义与 Prompt（6 人天）

领域包工程 `tioka-pack-lease`，产物是一个签名的插件 jar（ONT-05）。目录：

```text
tioka-pack-lease/
├── plugin.yaml                     # packKey: lease, spiVersion: 1, permissions: [cpu]
├── definitions/lease.contract.yaml # 模型定义（ADR-036 ModelDefinition）
├── schemas/                        # lease.finding、lease.findingList、lease.contract.inventory 等手写 Schema
├── prompts/                        # 按 @model.build 步骤 × 对象类型
├── src/main/java/.../validators    # LSE-02
├── src/main/java/.../fold          # LSE-03
└── src/main/java/.../cel           # LSE-04
```

`lease.contract.yaml` 的内容按规格五支组织，第一期范围：

| 支 | 对象 / 陈述 | 第一期范围 |
| --- | --- | --- |
| 骨架 | 合同（种类、编号、签署日、生效日）、当事方、合同关系（主合同、补充、续约、变更、终止、转让） | 全部 |
| 标的与期限 | 标的（铺位、面积及口径）、租期、关键日期（交付、装修、开业、计租起始） | 全部 |
| 商务对象 | 费用项（CALC / SCHED / PAY / TAX / ABATE）、押金（32 类）、跨项规则（孰高、孰低、抵扣）、营业额口径 | 全部 |
| 权利义务 | 陈述：OBLIGATION、RIGHT、CONSEQUENCE、CONDITION、PROCEDURE | 只抽 56 个必备要点涉及的主题；19 个主题的覆盖仍全部输出 |
| 修改声明 | 修改类型、新内容、生效期、去向（变更操作） | 全部 |

权利义务第一期只抽必备要点涉及的主题，是阅读版里对规格「设计待确认」第 2 项的建议：J 类要点的判断本来就要回到条款原文，先把必备要点做准，再扩到全部 19 个主题。主题清单与必备要点的对应关系放在 `definitions/topic-checkpoint-map.yaml`，由 LSE-04 与法务一起维护。

Prompt 规则：

- 每个抽取 Prompt 只描述「这一类对象怎么抽」，不描述输出格式（格式由 Schema 约束）。
- 规格里的易错点直接写进对应 Prompt 的「注意」段：0 元不是免租、一次性金额不是月额、提成比例不是税率、面积不从租金反推、空白不是 0、违约金和滞纳金不是押金。这些同时由 LSE-02 的校验器兜底。
- 枚举值、码表来自模型定义的词表，Prompt 模板里用占位符引用，不手抄。

### LSE-02 校验器（5 人天）

规格「校验规则」16 条，逐条实现为 `ModelValidator`，编号与规格对应：

| 编号 | 规则 | 结果 |
| --- | --- | --- |
| V01 | 0 元不是免租 | REJECT |
| V02 | 一次性金额不是月额 | REJECT |
| V03 | 提成比例不是税率 | REJECT |
| V04 | 面积不从租金反推（面积的来源角色必须是「事实」且引文含面积单位） | REJECT |
| V05 | 金额溯源：引用证据里能找到归属本项的金额事实，等值或按标准换算，容差 0.02 | REJECT |
| V06 | 空白不是 0 | REJECT |
| V07 | 一个金额事实只归一个费用项 | REJECT（两个都退回） |
| V08 | 费种身份一致 | REJECT |
| V09 | 标的归属：缺标的、跨标的引用拒收 | REJECT |
| V10 | 期间完整：只做唯一回填，回填不了拒收 | REJECT |
| V11 | 新增还是调整：同标的已有同类费用时是调整 | REJECT |
| V12 | 续约 / 调价金额完整 | REJECT |
| V13 | 押金不抄旧额 | REJECT |
| V14 | 主体变更合法：只出现在甲方变更、转让、回购合同里 | REJECT |
| V15 | 生效日有据：没有依据标未知，依赖它的操作暂不应用 | REVIEW |
| V16 | 覆盖检查：含金额、期限或「应 / 不得 / 有权」措辞的证据单元，要么归入对象或陈述，要么明确排除 | REVIEW（列出未归属单元） |

V05 的金额事实识别用确定性的金额正则（阿拉伯数字、中文大写、「万元 / 年」「元 / 平方米 / 月」等单位），换算表放领域包配置。每个校验器至少 4 个单测（通过、拒收、边界、与其他规则的交互）。

### LSE-03 折叠引擎（8 人天）

实现 `FoldingEngine.fold(storeKey, chain)`，严格按规格「折叠与租约状态」：

1. **修改声明 → 变更操作**：按修改词表把每份合同的修改声明转成操作（合同层 `@CONTRACT_DECLARE`、`@TERM_RENEW` 等；标的与日期 `@SUBJECT_ADD` 等；费用项 `@ITEM_ADD` 等）。主合同本身转成一组 `DECLARE` / `ADD` 操作。
2. **分阶段执行**：① 结构（合同、关系、租期、关键日期、主体变更，按生效日）→ ② 建对象（只建空壳）→ ③ 取值（作用范围优先级 → 生效日 → 签署日 → 文档内顺序）→ ④ 续约补齐（只填续约期内没被覆盖的部分）→ ⑤ 边界（终止、缩短、结束类最后统一应用）。
3. **折叠规则**：R-1 迁址重新建档、R-2 临时变更到期恢复、R-3 专项协议在其费用范围内优先；R-4 重叠减免、R-5 附条件减免进复核（写 `review_items`，不自行决定）；以及规格列出的其余 11 条。
4. **合同号推导**：每个分段的合同号取「取值来源合同」与「当事方条目建立合同」中生效较晚的一份。

规格里仍标 `[?]` 的业务问题（N1 续约「其他条款不变」时递增是否继续、N2 终止时专项协议费用是否结束等）做成领域包配置项，缺省值为「进复核」，业务确认后改配置，不改代码。

测试：10 组样本租约的门店链各一个金标准状态（由开发预标、法务抽核，见 LSE-08），`FoldingEngineGoldenTest` 逐分段比对；另有乱序输入 3 种排列结果相同的性质测试。

### LSE-04 CEL 函数与 D 类要点表达式（6 人天，需法务配合）

- 领域包注册的 CEL 函数：`freeMonths(item)`、`escalationRate(item)`（年化递增率）、`depositMonths(deposit, baseItem)`、`cureDays(statement)`（补救期天数；「N 个工作日」怎么落码规格尚未确认，暂按 7/5 换算成自然日并标待复核）、`penaltyCap(statement)`、`overdueDaysToTerminate(m)`、`overdueTimesToTerminate(m)`、`hasStatement(topic, type)`。
- 70 个 D 类要点、16 个 H 类要点的规则部分都写成 ADR-036 的规则结构（`applies` / `requires` / `check` / `onBlank`），存在**业务系统的要点库**里（BIZ-04），不放在领域包里。领域包只提供函数和一份初始导入文件 `seed/checkpoints.yaml`。
- 发布要点库时业务系统调用 Tioka 的 `POST /ontology/rules:validate`（ONT-04 的编译接口），表达式编译不过或引用了不存在的路径就不能发布。
- 示例（阈值都来自阈值配置，带配置版本）：

```yaml
- code: D-017                  # 免租期不少于品牌红线
  topic: rent.abatement
  mode: D
  mandatory: true
  applies: has(m.feeItems.RENT)
  requires: [m.feeItems.RENT.abate]
  check: freeMonths(m.feeItems.RENT) >= cfg.minFreeMonths        # 缺省 2
- code: D-023                  # 租金递增每年不超过 5%
  topic: rent.escalation
  mode: D
  mandatory: true
  applies: size(m.feeItems.RENT.sched.segments) > 1
  requires: [m.feeItems.RENT.sched.segments]
  check: escalationRate(m.feeItems.RENT) <= cfg.maxEscalation    # 缺省 0.05
- code: H-004                  # 租金逾期解约门槛：单次超过 30 日或年度累计 3 次
  topic: termination.tenant_default
  mode: H
  mandatory: true
  applies: true
  requires: [m.statements.RIGHT.where(topic == 'termination.landlord')]
  check: overdueDaysToTerminate(m) > cfg.minOverdueDays || overdueTimesToTerminate(m) >= cfg.minOverdueTimes
                               # 规则先判，再由复核员看原文确认
```

## 2. 业务系统

### BIZ-01 骨架（3 人天）

Spring Boot 3、Java 17、PostgreSQL、Flyway、Keycloak 资源服务器；角色：`legal`（法务）、`legal_lead`（法务负责人，维护要点库与阈值）、`ops`（运营，提交合同）。门店归属区域，法务按区域授权。

> **2026-11-06 修订（ADR-029 第 69 条）**：Foundation 平台放在 M4 之后的 F 阶段，本系统在 M3 按 [S15](../systems/S15-Foundation基础平台系统.md) 第 19.2 节过渡约定实现权限：角色用共用 Keycloak realm 的客户端角色表达，不建角色表；建一张「用户 → 区域」授权表，区域编码即以后 Foundation 的 `region` 维度值，查询按该表过滤；在仓库维护权限清单文件。BIZ-01 因此由 3 人天增至 6 人天，由 M3 缓冲吸收。F 阶段经 BAS-28 迁到 Foundation。

### BIZ-02 合同与提交（4 人天）

运营或法务上传文件、填门店与合同种类、指定经办法务，点「提交审查」→ 写 `contract`、`contract_file`，经 outbox 发 `lease.contract.submitted`。

### BIZ-03 模型版本与确认（后端 4、前端 2 人天）

- `proposeModelDraft` 接收 Tioka 的草稿（只存引用与摘要，草稿正文按需从 Tioka 读），返回 `draftRef`。
- 确认页嵌入 `@tioka/ontology-confirm`（ONT-08）。确认或更正提交到业务系统后端：生成版本号、计算 `content_hash`、写 `model_version`、发 `contract.model.confirmed`。
- **确认时机**（规格 D24，按阅读版建议）：确认不阻塞审查。审查在草稿上进行；签署后、进入折叠前必须确认。业务系统在合同 `stage` 改为「已签署」时，若最新模型还不是 CONFIRMED，在工作台提示经办法务确认。

### BIZ-04 要点库、阈值、案例与正反例（后端 5、前端 6 人天）

- 维护界面给 `legal_lead`。要点按版本编辑，发布时调用 Tioka 的规则校验接口（LSE-04），通过后生成新的 `checkpoint_set`。
- 修订案例与正反例增删改时发 `lease.kb.changed`，由 LSE-07 同步到 Tioka 知识库。
- 初始数据由 LSE-04 的 `seed/checkpoints.yaml` 导入。

### BIZ-05 审查结果与处置（后端 4、前端 6 人天）

- `submitReviewDraft(reviewRunId, contractKey, round, modelVersion, checkpointSetVersion, thresholdConfigVersion, findings[])`：按 `Idempotency-Key` 去重；同一合同新一轮提交后，上一轮未处置的 Finding 标 `superseded_by`，已处置的保留并在新一轮里提示「上一轮已处置」。
- 结论处理页：按「必备不满足 → 不满足 → 缺失 → 待人工 → 满足 / 不适用」排序；每条显示结论、理由、建议修改、依据（模型取值 + 原文高亮，复用确认组件里的原文面板）、参考的修订案例与正反例。
- 法务处置：接受、修改（改结论或建议）、驳回（必填原因）。每次处置发 `lease.review.feedback`。全部必备项处置完才能把审查标为完成，完成时发 `lease.review.closed`。
- 导出修订意见（Word）放 M4，第一期不做。

### BIZ-06 租约状态展示（后端 2、前端 3 人天）

接收 `writeLeaseState`（按 `input_hash` 去重），门店页按时间轴展示费用项分段、减免、押金余额与复核项。只读；有异议时引导到对应合同的模型更正。

### BIZ-07 OpenAPI 与契约测试（2 人天）

业务系统发布 `lease-biz.openapi.yaml`，CON-07a 的连接器随包带它的快照。两边各跑一套契约测试（业务系统用 Spring Cloud Contract 生成桩，Tioka 的集成测试用这个桩）。

### BIZ-08 工作台、深链与登录（后端 1、前端 4 人天）

- 法务工作台：我经办的合同、待确认模型、待处置结论。
- 深链：`https://{lease-biz}/review/{reviewRunId}`，可带 `#finding={findingId}`。链接不带任何令牌（第 57 条）：未登录时走 Keycloak 登录后回到原地址；已登录时直接打开。权限由业务系统按区域判断，拿到别人的链接也看不到不该看的合同。

| `submitReviewDraft` | `POST /api/review-runs/{reviewRunId}/findings` | REVERSIBLE（新一轮覆盖，未处置的作废） | `lease.review.draft` | 入参 `$ref: lease.findingList@1` |
| `writeLeaseState` | `PUT /api/stores/{storeCode}/lease-state` | REVERSIBLE（派生数据，可重算覆盖） | `lease.state.write` | 由折叠投影钩子调用，不给 Agent |

所有写操作必须带 `Idempotency-Key`，业务系统保存 24 小时内的键与响应。业务系统**不提供**任何改已确认模型或改法务处置的接口给 Tioka。

### 业务系统发出的事件

统一信封：`{eventId, type, occurredAt, source: "lease-biz", subjectKey, data}`；`subjectKey` 为 `lease:{门店编码}:{合同号}:v{版本}`（审查与确认类事件）或 `lease-store:{门店编码}`（门店类事件）。

| type | data 关键字段 | Tioka 处理 |
| --- | --- | --- |
| `lease.contract.submitted` | `contractKey`、`storeCode`、`kind`、`files[{fileId,sha256,mime}]`、`assignee`、`priorKeys[]`、`requestedBy` | 编排规则 → 审查主管 Run（经办人 = `assignee`） |
| `contract.model.confirmed` | `contractKey`、`version`、`contentHash`、`confirmedBy`、`aclPrincipals[]` | ONT-02 入库 → 折叠 → 必要时重审 |
| `lease.review.feedback` | `reviewRunId`、`findingId`、`checkpointCode`、`action`、`finalConclusion`、`reason`、`handledBy` | 评测与经验（LSE-08、EVO） |
| `lease.review.closed` | `reviewRunId`、`stats` | 关闭编排 Run 的回执；M4 起记价值账本（TRU-13） |
| `lease.kb.changed` | `kind`（revision_case / example）、`ids[]`、`op` | LSE-07 增量同步 |
| `lease.performance.*` | 预留：`eventKind`、`storeCode`、`occurredAt`、`amount?`、`ref` | 执行风险与权益预警场景使用，本期只登记 Schema |

事件可以经 HTTP 或 RocketMQ 进入（CON-07a），处理方式相同。

## 4. 审查链路

### LSE-05 Agent、授权书与编排规则（5 人天）

M3 用 `agent.delegate`（RT-12）组织多智能体，不用 M4 的 TeamSpec。四个 Agent、两个 Flow：

| 角色 | 资产 | 做什么 | 模型 |
| --- | --- | --- | --- |
| 审查主管 | Agent `lease.review.lead` | 拉合同、确保模型、取要点、分派、汇总、提交、通知 | 推理强的模型（如 DeepSeek 推理模型） |
| 建模 | Flow `ontology.build.lease.contract`（作为工具） | @model.build | 抽取路由（百炼主、DeepSeek 备） |
| 规则判定 | Flow `lease.review.evaluate`（作为工具） | 对 D 类和 H 类的规则部分批量 `rule.evaluate`，不调模型 | — |
| 复核员 | Agent `lease.review.checker` | H 类：看规则结论、取值和原文，确认或改判 | 抽取路由 |
| 判断员 | Agent `lease.review.judge` | J 类：按主题组判断，参考修订案例与正反例 | 推理路由 |
| 质检员 | Agent `lease.review.qa` | 对「不满足」、必备「缺失」和判断分歧项做第二意见 | 与判断员不同的模型族 |

主管的执行步骤（写在主管的 Instructions 里，同时由工具白名单约束顺序上的必要条件）：

```text
1. getContract、getContractFiles；文档 ingest（DOC-01）
2. 模型：有已确认版本且文件哈希未变 → 用确认版；否则调建模 Flow 得草稿（modelVersion = draft:{rev}）
3. getCheckpoints(latest)、getThresholds；@model.coverage 一次，得主题覆盖
4. 调规则判定 Flow：D 类 70 个得结论；H 类 16 个得规则初判
5. 分派（agent.delegate，并发上限 6）：
   - 复核员 × 1：H 类 16 个，一次一组 4 个
   - 判断员 × N：J 类 24 个按主题分组（廉洁类 6 个一组，其余按主题 3〜5 个一组），每组两次独立判断
6. 质检：不满足、必备缺失、两次判断不一致的项交给质检员；质检仍无法定论的标 UNCERTAIN（待人工）
7. 汇总成 lease.findingList（输出契约，SCH-03 校验）→ submitReviewDraft
8. 通知经办法务（飞书卡片 + 邮件）
```

子 Agent 的委派授予（MAS-01）按「只收窄」给：复核员、判断员只有 `ontology.read`、`ontology.read_draft`、`@doc.unit`、`knowledge.search`（限审查知识库）；没有任何 `biz.lease.*` 写工具，也没有通知工具。只有主管能 `submitReviewDraft` 和发通知。

**授权书**（ADR-032）：

| 项 | 主管 `lease.review.lead` |
| --- | --- |
| 范围 | `contractKey` 等于本次事件的合同；门店区域 = 经办法务的区域 |
| 可用动作类别 | `lease.read`、`ontology.read*`、`lease.draft.write`、`lease.review.draft`、`notify.internal` |
| 禁区 | 改已确认模型、改法务处置、`notify.external`（对外渠道） |
| `delegable` | `ontology.read`、`ontology.read_draft`、`knowledge.search` |
| 自治上限 | `lease.review.draft`、`lease.draft.write`、`notify.internal` 上限 L3；初始见下文「上岗」 |
| 预算 | 每 Run 最多 300 万 token、80 步、委派深度 1 |

**编排规则**（ADR-020）：`lease.contract.submitted` → 接单模式 `auto`，Mandate 的 `scope_json` = `{contractKey}`，经办人 = `data.assignee`（`on_behalf_of`），超时 2 小时转人工；`contract.model.confirmed` 且差异涉及审查依赖路径 → 重审（见下）。

### LSE-06 Finding 与轮次（3 人天）

`lease.finding@1` Schema（随领域包发布）：

```json
{
  "$id": "tioka://schema/lease.finding@1",
  "type": "object",
  "x-tioka-compare": { "key": ["checkpointCode"], "value": ["conclusion"] },
  "x-tioka-evidence": "required",
  "required": ["findingId", "checkpointCode", "mode", "mandatory", "conclusion", "modelVersion", "reason", "modelRefs", "producedBy"],
  "properties": {
    "findingId":      { "type": "string" },
    "checkpointCode": { "type": "string", "pattern": "^[DHJ]-\\d{3}$" },
    "topic":          { "type": "string" },
    "mode":           { "enum": ["D", "H", "J"] },
    "mandatory":      { "type": "boolean" },
    "conclusion":     { "enum": ["SATISFIED", "NOT_SATISFIED", "MISSING", "NOT_APPLICABLE", "UNCERTAIN"] },
    "modelVersion":   { "type": "string" },
    "thresholds":     { "type": "array", "items": { "type": "object", "required": ["name", "value", "configVersion"] } },
    "modelRefs": {
      "type": "array",
      "x-tioka-identity": ["path"],
      "items": {
        "type": "object",
        "required": ["path", "valueStatus"],
        "properties": {
          "path":        { "type": "string", "x-tioka-path": true },
          "value":       {},
          "valueStatus": { "type": "string" },
          "evidence":    { "type": "array", "items": { "$ref": "tioka://schema/platform.citation@1" } }
        }
      }
    },
    "reason":      { "type": "string", "maxLength": 1000 },
    "suggestion":  { "type": "string", "maxLength": 2000 },
    "references":  { "type": "array", "items": { "type": "object", "properties": { "kind": { "enum": ["revision_case", "example"] }, "id": { "type": "string" } } } },
    "needsReview": { "type": "boolean" },
    "producedBy":  { "type": "object", "required": ["agent", "turnId"], "properties": { "agent": {}, "turnId": {}, "secondOpinion": {} } },
    "reviewRound": { "type": "integer" }
  }
}
```

- 四态之外的 `UNCERTAIN` 只用于「质检后仍无定论」，业务系统显示为「待人工」，不算 Agent 给出的结论。
- **重审**：模型确认后，若 `diff_draft`（人工更正）涉及的路径与上一轮任一 Finding 的 `modelRefs.path` 相交，或者涉及某个要点的 `requires` 路径，就只对这些要点重跑，`reviewRound + 1`；未受影响的要点沿用上一轮结论（复制并改 `modelVersion`）。要点库发布新版本时不自动重审，由法务在业务系统里手动发起。
- Tioka 侧 V175 建 `lease_review_round`（`review_run_id`、`round`、`tioka_run_id`、`model_version`、`checkpoint_set_version`、`status`、`stats_json`），只做幂等与重审判断；结论本身只存在业务系统。

### LSE-07 修订案例与正反例同步（3 人天）

- 用通用连接器 SDK（ADR-018 `DataSourceConnector`）写 `lease-biz` 数据源：全量 + 按 `lease.kb.changed` 增量。
- 写入 Tioka 知识库 `lease-review-kb`，每条一个块，`metadata` = `{kind, checkpointCode, topic, polarity}`；判断员检索时 `metadataFilter` 固定为本组要点的 `checkpointCode`，再按向量相似度取前 5。
- 这是**参考资料检索**，与合同原文无关：合同证据只通过证据单元定位（第 51 条）。

### 通知

主管在提交成功后调用 `notify`（NTF-01）：

- 收件人：经办法务（`assignee`）；必备不满足数 ≥ 1 时抄送法务负责人。
- 渠道：飞书卡片 + 邮件（第一期）。`noticeKey = lease-review:{reviewRunId}:{round}`，重试与重复事件都不会重复发送。
- 卡片内容：门店、合同号、合同种类、轮次；统计（必备不满足 / 不满足 / 缺失 / 待人工）；最多 3 条必备不满足的要点名称与一句话理由；按钮「去处理」打开深链。不放合同原文与金额，标签 INTERNAL。
- 法务处置完成（`lease.review.closed`）后，Tioka 用 `update` 把飞书卡片改成「已处理」。
- 影子期（`visibility = SHADOW`）不发任何通知（第 58 条）。

### 时延与调用量

| 环节 | 模型调用（一份 30 页合同） | 目标时延 |
| --- | --- | --- |
| 解析 + OCR | 0〜30（扫描页数） | 3 分钟 |
| @model.build | 约 60〜70 | 12 分钟 |
| 规则判定 | 0 | 10 秒 |
| 复核员（H） | 约 4〜6 | 3 分钟 |
| 判断员（J） | 约 14（7 组 × 2） | 5 分钟（并行） |
| 质检 | 约 5〜15 | 3 分钟 |
| 合计 | 约 90〜130 | 提交后 30 分钟内出草稿 |

按每天 10 份，每天约 1,000〜1,300 次模型调用，用现有路由计划与配额即可，不需要专门扩容。

## 5. 上岗与评测

### 上岗（ADR-034）

- **M3 影子期**：前 50 份合同（约 5 个工作日）`review_run.visibility = SHADOW`。结论写入业务系统但不展示给经办法务，法务照常人工审查并在业务系统里录入自己的结论；LSE-08 对比两者。影子期用业务系统的可见性开关实现，不依赖 M4 的 TRU-11。
- 影子期达标（见下）后，`lease.review.draft` 设为 L2：提交草稿自动执行（可逆），通知自动发出（内部、INTERNAL）。
- M4 上线 TRU-11 后，新版本的审查 Agent 改用平台影子模式上岗，业务系统的开关只保留作兜底。

### LSE-08 评测（4 人天）

**金标准**：规格中的 10 组样本租约。业主原稿用来标注模型（对象、属性、陈述），修订处作为审查「不满足」的参考答案。标注按阅读版建议分工：开发先用模型预标，人工逐条核对模型层；法务只看「不满足」与有争议的结论，不从零标。

**指标与门槛**（影子期结束时判定）：

| 指标 | 计算 | 门槛 |
| --- | --- | --- |
| 必备要点四态一致率 | 与法务结论一致的必备要点 / 必备要点总数（UNCERTAIN 算不一致） | ≥ 85% |
| 必备「不满足」召回率 | Agent 判不满足且法务也判不满足 / 法务判不满足 | ≥ 90% |
| 「不满足」精确率 | 同上 / Agent 判不满足 | ≥ 70% |
| 证据绑定率 | 有证据且通过引文校验的 Finding / 全部 Finding | 100%（平台保证） |
| 模型层 | 商务对象属性 F1、主题覆盖率 | 属性 F1 ≥ 0.9；覆盖率按主题出报告，不设门槛 |
| 时延 | 提交到草稿 | P90 ≤ 30 分钟 |

召回率门槛高于精确率：漏掉一个必备不满足项的代价远大于法务多看一条误报。

**线上反馈**：每条 `lease.review.feedback` 写入 EVO-01 的线上评测记录；按要点统计驳回率，周报列驳回率最高的 10 个要点给法务负责人和开发，决定改 Prompt、改阈值还是改要点表达式。M4 起，修改与驳回的原因进入经验库（EVO-05），判断员检索经验作为提示。

**影子期抽样**：上线后每天抽 2 份（约 20%）由法务负责人全量复核，持续 4 周；之后按 ADR-034 L3 的 10% 抽检规则。

## 6. 闸门用例

> 关闭 mock、双实例、开启鉴权。业务系统桩（BIZ-07 生成）提交一份扫描版主合同和一份补充协议 → 30 分钟内业务系统收到一轮草稿结论，每条都有模型取值和可定位的原文 → 飞书与邮件各收到一条卡片 / 邮件，点「去处理」在已登录状态下直接进结论页 → 法务驳回一条、修改一条 → Tioka 收到反馈事件并计入评测 → 法务在确认页更正一个免租期取值并确认 → 只有依赖该路径的要点重跑，第二轮结论与第一轮的差异在结论页标出 → 复核员试图直接调用 `submitReviewDraft` 被拒，审计里有委派链。
