## 0. 范围与工作项

本文覆盖 **应用 → 应用**的授权访问：应用 A 调应用 B 的接口，既包括没有人参与的定时任务与后台流程（M2M），也包括「应用 A 代表当前登录用户去访问应用 B」（OBO 用户委派）。**不是**「Agent → 工具」（CON-07a）、不是「父 Agent → 子 Agent」（ADR-039）、不是「本平台 Agent ↔ 外部组织 Agent」（ADR-045 / A2A）——边界见 §8。

| 工作项 | 内容 | 人天 | 迁移 | 闸门 |
| --- | --- | --- | --- | --- |
| BAS-29 | 应用间授权主数据：`fdn_app_grant`、授权登记与撤销、生效校验接口 | 5 | V200〜V201 | 并入 `GfAppGrantGateIT` |
| BAS-30 | 应用间调用执行：`foundation-starter-security` 撤销与授权校验、`@RequireAppGrant`；`foundation-starter-client` M2M / OBO 取令牌与透传 | 5 | —（starter 无表） | `GfAppGrantGateIT` |
| BAS-FE-15 | 应用间授权管理页：授权登记与撤销、高风险复核入口 | 前端 3 | —（纯前端） | 前端 vitest |

**硬约束（贯穿全文，Code Review 必查）**：

- **禁止** `tenant_id` / `sys_tenant`（ADR-029 第 60 条）；隔离边界只有组织单元树与「人员 + 应用」，应用间授权以「应用编码对」为键。
- 主键 ULID，带前缀时列宽 `VARCHAR(32)`；本文前缀：`agr` 应用授权。
- 时间列一律 `TIMESTAMPTZ`；DO 字段 `LocalDateTime`（UTC），领域对象与 API 用 `Instant`。
- **令牌只带身份**（`sub` / `act` / `azp` / `aud`），**不带权限**（延续 ADR-051 第 3 条、S15 §9.2）；能力判定在被调应用侧，且 **OBO 收窄后不得放大**。
- **Foundation 不进请求热路径**：校验在被调应用内用本地缓存完成，令牌校验只做签名与声明提取（ADR-051 第 5 条）。
- 错误码沿用 ADR-029 第 14、18 条口径：未认证 → `UNAUTHORIZED(40100)`/401；无权限或授权不足 → `FORBIDDEN(40300)`/403。

## 1. 两种模式总览

| 模式 | 协议 | 适用 | 令牌主体与声明 | 被调应用的有效能力 |
| --- | --- | --- | --- | --- |
| **M2M**（机器对机器） | OAuth 2.0 `client_credentials` | 定时任务、后台流程、系统间数据同步 | `sub` = 调用方服务账号、`aud` = 被调应用、`act` = 调用方应用、`azp` = 调用方客户端 | `fdn_app_grant` 中「调用方 → 被调方」的被授予能力（无用户，不做用户收窄） |
| **OBO**（用户委派，on-behalf-of） | OAuth 2.0 Token Exchange（RFC 8693） | 应用 A 在用户已登录时代表该用户访问应用 B | `sub` = 用户、`act` = 应用 A、`aud` = 被调应用、`azp` = 调用方客户端 | **用户在该应用的有效权限 ∩ 调用方被授予能力**（收窄，见 §4） |

- 两种模式都由 **Keycloak 承担协议与令牌签发**（延续 ADR-051 第 2 条）；Foundation 只做授权关系登记与生效校验（主数据 + 校验接口），不参与令牌签发时序。
- 令牌**只带身份与调用方标识，不带权限**；被调应用按「调用方应用 + 被调应用」取授权关系判定，OBO 再叠加用户快照收窄。
- **默认拒绝**：没有登记「调用方 → 被调方」授权关系的调用，被调应用一律 **403**（ADR-076 决定 2）。
- OBO 的协议前提：Keycloak 需开启 Token Exchange（RFC 8693）与 audience 映射；不支持时该项按 [S15 §21 第 7 条](../systems/S15-Foundation基础平台系统.md) 处理（升级或该场景退回 M2M）。

## 2. 主数据 `fdn_app_grant`（BAS-29）

### 2.1 领域模型

应用授权（`com.tioka.foundation.appgrant.domain.AppGrant`）：

| 字段 | 说明 |
| --- | --- |
| `id` | ULID，前缀 `agr` |
| `grantorApp` | **授权方应用**（被调应用 B，授予对自身接口的访问） |
| `granteeApp` | **被授权方应用**（调用方应用 A，被授予能力） |
| `capabilities` | 被授予能力：权限码集合（格式 `资源:动作`，与 S15 §11.1 一致）；JSON 数组；**去重排序后入库** |
| `mode` | `M2M` / `OBO` / `BOTH` |
| `status` | `PENDING`（待审批）/ `ACTIVE`（生效）/ `REVOKED`（已撤销） |
| `effectiveFrom` | 生效时间（可空 = 立即） |
| `effectiveTo` | 失效时间（可空 = 长期） |
| `source` | 来源：`MANUAL`（管理台登记）/ `APPLICATION`（应用申请）/ `IMPORT`（批量导入）——**审批来源** |
| `reviewState` | 高风险复核状态：`NONE` / `PENDING` / `APPROVED` / `REJECTED`（见 §7） |
| `approvalRef` | 复核/审批记录引用（安全管理员操作记录 ID，可空） |
| `version` | 单调递增版本号，用于事件与缓存失效；每次变更 +1 |
| 审计列 | `create_at/update_at/create_by/update_by` |

### 2.2 唯一约束与幂等

- **唯一约束**：`UNIQUE (grantor_app, grantee_app)`。「调用方对」是这条主数据的身份；`mode` 是行上的属性（取 `BOTH` 时同时允两种模式），因此一个应用对**至多一行**。
- **生效区间**：同一行的有效窗口由 `effective_from` / `effective_to` 表达；窗口外的行视为不生效（不删行，保留审计）。
- **幂等**：登记接口要求 `Idempotency-Key`（S15 §14.1 所有写接口）；同 `(grantor_app, grantee_app)` 重复登记为 **UPSERT**（更新同一行，`version +1`、`capabilities` 去重排序），不产生第二行、不产生重复事件之外的副作用。
- **撤销**：`POST …:revoke` 置 `status = REVOKED`、`version +1`；**不物理删除**（保留「曾经授予过谁」）。
- **默认拒绝**：`fdn_app_grant` 无对应行 → 拒绝。管理台删除/停止被调应用、调用方应用状态变为 `DISABLED` 时，相关行按业务规则置 `REVOKED` 并在校验侧视为不生效。

### 2.3 迁移 SQL 示意

```sql
-- V200 应用间授权（Foundation 库，Flyway 自 V1 起；F2 批次独立号段 V200+）
-- 不带 tenant_id（ADR-029 第 60 条）；隔离边界为「应用编码对」
CREATE TABLE fdn_app_grant (
    id             VARCHAR(32)  PRIMARY KEY,                 -- ULID，前缀 agr_
    grantor_app    VARCHAR(64)  NOT NULL,                    -- 授权方（被调应用 B）
    grantee_app    VARCHAR(64)  NOT NULL,                    -- 被授权方（调用方 A）
    capabilities   JSONB        NOT NULL,                    -- 权限码集合，如 ["contract:read"]
    mode           VARCHAR(8)   NOT NULL DEFAULT 'M2M',      -- M2M / OBO / BOTH
    status         VARCHAR(16)  NOT NULL DEFAULT 'PENDING',  -- PENDING / ACTIVE / REVOKED
    effective_from TIMESTAMPTZ,
    effective_to   TIMESTAMPTZ,
    source         VARCHAR(16)  NOT NULL DEFAULT 'MANUAL',   -- MANUAL / APPLICATION / IMPORT
    review_state   VARCHAR(16)  NOT NULL DEFAULT 'NONE',     -- NONE / PENDING / APPROVED / REJECTED
    approval_ref   VARCHAR(64),
    version        BIGINT       NOT NULL DEFAULT 1,          -- 每次变更 +1
    create_at TIMESTAMPTZ NOT NULL DEFAULT now(), update_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    create_by VARCHAR(64) NOT NULL DEFAULT 'system', update_by VARCHAR(64) NOT NULL DEFAULT 'system',
    UNIQUE (grantor_app, grantee_app));                      -- 一个应用对至多一行（UPSERT 幂等）
CREATE INDEX idx_app_grant_lookup ON fdn_app_grant (grantor_app, grantee_app, status);

-- V201 授权变更事件走 Foundation 自己的 outbox（示意表 fdn_outbox 由 BAS-07 建立；本表复用）
-- 无新增表。
```

> 若未来需要「M2M 与 OBO 使用**不同**的能力集合」，则改为按 `(grantor_app, grantee_app, mode)` 唯一、一行一模式；默认不这样做（保持与 ADR-076 的 `M2M / OBO / 两者` 一致）。

## 3. 令牌与协议（Keycloak 侧与 claim）

### 3.1 Keycloak 配置

| 项 | 配置 | 用途 |
| --- | --- | --- |
| 调用方 A 的 OIDC 客户端 | 追加 `client_credentials` 授权类型；启用服务账号 | M2M 取令牌 |
| Token Exchange | 开启 RFC 8693（Keycloak 24 的 token-exchange 能力）；授权调用方客户端可执行 token-exchange | OBO 换取用户委派令牌 |
| Audience 映射 | 为被调应用 B 建立 audience mapper，使令牌 `aud` 含 B | 被调侧撤销校验（`aud` 是否为本应用） |
| `act` 声明 | 以协议映射写入 `act`（调用方应用标识） | OBO 与被调侧识别「代表人的应用」 |
| Realm / 客户端 | 沿用共用 realm 与 Foundation 自动开通的客户端（BAS-04），不新增 realm | 与既有 SSO 一致 |

**协议遵守**：Foundation 不重写认证协议（延续 ADR-051 第 2 条），只负责登记与校验；签发与声明由 Keycloak 保证。

### 3.2 令牌 claim 与签发

| 模式 | 签名来源 | `sub` | `act` | `azp` | `aud` | 是否带权限 |
| --- | --- | --- | --- | --- | --- | --- |
| M2M | 服务账号 `client_credentials` | 调用方服务账号 | 调用方应用 | 调用方客户端 | 被调应用 | 否 |
| OBO | RFC 8693 Token Exchange（`subject_token` = 用户访问令牌） | 用户 | 应用 A | 调用方客户端 | 被调应用 | 否 |

- **M2M 签发**：应用 A 用 `foundation.service-account.*`（`client_credentials`）向 Keycloak 取令牌，`aud` 指定为被调应用 B；令牌只带身份与调用方标识，**不带权限**。
- **OBO 签发**：应用 A 在用户已登录的前提下，以用户的访问令牌为 `subject_token` 做 Token Exchange，换出 `sub = 用户`、`act = 应用 A`、`aud = 被调应用 B` 的令牌；`act` 只表示「谁代表用户」，不携带能力。
- **校验（被调应用 B 侧，starter）**：
  1. 验签与有效期；`aud` 必须含本应用（否则视为**目标不符**拒绝）；
  2. `act`（M2M 下取调用方应用标识，OBO 下取 `act` 内的应用）→ 得到**调用方应用 A**；
  3. 取 `(B, A)` 的 `fdn_app_grant`（本地缓存，事件失效，TTL 兜底）→ 校验登记、`status = ACTIVE`、在生效区间内、`mode` 与本次调用匹配；
  4. OBO 时叠加用户权限收窄（§4）；M2M 不叠加用户。
- **透传**：调用方出站请求带 `traceparent` 与 `request_id`（ADR-073），并按 ADR-074 写 `ext_interaction` 台账（`auth_mode`：M2M = `SERVICE`，OBO = `DELEGATED`；`actor_id` / `run_as` 分别记「人」与「代表人的应用」）。

## 4. OBO 权限收窄算法（不得放大）

**定义**：被调应用 B 执行 OBO 调用时的有效能力 = **调用方被授予能力 ∩ 用户在该应用的有效权限**（ADR-076 决定 4、S15 §22.4）。

- 用户权限：取自该用户在 **B 应用**的授权快照（S15 §11.3 / [F-06](F-06-数据权限与授权快照.md) 的 `AuthzSnapshot.permissions`）；
- 调用方能力：取自 `fdn_app_grant` 中 **A → B** 的被授予能力；
- 两者**取交集**，避免「应用把自己没有的能力借助高权限用户放大」。语义与 ADR-039 委派授予一致（只能取交集，永不放大）。

```text
effective(user, A→B, required):
  grant = fdnAppGrantCache.lookup(grantorApp = B, granteeApp = A)   # 本地缓存/回源
  if grant == null:                          return DENY            # 默认拒绝：未登记
  if grant.status != ACTIVE:                 return DENY            # 待审批 / 已撤销
  if now ∉ [grant.effectiveFrom, grant.effectiveTo): return DENY    # 生效区间
  if requiredMode ∉ grant.mode:              return DENY            # 模式不符（M2M/OBO/BOTH）

  if token.sub 是服务账号:                                            # M2M：无用户
      effective = grant.capabilities
  else:                                                             # OBO：sub 为用户
      userPerms = authzSnapshotClient.load(personId(token.sub)).permissions   # 用户在该应用的权限
      effective = grant.capabilities ∩ userPerms                    # 收窄，且永不放大

  return required ∈ effective ? ALLOW : DENY                        # 不满足 → 403
```

**示例**（被调应用 B，调用方应用 A）：

| # | A → B 被授予能力 | 用户在某应用的有效权限 | 请求能力 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | `{contract:read, contract:write}` | —（M2M） | `contract:read` | 允许 |
| 2 | `{contract:read}` | `{contract:read, contract:write}` | `contract:write` | **拒绝**（收窄：A 无 `write`，不得借用户放大） |
| 3 | `{contract:read}` | `{contract:read}` | `contract:read` | 允许（交集非空且命中） |
| 4 | `{contract:read}` | `{}`（用户在该应用无权限） | `contract:read` | **拒绝**（交集为空） |
| 5 | 无登记行 | 任意 | 任意 | **拒绝**（默认拒绝） |
| 6 | `{contract:read}`（已撤销） | 任意 | `contract:read` | **拒绝**（状态非 `ACTIVE`） |

**边界**：收窄只对 OBO 生效；M2M 无用户上下文，有效能力即被授予能力。收窄结果**只在被调应用内用于本次请求判定**，不回写、不缓存为用户权限；用户权限变化由 `fdn.authz.changed`（[F-06](F-06-数据权限与授权快照.md)）失效快照，授权关系变化由 `fdn.app.grant.changed`（§6）失效本地授权副本。

## 5. 执行在应用内，不做网关（BAS-30）

延续 ADR-051 第 5 条与 ADR-076 决定 5、10：**不把 Foundation 做成所有应用间调用的代理**。执行落在两端 starter 内，Foundation 不在请求热路径。

### 5.1 被调侧：`@RequireAppGrant`（`foundation-starter-security`）

替换 [F-07 §9](F-07-后端接入starter.md) 的占位注解，给出实现语义：

```java
// com.foundation.starter.security.appgrant
public @interface RequireAppGrant {
    /** 被调应用（授权方）编码；留空时取 foundation.app-code（本应用）。 */
    String appCode() default "";
    /** 允许的调用方应用编码；留空表示不限定具体调用方（仅按能力 + 登记判定）。 */
    String callerApp() default "";
    /** 需要的能力（权限码，格式 资源:动作）。 */
    String permission();
}
```

- `AppGrantAspect`（`order` 早于事务，与 `PermissionAspect` 同级）：解析当前调用令牌 → 取 `act`（调用方 A）与 `sub`（服务账号 / 用户）→ 按 §4 算法判定 → 不满足抛 `BizException(FORBIDDEN, 40300)`，并以**独立事务**写一条 `DENIED` 审计（沿用 M1-01 / F-07 §6 的拒绝路径）。
- 判定**全部走本地缓存**（`fdn:appgrant:{grantor}:{grantee}:{version}`，应用侧 Redis；未引入 Redis 时退化为进程内缓存），事件失效 + TTL 兜底；**降级拒绝**：缓存过期且回源失败 → 拒绝（不放行），与快照同机制（[F-07 §4](F-07-后端接入starter.md)）。
- 与 **Tioka 侧**：本注解与 Tioka 的 `@RequirePermission`、`ResourceGuard` 并存、互不替代——前者判「应用间调用授权」，后者判「用户在某应用内的权限」。

```java
@RestController
@RequestMapping("/api/contracts")
public class AppFacadeController {

    // 允许调用方以 contract:read 访问（调用方从令牌 act 取；此处不限定具体调用方）
    @RequireAppGrant(permission = "contract:read")
    @GetMapping("/{id}")
    ContractView get(@PathVariable String id) { ... }

    // 只允许 contract-biz 以 contract:write 调用；且该能力为高风险（登记需复核，见 §7）
    @RequireAppGrant(callerApp = "contract-biz", permission = "contract:write")
    @PutMapping("/{id}")
    void update(@PathVariable String id, @RequestBody ContractCmd cmd) { ... }
}
```

### 5.2 调用侧：`AppTokenClient`（`foundation-starter-client`）

沿用 [F-07 §9](F-07-后端接入starter.md) 的占位签名（`onBehalfOf(targetAppCode, Principal user)`），本文给出实现语义：

```java
public interface AppTokenClient {
    /** M2M：用本应用服务账号取 aud=targetAppCode 的令牌（client_credentials）。 */
    String clientCredentials(String targetAppCode);
    /** OBO：以用户访问令牌为 subject_token 换取 sub=用户、act=本应用的令牌（RFC 8693）。 */
    String onBehalfOf(String targetAppCode, Principal user);
}
```

- **令牌缓存**：按 `(targetAppCode, subject)` 缓存至过期前（含安全余量）；OBO 的 `subject` 取当前用户身份。
- **OBO 的 `subject_token`**：实现从当前请求上下文（`SecurityContext` / `PrincipalHolder` 关联的访问令牌）取得用户令牌；`Principal` 参数用于身份核对、`act` 归属与审计，不用于携带权限。
- **透传与台账**：出站带 `traceparent` 与 `request_id`（ADR-073）；经 `EgressClient` 按 ADR-074 写 `ext_interaction`（`kind = http`，`auth_mode` 如上）。
- **不重试越权**：`clientCredentials` / `onBehalfOf` 的失败按 [F-07 §11](F-07-后端接入starter.md) 的轻量重试与熔断处理；**不因 403 重试**（403 是判定结论，不是瞬时故障）。

```java
// 调用方示例：定时任务用 M2M，用户请求用 OBO
ContractDto dto = http.get(baseUrl + "/api/contracts/" + id, auth = tokenClient.clientCredentials("contract-biz"));
ContractDto mine = http.get(baseUrl + "/api/contracts/mine", auth = tokenClient.onBehalfOf("contract-biz", PrincipalHolder.require()));
```

### 5.3 与授权快照（F-06）的关系

- OBO 收窄读取的「用户在该应用的有效权限」**就是** [F-06](F-06-数据权限与授权快照.md) 定义的授权快照 `permissions`；starter 复用同一个 `AuthzSnapshotClient` 与缓存，**不新增第二套拉取路径**。
- 两条失效链独立：用户权限 → `fdn.authz.changed`；应用间授权关系 → `fdn.app.grant.changed`（§6）。任一变化都在 **5 秒级**内对本应用生效（事件 + TTL 兜底）。

| --- | --- | --- |

## 6. 事件与失效

- **事件**`fdn.app.grant.changed`（S15 §14.2）：经 **Foundation 自己的 outbox → RocketMQ 主题 `fdn-events`** 投递（沿用 BAS-07 / [F-06](F-06-数据权限与授权快照.md) 的 outbox，不新建通道）；可同时投 Webhook。
- **事件体只带 ID、版本与变化类型**（不带 `capabilities` 等敏感字段，订阅方需要详情时回查 `lookup` 接口）：

```json
{
  "eventId": "evt_01J...",
  "type": "fdn.app.grant.changed",
  "grantorApp": "contract-biz",
  "granteeApp": "tioka",
  "version": 7,
  "changeType": "UPSERT",
  "occurredAt": "2026-11-13T03:00:01Z"
}
```

- `changeType` ∈ `UPSERT`（登记或更新）/ `REVOKED`（撤销）；`version` 单调递增（同一应用对不回退）。
- **失效**：被调应用 starter 订阅后按 `(grantorApp, granteeApp)` 失效本地缓存 `fdn:appgrant:{grantorApp}:{granteeApp}:{version}`；**事件丢失时靠缓存 TTL（默认 5 分钟）兜底**（与 [F-06](F-06-数据权限与授权快照.md) 的快照机制同构）。
- **即时生效**：授权登记/撤销的即时生效**不依赖令牌吊销**——已签发令牌按短生命周期自然过期属「慢路径下线」，**与本机制无关**；即时生效靠被调应用**每次请求**按当前 `fdn_app_grant`（版本 + 本地缓存）判定。事件的作用是**让缓存与本地授权副本尽快失效**，不是生效的唯一依据。

## 7. 权限、复核与审计

### 7.1 权限码与复核

- 新增权限码 **`fdn:appgrant:admin`**（S15 §22.6、ADR-076 决定 8）：应用间授权的登记、修改、撤销与查询（管理台）。
- **高风险复核**：当授权涉及**写操作或跨应用数据访问**的能力（如 `*:write`、跨应用数据读取）时，登记与撤销需**安全管理员**（`security_admin`）复核后生效，与三员分立（[F-09](F-09-公共服务.md) BAS-19、ADR-053 第 1 节）一致：
  - 登记/撤销写入 `review_state = PENDING`，待复核通过置 `APPROVED`（`status` 方可为 `ACTIVE`）；复核拒绝置 `REJECTED`。
  - 低风险能力（纯只读、无跨应用数据访问）默认免复核（`review_state = NONE`），可由配置调整。
  - 复核走 Foundation 内置的简单复核（S15 §15「高风险授权」），不依赖 Tioka 审批台。

### 7.2 审计（双向）

| 侧 | 记什么 | action 建议 |
| --- | --- | --- |
| 管理面（Foundation） | 谁在何时把哪个应用能力授予/撤销给了谁（`grantorApp`/`granteeApp`/能力集合/模式）、复核结论 | `appgrant.create` / `appgrant.update` / `appgrant.revoke` / `appgrant.review` |
| 调用方 A | 「我调了谁、代表谁」（`grantorApp`、`sub`、`act`） | `appgrant.outbound`（与 ADR-074 台账以 `request_id` / `tools` 关联） |
| 被调方 B | 「谁调了我、代表谁、结果如何」（`granteeApp`、`sub`、`act`、`outcome`） | `appgrant.invoke`（拒绝同路径记 `DENIED`） |

- **OBO 必须区分「人」与「代表人的应用」**：审计与台账同时记录 `sub`（人）与 `act`（代表人的应用），不允许只留其一（延续 ADR-072、ADR-074、ADR-076 决定 7）。
- 拒绝记录用独立事务（`REQUIRES_NEW`），不随业务回滚（沿用 M1-01 / [F-07 §6](F-07-后端接入starter.md)）。

## 8. 边界与不做

| 不做 | 原因 |
| --- | --- |
| **不做集中式应用网关** | 把 Foundation 做成所有应用间调用的代理会把 Foundation 拉进请求热路径，违反 ADR-051 第 5 条，并放大单点故障面（ADR-076 决定 10）。执行在被调/调用两端 starter 内。 |
| **不做跨应用数据直连** | 应用间只走**受控的请求-响应式调用**（带令牌 + 授权关系校验）；不允许各应用自行约定共享密钥/内网直连绕过登记与审计。 |
| **不做令牌透传到前端** | 应用间令牌只在后端使用，不下发前端、不写 URL、不进 Cookie；前端只见自身会话（延续 ADR-029 第 32 条口径）。 |
| 不做应用间**事件订阅**授权 | 事件订阅用事件契约与订阅白名单（S15 §14.2），本文只管请求-响应式调用（ADR-076 决定 9）。 |
| 不替代 CON-07a / ADR-039 / ADR-045 | 分别是「Agent → 工具」「父 Agent → 子 Agent」「跨组织 Agent 互操作」；本文是「企业内应用 → 应用」，可组合但边界清晰。 |

**与 ADR-074 外部交互台账的关系**：应用间调用是本企业内的跨应用调用，出站经 `EgressClient` 按 ADR-074 写 `ext_interaction`（`kind = http`，`counterparty` = 被调应用，`auth_mode` = `SERVICE` / `DELEGATED`，`actor_id` / `run_as` 记录「人」与「代表人的应用」）；台账记「跨边界发生了什么」，审计记「谁决定做这件事、是否被允许」，二者以 `request_id` 关联。台账只增、纳入哈希链与保留类别，本文不改台账结构。

### 10.3 闸门 `GfAppGrantGateIT`（`@Tag("gate")`）

由 BAS-29/30 在 F2 内转绿（对应 [S15 §18.1 BAS-29/30 验收](../systems/S15-Foundation基础平台系统.md)）：

1. **M2M 允许 / 拒绝**：登记后允许；未登记对一律拒绝。
2. **OBO 允许 / 拒绝**：收窄后允许；越权收窄失败。
3. **默认拒绝**：无授权行、`status ≠ ACTIVE`、生效区间外，全部 403。
4. **即时生效**：撤销后 5 秒内被调应用拒绝该调用方的后续请求。
5. **降级拒绝**：缓存过期且 Foundation 不可达 → 拒绝。

## 11. 完成标准

- [ ] `fdn_app_grant`（V200+）落地，唯一约束 `(grantor_app, grantee_app)` 生效；登记为 UPSERT 幂等；撤销不物理删除。
- [ ] 登记 / 更新 / 撤销发 `fdn.app.grant.changed`（经 outbox → `fdn-events`，**只带 ID、版本、变化类型**），5 秒级内使被调应用缓存失效。
- [ ] 被调应用经 `@RequireAppGrant` 校验：`aud` 撤销、调用方登记、授权关系生效、OBO 叠加用户收窄；不满足返回 **403** 并上报审计。
- [ ] OBO 收窄 = 用户权限 ∩ 调用方被授予能力，**永不放大**（§4 六个示例全部成立）。
- [ ] 调用方经 `AppTokenClient` 取 M2M / OBO 令牌、透传 `request_id`/`traceparent`（ADR-073）、按 ADR-074 写台账。
- [ ] **默认拒绝**在无登记、非生效、模式不符、收窄为空等所有场景成立；缓存过期且回源失败时**拒绝**不放行。
- [ ] 权限码 `fdn:appgrant:admin` 生效；高风险授权登记/撤销需 `security_admin` 复核；审计区分「人」与「代表人的应用」。
- [ ] BAS-FE-15 管理页可用：列表、登记/编辑、撤销、复核入口、审计视图；权限显隐与直访 403 正确；`npm test` / `npm run typecheck` 绿。
- [ ] 全程**未引入 `tenant_id`**；主键 ULID、时间列 `TIMESTAMPTZ`；令牌只带身份；**不做集中式网关**。
- [ ] `GfAppGrantGateIT` 转绿；`foundation-test` 的 ArchUnit 规则在应用侧仍生效。
