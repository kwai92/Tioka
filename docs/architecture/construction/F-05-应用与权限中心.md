## BAS-04 应用登记与 OIDC 客户端（P0，4 人天）

### 领域模型

应用（`com.tioka.foundation.app.domain.App`）：

| 字段 | 说明 |
| --- | --- |
| `id` | ULID，前缀 `app` |
| `code` | 应用编码，全局唯一，**不可改**；正则 `^[a-z][a-z0-9-]{1,31}$` |
| `name` | 名称 |
| `icon` | 图标（URL 或图标名） |
| `accessUrl` | 访问地址（门户入口与单点登录回跳的默认地址） |
| `ownerUserId` | 负责人（人员 ID）；负责人离职进入交接待办（BAS-14） |
| `status` | `ENABLED` / `DISABLED` |
| `kind` | `PORTAL` / `ADMIN` / `SUB`；**Foundation 管理台与门户本身也登记为应用**（`PORTAL`、`ADMIN`），保证菜单、角色、权限码口径统一 |
| `manifestVersion` | 当前生效的权限清单版本号（清单导入时递增，见 BAS-05） |
| 审计列 | `create_at/update_at/create_by/update_by` |

客户端（`AppClient`）：一个应用可有一个或多个 OIDC 客户端，登记后在 Keycloak 自动开通。

| 字段 | 说明 |
| --- | --- |
| `id` / `appId` | ULID / 归属应用 |
| `clientId` | Keycloak `clientId`，登记规则 `{appCode}`（门户/管理台为固定值） |
| `redirectUris` | 回调地址列表（逗号分隔，精确匹配） |
| `grantTypes` | 默认 `authorization_code,refresh_token`；服务账号客户端追加 `client_credentials` |
| `secretRotatedAt` | 最近一次密钥轮换时间；**密钥明文不落库**，由 Keycloak 保管 |
| `status` | `ACTIVE` / `ROTATING` / `DISABLED` |

服务账号（`ServiceAccount`）：账号主体是 BAS-03/F-04 的 `fdn_account`（`type=SERVICE`）一行，本表只存「账号与应用的绑定 + 可用权限码」：

| 字段 | 说明 |
| --- | --- |
| `id` / `accountId` | ULID / 引用 `fdn_account.id`（`type=SERVICE`） |
| `appId` | 所属应用 |
| `clientId` | 对应的 Keycloak 客户端（`client_credentials` 流程） |
| `name` | 名称 |
| `permissionCodes` | 可用权限码白名单（JSON 数组；最终权限 = 快照权限 ∩ 该白名单） |
| `ownerUserId` | 负责人；离职进入交接待办 |
| `status` / `expiresAt` | `ACTIVE`/`DISABLED`；过期时间 |

**只用 `client_credentials`**（S15 8.2），服务账号不能交互登录、无密码。

首次启动初始化（延续 F-00 §5「初始化」）：建 realm、登记 `portal`、`admin`（Foundation 门户与管理台）两个 `kind` 应用、三员内置角色与应急管理员（停用状态）。

### 自动开通与密钥轮换

`AppRegistrar.register(cmd)` 事务内做三件事，Keycloak 调用放在事务外，失败回滚登记（本地不落半成品）：

1. 写 `fdn_app` + `fdn_app_client`（`status=ROTATING`）。
2. 调 Keycloak 管理接口（`KeycloakAdminClient`，服务账号令牌）：建客户端、设回调、按 `grantTypes` 开协议映射。
3. 需要服务账号时建 `fdn_account`（`type=SERVICE`，由 F-04 的 `AccountApi`）+ `fdn_service_account` + 客户端 `client_credentials` 协议。
4. 全部成功后把客户端置 `ACTIVE`。

密钥轮换 `ClientSecretRotator.rotate(appCode, clientId)`：调 Keycloak 生成新密钥 → 新旧并存窗口（可选，默认 0 秒）→ 撤销旧密钥；本地只更新 `secret_rotated_at`。轮换写审计 `app.client.rotate`；**轮换后旧密钥立即失效**（闸门断言）。

## BAS-05 权限中心（P0，6 人天）

### 领域模型

清单（`AppManifest`）：应用 + 版本 + 内容哈希 + 导入时间 + 导入人。**同哈希不重复导入**；**版本只能前进**（回滚应用版本时重新导入旧清单视为新版本，审计可见）。

菜单（`Menu`）：应用、编码、名称、类型（`DIR` 目录 / `MENU` 菜单 / `BUTTON` 按钮）、上级、路由路径、组件标识、图标、排序、是否显示、权限码。**来自清单**，管理台只能改名称、图标、排序、显示。

权限码（`PermissionCode`）：应用、编码（**`资源:动作`**，与 M1-01 权限点格式一致）、说明、风险级别（`LOW`/`MEDIUM`/`HIGH`）。高风险权限码授予时需二次确认并审计（BAS-19）。

角色（`Role`）：编码、名称、范围（`SYSTEM` 全局 / `APP` 某应用）、内置标志、权限码集合、数据范围、互斥角色。**内置角色不可删**；**全局角色只含 Foundation 自身的权限码**（`fdn:*`）。

授权（`RoleGrant`）：角色、授予对象（人员 `PERSON` / 组织单元 `ORG_UNIT` / 岗位 `POST`）、是否含下级、生效与失效时间、来源（`MANUAL` 手工 / `RULE` 规则 / `SYNC` 同步）。**同步与规则产生的授权不覆盖手工授权**。

### 清单导入规则

`ManifestImporter.import(appCode, manifestBytes, importSource)`：

1. 规范化（RFC 8785）+ SHA-256 得 `content_hash`；命中 `(app_id, content_hash)` → **幂等直接返回**，不产生新版本。
2. 版本必须 `> fdn_app.manifest_version`，否则拒（`CONFLICT`）。
3. 差异（`ManifestDiff`）：
   - **新增**权限码与菜单 → 直接生效，**默认不授予任何角色**（清单里的内置角色建议除外）。
   - **消失**的权限码/菜单 → 标 `OFFLINE`，记 `offline_at`；**保留 90 天后**由定时任务清理（`manifest-offline-retention-days`）。已下线项**从快照中剔除**。
   - **变更**的菜单只更新来自清单的字段（路由、组件、类型、上级），管理台覆盖过的名称/图标/排序/显示**不覆盖**。
4. 事务内提交后递增 `fdn_app.manifest_version`、写 `fdn_app_manifest`，经 **outbox → RocketMQ `fdn-events`** 发 `fdn.app.manifest_imported`。

### 有效角色与互斥

`EffectiveRoleResolver.resolve(personId, appCode, at)`：

```text
有效角色 = 直接授予(personId)
         ∪ 组织单元授予(personId 所在组织单元 ∈ 授权组织单元子树)
         ∪ 岗位授予(personId 当前岗位 ∈ 授权岗位)
再过滤：effective_from ≤ at ≤ effective_to（为空视为不限）
     且 不含与已选角色互斥的角色（按 fdn_role_mutex，两个互斥角色同时命中时后者丢弃并告警）
```

- **只增不覆盖**：同一 (role, subject) 存在 `source=MANUAL` 时，`RULE`/`SYNC` 授权不修改、不删除它；`RULE`/`SYNC` 只清理自己来源的行。
- 有效角色 → 权限码集合 = 各角色权限码并集 ∩ 应用可用权限码；全局角色只含 `fdn:*`。
- 结果供 BAS-07 生成授权快照（含可见菜单树、部门范围、维度取值）。

### 接口（S15 §14.1「权限」分组）

| 方法与路径 | 权限 | 说明 |
| --- | --- | --- |
| `POST /api/apps/{code}/manifest` | `fdn:manifest:import`（应用 CI 服务账号） | 清单导入；同哈希幂等 |
| `GET /api/apps/{code}/menus`、`PUT /api/menus/{id}` | 读 `fdn:menu:read`；写 `fdn:menu:admin` | 菜单树；管理台只能改名称/图标/排序/显示 |

## BAS-27 子系统/模块/功能目录与授权模式（P0，4 人天）

### 目录层级与来源

层级为 **子系统 → 模块 → 功能 → 操作**（S15 §6.1、ADR-054）：

| 层级 | 含义 | 举例 | 来源 |
| --- | --- | --- | --- |
| 子系统 | 独立部署、独立登录客户端的系统（=应用） | Tioka、合同业务系统、Foundation 管理台 | `fdn_app` + `fdn_subsystem` |
| 模块 | 子系统内业务板块，对应一级菜单或一个前端子应用 | Tioka「模型中枢」「知识」「工作流」 | 清单声明 → `fdn_module` |
| 功能 | 一个可授权的页面/能力，对应一个菜单项 | 「供应商管理」「合同台账」 | 清单声明 → `fdn_function`（与 `fdn_menu` 的 `MENU` 项一一对应） |
| 操作 | 功能内的按钮或接口，对应权限码 | `contract:submit`、`model:credential:admin` | 清单声明 → `fdn_permission_code` |

目录**由子系统的权限清单声明**，管理台按子系统 → 模块 → 功能 → 操作展示一棵树，授权时可整模块勾选。模块与功能的编码在清单中声明；`fdn_function.code` 与 `fdn_menu.code`（`type=MENU/BUTTON`）对齐，避免两套口径。

### 四种授权模式

`fdn_subsystem.auth_mode` 四选一（S15 §6.2）：

| 模式 | Foundation 管什么 | 子系统管什么 | 适用 |
| --- | --- | --- | --- |
| 集中授权 `CONCENTRATED` | 角色、菜单、权限码、数据范围全部 | 只执行（starter 校验） | 新建业务系统，如合同业务系统 |
| 分级授权 `GRADED` | 同上，但该子系统的角色与授权交给「子系统管理员」维护，系统管理员只指定子系统管理员 | 只执行 | 子系统较多、各业务线自己管人的企业 |
| 混合授权 `HYBRID` | 菜单、功能、权限码与系统级角色 | 资源级权限（谁能编辑哪个 Agent、哪个知识库） | **Tioka**（空间成员与资源 ACL 仍在 Tioka） |
| 自管授权 `SELF` | 只提供身份、组织与单点登录 | 全部授权自管；Foundation 只登记入口与菜单链接 | 外购系统、遗留系统 |

约束：`HYBRID` 时 Foundation 不下发资源级授权；`SELF` 时子系统自管角色不进 `fdn_role`，只登记入口。

### 功能开关

管理员可按**子系统、模块、功能**停用（`fdn_feature_toggle`，如某客户不买「工作流」模块）。停用效果（三处一致，均在 BASIS 侧统一生效，子系统不自判）：

1. 从**所有人的授权快照**中剔除该范围内的菜单与权限码；
2. 门户/子应用**菜单不显示**；
3. 接口由 **starter 直接返回 403**（`FeatureToggleAspect` 优先于业务权限判断，命中停用范围即拒）。

开关作用域从父向子继承（停子系统 → 其下所有模块/功能停用）；最具体的作用域优先（功能级开关覆盖模块级）。

### 组织分级管理员

`fdn_org_admin_scope`：把某个组织单元子树的人员维护与授权交给该单位管理员。约束：

- 组织分级管理员**只能看到并授予自己被授权范围内的角色**（`grantable_role_codes` 白名单 + 组织范围）；
- **不能把高于自己的权限授给别人**（越权授予 → 403 + 审计 `DENIED`）；
- 范围可含下级（`include_descendants`）；树深沿用组织单元上限 10 层。

### 自管子系统→集中的一次性导入

自管子系统可改为集中授权。Foundation 提供**一次性导入**：`POST /api/subsystems/{code}/self-imports` 先**预览**（导入子系统现有角色与用户角色，算出差异：新建角色数、授权数、冲突数），管理员确认后 `POST /{batchId}/apply` **再生效**；生效后把该子系统 `auth_mode` 改为 `CONCENTRATED`。导入结果幂等（按 `来源 + 外部角色码 + 外部用户 ID`）。
