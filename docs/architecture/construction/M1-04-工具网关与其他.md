## CON-01 工具网关统一鉴权、限流、审计（P0，6 人天）

### 接口变化

```java
// runtime-api spi/ToolGateway.java（改）
public interface ToolGateway {
    List<ToolDescriptor> listTools(ToolCallContext ctx);
    ToolResult call(ToolCallContext ctx, String toolName, Map<String, Object> args);
    List<Map<String, Object>> asOpenAiTools(ToolCallContext ctx);

    /** 取代 SessionToolContext：带完整 Principal 与来源。 */
    record ToolCallContext(Principal principal, String threadId, String turnId, String agentVersionId,
                           String origin, List<String> toolAllowList, Map<String, Object> agentToolConfig) {}
}
```

`agentToolConfig` 由调用方（Runtime）从 Agent 版本快照取出，包含 MCP 授权（见 ENG-06），工具提供方不再反查 Agent。

### `DefaultToolGateway.call` 顺序

```text
1. 解析工具：name → (provider, descriptor)；不存在 → ToolResult(false, "工具不存在")
2. 白名单：toolAllowList 非空且不含 name → DENIED
3. 授权：
   - 内置工具（echo、kb_search…）：principal 需有该工具声明的 requiredPermission（如 kb_search → kb:read）
   - MCP 工具：agentToolConfig.mcpGrants 中有 server 且 allowlist 匹配；且 guard.allows("mcp", serverId, USE)
   - 知识库工具：参数中的 kbId 逐个 guard.allows("kb", kbId, USE)，无权的 kbId 从参数中剔除，全部无权则 DENIED
4. 权限重载：距本 Turn 上次加载 Principal 超过 60s 则重新加载（ADR-029 第 6 条）
5. 限流：quota tool_rpm（tool:{name}、workspace:{ws} 两个桶）→ 超出 RATE_LIMITED
6. 参数校验：按 inputSchema（networknt json-schema-validator，已在依赖中）→ 失败返回 ok=false，不调用
7. 出网：provider 声明的外部地址先过 EgressGuard
8. 调用：provider.invoke，带超时（来自 Runtime 的 tool-timeout）
9. 审计（调用返回后单独写，ADR-029 第 8 条）：action=tool.invoke，resource=tool:{name}，
   details={argsDigest(SHA-256), argsPreview(前 500 字、敏感键打码), ok, durationMs, outputChars}
   DENIED 情况同样写一条，outcome=DENIED，reason=第几步拒绝
```

实现要求（M1-00 第 6 节 F1、F2，避免 M2/M3 返工）：

- 第 1〜7 步实现为 `ToolCallPipeline.authorize(ctx, name, args) → AuthorizedCall`，`call()` = `authorize` + 第 8 步调用 + 第 9 步审计。M2 的 TRU-05 增加 `prepare`/`commit` 时复用 `authorize`（ADR-033「1〜6 与 M1-04 相同」）。
- 第 2 步之后预留第 2.5 步「授予」（ADR-029 第 46 条）：M1 注入一个恒放行的 `GrantCheck` Bean，M3 的 MAS-01 替换实现。
- `ToolDescriptor` 改为 builder 构造，M1 只加 `risk`、`requiredPermission`；M2/M3 的 `reversibility`、`actionClass`、`policyFields` 以带默认值的方式追加，不再新增位置参数构造器。
- `ToolCallContext` 只经 `ToolCallContexts.forTurn(...)` 构造；M3 增加 `grantId`、`chain`、`onBehalfOf` 时只改工厂。

拒绝返回给模型的结果统一为 `ToolResult(false, "无权调用工具 {name}：{原因}")`，不抛异常、不终止 Turn。

`ToolDescriptor` 增加 `requiredPermission`（可空）与 `risk`（[M1-02](M1-02-Runtime异步与审批.md) RT-07）。

## KNW-02 知识库按空间授权、检索时 ACL 过滤（P0，5 人天）

### 规则

- `kb_base` 属于空间（FND-03 自动过滤），并有 `visibility` 与 ACL（FND-04）。
- 检索必须把可见范围下推到 SQL（ADR-018：不得召回后再过滤），否则 topK 会被无权文档挤占。
- 文档级 ACL（ADR-029 第 23 条，连接器带来的 `aclPrincipals`）在 M1 先建列不启用：V118

```sql
ALTER TABLE kb_document ADD COLUMN acl_principals TEXT;        -- JSON 数组，如 ["user:1001","group:g_x"]；空 = 继承知识库
ALTER TABLE kb_chunk    ADD COLUMN workspace_id VARCHAR(64);
UPDATE kb_chunk c SET workspace_id = b.workspace_id FROM kb_base b WHERE c.kb_id = b.id;
ALTER TABLE kb_chunk ALTER COLUMN workspace_id SET NOT NULL;
CREATE INDEX idx_chunk_kb ON kb_chunk (kb_id);
```

### 检索实现

```java
public List<Hit> retrieve(RetrieveCmd cmd) {                        // cmd: kbIds(可空), query, topK
    Principal p = holder.current();
    VisibilityFilter vf = guard.filter("kb", AccessLevel.USE);
    List<String> kbIds = cmd.kbIds() == null ? null : cmd.kbIds().stream().filter(id -> guard.allows("kb", id, USE)).toList();
    if (kbIds != null && kbIds.isEmpty()) return List.of();
    float[] q = gateway.embed(ctx(EMBEDDING), new EmbeddingRequest(null, List.of(cmd.query()))).vectors().get(0);
    return chunks.searchVisible(q, kbIds, vf, cmd.topK());
}
```

```sql
-- ChunkMapper.searchVisible（workspace_id 条件由拦截器自动加）
SELECT c.id, c.doc_id, c.kb_id, c.text, c.embedding_vec <=> #{q}::vector AS distance
  FROM kb_chunk c JOIN kb_base b ON b.id = c.kb_id AND b.deleted = FALSE
 WHERE c.deleted = FALSE
   <if kbIds> AND c.kb_id IN (…) </if>
   AND ( ${vf.sql 以 b 为别名} )
 ORDER BY c.embedding_vec <=> #{q}::vector
 LIMIT #{topK};
```

`kb_chunk.embedding`（TEXT 列）删除，只保留 `embedding_vec vector(N)`；N 由 `tioka.knowledge.embedding-dim` 决定，V119 用 Flyway 占位符 `${embeddingDim}` 重建列（`flyway.placeholders.embeddingDim`），已有数据需重嵌入：V119 将所有文档置 `status='REINDEX_PENDING'`，`ReindexJob` 后台逐个重嵌入（KNW-01 的网关）。

### 测试

`KnowledgeAclIT#restrictedDocInvisible`（34 号验收：无权用户检索不到受限文档）、`#topKNotStarvedByInvisible`（无权文档相似度更高时，有权文档仍能返回 topK 条）、`#crossWorkspaceInvisible`。

## FLW-01 Branch 后汇合节点不执行（P1，3 人天）

### 原因

`FlowEngine.runDag` 中未被选中的分支边直接 `continue`，目标节点入度永远不会减到 0；汇合节点（多个前驱，其中一个在未选分支上）因此永不执行。

### 修复（M1 只修引擎，不重写；M3 按 ADR-019 换成事件驱动调度器）

每条边有三种状态：`PENDING`、`LIVE`、`DEAD`。节点在所有入边都不是 `PENDING` 时就绪：

```text
on node finished(n, output):
   for e in out(n):
       e.state = (n 是 Branch 且边条件不匹配) ? DEAD : LIVE
       settle(e.to)
on node skipped(n):
   for e in out(n): e.state = DEAD; settle(e.to)
settle(m):
   if 任一入边 PENDING: return
   if 所有入边 DEAD: 标记 m 为 SKIPPED（trace 记 status=SKIPPED），skipped(m)
   else: m 进入 ready，输入只取 LIVE 入边的前驱输出
```

`resolveInput` 改为只合并 LIVE 前驱的输出（多前驱时保持现有合并规则：`Map{前驱ID: 输出}`）。Output 节点被 SKIPPED 时，Flow 输出为 `null` 且 run 状态仍为 `SUCCEEDED`，trace 中可见。

### 测试（`FlowEngineJoinTest`，纯单元）

| 图 | 断言 |
| --- | --- |
| Start → Branch → (A \| B) → Join → Output，条件为真 | A、Join、Output 执行；B 为 SKIPPED |
| 两层嵌套 Branch 汇合 | 全部汇合点正确执行一次 |
| 所有分支都不匹配 | 下游全部 SKIPPED，run 成功 |
| 并行 A、B 汇合（无 Branch） | 行为与修复前一致（回归） |

## ENG-06 拆模块循环，server 只依赖 -api（P1，4 人天）

### 现状

| 依赖 | 问题 |
| --- | --- |
| `agent-biz → mcp-api`，`mcp-biz → agent-api` | biz 层双向依赖：`McpToolProvider` 用 `AgentQueryApi` 反查 Agent 的 MCP 授权 |
| `tioka-server → 所有 *-biz` | 装配需要，但 `OpsFacadeController` 等直接调用 biz 类 |

### 改法

1. MCP 授权随 Agent 版本快照：由 [M1-05](M1-05-Agent资产与G1闸门基座.md) AST-01 的 `AgentSpec.tools.mcp`（`[{serverId, allowlist[]}]`）承载，不再单独加 `mcp_grants_json` 列（2026-11-06 从 V118 移除，避免两份快照）。Runtime 把它放进 `ToolCallContext.agentToolConfig`。`McpToolProvider` 删除对 `AgentQueryApi` 的依赖，`mcp-biz` 的 pom 去掉 `agent-api`。`mcp_grant` 表由 AST-01 的 V125 删除，编辑态在 `agent_draft`。本项排在 AST-01 之后。
2. `tioka-server` 的 pom 中 biz 依赖改为 `<scope>runtime</scope>`（只为装配进 fat jar），编译期只依赖 `-api`；`OpsFacadeController` 改为注入 `-api` 接口，缺的接口在对应 `-api` 中补。
3. 新增 Maven Enforcer 规则 `banCircularDependencies`（`extra-enforcer-rules:1.8.0`），以及 ArchUnit `serverDependsOnlyOnApi` 冻结库存清零。

测试：`mvn -pl tioka-server dependency:analyze` 无 biz 编译期依赖；Enforcer 通过；ArchUnit 绿。
