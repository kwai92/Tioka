## 摘要

建议分五个阶段推进：先用约 4 周做 **M0 地基加固**（测试变绿、鉴权、Runtime 内核、去单机假设），再按 M1 到 M4 逐步加厚。按 2 到 3 名后端 + 1 名前端估算，到 M4「可私有化交付」约需 12 个月（2026-11-05 选定合同场景排期方案 A，M3 延长约 10 周，见 ADR-029 第 59 条）。

规划依据两份前置文档：[差距分析](https://claude.ai/artifact/SAJrvKthNMeZJjsPeqJ1sm)（main 分支 fb27c4e 的现状）和[预期目标](https://claude.ai/artifact/2BjtRBWUmacrsMfd5jtMjA)（十层预期与 M1–M4 验收场景）。本文把预期拆成带编号的工作项；各模块详细设计见 ADR-015〜030。

规划遵循四条原则：

- **地基先于功能**。鉴权、异步 Runtime、多实例会改动几乎所有实体和接口签名，越晚做越贵，所以排在任何功能加厚之前。
- **一个内核、一套治理**。所有入口（Chat、Flow、Orchestration、IM）都经同一个 Runtime 和 Model Hub，配额和审计只在这两个入口各接一次。
- **完成度以自动化验收为准**。每个里程碑用一条「关闭 mock、双实例、开启鉴权」的端到端用例判定，进 CI，不再用文档勾选。
- **假实现先下线**。6 个对外暴露的假 API 在 M0 返回 501 或删除，做真时再上线。

工期按 2–3 名后端 + 1 名前端估算，已于 2026-11-05 确认。

## 分阶段推进计划

五个阶段按顺序推进，只有 M3 可以在 M2 后半段并行启动。每个阶段末尾有一道闸门：验收用例在 CI 里通过才进入下一阶段。周次以启动周为 W1。

> 路线图图示见阅读版文档。

M3 在 M2 后半段并行启动，因为它只依赖 M1 的 Runtime 协议和 Model Hub 收口，只有数据源增量同步要等 M2 的 MQ。

1. **M0 地基加固（W1–W4）**。修红测试并做数据隔离；CI 加前端构建；认证拦截 + 请求级 Principal + 实体 owner/workspace 归属；Runtime 按会话加锁、Turn/Part 入表、多步工具循环；引入 Redis 并把 SSE 与 cancel 跨实例化；下线假实现 API。
   - 闸门 G0：`mvn test` 与前端构建全绿；未登录请求全部 401；双实例下一个需要 3 次工具的任务自动完成，另一实例可以 cancel。
2. **M1 安全可用的单内核（W5–W12）**。OIDC 登录（Keycloak）、角色权限点与资源级权限；Runtime 异步 Turn、可恢复、审批挂起；Model Hub 轮次冻结、自动故障接力、限流重试；配额与审计接入 Runtime 和 ModelRouter 入口；全仓模型调用收口到 Model Hub。
   - 闸门 G1：Keycloak 登录 → 选已发布 Agent → 真实模型多步调用 MCP 工具 → 双实例流式与取消正常 → 用量计入空间配额 → 审计可查。对外口径：可做企业 PoC。
3. **M2 人机协作闭环（W13–W22）**。RocketMQ + outbox；Orchestration 派工器、规则引擎、Attention 挂起续跑、定时；飞书入站事件与卡片回调；Part 协议对齐 AG-UI；审批台、轨迹视图；写工具的预演与变更单卡片（TRU-05、TRU-06）。
   - 闸门 G2：飞书事件触发 Agent → 飞书卡片审批 → 续跑 → 结果回写，中途重启服务不丢任务，多 worker 不重复领取。
4. **M3 构建者工具链与合同场景（W19–W40）**。Knowledge 真 embedding 默认化、结构切块、Rerank、3 类数据源增量同步、评测进 CI；Flow 节点走 Runtime、汇合调度修复、自定义节点、发布为 API/工具/MCP；Chat 编辑重试、真分叉、记忆注入。
   - **多智能体与运行时权限（M3 部分）**：子 Agent（RT-12，从 M4 提前）与委派授予、链上禁区、`on_behalf_of` 同期上线；数据集行列策略、数据标签与按标签选模（MAS-01〜03、DAT-01〜04）。
   - **业务本体与合同场景（M3 部分）**：文档层与 OCR、Schema 登记表与 `data` item、合同模型投影与读模型工具、`rule.evaluate`、@model.build、通知渠道（飞书 + 邮件）、最小业务连接器；租赁领域包、新建业务系统、审查 Agent 与影子期（DOC、SCH、ONT、LSE、BIZ，排期方案见第 59 条）。
   - **可信放权（M3 部分）**：工具调用策略引擎（GOV-07，从 M4 提前）、岗位授权书与负责人生命周期、撤销与爆炸半径、自治等级 L1〜L4 与自动降级（TRU-01〜03、TRU-07〜10）。
   - 闸门 G3：上传文档后引用问答召回率达基线；Studio 建流 → 发布为工具 → Agent 调用 → 用量计入该 Agent 配额；超授权书额度的写操作转审批，撤销一次 5 步写操作后业务桩状态完全复原，撤销触发降级；子 Agent 调用父有、自己没有的工具被拒并记录委派链；两位不同区域用户查同一数据集得到不同的行与掩码。
5. **M4 企业完备（W41–W52）**。SCIM 与组织同步、资产发布审批、OTel、容器沙箱代码解释器、上下文压缩、多智能体团队（任务图、黑板、仲裁，MAS-04〜07）、Helm 与空气隔离安装包；可信放权的影子上岗、转正申请与价值账本（TRU-04、TRU-11〜15）。钉钉/企微（CON-06）延后到 M4 之后。
   - 闸门 G4：离线环境一键安装；普通成员越权操作被拒并留审计；代码解释器在沙箱内运行；影子 Run 不产生任何写入并生成上岗报告；经营看板上任一数字可从账本明细复算。

**关键依赖**：M2 的挂起续跑依赖 M1 的异步 Turn 和审批挂起；M3 的 Flow Agent 节点依赖 M1 的 Runtime 协议，数据源增量同步依赖 M2 的 MQ；M3 的策略引擎（GOV-07）依赖 M1 的权限模型和审计管道；M3 的撤销依赖 M2 的 outbox；M4 的影子上岗依赖 M2 的编排派工和 M3 的批次评测。

**与仓库现有 R0–R6 计划的关系**：`33-差距收口与后续推进计划.md` 中的 R2–R5（各域功能保真）整体后移到 M3；建议把本文定为新的权威计划，旧文档标注为已取代。

## 十层目标拆解

十层预期加一组工程基线，共拆成 94 个工作项，其中 P0 共 40 项，集中在 M0 和 M1。2026-11-05 追加可信放权 15 项（TRU-01〜15，其中 P0 5 项），合计 109 项、P0 45 项。编号可直接用作 Issue 标题前缀。优先级含义：P0 不做则该里程碑闸门不过；P1 该里程碑应做；P2 可顺延。

## 风险与待确认事项

**主要风险**

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| M0 改动面大（几乎所有表和 Controller），与功能开发并行会反复冲突 | M0 拖期 | M0 期间冻结新功能，只合并地基工作项 |
