# ADR-078 — 多源同步来源扩展（同步来源 SPI 与适配器）

- 状态：Accepted（设计定案，待实现；放入 F 阶段之后的 **F2 增强批次**，见 ADR-029 第 81 条）
- 日期：2026-11-13
- 覆盖工作项：BAS-32、BAS-33，扩展 BAS-11、BAS-12、BAS-FE-07
- 详细设计：[S15](../systems/S15-Foundation基础平台系统.md) 第 10 节
- 相关：[ADR-026](ADR-026-foundation.md)、[ADR-052](ADR-052-org-account-authz-center.md)、[ADR-051](ADR-051-foundation-platform.md)、[ADR-053](ADR-053-foundation-common-services.md)、[ADR-074](ADR-074-external-interaction-ledger.md)、[ADR-076](ADR-076-app-to-app-authorization.md)
- 约束：与 ADR-029 定案冲突时以定案为准；修改本 ADR 走 [ADR-030](ADR-030-anti-drift-process.md) 的变更流程。

## 背景

S15 第 10.1 节到 ADR-052 为止，同步来源只内置「飞书通讯录、LDAP/AD」，SCIM 为 P2，钉钉、企微、客户 HR 接口写的是「按同步来源 SPI 补实现，可由交付或客户二开」。负责人 2026-11-13 明确要求 Foundation 能从**企业微信、飞书、钉钉、北森云、泛微 OA、金蝶**同步员工、组织、岗位、任职等信息。

问题在于：这六类来源的对象范围、增量方式、认证方式差别很大，若每个来源各写一套同步逻辑，会出现「组织树口径不一致、删除保护各自实现、字段映射无法复用、新增来源要动主干」的漂移。ADR-052 第 4 条「一个部署只有一个权威来源」的约束也不能被六源全纳破坏。

## 决定

1. **统一「同步来源 SPI」**。把 ADR-026 `OrgDirectoryAdapter` 正式收敛为一组 SPI（`foundation-starter-sync` 定义，来源实现以插件包提供），能力面固定为：
   - **认证**：API 凭证 / 应用授权 / OAuth 客户端凭证，凭证复用 ADR-042 的密钥来源；
   - **拉取**：全量快照、增量（时间戳 / 变更号 / 事件回调，按来源能力声明）、单对象回查；
   - **分页与限流**：分页游标、速率上限、退避重试；
   - **字段映射与转换**：外部字段 → 人员 / 组织单元 / 岗位 / 任职 / 职级字段，支持默认值与转换；
   - **外部身份提供**：按工号 / 已验证邮箱给出候选关联（沿用 ADR-052 第 3 条，不按姓名匹配）；
   - **删除保护**：差异预演与阈值暂停（沿用 ADR-052 第 5 条）；
   - **幂等键**：`来源 + 外部 ID`。

2. **能力矩阵**。每个来源在适配器里声明「支持哪些对象 + 支持哪种增量方式 + 是否提供外部身份」，同步引擎据此编排，能力缺失时降级（如某来源无「任职」对象，就不生成任职差异）并在同步报告里标注「能力缺失」，不静默跳过。

   | 来源 | 类型 | 对象 | 增量方式 | 常见角色 |
   | --- | --- | --- | --- | --- |
   | 企业微信 | IM | 组织、人员、外部身份 | 事件回调 + 定时全量 | 权威来源或外部身份 |
   | 飞书 | IM | 组织、人员、外部身份 | 事件回调 + 定时全量 | 权威来源或外部身份 |
   | 钉钉 | IM | 组织、人员、外部身份 | 事件回调 + 定时全量 | 权威来源或外部身份 |
   | 北森云 | HR | 组织、人员、岗位、任职、职级 | 变更号 / 时间戳增量 | 权威来源首选 |
   | 泛微 OA | OA | 组织、人员 | 时间戳增量 | 权威来源备选或外部身份 |
   | 金蝶 | ERP | 组织、人员、岗位、任职 | 时间戳 / 分页增量 | 权威来源备选 |

   本地维护与 LDAP/AD、SCIM 仍在矩阵内，能力声明一致，只是内置实现方式不同。

3. **单一权威来源不变**（ADR-052 第 4 条）。一个部署只有一个来源负责组织树与人员主信息；其余来源只补外部身份。六源全纳**不等于六源并列写主信息**——权威来源之外的前五个来源只做「外部身份关联」，不覆盖人员主数据。

4. **适配器分三类，交付与落地分两批**：
   - **第一批（P1）**：IM 三源（企业微信、飞书、钉钉）+ 北森云（HR）。覆盖最常见的「IM 通讯录」与「HR 系统」两种权威来源，对应 BAS-32。
   - **第二批（P2）**：泛微 OA、金蝶。多为补充外部身份或权威来源备选，对应 BAS-33。

5. **字段映射与本地锁定统一**：所有来源共用同一套映射配置模型（外部字段 → 内部字段、默认值、转换函数），「本地锁定」字段（如手工修正的显示名）不被任何来源覆盖（沿用 S15 第 10.2 节）。

6. **增量与幂等统一**：幂等键 `来源 + 外部 ID`；具备增量能力的来源走增量，无增量能力的来源走分页全量 + 差异预演（同样是「先算差异再落地」）。

7. **删除保护与差异预演沿用 ADR-052 第 5 条**：一次停用超 5% 或 50 人、删除组织单元超过 10 个时暂停待确认；外部为准，规则产生的授权不覆盖手工授权。

8. **插件化交付**：六个适配器以插件包加载，遵循 FND-12 插件宿主约定（签名、版本、隔离类加载器）；客户自有来源按 SPI 二开，不改 Foundation 主干。架构守护：来源实现只依赖 `foundation-starter-sync` 的 SPI 接口与 `-api` 契约，不依赖中台 `-biz`。

9. **出网与台账**：来源访问走统一出网白名单（FND-07）；每次同步按 ADR-074 写 `ext_interaction` 台账（对方、身份模式与凭证 ID、关联键、结果与重试），带数据标签。

10. **同步变更事件不变**：同步结果仍发 `fdn.org.changed`、`fdn.person.*`（S15 第 14.2 节），新增来源不改事件模型，只增加「来源」字段的取值。

## 备选

| 备选 | 不选原因 |
| --- | --- |
| 每个来源各写一套同步逻辑（不抽 SPI） | 组织树口径、删除保护、字段映射各自实现，新增来源要动主干，与 ADR-030 防偏差冲突 |
| 只做 IM 三源（企微 / 飞书 / 钉钉），HR / OA / ERP 由客户二开 | 北森、泛微、金蝶是客户侧最常见的权威来源，不做会逼客户自写主数据同步，标准交付不完整 |
| 引入第三方 iPaaS / 集成平台统一接入 | 多一个重组件与运维面，凭证与数据标签要跨系统，与「Foundation 自己做同步引擎」重复 |
| 多个来源并列写人员主信息 | 来源互相覆盖、问题难以追查，ADR-052 已否决 |
| 把六个来源全做成必装引擎 | 客户实际只接 1〜2 个来源，必装会推高交付门槛；按插件加载、按客户装配更贴合 |

## 后果

- Foundation 新增 `foundation-starter-sync`（SPI、能力矩阵、字段映射、编排）与六个来源适配器插件；同步报告新增「能力缺失」标注。
- S15 第 10.1 节来源表由「三源」扩展为六源 + 本地 + LDAP/AD + SCIM；第 10.2 节补充能力矩阵与插件加载说明。
- 新增工作项 BAS-32（IM 与 HR 适配器：企业微信、钉钉、北森，含飞书对齐）、BAS-33（OA 与 ERP 适配器：泛微、金蝶）；来源管理前端扩展并入 BAS-FE-07。
- 闸门 `GfSyncVendorGateIT`：至少两个来源（一个 IM、一个 HR）完成全量 + 增量 + 差异暂停 + 外部身份关联的端到端用例。
- 排期：F2 增强批次，后端 BAS-32（5）、BAS-33（5）；闸门 `GfSyncVendorGateIT`。
