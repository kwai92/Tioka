## 背景

2026-11-06 负责人提出：模型供应商、模型、模型别名路由、供应商配额、模型配额、Prompt 都属于管理面，整体要有版本化管理，也要有监控和统计能力。对照现有设计，有四处缺口：

1. **版本化不完整**。只有 Agent（ADR-023）和路由计划（ADR-024）有草稿与不可变版本。供应商、模型 binding、别名、配额都是直接改表、立即生效，没有历史、没有 diff，也不能回滚。
2. **配额只有需求侧**。现在只按空间、Agent、用户限额（ADR-017、GOV-03）。供应商账号的总额度、单个模型的预算都没有设计。binding 上的 RPM/TPM 只是限流，不是预算。
3. **Prompt 散落在五处**：AgentSpec 的 instructions、Flow LLM 节点配置、决策器的固定提示词、领域包的 PromptBundle（ADR-036）、Chat 提示词库（CHT-06）。没有统一的版本，也查不到引用关系。
4. **监控和统计太薄**。监控只在 GOV-08 里列了一句指标清单，私有化环境没有 Prometheus 时什么也看不到。统计只有 GOV-05 的成本汇总，加上 M3 的一个 P2 看板（MH-07），不能按版本对比。

## 决定

1. **管理面对象分成两类，共用一套版本框架**。
   - 发布型：先改草稿，校验通过后发布成不可变版本，可以回滚。
   - 即时型：改了立即生效，但每次改动都写一条变更记录（改前、改后、谁、为什么），可以按记录回滚。
   - 两类共用同一套历史、对比、引用查询和界面组件（GOV-12、FE-07）。
2. **执行侧只读当前生效版本，每次调用都记下版本号**。统计按版本号切片，所以"改了什么"和"改完效果如何"能对上。
3. **配置归各自的领域，不单独建一个管理模块**。Model Hub 管供应商、模型、别名、路由计划、Prompt；Governance 管配额框架和告警。前端统一放进"模型中枢"管理区。理由是配额、限流、审计都只在 `ModelGateway` 一个卡点执行（ADR-017），配置和执行放在同一领域才不会走样。

## 1. 对象清单与归属

| 对象 | 归属模块 | 类型 | 进版本的内容 | 不进版本的运行开关（走变更记录） |
| --- | --- | --- | --- | --- |
| 供应商（ProviderConnection） | model | 发布型 | 协议、Base URL、密钥引用（只存引用，不存值）、请求头模板、超时、出网策略 | 启停、手动熔断、密钥轮换（只记时间和操作人，不记值） |
| 模型（ModelBinding） | model | 发布型 | 所属供应商、模型名、kind、能力、上下文长度、嵌入维度、单价、RPM/TPM | 启停、手动熔断 |
| 模型别名（ModelAlias，由 ADR-024 的 LogicalModel 改名扩展） | model | 发布型 | 稳定名称（如 `chat.default`、`qwen-max`）、用途、指向（一个路由计划或一个 binding） | — |
| 路由计划（RoutingPlan） | model | 发布型 | ADR-024 的 RoutingPlanSpec | — |
| Prompt 模板（PromptTemplate） | model（`prompt` 包） | 发布型 | 分段正文、变量定义、用途、输出格式、建议使用的别名、样例变量 | — |
| 配额与预算（QuotaPolicy） | system（Governance） | 即时型 | — | 作用对象 × 指标 × 上限 × 预警比例 |
| 告警规则（AlertRule） | system | 即时型 | — | 条件、窗口、通知渠道、静默时段 |

已有自己版本表的对象不迁移，只通过适配器接入统一的历史、对比和引用界面：Agent（`agent_version`，ADR-023）、Cedar 策略（`gov_policy`，ADR-025）、Skill（ADR-023）。

### 引用方式：模型侧跟随，Prompt 钉版本

| 被引用对象 | 引用方 | 默认方式 | 原因 |
| --- | --- | --- | --- |
| 别名、路由计划 | Agent、Flow 节点、知识库嵌入、决策器 | **跟随**：总用当前发布版本 | 换供应商、切备用模型是运维动作，必须一次对全平台生效（ADR-024「集中路由」） |
| Prompt 模板 | Agent、Flow 节点 | **钉版本**：发布 Agent 或 Flow 时解析为 `模板@版本号` 写进快照 | Prompt 决定行为。改 Prompt 要经过 Agent 发布和评测，不能绕过 |
| 系统内置 Prompt（`sys.*`） | 决策器、胜任度打分、上下文压缩、`@model.build` | 跟随 | 平台行为，由系统管理员统一调整 |

调用链变为：调用方引用别名 → 别名指向路由计划（或单个 binding）→ 路由计划给出候选 binding。M1 的 `model_default_plan`（按用途的默认方案）在 MH-08 中迁移为系统别名 `sys.chat`、`sys.flow`、`sys.embedding`、`sys.rerank`、`sys.decision`。ADR-024 原来"Agent 引用计划 ID"的写法保留，但推荐引用别名。

## 2. 版本框架（GOV-12）

### 存储

| 表 | 用途 | 主要字段 |
| --- | --- | --- |
| `cfg_draft` | 每个发布型对象一份可编辑草稿 | 对象类型、对象 ID、spec（JSON）、`revision`（乐观锁）、基于哪个版本、最后修改人与时间 |
| `cfg_version` | 不可变版本 | 版本 ID、对象类型、对象 ID、版本号（按对象递增）、spec、规范化哈希、状态（`PUBLISHED` / `PENDING_APPROVAL` / `RETIRED`）、发布说明、发布人与时间、上一个生效版本 |
| `cfg_change` | 即时型改动、运行开关、发布与回滚动作的统一流水 | 对象类型、目标键、改前（JSON）、改后（JSON）、操作人、原因、时间、traceId |

现有的类型表（`model_provider`、`model_binding`、`model_alias`、`model_routing_plan`、`prm_template`）保留，作为"当前生效版本的投影"供执行侧读取，各加两列：当前版本 ID、当前版本号。ADR-024 设计的 `model_routing_plan_version` 不再单独建表，并入 `cfg_version`。

### 生命周期

| 动作 | 规则 |
| --- | --- |
| 保存草稿 | 不影响执行；乐观锁冲突返回 409；不写审计 |
| 校验 | 每类对象一组检查项，沿用 AST-02 的 `PublishCheck` 做法。例：binding 所属供应商已发布；别名指向的对象存在且用途匹配；路由计划的候选都已启用；Prompt 正文里的占位符与变量定义一致，并能用样例变量渲染成功 |
| 发布前影响分析 | 展示与当前版本的 diff、全部引用方（递归展开：别名 → 计划 → 引用它们的 Agent、Flow、知识库）、该对象最近 7 天的调用量和成本 |
| 发布 | 同一事务内：写版本行、更新投影、移动当前指针、写审计 `config.publish`。提交后广播 `tioka.config.published.v1`（对象类型、对象 ID、新版本、旧版本）。空间开启发布审批（GOV-06，M4）时先进入 `PENDING_APPROVAL` |
| 回滚 | 把当前指针移回旧版本并重新投影，写审计 `config.rollback`，广播同一事件。不产生新版本号，与 ADR-023 一致 |
| 归档 | 仍被引用时拒绝，并列出引用方；版本历史保留 |
| 导出、导入 | 导出所选对象的已发布版本（不含密钥值），导入后生成草稿，再逐个发布。在 GOV-11 多环境推迟期间，用它在测试和生产部署之间搬配置 |

### 特殊规则

- **嵌入模型**：别名 `sys.embedding` 或知识库所用 binding 改指向时，维度不同直接拒绝（ADR-029 第 23 条）；维度相同但换了模型，发布对话框必须二次确认，发布后自动创建重嵌入任务。
- **进行中的 Turn 不受影响**：Turn 开始时把 binding 和路由计划版本写入冻结（MH-01），同一 Turn 内后续步骤沿用。供应商连接配置（地址、超时）总读当前版本。
- **只读执行路径**：执行侧只能经 `ModelCatalog` 这类带缓存的只读接口读取投影，不得直接读 `cfg_*` 表；`cfg_version` 不可更新。两条都写成 ArchUnit 规则。

### 跨实例刷新

每个实例在本地缓存投影和版本号。收到广播（Redis 发布订阅）立即刷新；为防消息丢失，每 30 秒比对一次各对象的当前版本号。不经过 outbox，因为投影已经在库里，广播只是通知。

## 3. 配额与预算（扩展 ADR-017、GOV-03）

配额分为需求侧和供给侧两类，命中后的后果不同：

| 侧 | 作用对象 | 指标 | 命中后果 |
| --- | --- | --- | --- |
| 需求侧（已有） | 空间、Agent、用户 | 月度 token、并发 Turn，新增**月度成本** | 拒绝请求，返回 `QUOTA_EXCEEDED` |
| 供给侧（新增） | 供应商 | 月度 token、月度成本、账号级 RPM/TPM | 该供应商下的候选全部视为不可用，路由跳到下一个候选 |
| 供给侧（新增） | 模型 binding | 月度 token、月度成本 | 该候选不可用，跳到下一个 |
| 供给侧（新增） | 别名 | 月度成本 | 别名下全部候选不可用 |

- 供给侧不直接拒绝，而是让路由器跳过这个候选，并写一条路由事件"因预算跳过"。全部候选都耗尽时才失败，错误码为 `MODEL_BUDGET_EXHAUSTED`，与需求侧的错误码分开。
- 供应商账号级 RPM/TPM 与 binding 级 RPM/TPM 叠加生效。厂商通常按 API Key 汇总限流，多个 binding 共用一个 Key 时只看 binding 级会超。
- 检查位置：需求侧仍在 `ModelGateway` 第 2 步，每次调用检查一次；供给侧放进选模时的候选过滤链（M1 预留的 `BindingFilter`，M1-00 约束 F8）。记账时同时累加需求侧和供给侧所有作用对象。
- 计数方式沿用 GOV-03 的 Redis 结构，增加成本计数键；单次调用可以超额，下一次被拒或被跳过（ADR-029 第 7 条）。
- 计费周期按自然月，边界用配置的业务时区计算，默认 `Asia/Shanghai`；存储仍用 UTC。
- 每个配额有预警比例，默认 80%。用量越过预警线和 100% 时各发一次 `tioka.quota.threshold.v1`，同一周期不重复发，由告警规则（GOV-13）转成通知。
- 配额的每次修改写入 `cfg_change`，在"变更记录"里能看到历史，也能恢复到某条记录之前的值。

## 4. Prompt 模板（AST-07〜AST-09）

### 模板内容

| 字段 | 说明 |
| --- | --- |
| 名称与作用域 | 系统级（`sys.*`、领域包注册的 `pack.{包}.{名}`）、空间级、个人级。个人级就是 CHT-06 提示词库，不走发布审批 |
| 用途 | agent、flow、decision、summarize、extract、chat_snippet |
| 分段正文 | 按角色分段（system、user），占位符用 `{{变量名}}` |
| 变量定义 | 变量名、类型、是否必填、默认值、说明；发布时校验正文里的占位符都已定义 |
| 输出格式 | 文本或 JSON；JSON 时引用 ADR-037 的结构化输出 Schema |
| 建议别名 | 编辑器"试运行"默认使用的模型别名 |
| 样例变量 | 用于发布校验时渲染测试，也用于编辑器预览 |

渲染使用无逻辑模板（只做变量替换、条件段和列表展开，不允许执行表达式）。缺少必填变量时，发布阶段报校验错误；运行阶段该步骤失败，错误码为 `PROMPT_RENDER_ERROR`。

### 接入方（AST-08）

| 接入方 | 方式 |
| --- | --- |
| AgentSpec | `instructions` 的每一段可以是内联文本，也可以是"模板引用 + 变量取值"。AST-02 的发布校验增加一项：模板版本已发布、变量取值满足定义。发布时钉住版本号 |
| Flow LLM 节点 | 同上，Flow 发布时钉住版本号 |
| 决策器、胜任度打分、上下文压缩 | 改为读取 `sys.decider`、`sys.competence`、`sys.summarize` 等内置模板。平台随版本发布第 1 版；系统管理员可以发布覆盖版本，也可以回滚到内置版本 |
| 领域包 PromptBundle（ADR-036） | 安装领域包时把每条提示词登记为 `pack.*` 模板；升级领域包时发布新版本 |
| Chat 提示词库（CHT-06） | 基于个人级、空间级模板实现，不另建表 |

编辑器提供"试运行"：用样例变量或手填变量渲染，再经 `ModelGateway` 调用所选别名（用途记为 `prompt_test`），用量计入操作人自己的配额。

### 发布评测（AST-09，M4）

模板可以绑定一个评测数据集（EVO-02）。发布新版本时自动用新旧两个版本各跑一遍，结果附在版本上；空间可以设置"有回归就阻止发布"。这一项与 EVO-06（Agent 发布回归门禁）用同一套机制。

## 5. 监控（MH-10）

监控分两层：内置状态页不依赖任何外部组件，客户已有监控体系的再对接 Prometheus。

### 5.1 内置运行状态

`ModelGateway` 每次调用结束时，把结果异步写进 Redis 滚动窗口：最近 60 分钟按 1 分钟分桶，最近 24 小时按 5 分钟分桶。每个供应商、binding、别名各记一份：调用数、按类别的错误数（429、5xx、超时、鉴权失败、其他）、延迟分布、首 token 延迟、token 数、成本。

状态接口按供应商、binding、别名返回：健康状态、调用速率、错误率、P50/P95 延迟、P95 首 token 延迟、各配额已用比例、熔断状态、最近一次错误样本（错误码、截断后的消息、时间、traceId）。

| 健康状态 | 判定 |
| --- | --- |
| DISABLED | 已停用 |
| BUDGET_EXHAUSTED | 供给侧配额已用完 |
| COOLDOWN | MH-03 冷却中 |
| DOWN | 主动探测连续 3 次失败，或 5 分钟内错误率超过 50%（至少 10 次调用） |
| DEGRADED | P95 延迟超过近 24 小时基线的 2 倍，或 429 占比超过 10% |
| UP | 以上都不满足 |

**主动探测**：每个供应商可单独配置，默认每 60 秒调用一次免费的模型列表接口。没有这类接口的协议，可以开启"1 token 补全"探测，默认关闭，因为会产生费用。探测请求同样经过出网守卫（FND-07）。探测结果写入 Redis，并同步到 `model_provider` 的健康列（ADR-024）。

### 5.2 Prometheus 指标（细化 ADR-025 GOV-08）

| 指标 | 类型 | 标签 |
| --- | --- | --- |
| `tioka_model_calls_total` | 计数 | provider、binding、alias、purpose、status |
| `tioka_model_errors_total` | 计数 | provider、binding、error_class |
| `tioka_model_latency_seconds` | 直方图 | provider、binding、purpose |
| `tioka_model_ttft_seconds` | 直方图 | provider、binding |
| `tioka_model_tokens_total` | 计数 | provider、binding、direction（in / out / cached） |
| `tioka_model_cost_micros_total` | 计数 | provider、binding |
| `tioka_model_failover_total` | 计数 | from_binding、reason |
| `tioka_model_route_decisions_total` | 计数 | plan、group、decider、outcome |
| `tioka_model_circuit_state` | 仪表 | binding |
| `tioka_quota_usage_ratio` | 仪表 | scope_type、scope_id、metric |
| `tioka_prompt_render_errors_total` | 计数 | template |
| `tioka_config_publish_total` | 计数 | kind、action（publish / rollback / archive） |

基数规则：任何指标都不带用户、会话、Turn 的标签。配额仪表上，供给侧总是输出；需求侧只输出空间级，且空间数超过 200（可配置）时关闭。M4 的 Helm 包附带一份 Grafana 看板。

### 5.3 告警（GOV-13）

| 项 | 规则 |
| --- | --- |
| 监控对象 | 供应商、binding、别名、配额作用对象，或"全部" |
| 条件 | 健康状态变为某值；错误率、P95 延迟、故障接力率在 N 分钟内超过阈值；配额越过预警比例或用完；有配置被发布或回滚（用于知会） |
| 通知 | 站内消息，以及 ADR-036 的通知渠道适配器（飞书、邮件，M3 BIZ 提供） |
| 去重与恢复 | 同一规则对同一对象只在状态变化时发；恢复时发恢复通知；可设静默时段 |
| 求值 | 每 30 秒由一个实例执行（Redis 锁）；告警事件入库，可查历史 |
| 内置默认规则 | 供应商 DOWN；任一供给侧配额达到 80% 或 100%；10 分钟内故障接力率超过 20% |

## 6. 统计（MH-11，取代 MH-07）

### 数据来源

- **明细**：`model_usage`（MH-05）新增列：供应商 ID、别名 ID、binding 版本 ID、路由计划版本 ID、Prompt 版本 ID（产生 system 消息的那个模板）、首 token 延迟、缓存命中 token 数、错误类别。
- **日汇总**：沿用 ADR-024 的 `model_usage_daily`，汇总维度扩展为：日期、空间、Agent、供应商、binding 及其版本、别名、路由计划版本、Prompt 版本、用途、状态。度量包括：调用数、输入/输出/缓存 token、成本、延迟总和、延迟分桶、首 token 延迟分桶、错误数。用分桶可以算出任意组合的 P50/P95。
- **汇总任务**：每小时重算今天和昨天两天的数据（幂等覆盖），迟到的明细也能算进去。
- **保留期**：明细默认保留 180 天（可配置），日汇总长期保留。

### 查询能力

| 能力 | 说明 |
| --- | --- |
| 分组汇总 | 按供应商、binding、别名、路由计划版本、Prompt 版本、空间、Agent、用户、用途任选分组；给出调用数、token、成本、错误率、P50/P95 延迟、平均首 token 延迟。按用户分组只查明细，时间范围不超过 31 天 |
| 趋势 | 按小时或按天的时间序列 |
| **版本对比** | 选一个对象和两个版本（默认当前版本与上一版本），在相同时间长度的窗口内对比：错误率、延迟、每次调用成本、故障接力率、胜任度平均分（MH-07 的 `model_competence`）、用户负反馈率（EVO-01） |
| 导出 | CSV，供与厂商账单对账 |

可见范围：系统管理员看全部；空间管理员只看本空间的需求侧数据；供给侧成本（按供应商、binding）需要系统级 `stats:read`。M1 的 GOV-05 成本接口保留，数据量大后改读日汇总表。

## 7. 界面（FE-07〜FE-10）

"模型中枢"管理区包括这几页：供应商、模型、别名与路由、Prompt、配额与预算、运行状态、统计、变更记录。

| 工作项 | 内容 |
| --- | --- |
| FE-07 通用版本组件 | 版本历史（标出当前版本）、按 Schema 显示字段名的 diff、发布对话框（diff、校验结果、影响范围、发布说明）、回滚对话框、引用方面板、变更记录时间线（版本动作和即时改动混排，可按对象类型和操作人筛选） |
| FE-08 模型中枢配置页 | M1 的模型页（FE-03）和配额页改为基于草稿与发布；新增别名页、供应商级与模型级配额 |
| FE-09 运行状态与统计页 | 健康网格、迷你趋势图、最近错误、告警列表；分组表、趋势图、版本对比 |
| FE-10 Prompt 管理 | 分段编辑、变量定义表单、渲染预览、试运行、版本与引用方；Agent 编辑器（FE-02）中的模板选择器 |

### G3 闸门增加的用例

`G3ConfigVersionGateIT`：
1. 发布 binding 的第 2 版，把地址指向一个会报错的桩，错误率上升，"供应商 DOWN"告警触发。
2. 回滚到第 1 版后调用恢复；统计里两个版本的调用分开可查。
3. 把供应商 A 的月度预算设为已用完，路由跳到供应商 B，并留下一条"因预算跳过"的路由事件。
4. Agent 钉住的 Prompt 模板发布了新版本，已发布的 Agent 仍使用旧版本；重新发布 Agent 后才使用新版本。
