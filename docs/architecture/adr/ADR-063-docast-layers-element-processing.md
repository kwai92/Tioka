## 背景

负责人指出：MinerU、PaddleOCR、PDFBox / POI、百炼 OCR 都产不出类似 AST 的结构树，也做不到 TextIn / xParse 那样的「图层处理 + 元素划分专项优化」。调研 06 证实：开源引擎只有「文档标题 / 段落标题」标签，没有层级；商业产品（TextIn、阿里云、Google）的结构树都是它们在识别之后自己重建的，而且各家定义不同。ADR-060 只有一个「组装」阶段和块上的 `parentId` / `level`，没有章节树、行内对象、字符级信息、图层与关系（调研 06 第 5 节 H1〜H7）。

## 决定

1. **契约 `tioka.parse/v1` 增补为完整的文档结构树 DocAST**（第 1 节）：章节树、行内对象、字符级信息、图层、关系、键值对。都是可选字段，符合 v1「只增不改」，已有消费方不受影响。
2. **结构树由 Tioka 自建的结构重建器产生**，与引擎无关（第 2 节）。引擎给的树、标题标签、字体特征都只是输入信号，合同编号规则优先。
3. **每页建立图层**，同一页的原图、规范化图、去水印图、去章图、印章层、手写层相互对齐（第 3 节）。识别在合适的图层上进行，例如被印章遮挡的文字在去章图上重新识别。
4. **路由细化到元素级**：版面分析之后按元素类型分派给专项处理器链（第 4 节）。专项能力来自引擎，Tioka 只自研低成本兜底（红蓝印章颜色分离、二维码与条码解码）。

## 1. DocAST：契约增补

### 1.1 章节树 `tree`

| 字段 | 说明 |
| --- | --- |
| `nodeId` | 文档内唯一，`S{序号}` |
| `kind` | `DOCUMENT`（根）、`PART`（编 / 部分，如「通用条款」「专用条款」「附件」）、`CHAPTER`（章）、`ARTICLE`（条）、`CLAUSE`（款）、`ITEM`（项）、`SECTION`（非合同文档的一般小节） |
| `level` | 从 1 开始的层级 |
| `label` | 规范化编号，如「第二十二条」「4.1.1」「（三）」 |
| `path` | 从根到本节点的编号路径，如「专用条款/第二十二条/（三）」；即 ADR-036 的 `clause_path` |
| `titleBlockId` | 标题所在块；无标题的条款为空 |
| `blockRange` | 所辖块的阅读顺序区间（含子节点） |
| `children` | 子节点 ID 列表 |
| `signals` | 判定依据：`NUMBERING`、`FONT`、`LAYOUT_TITLE`、`ENGINE_TREE`、`TOC`、`LLM`；以及置信度 |

块上原有的 `parentId` 仍保留（块与块的包含关系，如表格与单元格）；块与章节的归属以 `tree` 为准。

### 1.2 行内对象 `inlines`

挂在块上，表示块内文字的一段：

| 字段 | 说明 |
| --- | --- |
| `type` | `HANDWRITING`、`SEAL_OCCLUDED`、`FORMULA`、`CHECK_MARK`、`STRIKETHROUGH`、`BLANK_FILLED`（填写位里补填的内容）、`CROSS_REF`（「见第十条」） |
| `range` | 块 `text` 内的字符区间，左闭右开 |
| `regions` | 坐标 |
| `confidence` | 本段识别置信度 |
| `attrs` | 类型相关：`CROSS_REF` 的目标节点 ID、`FORMULA` 的 LaTeX |

ADR-062 的手写、印章遮挡规则改为按行内对象判断：只有落在行内对象区间内的取值才置「待复核」，不再整块降级。

### 1.3 字符级信息 `chars`（可选）

- 只在解析方案开启时产出（合同用途默认开启，知识库默认关闭），按页分片单独存放，不随块一起返回。
- 每个字符：在块内的序号、坐标、置信度、最多 3 个候选字。
- 用途：引文高亮到字；低置信字在查看器标出；数字与日期的候选字不一致时打 `SOURCE_CONFLICT`。

### 1.4 图层 `layers`

挂在页上，见第 3 节。

### 1.5 关系 `relations`

| 类型 | 起点 → 终点 |
| --- | --- |
| `CAPTION_OF` | 题注块 → 表格或图片块 |
| `CONTINUES` | 续表或续段 → 上一页的表格或段落（取代表格的 `continuedFrom`，后者保留为兼容字段） |
| `KEY_VALUE` | 键块或键文字区间 → 值块或值文字区间（表单类页面、证照） |
| `REFERS_TO` | 交叉引用的行内对象 → 章节节点 |
| `AMENDS` | 补充协议中的修改条款 → 被修改的原合同条款（跨文档，由 @model.build 第 5 步写入，不由解析产生） |

### 1.6 版本与兼容

- 增补字段在契约中统一标为可选；契约文档标注为 `tioka.parse/v1`（2026-11-07 增补）。
- 知识库（ADR-055）可以用 `tree` 取代自行推算的标题路径；不用也不受影响。
- 文档层 `doc_clause` 由 `tree` 中 `ARTICLE` 及以下节点生成，`clause_path` 取 `path`；M3 的正则建树（M3-03）在 M4 由结构重建器取代，输出口径一致。

## 2. 结构重建器（PRS-14）

### 2.1 输入信号

| 信号 | 来源 | 说明 |
| --- | --- | --- |
| 编号 | 块文字与 Word 渲染后的 `listLabel` | 合同编号体系：编 / 部分标题、「第 X 章」「第 X 条」、「X.X.X」、「（X）」「X、」「X)」；中文数字与阿拉伯数字互转 |
| 字体 | Word 样式与大纲级别；文字型 PDF 的字号、粗体 | 同一层级字体通常一致 |
| 版面标题标签 | 版面引擎（文档标题、段落标题） | 只说明「是标题」，不说明层级 |
| 引擎的树 | TextIn `title_tree`、阿里云 `docTree` 等 | 作为参考层级 |
| 目录页 | 识别为目录的页 | 目录中的编号与页码用于校验正文树 |
| 大模型 | 可选 | 只用于以上信号冲突、无法判定的标题，一份文档最多一次调用 |

### 2.2 规则

1. **编号优先**：能识别出编号体系的文档，层级由编号体系决定；同一体系内编号必须连续（「第二十一条」之后应是「第二十二条」），跳号或重复时记 `TREE_GAP` 警告，不自动修补。
2. **编号体系的层级顺序按出现顺序学习**：先出现的体系为上层，例如「第 X 条」之下出现「（一）」，则「（一）」为款；同一文档中再遇到「1.」在「（一）」之下则为项。
3. **无编号的标题**按字体与版面标签归入最近的上层节点；字体信号与编号冲突时以编号为准。
4. **部分切换**：遇到「定义」「专用条款」「通用条款」「附件」等标题时开新的 `PART`，沿用 M3-03 的 `section` 判定。
5. **目录校验**：有目录页时，正文树中每个节点应能在目录中找到；缺失或多出的节点记警告并在查看器标出。
6. **引擎的树**只在没有编号体系的文档（如制度、报告）中作为主信号。
7. **跨页合并**（取代 PRS-06 的跨页部分）：段落在下一页开头无编号且上一页末行不以句末标点结束时合并；表格在列数一致或表头重复时合并为一个表格，重复表头去除，单元格保留各页坐标；引擎已合并的结果（MinerU、TextIn `merged` 模式）直接采用，但仍按本规则校验。
8. **列表、题注、键值**：列表项按编号或项目符号归组；题注按就近与「图 / 表」前缀关联；表单类区域（左键右值、冒号分隔）生成 `KEY_VALUE` 关系。

### 2.3 指标

章节树指标加入 ADR-062 评测集：节点层级正确率 ≥ 98%（合同子集）、条款路径正确率 ≥ 98%（取代原「条款路径识别率 ≥ 95%」）、跨页表合并正确率 ≥ 95%。

## 3. 图层（PRS-15）

### 3.1 每页的图层

| 图层 | 内容 | 产生方式 |
| --- | --- | --- |
| `ORIGINAL` | 原始页图 | 渲染或原图 |
| `NORMALIZED` | 方向校正、纠偏、切边、曲面矫正后的图；记录与原图的坐标变换 | 引擎能力（TextIn 切边矫正、PaddleOCR 方向与矫正、MinerU 预处理）；无引擎时只做 90 度方向校正 |
| `TEXT_LAYER` | PDF 自带文字层 | PDFBox |
| `SEAL` | 印章掩膜与印章块 | 引擎印章检测；兜底为红、蓝色的颜色分离 |
| `SEAL_REMOVED` | 去章图 | 有去章能力的引擎；兜底为在印章掩膜内按颜色去除红 / 蓝像素 |
| `WATERMARK_REMOVED` | 去水印图 | 引擎能力（TextIn 去水印）；无引擎时不产出 |
| `HANDWRITING` | 手写区域掩膜 | 引擎手写检测或行内对象 |

- 所有图层的坐标都换算回 `NORMALIZED` 图的坐标系；契约里的 `regions` 一律以 `NORMALIZED` 图为准，并在页上记录到 `ORIGINAL` 的变换，查看器可以在原图上画框。
- 图层图片存对象存储，与页图同保留期；只有启用了对应能力的方案才产出。

### 3.2 识别在哪一层做

| 元素 | 识别所用图层 |
| --- | --- |
| 正文文字 | 有水印时用 `WATERMARK_REMOVED`，否则 `NORMALIZED` |
| 被印章遮挡的文字 | `SEAL_REMOVED`，结果作为 `SEAL_OCCLUDED` 行内对象 |
| 印章文字 | `SEAL`（只看印章区域，环形文字展开由引擎完成） |
| 手写 | `NORMALIZED` 中的手写区域，交给手写专项处理器 |

## 4. 元素级路由与专项处理器（PRS-16）

### 4.1 路由

ADR-060 第 4 节的路由表从「页类型 × 阶段」扩展为「页类型 × 阶段」加「元素类型 → 处理器链」。版面分析之后，每个区域按类型进入对应的处理器链；链中第一个可用且满足去向许可的处理器执行，失败或低置信时交给下一个。

### 4.2 专项处理器

| 元素 | 处理 | 默认处理器链（私有化方案） | 输出 |
| --- | --- | --- | --- |
| 正文 | 文字识别 | MinerU 4.x（standard）→ PaddleOCR | 块、字符 |
| 表格 | 结构识别（有框 / 无框、合并单元格）、单元格文字、表头识别、跨页合并 | MinerU 4.x → PaddleOCR 表格识别 v2 | 表格、单元格块 |
| 印章 | 检测、环形文字识别、属性分类（颜色：红 / 蓝 / 黑；形状：圆 / 椭圆 / 方 / 其他；类型：公章、合同专用章、财务专用章、发票专用章、个人章、其他）、骑缝章判定 | PaddleOCR 印章流水线 → MinerU 印章文字 | `SEAL` 块，`attrs` 含颜色、形状、类型 |
| 手写 | 检测、识别；金额、日期、期限类手写一律低可信 | PaddleOCR（PP-OCRv5 手写）→ 云端第二意见 | `HANDWRITING` 行内对象 |
| 签名 | 检测，不识别文字 | PaddleOCR 版面 | `SIGNATURE` 块 |
| 勾选框 | 检测与勾选状态 | 版面引擎 → 视觉模型判定 | `CHECKBOX` 块 |
| 二维码、条码 | 解码 | Tioka 自研（Java 开源解码库） | `PICTURE` 块，`attrs` 含解码内容 |
| 公式 | LaTeX | MinerU 4.x | `FORMULA` 块或行内对象 |
| 图表 | 转数据表 | PaddleOCR 图表转表格 | 关联表格，P3，默认关闭 |
| 页眉页脚、页码 | 归入 `FURNITURE` | 版面引擎 | 块 |

云端方案（`standard-cloud`）可在各链首位放 TextIn xParse（ADR-061 修订），在第二意见位放 `qwen-vl-ocr`。

### 4.3 印章属性的用途

- 审查要点「是否加盖公章或合同专用章」「印章名称与当事方是否一致」以 `SEAL` 块的类型与文字为证据（LSE 领域包）。
- 财务专用章、发票专用章出现在合同正文签章区时，在确认页提示。
