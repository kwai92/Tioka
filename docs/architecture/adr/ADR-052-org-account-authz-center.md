## 决定

### 组织与人员

1. 组织单元分集团、公司、部门三类；岗位、职级独立；**人员与账号分开**，一人可兼职多个组织单元（任职），恰有一个主任职。
2. 人员类型含「数字员工」，对应 Tioka 已发布的 Agent：出现在组织树、可有岗位、可被选为待办处理人，**没有登录账号**，负责人必填；权限仍由 Tioka 按 ADR-032、ADR-039 计算。
3. 组织与人员以 Foundation 为准，账号由 Foundation 推送到 Keycloak，每日对账。外部身份关联沿用 ADR-026：按工号或已验证邮箱，或本人用来源登录确认；不按姓名匹配；关联不上时生成待处理关联，不自动建人。

### 同步

4. 一个部署只有一个权威来源负责组织树与人员主信息（本地、飞书、LDAP/AD、SCIM、HR 接口之一）；其他来源只补外部身份。
5. 每次同步先算差异；一次停用超过 5% 或 50 人、或删除组织单元超过 10 个时暂停待确认。外部为准，「本地锁定」字段不覆盖；规则产生的授权不覆盖手工授权。
6. 停用、离职发 `fdn.person.disabled` 与 `fdn.account.sessions_revoked`；Tioka 据此执行 ADR-026 的离职处理与 TRU-03 的负责人失效处理。

### 权限

7. 菜单、按钮、权限码、数据维度由应用随版本提交**权限清单**导入，管理台只调显示与排序；消失的权限码标为已下线，90 天后清理。权限码格式沿用 `资源:动作`。
8. 角色分全局（Foundation 自身、三员）与应用级；授予对象可以是人员、组织单元（可含下级）、岗位；支持生效期与互斥。
9. **Tioka 空间角色不迁移**，仍在 Tioka；ADR-026 的「组 → 空间角色」规则改为以 Foundation 组织单元、岗位或应用角色为条件。Tioka 的 `tenant_admin` 改为 Tioka 应用的应用级角色。
10. 数据权限 = 若依部门五档 + **自定义数据维度**（如 `region`、`store`），维度值来源可为字典、组织树或应用上报。角色之间取并集，角色内部各项取交集。执行在应用内（starter 生成条件或应用读取取值集合）。
11. 授权快照的人员属性与维度取值同时作为 GOV-07 Cedar 的 principal 属性、ADR-040 CEL 的主体属性来源；M3-03 的 `acl_principals` 使用维度值编码。执行位置不变。
12. 三员（系统管理员、安全管理员、审计管理员）内置且互斥，可在部署时关闭；带高风险权限码的授予需安全管理员复核。

## 备选

| 备选 | 不选原因 |
| --- | --- |
| Keycloak 作组织主数据 | 表达不了岗位、兼职、职级和数据维度 |
| Keycloak 用户存储扩展回读 Foundation | 需要在 Keycloak 内部署自写扩展，升级有兼容风险；需要强一致时可改选 |
| 管理台手工维护菜单与权限码（若依做法） | 代码与配置漂移 |
| 把 Tioka 空间角色也搬到 Foundation | 空间是 Tioka 的业务概念，搬过去会让 Foundation 理解 Tioka 的内部结构 |
| 多来源并列写人员主信息 | 来源互相覆盖，问题难以追查 |
