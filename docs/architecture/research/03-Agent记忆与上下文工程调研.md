## 0. 结论摘要

1. **上下文是 Agent 的稀缺资源，不是越多越好。** Chroma 对 18 个模型的测试显示，输入越长，表现越不可靠；同一批问题只给相关的约 300 token 时，所有模型都明显好于给完整的约 11.3 万 token [5]。Anthropic 把这称为「上下文腐化」（context rot），主张找「最小的高信号 token 集合」[1]。所以上下文工程的目标不是塞满窗口，而是**每一步只放该放的东西**。
2. **业界做法已经收敛成四个动作**：写到窗口外（笔记、文件、记忆）、按需选入（检索、工具结果、记忆）、压缩（清理旧工具结果、摘要）、隔离（子 Agent 各用各的窗口）[4]。Anthropic [1]、OpenAI [8][9]、Google ADK [13]、Manus [3] 在这四点上说法一致，差异只在细节。
3. **提示缓存是成本和延迟的第一杠杆。** Manus 称 KV 缓存命中率是生产 Agent「最重要的单一指标」，输入与输出 token 之比约 100:1，缓存读取价格是未缓存的十分之一 [3]。Tioka 用的百炼、DeepSeek 都有前缀缓存：百炼显式缓存命中按输入价 10% 计，隐式缓存命中多数模型按 20% 计 [17]；DeepSeek 默认开启硬盘缓存 [16]。**前缀只要有一个字不同，后面全部不命中**，所以缓存命中率由上下文组装顺序决定，不是网关层能补救的。
4. **Tioka 现有组装顺序对缓存不友好。** ADR-027 / ADR-031 的顺序把「用户记忆、经验、知识自动检索结果」这些每轮都变的段放在历史对话**之前**，等于每一轮都让历史部分的缓存失效。这是本次调研发现的最大问题，而且 RT-10 在 M3 就要按这个顺序实现，需要在 M3 前改掉。
5. **记忆要分层，并且分清谁能写、谁能读。** 主流框架把记忆分成工作记忆、会话记忆和长期记忆，长期记忆又分语义（事实）、情景（经历）、程序（做法）三类 [4][21]。Tioka 现在只有「用户长期记忆」（ADR-022 CHT-05）和「Agent 经验」（ADR-031），缺空间级共享记忆、缺时间有效性、缺来源追溯，`chat_memory_item` 还带着已被第 60 条禁止的 `tenant_id`。
6. **共享记忆是投毒入口。** MINJA 攻击只靠普通用户提问就能把恶意记录写进共享记忆库，注入成功率平均 98.2%，之后诱导其他用户的会话执行恶意推理的成功率平均 76.8%；检测提示词在一个场景能拦 131/135，换个场景拦截数为 0 [24]。结论是：**共享范围的记忆必须人审，个人记忆只从用户本人说的话里抽取，不从工具结果和网页里抽取。**
7. **不建议引入 Mem0、Letta、Zep 作为运行时依赖**，建议在 PostgreSQL + pgvector 上自建，借用它们的算法：Mem0 的「新增 / 更新 / 失效 / 不变」四种写操作 [18]，Zep 的双时间有效期（失效而不是删除）[20]，LangMem 的命名空间与「对话中写 / 后台写」两条写路径 [21]，Letta 的「常驻小块记忆 + 按需检索大库」[19]。同时留一个记忆引擎 SPI，客户坚持用外部引擎时可以接。
8. **建议新增三份 ADR**：ADR-048 上下文组装、预算与压缩；ADR-049 提示缓存；ADR-050 记忆体系。M3 只改组装顺序、工具结果清理和缓存友好规则（约后端 4.5 人日，与 RT-10 一起做），记忆本体放 M4。

## 1. 为什么上下文成了关键

| 现象 | 证据 | 对 Tioka 的含义 |
| --- | --- | --- |
| 上下文越长，表现越不可靠 | Chroma 测 18 个模型（含 Claude 4、GPT-4.1、Gemini 2.5、Qwen3）：表现随输入变长而下降；问题与答案相似度越低，下降越快；哪怕加一条干扰内容也会变差；结构连贯的长文反而比打乱顺序的更难 [5] | 「模型支持 128K」不等于「放满 128K 还好用」。需要一个**有效预算**，低于模型窗口 |
| 注意力是预算 | Anthropic：每多一个 token 都在消耗注意力预算；Transformer 的两两关系是 n² 级，长上下文训练数据也少，所以退化是渐进的，不是到某个长度突然失效 [1] | 压缩不应只在快溢出时才做 |
| 聚焦输入效果更好 | Chroma 在 LongMemEval 上：完整输入平均约 11.3 万 token，只给相关部分约 300 token，所有模型在后者上都明显更好 [5]；Zep 报告用 1.6K token 的记忆上下文替代 11.5 万 token 全量历史，gpt-4o 准确率从 60.2% 升到 71.2%，延迟降约 90%（经摘要）[20] | 长期记忆和检索的价值在于「挑」，不是「存」 |
| 但全量也有上限优势 | Mem0 论文的 LoCoMo 结果中，全量上下文的综合分（72.90）仍高于 Mem0（66.88）和其图版本（68.44），代价是 p95 延迟 17.1 秒对 1.4 秒、token 约 2.6 万对 1,764（经摘要）[18] | 记忆系统是拿少量准确率换大量成本和延迟；短会话直接用全量历史更好 |
| 成本主要在输入 | Manus：典型任务约 50 次工具调用，输入与输出 token 之比约 100:1 [3]；Anthropic 多 Agent 研究系统的 token 用量约为普通对话的 15 倍 [4] | Agent 的钱主要花在「反复读上下文」，缓存命中率直接决定成本 |

## 2. 上下文工程：各家做法

### 2.1 四个动作（LangChain 的归纳）

LangChain 把上下文工程归为写、选、压、隔四类 [4]，并引用 Drew Breunig 的四种失败：投毒（错误信息进上下文后被反复引用）、分心（上下文太长压过训练知识）、混淆（无关内容影响回答）、冲突（上下文前后矛盾）。

| 动作 | 做法 | 代表 |
| --- | --- | --- |
| **写**（存到窗口外） | 草稿本（工具写文件或写运行状态）、跨会话记忆 | Anthropic 结构化笔记 [1]；Manus 的 todo.md [3]；Claude memory 工具 [7] |
| **选**（按需拿进来） | 读草稿本；检索记忆（情景记忆当示例、程序记忆当指令、语义记忆当事实）；对工具描述做检索（工具选择准确率约提升 3 倍）；知识检索 | LangChain [4]；Tioka RT-13 工具检索已采纳 |
| **压**（只留必要的） | 摘要（Claude Code 在用到 95% 时自动压缩）；裁剪（按规则丢旧消息） | [4][8][9] |
| **隔**（分开窗口） | 多 Agent 各自窗口；沙箱里保存大对象只回传摘要；运行状态只把部分字段暴露给模型 | [4][1][2] |

### 2.2 Anthropic

来源：《Effective context engineering for AI agents》（2025-09-29）[1]，Claude API 文档 [6][7]，多 Agent 研究系统 [2]。

- **系统提示要在「合适的高度」**：介于写死的 if-else 和空泛指导之间；从最小提示开始，按观察到的失败补指令 [1]。
- **工具要少、不重叠**：「人类工程师都说不清该用哪个工具时，不能指望 Agent 做得更好」[1]。
- **即时检索**：上下文里只放轻量标识（文件路径、查询、链接），运行时再读内容；静态内容可以混合：CLAUDE.md 一开始就放进去，其他文件用 glob、grep 按需读 [1]。
- **压缩**：接近上限时摘要并用摘要重开。Claude Code 保留「架构决定、未解决的缺陷、实现细节」以及最近访问的 5 个文件；调优时先保召回再提精度 [1]。
- **工具结果清理**：「最安全、最轻量的压缩形式」，把历史深处的原始工具结果去掉 [1]。
- **结构化笔记**：把笔记写到窗口外（NOTES.md、待办清单、memory 工具），之后再读回来 [1]。
- **子 Agent**：子 Agent 可能用掉几万 token 探索，但只返回 1,000〜2,000 token 的提炼结果 [1]。
- **选法**：来回对话多的用压缩；有里程碑的迭代任务用笔记；可并行的研究用多 Agent [1]。

Claude API 把这些做成了平台能力 [6][7]：

| 能力 | 机制 | 默认值与要点 |
| --- | --- | --- |
| 工具结果清理（context editing） | 服务端在发给模型前清掉最早的工具结果，换成占位文本；客户端保留完整历史 | 触发默认 10 万输入 token；保留最近 3 次工具调用；可设「至少清掉多少」避免为清理一点点而打断缓存；可排除指定工具；**清理会让缓存前缀失效** [6] |
| 思考块清理 | 清掉更早 Turn 的思考内容 | 默认保留 1 个 Turn；保留越多缓存越稳 [6] |
| 阈值压缩（compaction） | 输入超过阈值时由同一模型生成摘要块，之后请求丢弃摘要块之前的消息 | 默认阈值 15 万，最小 5 万；可自定义摘要提示（完全替换默认）；摘要期间模型可能调用工具，文档建议在提示里禁止 [6] |
| 按需压缩 | 应用自己决定何时压缩，单独请求一次摘要 | 被摘要消息中的图片、文档、抓取的网页在压缩后丢失 [6] |
| memory 工具 | 客户端执行：模型发出查看、创建、替换、插入、删除、改名等命令，由应用写到自己的存储（目录 `/memories`） | 应用负责：校验所有路径必须在 `/memories` 下、拒绝 `../` 及其编码形式、限制文件大小、长期不访问的记忆过期、剥离敏感数据；接近清理阈值时模型会被提醒先把重要信息写进记忆 [7] |

多 Agent 研究系统 [2]（未重新读原文，数字取自 01 号调研已核实部分与 LangChain 转述 [4]）：多 Agent 的 token 用量约为普通对话的 15 倍；子 Agent 把结果写到文件系统再交引用，避免「传话游戏」式失真。

### 2.3 OpenAI

| 能力 | 机制 | 来源 |
| --- | --- | --- |
| 服务端压缩 | Responses API 的 `context_management` 设压缩阈值，超过时服务端自动压缩，返回**加密的**压缩条目；也有独立的压缩端点，输入完整窗口返回压缩后窗口，返回结果不得再裁剪 | [8]（经摘要） |

加密压缩条目对 Tioka 不适用：轨迹必须可读、可审计、可跨供应商复用（第 9 节）。

### 2.4 Manus

《Context Engineering for AI Agents: Lessons from Building Manus》（2025-07-18）[3]，框架重写过四次：

1. **围绕 KV 缓存设计**：前缀保持稳定，系统提示开头不要放精确到秒的时间戳；上下文只追加不修改；序列化要确定（JSON 键序固定）；需要时显式标缓存断点；自部署 vLLM 要开前缀缓存并按会话 ID 路由。
2. **屏蔽而不是删除工具**：任务中途增删工具会让缓存失效，还会让模型看到引用了已不存在工具的历史而困惑；改用状态机在解码时屏蔽；工具名用统一前缀（如 `browser_`、`shell_`）便于成组屏蔽。
3. **文件系统就是上下文**：容量无限、天然持久；压缩必须**可恢复**：网页内容可以丢，但留 URL；文档可以丢，但留路径。
4. **复述目标**：不断重写 todo.md，把目标「复述」到上下文末尾，对抗长任务中的「迷失在中间」。
5. **保留错误**：把走错的步骤留在上下文里，抹掉失败等于抹掉证据；错误恢复是「真正 Agent 行为最清楚的标志之一」。
6. **避免被少样本带偏**：重复的「动作-观察」对会让模型照着模仿；用结构化的变化（不同序列化模板、措辞、轻微顺序变化）打破。

### 2.5 Google ADK

Google 的 ADK 博客（2025-12-04）[13] 给出了最接近 Tioka 架构的抽象：**「上下文是对更丰富的有状态系统的编译视图」**。

| 概念 | 含义 |
| --- | --- |
| 会话（Session） | 按时间排列的结构化事件（用户消息、回答、工具调用、结果、控制信号、错误） |
| 状态（State） | 会话内的结构化草稿变量 |
| 记忆（Memory） | 跨会话、可检索的长期知识。两种召回：Agent 主动调 `load_memory`；或在模型调用前按最新输入自动预加载 |
| 产物（Artifacts） | 带名称和版本的大对象，默认只给模型看名字和摘要，需要时用工具加载，用完即卸载 |
| 处理器管线 | 从会话、记忆、产物「编译」出本次调用的工作上下文，每一步变换显式、有名字、有顺序 |
| 压缩 | 达到阈值后用模型对滑动窗口内的旧事件做摘要，写回会话作为「压缩」事件，原始事件之后可以裁掉 [13][14] |
| 缓存 | 上下文分成稳定前缀（系统指令、身份、长期摘要）和可变后缀；「静态指令」保证系统提示不变以保住缓存前缀 |
| 多 Agent | **默认最小范围**：每次模型调用和子 Agent 只看到必需的上下文；「Agent 作为工具」时被调方只看到专门构造的提示和需要的产物；交接时把上一个 Agent 的回答改写成叙述（「[供参考]：Agent B 说……」），避免新 Agent 把它当成自己说过的话 |

ADK 的记忆服务接口按「应用名 + 用户 ID」划分范围，支持整段会话入库、增量事件入库、显式写入条目与检索；托管版会用模型抽取并合并记忆 [14]。

### 2.6 Cognition 的反对意见

Cognition（Devin）《Don't Build Multi-Agents》[12]：多个 Agent 各自只看到部分上下文时，各自的动作里隐含的决定会相互冲突；主张共享完整上下文与完整轨迹，长任务用专门的压缩模型。这与 Anthropic、ADK 的「隔离」看似相反，实际是适用面不同：**需要连续一致判断的任务（写同一份代码）不要拆；可并行、结果可结构化汇总的任务（多路检索、逐条审查）适合隔离**。ADR-038 用「结构化产物 + 决定日志（MAS-08）」处理隐含决定冲突，与这条意见是一致的。

## 3. 上下文窗口管理：压缩、清理、卸载、隔离

把各家机制按「代价从轻到重」排列：

| 层 | 做法 | 信息损失 | 对缓存的影响 | 代表 |
| --- | --- | --- | --- | --- |
| 0 卸载 | 大结果写文件 / 对象存储，上下文只放预览和路径 | 无（可读回） | 无（入库时就决定） | Manus [3]、ADK 产物 [13]、**Tioka ADR-027 已有（> 8000 token）** |
| 1 清理 | 把较早的工具结果换成占位符，保留调用记录 | 小（可重新调用或读文件） | 清理点之后全部失效，所以要「攒够再清」 | Claude context editing [6]、Anthropic [1] |
| 2 摘要 | 较早的历史压成结构化摘要，近几轮原样保留 | 中（可能失真，可能「投毒」） | 整体重建，之后再稳定 | Claude compaction [6]、OpenAI [8][9]、ADK [14]、**Tioka ADR-027 已有（75% 时）** |
| 3 裁剪 | 直接丢掉旧消息 | 大 | 同上 | OpenAI Agents SDK 裁剪 [9]、Spring AI 消息窗口（默认 20 条）[22] |
| 隔离 | 子任务在独立窗口执行，只回传 1〜2K token 的结果 | 父窗口不知道细节 | 子窗口有自己的缓存 | Anthropic [1]、ADK [13]、**Tioka ADR-027 / ADR-038 已有委派，但没规定传什么、回什么** |

几个共识：

- **先清理后摘要**：清理是可逆的，摘要不可逆 [1][6]。
- **摘要要结构化**：要求列出目标、约束、决定、标识符、未决问题、下一步 [1][9]；摘要时禁止调用工具 [6]。
- **摘要会丢多模态内容**：图片、文档、抓取的网页在压缩后丢失 [6]，所以要先卸载成文件引用再摘要。
- **计划与待办要原样保留并复述到末尾** [3]。
- **客户端保留完整历史**：Claude、ADK 都是「发给模型的是编辑后的视图，存储里是完整记录」[6][13]。Tioka 的 item 落库模式天然如此。

## 5. 提示缓存

### 5.1 各供应商规则

| 供应商 | 模式 | 最小长度 | 有效期 | 价格 | 关键限制 |
| --- | --- | --- | --- | --- | --- |
| Anthropic [15] | 自动 + 显式断点（最多 4 个） | 1,024〜4,096（按模型） | 默认 5 分钟（每次命中刷新），可选 1 小时 | 写 1.25 倍（1 小时为 2 倍），读 0.1 倍 | 前缀顺序为工具 → 系统 → 消息；从断点向前最多回看 20 个块；**改工具定义会让全部缓存失效**；增删图片、改 `tool_choice`、改思考参数让消息部分失效；自 2026-02-05 起按 workspace 隔离 |
| OpenAI [15b]（经摘要） | 默认自动；新模型可选显式断点 | 1,024 | 新模型 30 分钟或 12 小时；旧模型内存级或 24 小时 | 读最多便宜 95%；新模型写 1.25 倍 | 按前缀哈希和 `prompt_cache_key` 路由到机器；改模型、工具（含顺序）、并行工具开关、输出格式、推理强度、压缩都会失效；建议用「允许工具列表」代替删除工具定义 |
| DeepSeek [16] | 硬盘缓存，默认开启，不可关 | 未说明 | 几小时到几天内清理 | 页面未写折扣（价格页另列） | 请求必须完整匹配一个已缓存的前缀单元；尽力而为，不保证命中 |
| 阿里云百炼 [17] | 显式（`cache_control`，最多 4 个标记）与隐式（自动）二选一 | 1,024 | 显式 5 分钟（命中刷新）；隐式不固定 | 显式：创建 125%，命中多数模型 10%；隐式：命中多数模型 20%，无写入费 | 工具定义属于系统消息的缓存，**必须逐字节一致**（工具顺序、字段顺序、可选字段都要一致）；从标记向前最多回看 20 个块；按账号和模型隔离 |
| 自部署（vLLM / SGLang） | 前缀缓存（vLLM Automatic Prefix Caching、SGLang RadixAttention） | — | 显存 / 内存容量决定 | 省 GPU 计算 | 多副本时要**按会话亲和路由**，否则命中率随副本数下降 [3]；vLLM 的具体参数未核实 |

### 5.2 对 Tioka 的含义

1. **缓存只认前缀**，所以组装顺序就是缓存策略。每轮都变的内容必须放在末尾。
2. **工具列表在一个会话内要稳定且确定排序**。百炼要求逐字节一致 [17]；Anthropic 改工具定义会让全部缓存失效 [15]。ADR-016 RT-13 已要求「常用工具集合在一个 Turn 内不变」，还需要扩展到整个 thread，并规定排序与序列化。
3. **系统提示里不放时间戳**。日期放到末尾，精确到天 [3]。
4. **换模型就是换缓存**。ADR-024 的 `preferPreviousInGroup` 已经要求同组沿用上一个模型 [ADR-024]；需要明确只在压缩点或用户显式切换时换模型。
5. **清理与压缩会打断缓存**，所以要「攒够再清」，一次清掉足够多 [6]。
6. **成本核算要分开写入与读取**。显式缓存写入比普通输入贵 25%〜100%，命中便宜 80%〜90%；ADR-041 只记了「缓存命中 token」，没记写入 token 和对应单价。
7. **私有化部署要在部署指南里写清会话亲和路由**，否则多副本推理服务的命中率很低。

## 8. 记忆的安全与治理

### 8.1 威胁

| 威胁 | 说明 | 来源 |
| --- | --- | --- |
| **查询式记忆注入（MINJA）** | 攻击者只是普通用户，不能直接写记忆库，只能提问和看输出。通过「桥接推理步骤 + 诱导提示 + 逐步缩短」构造看似正常的记录，被检索为其他用户会话的示例。注入成功率平均 98.2%，攻击成功率平均 76.8%。针对性检测提示在一个场景拦 131/135，在另一个场景拦 0/135；通用检测提示误报 34/50；向量层面的清洗无效 [24] | [24] |
| 间接提示注入写进记忆 | 网页、文档、工具结果里的指令被抽取成「用户偏好」长期生效 | 由 [24] 与 ADR-039「工具结果不可信」推出 |
| 摘要投毒 | 一个错误事实进了压缩摘要，此后一直被引用 | [9]、[4] |
| 跨范围泄漏 | 在高密级空间学到的事实被注入到低密级空间的会话 | Tioka 场景推出（ADR-040） |
| 越权读取 | 管理员或其他 Agent 读个人记忆 | 合规要求 |

OWASP 2026 年 Agent 应用十大风险（2025-12-09 发布）[27] 中有「记忆与上下文投毒」一项（编号与缓解措施原文未读到，**未核实**）。

### 8.2 业界缓解做法汇总

1. 只对经过校验的数据入库，入库是显式动作 [14]。
2. 每条记忆带来源（用户、会话、时间）[14][20]。
3. 按用户、应用隔离，**非必要不做跨用户共享记忆库**，MINJA 的前提就是共享库 [24]。
4. 记忆作为带标签的参考数据进入上下文，不作为指令 [13]。
5. 子 Agent 默认最小上下文，限制投毒扩散 [13]。
6. 大的、不可信的内容放产物里按需加载 [13]。
7. 单一检测手段不可靠，要分层：来源限制 + 人审 + 监控写入量与命中异常 [24]。
8. 记忆要能删除和过期 [7][14]。个人信息还要满足《个人信息保护法》的删除权（第四十七条）与知情同意。

| G11 | `chat_memory_item` 带 `tenant_id`，违反第 60 条；没有 `workspace_id`、标签、状态 | 实现时会违反护栏 | 中 |

## 10. 设计建议与选项

编号接 02 号调研（选项 I、J）。每个决定给出推荐与备选，推荐方案已写成 ADR。

### 选项 K：上下文组装（ADR-048）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **K1 分区组装 + 三层削减（推荐）** | 上下文分四区：稳定前缀（Agent 版本级）→ 会话快照（thread 级冻结）→ 历史 → 本轮尾部（按 Turn 冻结）。削减按「卸载 → 清理 → 摘要 → 失败」四级。每次模型调用记录上下文清单 | 缓存友好；与 Claude、ADK 的做法一致；不依赖供应商能力 | 记忆、经验、知识结果从「历史之前」挪到「本轮末尾」，需要改 ADR-027、ADR-031 的顺序 |
| K2 保持现顺序，只加清理层 | 改动最小 | 不改已定顺序 | 缓存问题不解决 |
| K3 用供应商原生压缩 / 清理 | Claude、OpenAI 的服务端能力 | 省开发 | 百炼、DeepSeek 没有；OpenAI 返回加密条目，轨迹不可审计；与「一个内核、多供应商」原则冲突 |

### 选项 L：提示缓存（ADR-049）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **L1 组装器给出与供应商无关的断点提示，网关按供应商能力落地（推荐）** | binding 声明缓存模式（无 / 隐式 / 显式）、最小长度、有效期选项、写读单价；显式的打标记，隐式的传亲和键；记录写读 token；命中率指标与告警；断点诊断 | 一处设计覆盖所有供应商；成本可算 | 网关要为每类协议写适配 |
| L2 只依赖隐式缓存 | 什么都不做，靠组装顺序 | 零开发 | 百炼显式缓存（10%）比隐式（20%）更便宜，用不上；Anthropic 兼容协议必须打标记才缓存 |
| L3 自建语义缓存（相似问题直接返回缓存答案） | — | 省调用 | 对 Agent 多步任务无效，有返回错误答案的风险；不建议 |

### 选项 M：记忆体系（ADR-050）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **M1 自建分层记忆（推荐）** | PostgreSQL + pgvector；作用域：个人（USER）、空间（SPACE），程序记忆即 ADR-031 经验（AGENT）；个人记忆只从用户本人的话里抽取；空间记忆必须人审；双时间有效期、失效不删；来源、标签、可移植规则；读路径分「会话快照（常驻）+ 本轮检索 + 工具检索」；SPI 预留外部引擎 | 权限、标签、审计、私有化都能落在已有体系里；不引入 Python 服务 | 自研工作量（M4 约后端 14 人日） |
| M2 引入 Mem0 开源版作为旁路服务 | 抽取与更新交给 Mem0 | 抽取算法现成 | 多一个 Python 服务与存储；作用域、标签、审计、删除要再包一层；私有化部署变重 |
| M3 引入 Zep / Graphiti 或 Letta | 时间图谱或有状态 Agent 服务 | 时间推理更强 | 需要图数据库（Neo4j）或改变 Runtime 的状态归属，与 ADR-016 冲突 |
| M4 只做个人记忆，不做空间记忆 | 维持 CHT-05 范围 | 工作量小（约后端 8 人日） | 团队约定没有落脚点，只能写进知识库或提示词 |

### 选项 N：子 Agent 与交接的上下文传递（ADR-048 第 5 节）

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **N1 默认隔离（推荐）** | 子 Agent 只收任务简报和显式引用的产物；可选附父会话最近一次压缩摘要；不提供完整历史；回传结果默认上限 2000 token，超出部分转为产物 | 与收窄授予一致，不会把父会话里超出子授予的数据带过去；父窗口不被撑爆 | Cognition 指出的「隐含决定」问题要靠任务简报和决定日志（MAS-08）补 |
| N2 默认继承完整历史 | 与 Cognition 主张一致 | 一致性好 | 绕过授予收窄与数据标签；成本高 |

### 推荐组合与分期

| 阶段 | 内容 | 人日 |
| --- | --- | --- |
| **M3**（与 RT-10 一起） | 分区组装与尾部冻结、清理层、结构化摘要与溢出兜底（CTX-01）；确定性序列化、日期下沉、会话内工具列表稳定、缓存写读分记（CCH-01）；AgentSpec 预留 `context`、`memory` 段（AST-11） | 后端约 4.5 |
| **M4**（取代原在 M4 之后的 CHT-05） | 上下文清单落库与查询、子 Agent 隔离与结果上限、交接叙述化、计划复述（CTX-02）；缓存适配、命中率告警、断点诊断（CCH-02）；记忆核心（MEM-01，取代 CHT-05）、空间记忆与审核（MEM-02）、记忆与压缩评测（MEM-03）；前端 FE-30、FE-31 | 后端约 20，前端约 6 |
| **M4 之后** | 历史会话回忆工具（MEM-04）、外部记忆引擎 SPI（MEM-05）、供应商原生压缩适配（CTX-03） | 后端约 10 |

不做：语义缓存（L3）、参数记忆（微调）、Agent 自由改写自己的指令（程序记忆只经发布与人审改变）、跨用户共享的情景记忆库。

## 11. 排期影响

基准为负责人 2026-11-06 在 PR #17（M3-00）选定的方案 B：M3 为 W24–W53（前端 W21 起），M4 为 W54–W67（已含第 67 条预计的 +2 周），总工期约 15.5 个月。方案 B 已把 CHT-05 移到 M4 之后。

- **M3**：净增后端约 4.5 人日（CTX-01 3、CCH-01 1、AST-11 0.5）。建议与 RT-10 同由 BE-B 在 W48 前完成，在 M3 的 85% 负载余量内吸收，不延长 M3；若 W48 无余量，按 M3-00 的让路顺序可与 RT-10 一起后移，但**组装顺序本身不能推迟到 M4**，否则 M4 要返工 RT-10。
- **M4（推荐）**：MEM-01 取代原本在 M4 之后的 CHT-05 提前进 M4。M4 净增后端约 20（CTX-02 3、CCH-02 3、MEM-01 8、MEM-02 4、MEM-03 2）、前端约 6（FE-30 4、FE-31 2）人日，按 3 名后端 85% 负载约 1.5 周，M4 预计延长约 1.5 周到约 W69，总工期约 15.9 个月。在写 M4-00 时按人力核算确认。
- **备选一**：MEM-02、MEM-03、FE-31 移到 M4 之后（后端 −6、前端 −2），M4 延长约 1 周到约 W68。
- **备选二**：记忆仍按方案 B 放在 M4 之后，M4 只做 CTX-02、CCH-02（后端 6），在 M4 余量内吸收，M4 保持 W67。代价是 M4 交付时仍没有长期记忆。
