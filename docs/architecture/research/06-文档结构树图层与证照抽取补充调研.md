# 文档结构树、图层处理与证照抽取：补充调研

- 日期：2026-11-07
- 落地：推荐方案已写成 [ADR-063](../adr/ADR-063-docast-layers-element-processing.md)、[ADR-064](../adr/ADR-064-certificate-structured-extraction.md) 与 ADR-060〜062 的修订，见 ADR-029 第 72 条。负责人复核时可改选第 6 节的备选方案。
- 状态：调研报告 + 设计建议（背景材料，不是执行依据）。
- 缘起：负责人对已合并的 [调研 05](05-文档解析与OCR调研.md) 与 ADR-060〜062 提出：MinerU、PaddleOCR、PDFBox / POI、百炼 qwen OCR 都产不出类似 AST 的结构树；证照类文件也产不出结构化数据；解析过程也做不到 xParse、TextIn 那样的「图层处理 + 元素划分专项优化」。负责人另提醒：MinerU 已到 4.x 且仍开源，能力有很大提升。
- 写法：只有文字和表格，不含代码。引用编号见文末，资料于 2026-11-07 联网读取；标「经摘要」的来自工具对长页面的摘要，标「未核实」的没有读到原文。

## 0. 结论摘要

1. **负责人的判断成立，而且原设计低估了这一层。** 开源引擎输出的是「扁平元素 + 少量标题标签」：PP-StructureV3 只有「文档标题」「段落标题」两种标题标签，文档里没有层级字段 [4]；MinerU 4.x 的输出说明里也没有标题层级字段（未找到）[6]；PDFBox、POI 只给文字或段落。ADR-060 第 2 节把「组装」写成一个阶段，第 3 节的块只有 `parentId` 与 `level`，没有显式的章节树、行内对象、字符级坐标、图层、元素间关系与键值对。
2. **商业产品的结构树也是「识别之后再重建」出来的。** TextIn xParse 的标题树是可选能力（`title_tree`，最多 6 级），元素带 `parent_id`、`children_ids`、`category_depth` 与题注引用 [1][2]；它的流水线还能把 MinerU、PaddleOCR 作为底层引擎 [3]。阿里云文档智能（`doctree` 模式）返回 `docTree` 节点（层级、上级、下级链接）[7]；Google Document AI 版面解析器把元素组织成树 [8]；Reducto 没有显式层级，只有标题类块 [9]。**结构树是解析产品自己的后处理层，Tioka 也必须有自己的这一层**，否则换引擎就换结构、换证据。
3. **TextIn 的「图层与元素专项」能力可以逐项对上**：去水印、切边与曲面矫正、印章检测与属性（颜色、形状、公章 / 合同专用章 / 财务章等类型）、手写作为行内对象、跨页表合并（含每页来源区域与表头去重）、有框 / 无框表、字符级坐标与置信度和候选字、公式与化学式、二维码与条码 [1][2][10]。没有查到「去章」能力 [10]。
4. **证照与票据**：TextIn 文档抽取 v3 按 JSON Schema 抽取，每个字段返回引用（页码、位置、原文）与印章列表，但没有字段级置信度 [10]；TextIn 票据识别覆盖 40 多类票据，没查到营业执照、身份证产品页 [11]。百炼 `qwen-vl-ocr` 的信息抽取任务支持约 50 种常见证照与票据，可自定义 `result_schema`（最多 3 层）[12]。PP-ChatOCRv4 需要接入大模型做关键信息抽取 [13]。**证照抽取 = 文档分类 + 按 Schema 抽取 + 引用回指与校验**，Tioka 已有 Schema 登记表与证据绑定（ADR-037），缺的是这一层编排。
5. **MinerU 4.x 确有大幅提升**（负责人的提醒正确，调研 05 只读到旧资料）：许可在 3.1.0（2026-04-18）由 AGPLv3 改为「Apache-2.0 + 附加条款」；原生解析 DOCX（3.0.0）、PPTX、XLSX（3.1.0）以及 OFD、RTF、HTML 等；四档质量（flash / basic / standard / advanced），CPU 可跑到 standard（12 核以上）；跨页表合并；印章文字识别；统一文档模型可渲染九种目标；`/v1/tasks` 任务接口与 Docker 部署 [5][6][14]。没找到：标题层级字段、水印处理、关键信息抽取 [6]。
6. **不假定客户装了哪些引擎**：除进程内引擎外都是可选的，系统按客户实际安装的引擎自动装配，缺失能力按规定降级并报告（ADR-063 第 5 节）。
7. **建议**：Tioka 自建三样东西——**文档结构树 DocAST**（契约 v1 增补）、**结构重建器**（与引擎无关，合同编号规则优先）、**图层与元素级编排**（按元素类型选专项处理器）；再加一层**证照与票据结构化抽取**（`@doc.extract`）。识别能力不自研：私有化默认改为 **MinerU 4.x（主）+ PaddleOCR（印章、手写专项）**，最终以合同评测集的对比结果定；云端外购参考适配器由阿里云文档解析改为 **TextIn xParse**（功能与本需求最贴合），但其私有化与数据处理条款公开资料未写明，须采购时书面确认。
8. **排期**：M4 再增后端约 23、前端约 6 人日（含 2026-11-07 追加的按已装引擎自动装配）（已扣除被取代的 PRS-06），M4 预计再延长约 2 周（到约 W75，F 阶段约 W76–W86）；吃紧时把图层分离（PRS-15）与查看器增强（FE-39）移到 M4 之后，M4 约 W74。M3 不变。

## 1. 「AST」到底指什么

负责人说的 AST，落到文档上是四样东西，缺一样都不够：

| 组成 | 含义 | 合同场景的用途 |
| --- | --- | --- |
| 章节树 | 章 → 条 → 款 → 项的嵌套结构，每个节点有层级、编号、标题与所辖内容范围 | 条款路径（「第二十二条第（三）款」）、按条款审查、目录导航 |
| 元素节点 | 段落、列表项、表格（含单元格）、图片、印章、签名、勾选框、填写位、公式 | 证据单元、表格取值 |
| 行内对象 | 段落内的手写片段、印章遮挡片段、公式、勾选符号、删除线；带字符区间 | 「这一句里的金额是手写的」这类细粒度判断 |
| 关系 | 题注 → 图表、续表 → 上表、键 → 值、交叉引用（「见第十条」）、补充协议 → 被修改条款 | 跨页表、表单类证照、条款引用核对 |

再加两层支撑：**图层**（同一页的原图、去水印图、去章图、印章层、手写层，各自来源与坐标对齐）与**字符级信息**（坐标、置信度、候选字），后者用于引文高亮与低置信定位。

## 2. 各家怎么出结构树

| 产品 / 方案 | 结构树 | 元素与关系 | 图层与专项 | 来源 |
| --- | --- | --- | --- | --- |
| TextIn xParse | `title_tree`（可选）：节点含元素 ID、标题、层级（1 为顶层）、页码、子节点；最多 6 级 | 15 种元素类型；`parent_id`、`children_ids`、`category_depth`、题注 `ref_element_id`、续接 `is_continuation` / `continuation_of`；行内对象（带字符区间）；字符级坐标、置信度、候选字 | 去水印、切边矫正；印章为图片子类型 `stamp`；手写为行内对象；有框 / 无框表；跨页表 `merged` 模式（来源区域、表头去重、单元格角色）；五种解析模式（auto、scan、parse、lite、vlm）；坐标为 0〜1 归一化四点 | [1][2][10] |
| 阿里云文档智能（文档智能解析） | `doctree` 模式：`docTree` 节点含层级、上级与下级链接（链接表，不是嵌套） | 版面元素含阅读顺序 `index`、类型与子类型（文档标题、段落标题、正文、表格、表名、表注、图、页眉页脚、目录、侧栏、脚注、公式等）、四点坐标；段落与表格键值对 | 未找到印章、手写、水印、勾选框类型；异步提交加轮询（建议 10 秒），结果保留 24 小时；PDF / Word ≤ 1000 页、100 MB | [7]（后半经摘要） |
| Google Document AI 版面解析 | 所有元素组织成树（`DocumentLayout`），分块带祖先标题 | 图、段落、表格、标题、页眉页脚，HTML / DOCX 加列表 | 未提印章、手写、水印、勾选框 | [8] |
| Reducto | 无层级字段，只有 Title / Section Header 顺序 | 10 种块，含 Checkbox、Key Value；0〜1 坐标；高 / 低置信 | 宣称支持手写表单、旋转页、嵌套表 | [9] |
| PP-StructureV3 | 无层级字段，只有文档标题、段落标题标签 | 17 或 23 类版面标签（含印章 Stamp / seal、页眉页脚、脚注、图表标题） | 印章检测与识别流水线；图表转表格；方向与矫正 | [4]（部分经摘要） |
| PaddleOCR-VL | 有「重建多级标题」的接口（经摘要，未核实输出格式） | 版面标签与阅读顺序 | 印章与图表识别默认关闭 | [4] |
| MinerU 4.x | 未找到标题层级字段 | 统一文档模型；中间 JSON 按页列出块（类型、序号、内容） | 跨页表合并；印章文字识别；未找到水印 | [5][6] |
| Docling | `body` 与 `furniture` 两棵树，`groups` 表示章节与列表 | 文本、表格、图片、键值对；JSON 指针引用 | 未提印章 | 调研 05 [12] |

**结论**：只有 TextIn、阿里云、Google 交付了显式的树；开源引擎都要自己重建。即便采购了带树的产品，也要映射成 Tioka 自己的树：各家层级定义不同（TextIn 按标题、最多 6 级；阿里云是链接表），而合同条款路径要按「第 X 条」「4.1.1」「（三）」这类编号规则确定，标题识别模型不一定把「第二十二条」判为标题。

## 3. 证照与票据结构化

| 方案 | 做法 | 引用回指 | 置信度 | 来源 |
| --- | --- | --- | --- | --- |
| TextIn 文档抽取 v3 | 只支持 JSON Schema 字段模式（Prompt 模式在 v2）；类型含字符串、数字、枚举、对象、数组；最多 3 层、≤ 100 个叶字段；可同时返回印章列表（颜色、形状、类型、文字、位置）；价格为解析的 2 倍 | 每个字段返回页码、位置、原文（快速开始与接口规格对默认值和坐标单位说法不一致，须实测） | 无字段级置信度 | [10] |
| TextIn 票据识别 | 40 多类票据（增值税发票、全电票、火车票、行程单、医疗票据等），支持 OFD | 未核实 | 未核实 | [11] |
| 百炼 qwen-vl-ocr 信息抽取 | 约 50 种常见证照与票据；自定义 `result_schema`（最多 3 层）或全量抽取；qwen3.5-ocr 加强了身份证、驾驶证等 | 抽取结果为键值，未见位置（未核实） | 未见 | [12] |
| PP-ChatOCRv4 | OCR + 版面 + 印章 + 大模型（需千帆或自部署 OpenAI 兼容端点）按给定键抽取 | 未写明 | 未写明 | [13] |
| 阿里云读光 OCR | 营业执照、身份证等专用接口按次计费（调研 05） | — | — | 调研 05 [21] |

**结论**：证照抽取没有一家能直接满足「每个字段有原文位置且可校验」：TextIn 有引用但没有置信度，qwen-vl-ocr 有类型覆盖但没有位置。Tioka 应当**先解析成 DocAST，再按 Schema 抽取，抽取结果的每个值必须回指到 DocAST 的块或字符区间并通过归一化比对**，比对不上置「待复核」。这与 ADR-037 的证据绑定、DOC-03 的引文校验是同一套机制。

租赁合同场景用得上的证照：承租方营业执照、法定代表人或经办人身份证、不动产权证书（或房产证）、授权委托书、租金与押金发票。它们通常作为合同附件一起上传，现在只会被当成普通页解析。

## 4. MinerU 4.x 的变化

| 项 | 内容 | 来源 |
| --- | --- | --- |
| 许可 | 3.1.0（2026-04-18）由 AGPLv3 改为「MinerU 开源许可」= Apache-2.0 + 附加条款（月活超 1 亿或月收入超 2,000 万美元需商业许可；基于 MinerU 向第三方提供在线服务须注明）；3.0.0 移除了两个 AGPLv3 模型和一个 CC-BY-NC-SA 模型 | [5][14] |
| 原生格式 | DOCX（3.0.0）、PPTX、XLSX（3.1.0）；另有 DOC、PPT、XLS、RTF、ODT 系列、EPUB、**OFD**、HTML、CSV；这些走 flash 档 | [5][6] |
| 质量档 | flash（原生文档、快速预览）、basic（OCR、公式、表格，小模型，无 VLM）、standard（复杂版面，小模型 + VLM，PDF 默认）、advanced（同 standard，更多推理算力） | [6] |
| 硬件 | 默认安装支持 CPU；CPU 12 核以上可用到 standard，4〜11 核到 basic；高吞吐部署建议 ≥ 16 GB 内存；Docker 镜像目前只有 NVIDIA 版 | [6] |
| 推理后端 | 小模型 ONNX / Torch；VLM 用 llama.cpp、vLLM、LMDeploy、MLX | [6] |
| 统一文档模型 | 一个文档模型渲染九种目标（Markdown、HTML、LaTeX、DOCX、EPUB、PDF、结构化内容、内容列表 V1 / V2）；中间 JSON 标识为 `docvortex.middle` 2.0 | [5][6] |
| 跨页表 | 2.2.0 起支持，此后多次改进，VLM 在 3.1.0 支持 | [14] |
| 印章、手写、水印 | 3.0.0 提到印章文字识别；手写只有缺陷修复；水印未找到 | [14] |
| 接口 | 4.1.0 统一为 `/v1/tasks`（破坏性变更），另有 `/v1/file_parse`；Docker Compose 提供 API、路由与 WebUI | [6][14] |
| 未找到 | 标题层级字段、关键信息抽取 | [6] |

**对 Tioka 的含义**：

- 调研 05 把 MinerU 列为备选的两个理由（许可要法务确认、没有印章）都已减弱：许可已不是 AGPL，附加条款对「企业内部私有化部署」影响很小，只需在产品文档中注明；3.0 起有印章文字识别。
- MinerU 4.x 原生支持 OFD、DOC、XLSX，覆盖了 ADR-060 规范化阶段里 LibreOffice 转换与 PRS-11（OFD）的大部分工作。
- MinerU 的 CPU standard 档对 12 核以上机器可用，私有化客户不一定有 GPU，这一点比 PaddleOCR-VL（推荐 GPU）更友好。
- 印章与手写专项仍是 PaddleOCR 更完整（印章检测与识别流水线、PP-OCRv5 手写）。
- 两者都不出标题层级，结构树仍要 Tioka 自己重建。

## 5. 与 ADR-060〜062 的差距

| # | 差距 | 原设计 | 建议 |
| --- | --- | --- | --- |
| H1 | 没有显式章节树 | 块只有 `parentId`、`level` | 契约增加 `tree`（章节节点：层级、编号、标题块、所辖块区间、子节点） |
| H2 | 结构重建只是一个「组装」阶段，没有规则与指标 | ADR-060 第 2 节阶段 8 | 独立的结构重建器：编号规则、字体特征、版面标题标签、引擎给的树作为提示，四路合并；目录页识别与对齐；评测指标 |
| H3 | 没有行内对象与字符级信息 | 块级 `text` 与 `confidence` | 增加 `inlines`（字符区间 + 类型 + 坐标 + 置信度）与可选 `chars`（按页分片存放） |
| H4 | 没有图层概念 | 只有页图 | 每页图层清单：原图、规范化图、去水印图、去章图、印章层、手写层；各层的来源引擎与坐标变换 |
| H5 | 路由按「页类型 × 阶段」，不按元素 | ADR-060 第 4 节 | 增加元素级路由：每种元素类型配专项处理器链 |
| H6 | 印章只有存在与文字 | ADR-062 第 2 节 | 增加印章颜色、形状、类型（公章、合同专用章、财务专用章、个人章等）；去章图上重新识别被遮挡文字 |
| H7 | 没有关系与键值对 | — | 增加 `relations`（题注、续表、键值、交叉引用） |
| H8 | 证照、票据没有结构化抽取 | 全文按普通页解析 | 文档与页的分类；`@doc.extract` 按 Schema 抽取并回指校验；预置证照 Schema |
| H9 | 默认引擎基于旧的 MinerU 认识 | PaddleOCR 为主，MinerU 在 M4 之后 | MinerU 4.x 为主、PaddleOCR 做印章与手写专项，以评测对比定稿 |
| H10 | 外购参考适配器选阿里云文档解析 | 阿里云未见印章、手写、水印 | TextIn xParse 为参考适配器（标题树、图层、印章属性、字符级、带引用的抽取齐全） |

## 6. 选项

### 选项 T：结构树由谁产生

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| T1 | 直接用引擎给的树（只在采购 TextIn 或阿里云时有） | 开源引擎没有树；换引擎即换结构；合同编号不一定被识别为标题 |
| **T2（推荐）** | Tioka 自建结构重建器，引擎给的树、标题标签、字体特征只作为输入信号，合同编号规则优先 | 与引擎无关；可用合同评测集衡量；工作量可控（规则为主） |
| T3 | 用大模型整体重排标题层级 | 灵活，但每份文档都要调模型、结果不稳定；只作为 T2 中歧义标题的兜底 |

### 选项 U：图层与元素专项能力从哪来

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| U1 | 全部自研（去水印、去章、曲面矫正、印章分类、手写识别） | 工作量大且难以追上专业产品，不推荐 |
| **U2（推荐）** | Tioka 自建图层模型与元素级编排；具体处理由引擎提供（TextIn 去水印与矫正、PaddleOCR 印章与矫正、MinerU 跨页表）；只自研低成本的兜底（红蓝印章颜色分离、二维码与条码解码） | 编排与契约在自己手里，能力随引擎升级 |
| U3 | 全部交给一家商业产品 | 最省事；锁定供应商；私有化与数据条款未知 |

### 选项 V：证照与票据结构化

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| V1 | 每类证照接一个专用识别接口（读光营业执照、身份证等） | 字段固定、无位置；类型一多接口就多 |
| **V2（推荐）** | 文档分类 → 按 Schema 抽取（默认 qwen-vl-ocr 信息抽取或通用视觉模型，TextIn 抽取为可选引擎）→ 每个值回指 DocAST 并归一化比对 → 不通过置待复核；预置 5 类证照 Schema | 与 ADR-037 证据绑定一致；新证照只加 Schema |
| V3 | 只做全文解析，证照字段由 Agent 在对话里自己读 | 无结构化结果，无法校验 |

### 选项 W：自研与采购

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| W1 | 全部采购 TextIn（解析 + 抽取 + 结构树），Tioka 只做适配 | 上线最快；TextIn 私有化与数据条款未知；`SECRET` 文档与不允许出网的客户无法使用；证据格式随供应商 |
| **W2（推荐）** | 自建契约、结构重建、图层与元素编排、抽取校验与评测；识别层私有化用 MinerU 4.x + PaddleOCR，云端可采购 TextIn | 核心可控，识别可替换；采购是加分项不是前提 |
| W3 | 全部自研识别模型 | 不现实 |
