## 0. 结论摘要

1. **零件不少，但没有「一根线」。** 设计里已有：审计表 `audit_event`（GOV-02）与哈希链封印（GOV-09）、OTel 链路（GOV-08）、Turn 轨迹视图（HCI-07）、编排 Run 的 why 时间线、配置变更记录 `cfg_change`（ADR-041）、每次模型调用的上下文清单（ADR-048）、变更单与回执 `trust_action`（ADR-033）、委派链审计字段（ADR-039）、通知投递 `ntf_delivery`（NTF-01）、外部 OCR 外发审计（ADR-061）。但它们各自定义、各自存放，**没有统一的关联键，也没有一个按「一次请求」或「一份合同」把它们排成一条时间线的视图**。负责人问的「能否从 Trace + Timeline 串起来」，按当前设计的回答是：**一次 Turn 内部能串（M2 后在 Jaeger 和轨迹视图里），跨 Turn、跨审批等待、跨编排 Run、跨外部系统、按业务对象都串不起来。**
2. **OTel trace 不能当审计用。** trace 按采样、保留期一般只有数天到数周、长时间的人工审批等待会把一次业务过程切成很多条 trace；它适合排障，不适合回答「这份合同从进来到发出通知，谁、哪个 Agent、调了哪些外部系统、依据什么」。需要一个**业务关联键（subject）+ 持久的时间线投影**，trace_id 只作为其中一个可跳转的字段。
3. **系统审计的设计基本齐，实现有明显缺口。** PR #24 里审计管道（切面、转发、查询、导出）已经可用，登录、登出、OIDC 登录、访问拒绝、出网拒绝、工具调用、用户与成员管理、Agent 发布已经写审计；但：① **全部审计记录的 `trace_id` 都是空的**，没有任何代码填它；② `AuditCoverageIT` 的白名单里挂着约 55 个「待补」写接口（模型供应商与 binding、路由计划发布、MCP 服务与授权、Flow 发布与运行、知识库与数据源、Skill 导入与发布、Chat、编排等），实际覆盖率不到一半，测试形同虚设；③ 工具调用审计写失败只打日志、切面只拦 `BizException`，与 ADR-017「业务成功则审计必有」不一致；④ 保留期清理任务会**物理删除**已转发的审计记录，违反第 13 条「只增不改不删，按保留策略归档」，并会使 GOV-09 的哈希链断裂；⑤ 登录审计的客户端 IP 直接取 `X-Forwarded-For` 第一段，可被伪造；⑥ 定时任务（审计转发、保留清理、配额落库）没有多实例互斥，双实例时会重复外送。
4. **运行记录（Agent、MCP、Skill、子 Agent）分散，缺「运行清单」与非 Turn 调用的记录。** Turn 内的模型调用、工具调用、审批已有 `runtime_item`、`model_usage`、`audit_event`；子 Agent 有委派链字段（M3）；MCP 调用经 ToolGateway 审计。但 Turn 级别没有记录当次实际生效的策略版本、授权书版本、授予、护栏策略版本、Skill 版本（单次模型调用的版本见 ADR-041 / 048），也没有覆盖**不在 Turn 里的模型调用**（入库嵌入、解析的视觉模型、护栏分类器、记忆抽取、评测裁判）把什么数据发往了哪个云端模型。
5. **与业务系统和外部系统的交互没有统一台账。** 入站（飞书回调、Webhook、A2A、业务系统事件、数据源同步）和出站（业务连接器写回、通知、外部知识库查询、外部 OCR、云端模型、MCP 远端）各有零散的「写审计」一句话，但字段、去重键、对方回执号（如飞书 `message_id`、邮件 `Message-ID`、业务系统单号）、请求与响应摘要、耗时、重试、数据标签都没有统一定义；**允许的出网请求不留任何记录**（只记拒绝）；飞书回调在审计覆盖测试中被直接豁免。出了纠纷时，无法回答「我们在什么时候、以什么身份、往业务系统写了什么、对方返回了什么」。
6. **防篡改与保留排得太晚、口径不一。** GOV-09 哈希链是 M4 P2，而合同场景 M3 就进影子期、M4 上岗；审计保留期在代码里是 365 天，ADR-053 写 Foundation 不少于 180 天，ADR-041 / 048 明细 180 天，`runtime_item` 没有保留期；没有法律保全（冻结删除）机制，也没有处理「记忆删除 / 个人信息删除」与「审计只增不删」的冲突。《网络安全法》第二十一条要求网络日志留存不少于六个月，这是下限。
7. **推荐方案（已写成 ADR）**：
   - ADR-072 统一审计事件模型：动作目录（登记制）、必填上下文（trace、关联键、主体链、来源、客户端）、写入失败语义、覆盖门禁、审计的审计、保留分级与归档（取代物理删除）、GOV-09 提前到 M4 前段并升为 P1；
   - ADR-073 关联上下文与 Trace 传播：`trace_id` 之外定义**关联上下文**（请求号、会话 / Turn / Run / 审批 / 变更单、业务主体 `subject`），沿 HTTP、outbox、MQ、审批挂起续跑、子 Agent、外部调用全程传播并写入所有记录表；
   - ADR-074 外部交互台账 `ext_interaction`：入站与出站统一一张台账，记录对方、身份、对方回执号、摘要与哈希、结果、重试、数据标签；
   - ADR-075 统一时间线与证据包：以 `subject`（如一份合同）或请求号为键的**时间线投影**，把审计、运行、审批、变更单、外部交互、通知、配置版本按时间排成一条，带 Jaeger 跳转；可导出签名的证据包。
8. **排期**：M1 收口 4.5 人日（属 GOV-02 原验收，应在 G1 前补完）；M2 新增约 8.5 人日，放进 M2 约 18% 的余量，不延长；M3 新增后端约 11、前端约 5 人日，M3 已无缓冲，预计再延长约 1 周到 W24–W57；M4 新增后端约 15、前端约 3 人日，M4 约到 W83，F 阶段约 W84–W94。备选：M3 只做合同时间线的最小版与外部交互台账（约 6 人日，不延长），统一时间线投影推到 M4 前段（第 8 节）。

## 1. 问题分解

负责人的问题拆成五个可以核对的子问题：

| # | 子问题 | 「完善」的标准 |
| --- | --- | --- |
| Q1 | 系统层面审计 | 登录与会话、身份与权限变更、配置变更（含模型、密钥、策略）、密钥访问、数据导出、管理员操作、访问拒绝都可查；记录不可被悄悄改删；保留期满足法规；谁看过审计本身也有记录 |
| Q2 | Agent / MCP / Skill / 子 Agent 运行记录 | 任一次运行能回答：谁发起、以谁的身份、哪个 Agent 哪个版本、用了哪些 Skill 和工具（哪个版本）、调了哪些模型（版本、上下文构成）、做了什么写操作、谁批准、结果如何；子 Agent 能回溯到根用户 |
| Q3 | 与业务系统、外部系统的交互记录 | 每一次进出系统边界的交互都有一条记录：方向、对方、身份、对方回执号、内容摘要与哈希、结果、重试、数据标签；能与内部运行关联 |
| Q4 | Trace（技术链路） | 一次用户请求从入口到每个模型 / 工具 / 外部调用，在一条 trace 里父子正确；跨异步边界不断 |
| Q5 | Timeline（业务时间线） | 按「一次请求」或「一个业务对象（合同）」看到从头到尾的事件序列，能跳到 trace、审计、轨迹细节；可导出为证据 |

## 3. 设计缺口（文档层面没有回答的问题）

| # | 缺口 | 现状 | 影响 | 严重度 |
| --- | --- | --- | --- | --- |
| D1 | **没有业务关联键** | 唯一的跨表关联是 `trace_id`；`model_usage` 甚至没有 `trace_id` 列（ADR-025 说有，表里没有）。合同、业务单号、审批、变更单之间靠各自外键，没有统一的「这件事属于哪个业务对象」 | 无法回答「这份合同的全过程」；审批等待数小时后续跑会生成新 trace，前后断开 | 高 |
| D2 | **没有统一时间线** | 轨迹视图只看一个 Turn；why 时间线只看一个编排 Run；ADR-041 只看配置；没有跨 Turn / Run / Flow / 审批 / 外部交互 / 通知的视图 | 法务、审计员、运维各自翻 5〜6 个页面拼图 | 高 |
| D3 | **审计事件没有目录与字段约束** | 20 多个 ADR 各写「写审计」，动作名、`details` 字段、必填项都没登记；`AuditCoverageIT` 自述「文档写白名单除外但未列明细（文档缺口）」 | 动作名漂移、查询口径不一、SIEM 侧无法建规则 | 高 |
| D4 | **外部交互没有统一记录** | 只有通知有 `ntf_delivery`；业务连接器写回、外部知识库、MCP 远端、Webhook 与 IM 入站、A2A、云端模型外发各说各的；出网只记拒绝 | 纠纷与追责时缺对方回执号和内容摘要；无法统计哪些数据去了哪个外部系统 | 高 |
| D5 | **审计写入失败语义不统一** | ADR-017 说同事务「业务成功则审计必有」；ToolGateway 的设计没规定审计失败时怎么办；独立事务写拒绝记录在数据库不可用时怎么办没写 | 实现各自处理，出现「静默丢审计」 | 中 |
| D6 | **保留与归档没有策略** | 第 13 条说「按保留策略归档」，但没有任何文档定义保留策略；各处保留期 180 / 365 天不一；`runtime_item` 无保留期；无法律保全 | 要么无限增长，要么被实现成物理删除（见 I4） | 高 |
| D7 | **防篡改排期晚** | GOV-09 在 M4、P2，且没有施工设计；合同场景 M3 影子、M4 上岗 | 上岗时审计仍可被有库权限的人改写而不被发现 | 中 |
| D8 | **审计的审计** | 谁查了审计、谁导出了审计、谁看了轨迹（轨迹里有合同原文与工具结果）没有设计 | 敏感数据经轨迹与导出外泄无痕 | 中 |
| D9 | **非 Turn 的模型调用无内容去向记录** | `model_usage.purpose` 记了用途和 token，但入库嵌入、解析视觉模型、护栏分类、记忆抽取、评测裁判把哪份文档、什么标签的数据发往哪个云端模型，没有记录（ADR-048 的上下文清单只覆盖 Turn 内） | 第 49 条允许 CONFIDENTIAL 合同进云端模型，但事后无法列出「哪些合同发给了哪家模型」 | 中 |
| D10 | **Turn / Run 级运行清单** | 单次模型调用的版本由 ADR-041 / 048 覆盖；但 Turn 或 Run 当时生效的授权书版本、Cedar 策略版本、授予、护栏策略版本、Skill 版本、工具快照没有一处汇总 | 复盘「为什么当时放行了」要翻多张表并按时间推断 | 中 |
| D11 | **OTel 采样与保留、日志聚合未定** | 采样率写死 1.0；没有尾部采样策略；没有日志聚合方案（41-TA 只写「Loki / 等价」）；审计管道自身无健康指标 | 生产量大时要么成本高、要么错误 trace 被采掉；日志与 trace 无法互跳 | 低〜中 |
| D12 | **定时任务多实例互斥** | 第 4 条后系统按多实例设计，但没有任何文档规定 `@Scheduled` 任务的互斥机制（outbox 中继有单独设计） | 审计重复外送、保留清理并发、配额落库重复 | 中 |
| D13 | **客户端来源可信度** | 没有规定可信代理与 `X-Forwarded-For` 的处理 | 登录审计里的 IP 可被伪造 | 低 |

## 4. 实现缺口（main + PR #24 的代码）

只列与审计和可观测有关的项；其他问题见 PR #24 评审。

| # | 缺口 | 证据 | 与设计的关系 | 严重度 |
| --- | --- | --- | --- | --- |
| I1 | **`trace_id` 全部为空** | `AuditedAspect`、`DefaultToolGateway`、`AuthService`、`OidcFederationService`、`DefaultEgressGuard`、`RestAccessDenied` 构造审计时都不设 `traceId`；`AuditService.write` 也不补；项目里没有引入 OTel，MDC 只放了 `uid`、`ws` | 违反 ADR-017 / 025「审计带 traceId 可互相跳转」 | 高 |
| I2 | **写接口审计覆盖不到一半** | 各模块写接口与审计：agent 8 / 1 个文件、chat 8 / 0、flow 6 / 0、knowledge 7 / 0、mcp 5 / 0、model 8 / 0、orchestration 8 / 0、skill 2 / 0、server 运维门面 9 / 0；`AuditCoverageIT` 白名单里「待各域补 @Audited」约 55 条，包括**模型供应商（含密钥）、路由计划发布、MCP 授权、Flow 发布、Skill 发布**这些高敏操作；ENG-06 后又发现 5 个写接口漏挂 | GOV-02 验收「任意写操作可在审计中查到」实际未达成 | 高 |
| I3 | **审计失败被吞或漏记** | `DefaultToolGateway.auditInvoke` 捕获异常后只 `log.warn`；`AuditedAspect` 只处理 `BizException`，其他运行时异常（数据库、空指针）不记 ERROR | 违反 ADR-017「业务成功则审计必有」；失败操作无痕 | 高 |
| I4 | **保留清理物理删除** | `AuditForwarder.purgeExpired` 每天删除 365 天前且已转发的 `audit_event` | 违反第 13 条；GOV-09 启用后会破坏链 | 高 |
| I5 | **客户端 IP 可伪造** | `AuthController.clientIp` 直接取 `X-Forwarded-For` 第一段；`AuditedAspect` 不记 IP | — | 中 |
| I6 | **定时任务无互斥** | `AuditForwarder`（转发、清理）、`QuotaFlusher`、`QuotaReconciler`、`ReindexJob` 等均为裸 `@Scheduled`，项目里没有分布式锁 | 双实例时 SIEM 收到重复记录；清理与转发并发 | 中 |
| I7 | **审计查询能力弱** | 查询条件没有 `trace_id`、Turn、会话；分页用偏移量（大表慢）；导出单次最多 10 万行，未记录「谁导出」 | — | 中 |
| I8 | **工具审计缺主体链与版本** | `tool.invoke` 的 `details` 有 threadId、turnId、origin，但没有 Agent 版本、runAs 与发起人的区分、审批 ID；`argsPreview` 截前 500 字符 | MAS-01 前可接受，但 M1 应先放 Agent 版本与审批 ID | 低 |

## 6. 目标模型：三种记录、一套关联键

不把所有东西塞进一张表，而是明确三种记录各自的职责，再用同一套关联键串起来：

| 记录 | 回答什么 | 存储 | 保留 | 是否防篡改 |
| --- | --- | --- | --- | --- |
| **审计**（`audit_event`） | 谁、以谁的身份、对什么、做了什么、结果、依据（策略 / 审批） | 主库，只增；按月分区；冷归档 | 安全类 ≥ 1 年；业务类随业务主体 | 是（哈希链） |
| **运行记录**（`runtime_item`、`model_usage`、上下文清单、`flow_node_run`、`orch_decision`、`trust_action`、运行清单） | 过程细节：每一步的输入输出、版本、用量 | 主库；大内容进对象存储 | 明细 180 天，业务主体相关的随主体 | 运行清单与变更单进链，明细只记哈希 |
| **外部交互台账**（`ext_interaction`） | 跨系统边界的每一次往来 | 主库，只增 | 与审计同级 | 是 |
| **Trace**（OTel） | 技术链路与耗时，用于排障 | 客户的 APM / Jaeger | 天到周 | 否 |
| **时间线**（`timeline_entry`，投影） | 按业务主体或请求的事件序列 | 主库，由上面几类异步投影生成，可重建 | 随来源 | 不单独防篡改（可从来源重建并校验） |

**关联键**（ADR-073）：每条记录都带 `trace_id`、`request_id`（入口生成，跨异步不变）和 `subject`（业务主体引用，如 `lease.contract:HT-2026-0012`），按需带 `thread_id`、`turn_id`、`run_id`、`flow_run_id`、`approval_id`、`change_set_id`、`grant_id`。trace 断了，request_id 和 subject 不断。

以合同为例，时间线应能显示：业务系统推送合同（入站交互）→ 编排接单（Run）→ 文档解析与 OCR（外发记录）→ 抽取与判断（Turn、子 Agent、模型调用）→ 规则求值 → 生成审查草稿（变更单）→ 法务审批 → 写回业务系统（出站交互、对方单号）→ 飞书与邮件通知（投递与回执）→ 法务处置与原因码（反馈）→ 期间相关配置发布（别名、要点表达式版本）。

## 7. 方案选项与推荐

### 7.1 关联与时间线（A）

| 选项 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| A1 只靠 OTel | 所有东西挂在 trace 上，时间线就是 Jaeger | 不新增存储 | 采样、保留短、审批等待切断、业务人员不会用 Jaeger |
| **A2 关联键 + 时间线投影（推荐）** | 统一关联上下文传播；各记录表带关联键；异步投影到 `timeline_entry`；UI 下钻到原记录与 trace | 持久、按业务对象查、可重建、可导出 | 新增一张投影表与一个消费者 |
| A3 外部事件平台 | 全部事件送到 Kafka + ClickHouse / ES，时间线在外部平台 | 量大时扩展性好 | 私有化部署多一套组件；权限与数据标签要在外部再做一遍 |

### 7.2 外部交互（B）

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| B1 各自写审计 | 维持现状，每个适配器自定 `details` | 字段不一，无法统一统计 |
| **B2 统一台账（推荐）** | `ext_interaction` 一张表，`EgressClient` 与各入站入口统一写；通知、连接器、外部知识库、OCR、MCP 远端、云端模型都走它 | 一处实现，可按对方与数据标签统计 |
| B3 网关旁路 | 在出网代理（如 Envoy）记录 | 拿不到业务身份与关联键，HTTPS 内容不可见 |

### 7.3 防篡改（C）

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| C1 维持 GOV-09 M4 P2 | — | 上岗时无防篡改 |
| **C2 GOV-09 提前到 M4 前段、P1，链覆盖审计与外部交互、运行清单（推荐）** | 封印任务 + 外部锚点（SIEM / 对象存储 WORM）；数据库层对审计表撤销 UPDATE / DELETE 权限 | 合同上岗前具备；成本小 |
| C3 M3 就做 | — | M3 无缓冲；影子期不产生真实业务后果，必要性不足 |

### 7.4 排期（D）

| 选项 | 内容 | 影响 |
| --- | --- | --- |
| **D1 推荐** | M1 收口 4.5；M2 8.5（进余量）；M3 后端 11 + 前端 5；M4 后端 15 + 前端 3 | M3 +1 周到 W57；M4 约到 W83；F 约 W84–W94 |
| D2 M3 不延长 | M3 只做合同时间线最小版（按关联键联合查询、不建投影）与外部交互台账（约 6 人日，用 BE-B / BE-C 的 P1 让路） | 统一时间线投影、证据包、审计的审计推到 M4 前段；M4 约到 W84 |
| D3 全放 M4 | M3 只做 M1、M2 的收口 | 合同影子期没有时间线，复盘靠人工拼表 |

**推荐 A2 + B2 + C2 + D1**，理由：合同场景的价值在于「可追责的自动化」，影子期正是需要逐份复盘的时候，时间线与外部交互台账应在影子期前就绪；防篡改在真实上岗（M4）前就绪即可。
