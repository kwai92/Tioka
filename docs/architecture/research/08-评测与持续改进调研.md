## 0. 结论摘要

1. **Tioka 的评测「零件」大多已经有了，缺的是把它们串起来的规程和统计口径。** ADR-031 有数据集、评估器 SPI、批次评测、线上采样、实验、经验库和发布回归门禁；ADR-034 有影子上岗和 Wilson 区间；ADR-056、ADR-062、ADR-066、ADR-067 各有自己的评测集与闸门；ADR-041 有版本对比统计。但：① 没有「一个新场景 Agent 从立项到上线」要过哪些关、每关看什么的统一规程；② 评测集怎么建、怎么切分、谁来标、标签怎么随规范变化，没有规定；③ 模型打分（LLM-as-a-Judge）没有和人工标注做过一致性校准；④ 发布门禁「总分低于稳定版 2 个百分点就阻止」不考虑样本量和噪声，在小评测集上既会误拦也会漏拦；⑤ 模型选型没有流程，别名与路由计划一发布就对全平台生效、没有灰度；⑥ 法务驳回只有自由文字原因，进不了正反例。
2. **评测集从 20〜50 条真实失败开始就够用，关键是分层和保密。** Anthropic 的智能体评测指南建议从真实失败中取 20〜50 个任务起步，正例与反例要平衡，每个任务要能让两位领域专家独立得出相同结论，并且要有一个能通过全部检查的参考答案 [1]。能力评测（还有爬坡空间）与回归评测（应接近 100%）要分开，能力评测饱和后转入回归 [1]。Tioka 需要加一层**密封集**：不参与任何调参、只在准入时使用，防止团队对开发集过拟合。
3. **小样本下必须报区间、做配对比较。** Anthropic 的统计建议：每个分数附标准误；同一份材料派生的多道题要按材料聚类计算标准误（热门评测上聚类标准误可达朴素值的 3 倍以上）；比较两个版本用同一批题的**配对差异**，不用两样本检验；对有推理过程的任务每题多次采样取平均以降低方差；事先做功效分析决定题量 [2]。合同审查一份合同派生约 20 个必备要点，正是「聚类」场景。按估算，30 份合同的密封集做配对比较，能可靠分辨约 4〜5 个百分点以上的差异（第 4 节）；更小的差异只能报「不显著」，不能当作「没退步」。
4. **一次跑通不等于稳定。** pass@k（k 次里至少成功一次）随 k 上升，pass^k（k 次全部成功）随 k 下降：单次成功率 75% 的任务，3 次全成功只有约 42% [1]；τ-bench 提出 pass^k 正是为了衡量面向客户的 Agent 的一致性 [3]。业务结论类 Agent（合同审查）应以 pass^k 或「多次运行结论一致率」作为准入指标之一。
5. **模型打分要先被人工校准，校准的标准是 κ 而不是一致率。** 2026 年对 21 个裁判模型、约 54 万次判断的研究发现：只看完全一致率会高估裁判质量（κ 比一致率低 33〜41 个点）；裁判在不同基准上的排名可相差 14 位；重测信度 > 0.95 的裁判同时可以有 > 0.10 的位置偏差——「稳定」不等于「正确」[4]。另一项研究发现格式偏好（偏爱 Markdown）是最大的偏差，不同模型族的长度偏好方向相反 [5]。实践建议：人工标注一个校准集并保留不调参的留出部分，先测人与人之间的一致性，再测裁判与人的 Cohen's κ，κ 低于约 0.6 时改评分细则；报告裁判模型、提示版本与校准集规模；裁判、提示或任务变化后重新校准 [6]。**能用规则判的不用模型判**：合同四态结论与金标准逐项比对是规则评估，只有理由与建议文字的质量才需要裁判。
6. **上线要过「离线 → 影子 → 灰度 → 正式」四关，低流量场景的灰度要改成「双跑」。** 业界的模型发布做法是：影子（复制流量给候选版本、只返回旧版本结果，24〜72 小时）→ 按用户哈希的 1%〜10% 金丝雀 → A/B；模型版本与 Prompt 版本作为一个发布单元一起记录、一起回滚，回滚要是一次配置写入而不是一次部署 [7]（二手资料）。但合同审查每天约 10 份，按比例分流的金丝雀在统计上没有意义（A/B 检出 5% 的效果一般需要每组数万次会话 [7]）。适合 Tioka 的做法是**双跑灰度**：新版本对 100% 的真实输入在后台运行，结果不展示，与在岗版本以及法务最终结论做配对比较；高流量的对话型 Agent 才用按用户哈希的比例灰度。
7. **模型选型是一个漏斗，不是一张排行榜。** 公开基准和厂商排名只能做第一轮筛选：ContractEval 在 CUAD 上测 19 个模型做条款级风险识别，闭源模型 F1 约 0.64，最好的开源（Qwen3 8B 思考模式）0.54；思考模式通常提高定位精度但降低 F1；不同模型把「没有相关条款」误报的比例从 0 到约 31% 不等；FP8 量化略降、开思考时降得更多 [8]。这些差异在通用排行榜上看不出来，必须用**本场景的评测集、按角色**（抽取员、判断员、复核员、决策器、裁判）分别选，并同时看质量、成本、时延、稳定性和数据合规。
8. **国产模型的版本与价格变化很快，选型结论要能复跑。** DeepSeek 2026 年 4 月发布 V4-Pro 预览，5 月 22 日把 V4-Pro 价格永久下调 75%，7 月 31 日发布正式版 V4-Flash，8 月 13 日发布正式版 V4-Pro 并把部分价格上调最多 1100%（经摘要）[9]；阿里 Qwen3.8-Max 处于预览阶段 [10]。结论：选型报告要记录模型快照版本与当时单价，**调价超过阈值、发布新快照、厂商下线公告、夜间哨兵评测出现漂移**时自动触发复评；生产引用固定快照，不引用「最新版」。
9. **反馈回流的关键是区分「Agent 错了」和「业务改了主意」。** 法务改判不一定是 Agent 的错：可能是原文读错（解析）、取值错（抽取）、规则不当（要点表达式）、判断错（模型），也可能是业务接受该风险、或规范已经变了。只有带结构化原因码的反馈才能分诊到正确的改进手段；「业务接受风险」不能成为反例，「规范变化」要让旧标签失效而不是变成反例。分诊后：确认是 Agent 错误的进入回归集（反例），被法务原样接受的高置信结论按比例进入正例；改进手段（改规则、改 Prompt、加经验、换模型）都要再过准入。
10. **排期**：M3 只加合同场景上线前必须有的三件事——评测集规范与配对统计（并入 EVO-02）、法务处置原因码与最小分诊、合同场景的模型选型最小版，后端约 6 人日，M3 预计延长约 1 周到 W24–W56；裁判校准、上线准入单、双跑灰度、别名灰度、哨兵评测、选型全量、分诊全量、标注台放 M4，后端约 29、前端约 8 人日，M4 预计再延长约 2.3 周到约 W81，F 阶段约 W82–W92；M4 吃紧时 EVO-15 标注台、FE-45、按比例灰度移到 M4 之后，M4 约到 W80（第 10 节）。

## 1. 问题分解

### 1.1 负责人的两个问题

| 问题 | 实际要回答的 |
| --- | --- |
| 上一个新的场景 Agent 时如何评测 | 上线前：成功标准怎么定、评测集怎么建（多少条、从哪来、谁标）、用什么判（规则、模型、人）、过什么门槛；上线时：影子期多长、怎么和人比、怎么灰度；上线后：怎么监控、什么情况回滚、反馈怎么回来 |
| Agent 做模型选型时如何评测 | 候选从哪来、先用什么筛、在什么数据上比、比哪些维度（质量、成本、时延、稳定、合规）、比几次、差多少算「有差别」、多个角色怎么分别选、换模型后怎么平稳切换、什么时候重新选 |

### 1.2 评测对象的层次

一个场景 Agent 的结果由多层决定，评测要能把错误归到层上，否则「分数下降了」无法行动：

| 层 | 合同审查中的例子 | 已有评测 |
| --- | --- | --- |
| 解析 | 扫描件金额读错、条款树建错 | ADR-062 解析评测集（30 份）与八项指标 |
| 检索 | 判断员没找到相关条款与案例 | ADR-056 Recall@5、MRR、忠实度 |
| 抽取 | 免租期取值错、证据回指错 | ONT-09 模型层评测、SCH-05 字段级评测 |
| 结构化输出 | 输出不符合 Schema、兜底率高 | ADR-066 首次通过率、最终失败率 |
| 规则 | 要点 CEL 表达式不当 | 无（靠法务驳回暴露） |
| 判断 | 「不满足」漏判 | LSE-08 四态一致率、召回率、精确率 |
| 安全 | 合同中的注入改了结论 | ADR-067 护栏评测集 |
| 端到端 | 提交到草稿 30 分钟、成本 | LSE-08 时延；ADR-041 统计 |

### 1.3 合同场景的现实约束

- **量小**：每天约 10 份合同（负责人 2026-11-05 的数据）。上线后一个月约 200 份，任何线上统计都在小样本区。
- **标注贵**：唯一可信的标注者是法务，M3 只排了约 8 人日法务投入（M3-04 第 5 节）。
- **标签会变**：要点库是版本化的，法务负责人会改阈值和表达式（M3-04 LSE-04）；旧合同在旧规范下的「正确答案」在新规范下可能不正确。
- **代价不对称**：漏掉一个必备「不满足」远比多报一条误报严重（M3-04 已定召回率门槛高于精确率）。
- **影子期免费产出标签**：影子期的前 50 份合同法务照常人工审查，他们的结论就是现成的金标准，不需要另外标注。

## 2. 业界做法

### 2.1 Anthropic：智能体评测指南（2026-01）[1]

- 术语：**任务**（一组输入与成功标准）、**试验**（一次尝试，因输出有随机性要跑多次）、**评分器**（一个任务可有多个，每个有多条断言）、**轨迹**、**结果**（环境的最终状态，例如数据库里是否真有这笔预订，而不是 Agent 说「已预订」）。
- 评分器三类：代码（快、便宜、客观、可复现，但对合理变体脆弱）、模型（灵活、能处理开放输出，但不确定、需要与人校准）、人工（金标准，但贵且慢，用于校准模型评分器）。
- **评结果，不评路径**：死板地检查步骤顺序过于脆弱；多部件任务给部分分。
- 建集：从人工检查、缺陷单、客服队列中的真实失败取 20〜50 个任务起步；正反例平衡（如「该搜索」与「不该搜索」都要有）；每条试验从干净环境开始，避免共享状态；在多次试验中通过率为 0 更可能是任务本身坏了。
- 能力评测与回归评测分开；读轨迹，确认失败「看起来公平」；给裁判「无法判断」选项以减少幻觉；每个评分维度用单独的裁判。
- 评分器缺陷会严重扭曲结论：文中举例，某模型在 CORE-Bench 上因评分过严（拒绝 96.12 与 96.124991… 的差别）只得 42%，修正评分后为 95%。

### 2.2 统计方法 [2]

| 建议 | 做法 | 对 Tioka 的意义 |
| --- | --- | --- |
| 报标准误 | 均值 ± 1.96 × 标准误 | 报告里每个指标附区间 |
| 聚类标准误 | 按随机化单位（一篇材料）聚类 | 合同场景按合同聚类，否则区间偏窄 |
| 降低题内方差 | 有推理的任务每题多次采样取均值 | 准入评测每条用例跑 3 次 |
| 配对差异 | 两个版本在同一批题上比较；配对后方差随两者相关性上升而下降，前沿模型间相关约 0.3〜0.7 | 版本对比、模型对比一律配对 |
| 功效分析 | 按「A 比 B 高 3 个百分点」这类假设反推题量 | 评测集规模由要分辨的差异决定 |

### 2.3 裁判模型的可靠性 [4][5][6]

| 发现 | 来源 |
| --- | --- |
| κ 比完全一致率低 33〜41 个点；排名随基准变化最多 14 位；高重测信度可与严重位置偏差并存 | Norman 等，2026-06，21 个裁判、约 54 万次判断 [4] |
| 格式偏好（偏爱 Markdown）0.10〜0.76，是最大偏差；位置偏差 ≤ 0.04；长度偏好方向因模型族而异；思维链作为默认缓解手段 | Soumik，2026-04（后半部分经摘要）[5] |
| 校准流程：专家标注含难例的代表集并留出；先测人与人一致性；Cohen's κ（两人）/ Fleiss' κ（多人）；κ 低于约 0.6 时改细则；看混淆矩阵区分「误放」与「误杀」；交换顺序测位置偏差、构造等内容不同长度测长度偏差、「对但粗糙」与「错但漂亮」测文风偏差；裁判、提示、任务变化后重新校准 | MLflow，2026-10（厂商文章，所引研究未逐一核实）[6] |

### 2.4 发布：影子、金丝雀、A/B [7]

二手资料（个人技术博客，部分数字无出处），只取做法：

- 模型升级与代码发布不同：失败不报 5xx，表现为 Schema 漂移、能通过评测的语义漂移、时延与成本变化；真值慢且稀疏。
- 影子：复制流量给候选，只返回在岗结果，24〜72 小时，推理成本约翻倍。金丝雀：按用户哈希从 1%〜10% 起，每档停留约 24 小时。A/B：要证明「更好」而不只是「安全」，需要大样本。
- 每档放量前的检查：Schema 符合率与解析成功率不低于基线、P95 时延不超过基线 10%；多项不达标自动回退到 0%；回滚应在 5 分钟内完成且是配置写入。
- 把「模型版本 + Prompt 版本」（以及知识库快照）作为一个原子发布单元记录与回滚；生产固定模型快照（例如带日期的版本），不用「latest」。
- 观察指标：Schema 符合率、拒答率、输出长度分布、与在岗输出的相似度（只作变化信号，不作质量分）、分段时延与单次成本、重新生成率与点踩率。

### 2.5 产品对照

| 产品 | 相关能力 | 可借鉴 |
| --- | --- | --- |
| 阿里云百炼应用评测 [11] | 评测任务绑定已发布的评测集版本与应用（智能体或工作流）；评估器需把变量映射到评测集字段或应用输出（含轨迹）；建议每任务 3〜5 个评估器、最多 10 个；人工标签打标，有快速标注模式；任务创建后配置不可改 | 评测运行不可变、评估器变量映射、人工标签与自动评估并存 |

| 阿里云 PAI 裁判员模型 [12] | 输入问题与回答，返回分数与理由；先做场景分类再套用不同标准；可在线或离线批量调用 | 可作为一个外部裁判适配器，但须先过第 2.3 节的校准 |
| Langfuse [13] | 数据集与实验、线上评估、标注队列、模型打分 | 标注队列与线上评估的对象模型 |
| Braintrust / Promptfoo [14] | 实验对比、CI 回归闸门 | CI 闸门做法（ADR-030 已有录制回放） |

Tioka 不接入这些平台作为评测底座（ADR-031 已定：评测建立在 Runtime 自带轨迹上，不另接 SDK），只借鉴对象模型与流程。

### 2.6 一致性：pass^k [1][3]

τ-bench 在工具 + 用户模拟的真实领域任务上提出 pass^k，衡量 k 次独立运行全部成功的概率，用于暴露「平均分不错但不稳定」的 Agent [3]。对合同审查，「同一份合同跑 3 次，必备要点结论完全一致的比例」比单次一致率更能说明是否可交给法务信任。

## 3. 评测集工程

### 3.1 分层

| 层 | 用途 | 规模（合同场景） | 规则 |
| --- | --- | --- | --- |
| 冒烟集 | 每次提交、CI 录制回放 | 5 份合同 | 只看能跑通、结构化输出零失败 |
| 开发集 | 日常调 Prompt、调规则、选模型时反复用 | 起步 10 组样本租约（M3-04 已有），逐步到 30 份 | 团队可以看、可以针对它改 |
| **密封集** | 只在准入评测与模型选型终选时使用 | 起步 20 份（取自影子期 50 份中的留出部分），目标 30 份 | 只有评测负责人能看用例内容；任何人不得据其改 Prompt；每季度轮换 1/3 进开发集，补入新的线上样本 |
| 回归集 | 曾经出过错、修好后不能再错的用例 | 随反馈增长 | 必须全过（逐条，不看平均）；来自第 7 节的反馈分诊 |
| 专项集 | 解析、检索、护栏、结构化输出 | 各 ADR 已定 | 由各自 ADR 管 |

### 3.2 切分单位

一份合同派生多个要点、多个字段。**切分与统计都以合同（合同链）为单位**：同一合同链的主合同与补充协议必须在同一层，否则同一份原文同时出现在开发集与密封集，密封失效。

### 3.3 用例卡

每条用例除了输入与期望，还需要：来源（手工、导入、线上、影子期、反馈）、来源 Turn 或合同、标注人与复核人、标注规范版本、**适用的要点库版本与生效日期**、难度与类别标签（扫描件、补充协议、多门店……）、数据标签（ADR-040）、是否为反例、冲突记录。没有这些字段，标签变旧、密封失效、分层统计都无从谈起。

### 3.4 标注

- 开发预标、法务只看「不满足」与有争议的结论（M3-04 已定），继续沿用。
- 双人标注只用于**校准集**与**密封集**中的争议项：两人独立标，不一致的进入仲裁；人与人的 κ 是裁判 κ 的天花板 [6]。
- 标注规范（要点的判定口径）本身是版本化文档，变更时受影响的用例标记为「待重标」，不自动沿用旧标签。

## 4. 统计口径（以合同场景估算）

假设密封集 30 份合同、每份约 20 个必备要点，共约 600 个判定点；两版本配对比较时结论不一致的点约占 10%。

| 量 | 估算 | 说明 |
| --- | --- | --- |
| 单版本一致率的 95% 区间半宽（按 85%、600 点、设计效应 2） | 约 ±4 个百分点 | 设计效应来自按合同聚类；实际值以评测数据计算 |
| 配对差异的 95% 区间半宽 | 约 ±3.5 个百分点 | 配对把共同难度消掉，比两样本窄 |
| 可可靠分辨的差异 | 约 4〜5 个百分点 | 更小的差异报「不显著」 |
| 「不满足」召回率 | 法务判不满足的点可能只有约 60 个，区间半宽约 ±8 个百分点 | 召回率门槛判断要看区间下界，样本不足时扩充含「不满足」的合同 |

以上是规划用估算，不是承诺；评测报告按实际数据计算聚类标准误。推论：

1. 「比稳定版低 2 个百分点就阻止」（EVO-06）在这个规模下是噪声，应改为**非劣效判定**：配对差异的区间下界不低于 −容差（缺省 3 个百分点）才算通过；区间太宽无法判定时转人工审批并附报告，而不是自动放行或自动拦截。
2. 关键子集（回归集、必备「不满足」）逐条判定，不受平均分掩盖。
3. 召回率这类分母小的指标，用 Wilson 区间下界判断门槛（ADR-034 已用于晋级）。

## 5. 上线前后的闸门

### 5.1 场景 Agent 的生命周期

| 阶段 | 做什么 | 出口条件 |
| --- | --- | --- |
| E0 立项 | 写**场景评测规格**：业务目标、风险等级、成功标准、指标与门槛、评测集计划、标注人与人日、影子期计划 | 业务负责人与 Agent 负责人签字 |
| E1 开发 | 开发集 + 冒烟集迭代；按角色选模型（第 6 节） | 开发集达到门槛 |
| E2 准入 | 密封集 × 3 次运行；专项评测（解析、检索、结构化、护栏）；成本与时延；**上线准入单**汇总 | 全部硬门槛通过，软门槛有签字说明 |
| E3 影子 | 真实输入、结果不展示，与人工结论比对（ADR-034 TRU-11；M3 合同场景用业务系统可见性开关） | 影子一致率区间下界达标；上岗报告；负责人确认初始自治等级 |
| E4 灰度 | 新版本：双跑或按比例（第 5.3 节） | 配对比较非劣效、线上指标无告警 |
| E5 在岗 | 线上采样评测、哨兵评测、反馈分诊、抽检（ADR-034） | 告警即回滚或降级 |

### 5.2 变更分级

已上线的 Agent 每一次变更都按影响面走不同的关：

| 变更 | 例子 | 最低要求 |
| --- | --- | --- |
| C0 不影响行为 | 文案、展示 | 冒烟集 |
| C1 局部 | 单个要点表达式、单个 Prompt 片段、经验条目 | 开发集 + 回归集；涉及的要点在密封集上非劣效 |
| C2 全局 | 换模型、换路由计划、换解析方案、改输出 Schema、改检索配置 | 完整准入（E2）+ 双跑灰度（E4） |
| C3 新场景或新动作类别 | 新 Agent、新增写操作 | 全流程 E0〜E5 |

**平台侧变更也要能找到受影响的 Agent**：ADR-041 规定别名与路由计划「跟随」，一发布就对全平台生效，这意味着系统管理员换一个模型就是对所有引用它的 Agent 做了一次 C2 变更却没有评测。需要：发布前影响分析里列出引用方中「绑定了准入评测集」的 Agent，自动对它们跑一次准入评测；结果不达标时发布需要二次确认；并提供按 Agent 的分批切换（别名灰度）。

### 5.3 灰度方式的选择

| Agent 类型 | 流量 | 灰度方式 |
| --- | --- | --- |
| 业务结论类（合同审查）、工单类 | 低（每天数十次以下） | **双跑**：新版本对全部真实输入后台运行，结果不可见；与在岗版本、与人工最终结论做配对比较；默认 10 个工作日或 50 个用例 |
| 对话类、问答类 | 高 | 按用户哈希的比例灰度（5% → 25% → 100%），每档至少 24 小时；看点踩率、重新生成率、结构化失败率、时延、成本 |
| 只读类 | 任意 | 可直接按比例灰度 |

回滚是一次配置写入：Agent 版本指针（ADR-023）与别名指针（ADR-041）都已支持；灰度只是让「当前版本」在一段时间内有两个，按规则分流。

### 5.4 上线后的监控

- **线上采样评测**（EVO-03 已有）：无标准答案的评估器。
- **哨兵评测**：每晚用**生产配置**（当前别名指向的实际模型）跑密封集的一个固定子集（如 5 份合同），检测供应商悄悄更新、价格调整后路由变化、知识库变化带来的漂移；差异超过阈值告警。这是对 ADR-062「夜间回归」、ADR-066「夜间回归」的统一。
- **反馈指标**：按要点的驳回率、修改率（M3-04 已有周报）。
- **业务指标**：法务处理时长、价值账本（ADR-035）。

## 6. 模型选型

### 6.1 选型漏斗

| 轮 | 做法 | 淘汰条件 |
| --- | --- | --- |
| 0 准入过滤 | 数据标签与部署形态（`SECRET` 只能私有，ADR-040）、供应商留存与训练条款、上下文长度、工具调用、视觉、结构化能力记录（ADR-066，一致性测试通过）、区域与合规 | 任一硬条件不满足 |
| 1 冒烟 | 开发集中 5 份合同，跑 1 次 | 结构化最终失败或证据绑定错误 |
| 2 开发集 | 开发集全量，每份 3 次 | 质量明显落后（配对差异区间上界 < 0）且不更便宜 |
| 3 终选 | 密封集，每份 3 次，与在岗模型配对 | 生成帕累托表：质量、pass^k、成本、P95 时延、错误率 |
| 4 双跑 | 第 5.3 节 | 非劣效且线上无告警 |

### 6.2 按角色选

合同审查有多个模型调用角色，最优模型往往不同：

| 角色 | 关键指标 | 常见取向 |
| --- | --- | --- |
| 抽取员（字段与证据） | 字段准确率、证据绑定、结构化首次通过率 | 支持严格 Schema、长上下文、价格低的模型 |
| 判断员（要点结论） | 必备「不满足」召回率、四态一致率、pass^3 | 推理强的模型；思考模式要实测（ContractEval：思考模式可能降低 F1 [8]） |
| 复核员 | 与判断员的分歧检出率 | 与判断员**不同模型族**（ADR-024 模型多样性约束） |
| 路由与决策器 | 准确率、毫秒级时延 | 小模型或向量匹配 |
| 裁判（评测用） | 与人工的 κ | 与被测模型不同族；不能用被测模型给自己打分 |

### 6.3 成本与时延的测法

- 成本按**实测 token**（不同模型分词差异大）× 当时单价，含缓存读写价（ADR-049）、思考 token、修复与降级的额外调用（ADR-066）；报「每份合同成本」而不是「每百万 token 单价」。
- 时延报端到端 P50 / P95，含排队与限流等待；思考模式单独报。
- 稳定性：评测期间的错误率、限流次数、故障接力次数（ADR-024）。

### 6.4 国产模型的特殊点

| 点 | 说明 | 处理 |
| --- | --- | --- |
| 版本命名 | 百炼区分快照（带日期）、稳定版与最新版；DeepSeek 的正式版与预览版在 2026 年多次切换 [9] | 生产绑定固定快照；引用「最新版」时管理页标警告 |
| 价格变动 | DeepSeek 2026 年 5 月降价 75%、8 月部分上调最多 1100%（经摘要）[9] | 调价超过 20% 触发成本复算，超过 50% 触发复评 |
| 结构化能力不一致 | 见调研 07 第 3 节 | 以一致性测试为准 |
| 思考模式与 JSON 模式互斥 | 见 ADR-066 能力记录 `thinkingCompat` | 判断员若需思考模式，用「先推理后成形」 |
| 私有化 | 开源权重（Qwen3 系列等）量化后质量下降，开思考时更明显 [8] | 私有化部署的选型必须用实际量化版本测 |

### 6.5 复评触发

新快照发布、调价超过阈值、厂商下线公告、哨兵评测漂移、线上驳回率连续两周上升、季度例行。复评复用同一选型实验定义，只换候选臂，保证可比。

## 7. 反馈回流与持续改进

### 7.1 信号

| 信号 | 已有 | 缺什么 |
| --- | --- | --- |
| 法务处置 ACCEPT / MODIFY / REJECT（`lease.review.feedback`） | M3-04 | 只有自由文字原因；法务自己发现、Agent 没报的问题（漏报）没有入口 |
| 撤销、审批驳回、抽检「应撤销」 | ADR-033、ADR-034 | — |
| 点赞点踩 | EVO-01 | — |
| 线上低分 | EVO-03 待标注队列 | — |

### 7.2 原因码

法务改判时选一个原因（可多选，必选一个主因）：

| 原因 | 归属层 | 是否算 Agent 错误 | 去向 |
| --- | --- | --- | --- |
| 原文读错 | 解析 | 是 | 解析评测集与回归集 |
| 取值或证据错 | 抽取 | 是 | 模型层评测、回归集 |
| 要点规则不当 | 规则 | 是（规则资产） | 要点库修订；受影响用例重标 |
| 判断错误 | 判断 | 是 | 回归集（反例）、经验候选 |
| 漏报（法务新增问题） | 判断或规则 | 是 | 回归集（反例）、要点库候选 |
| 业务接受风险 | — | **否** | 不进反例；可进经验「何时可接受」的说明 |
| 规范已变化 | 标签 | **否** | 触发要点库版本与旧用例「待重标」 |
| 表述优化 | 文字 | 轻微 | 只统计，不进回归集 |

### 7.3 分诊与闭环

1. 每周由 Agent 负责人（开发）与法务负责人做一次分诊：批量确认原因码、合并同类问题。
2. 确认的 Agent 错误：生成回归用例（反例，带原合同与法务结论）；根因按层分派到改规则、改 Prompt、加经验（EVO-05）、改解析方案、换模型。
3. 正例：被原样接受、且多次运行一致的结论按比例（如 10%）抽入回归集，防止回归集只有反例导致过度保守 [1]。
4. 任何改进都按第 5.2 节分级再过准入；一个问题从发现到上线的周期作为改进效率指标。
5. 防过拟合：回归用例只进回归集与开发集，不进密封集；密封集按季度轮换。

### 7.4 偏好数据（M4 之后）

带原因码的「Agent 结论 → 法务结论」天然是偏好对，积累后可用于私有模型的偏好优化（DPO 一类）。这只在客户有私有化微调需求时考虑，需要单独的数据授权与评测，不在 M4 范围。

## 9. 方案选项

### 选项 A：评测方法的统一程度

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| A1 维持现状 | 各 ADR 各自定义 | 差距 1〜6 不解决 |
| **A2 统一方法规范（推荐）** | 一份 ADR 规定评测集分层、用例卡、标注、评分器优先级、裁判校准、多次运行、聚类与配对统计、报告格式；各专项 ADR 的评测集作为「专项集」挂入 | 不推翻已有设计，只补口径 |
| A3 引入外部评测平台 | 接 Langfuse 等 | 违背 ADR-031「建立在自带轨迹上」；数据出域问题 |

### 选项 B：发布门禁的判定

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| B1 固定阈值（现状） | 低于稳定版 2 个百分点阻止 | 小样本下是噪声 |
| **B2 配对非劣效 + 关键子集逐条（推荐）** | 配对差异区间下界 ≥ −容差通过；无法判定转人工；回归集与必备「不满足」逐条 | 统计上站得住；需要多次运行，评测成本约 3 倍 |
| B3 序贯检验 | 边跑边判，提前停止 | 实现复杂，样本本来就小，收益有限 |

### 选项 C：低流量场景的灰度

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| C1 按比例分流 | 10% 流量给新版本 | 每天 10 份合同时 10% 是 1 份，无意义 |
| **C2 双跑（推荐）** | 新版本对全部输入后台运行，配对比较 | 推理成本翻倍（合同场景每天约 10 份，可接受）；不需要 A/B 样本量 |
| C3 只靠离线 | 准入通过直接全量 | 离线集覆盖不到的输入分布无保护 |

### 选项 D：平台配置变更的评测

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| D1 维持跟随（现状） | 别名发布即全平台生效 | 未评测的 C2 变更 |
| **D2 跟随 + 发布前受影响 Agent 评测 + 按 Agent 分批切换（推荐）** | 保留集中路由的好处；发布对话框展示受影响 Agent 的评测结果；可按 Agent 白名单先切 | 故障接力、紧急切换仍可一键全量（紧急发布需填写原因，事后补评测） |
| D3 改为钉版本 | Agent 发布时钉住别名版本 | 失去集中切换能力，违背 ADR-024 |

### 选项 E：裁判模型

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| E1 直接用 | 选一个强模型打分 | 无校准 |
| **E2 先校准后使用、分类型优先（推荐）** | 每个裁判评估器绑定校准集，κ ≥ 0.6 才可用于门禁；Pass/Fail 分类优先于 0〜5 打分；与被测模型不同族；钉快照版本 | 校准集需要人工标注（每个裁判约 100 条） |
| E3 只用人工 | — | 不可扩展 |

### 选项 F：反馈回流

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| F1 自由文字 + 周报（现状） | — | 无法分诊 |
| **F2 原因码 + 每周分诊 + 回归用例自动生成（推荐）** | 第 7 节 | 法务每次处置多点一次选择；每周约 1 小时分诊 |
| F3 全自动 | 驳回即进反例、即改 Prompt | 把「业务接受风险」与「规范变化」当成错误，污染回归集 |

### 推荐组合与分期

推荐 **A2 + B2 + C2 + D2 + E2 + F2**。分期：

- **M3（合同场景上线前必须）**：评测集分层与用例卡字段、按合同聚类的区间与配对差异报告（并入 EVO-02）；法务处置原因码、漏报入口、最小分诊视图（业务系统与 Tioka 两侧）；合同场景模型选型最小版（同一数据集多臂、每份 3 次、成本时延汇总、选型报告模板），在影子期前完成。影子期 50 份合同的法务结论留出 20 份作为首个密封集。
- **M4**：裁判校准与偏差检查；EVO-04 / EVO-06 改为多次运行、非劣效判定；上线准入单与变更分级；双跑灰度与对话类按比例灰度；别名与路由计划的受影响 Agent 评测与分批切换、快照钉住；哨兵评测；选型全量与复评触发；反馈分诊全量、标签版本与重标；标注台；前端。
- **M4 之后**：偏好数据导出与私有模型微调、主动学习采样、序贯检验。

**排期备选**：
- 备选 1（M3 不延长）：M3 只做原因码与漏报入口（约 2 人日），选型由开发用 EVO-02 手工跑两次并在表格里汇总，统计口径与密封集移到 M4 前段。代价：G3 与影子期的报告没有区间，「达标」与否可能是噪声；选型结论无法复跑。
- 备选 2（全部 M4）：代价是合同场景影子期的反馈只有自由文字，前两个月的反馈无法分诊。
