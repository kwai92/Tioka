## 0. 结论摘要

1. **文档解析的主流做法已经从「OCR 出纯文本」变成「版面分析 → 区域识别 → 结构组装」**。2025〜2026 年领先的开源方案（PaddleOCR-VL、MinerU2.5、Docling）都先做版面检测和阅读顺序，再对每个区域做文字、表格、公式、印章识别，最后组装成带层级和坐标的结构化文档 [1][5][8][12]。只有 1B 左右参数的专用模型在 OmniDocBench 上已超过 Gemini 3 Pro、GPT-5.2 等通用大模型 [8][15]。
2. **端到端 VLM（整页图片直接生成 Markdown）不能作为合同证据的来源**。Thoughtworks 技术雷达把它放在「评估」环，原话是「生成式的本性使其容易幻觉」，低容错场景仍需要混合方案或确定性 OCR [16]；FireRed-OCR 论文把表格行错乱、凭空出现的结构称为「结构性幻觉」[15]；PaddleOCR-VL-1.6 论文承认模型有时会给出「稳定但错误、且置信度高」的结果 [8]。合同审查要求每个取值都能定位到原文位置并通过引文校验（ADR-036、ADR-037），所以 Tioka 应采用**流水线式解析**，VLM 只用作区域识别器，并保留逐块坐标与置信度。
3. **Tioka 现状与差距**：现有代码 `DocumentParser` 只输出纯文本（PDF 不带坐标，Word 只取段落，不含表格、自动编号、修订）；M3-03 设计的文档层已有证据单元、bbox、OCR 合并与低置信待复核，方向正确，但存在 13 处缺口（第 7 节），最要紧的是：**Word 自动编号会丢失导致条款树建不出来**、**扫描页只有行级 OCR，没有版面与表格结构**、**知识库与文档层各有一套解析器且没有共同契约**、**外购 OCR 产品没有接入模型**。
4. **建议新建「文档解析服务」**（ADR-060）：一条流水线（预检 → 规范化 → 页分类 → 版面 → 区域识别 → 融合 → 组装 → 质量评估），一份输出契约 `tioka.parse/v1`（页、块、表格、印章、坐标、来源、置信度、标记），文档层与知识库都从这里取结果。Markdown 只是派生视图，不是证据来源。
5. **建议默认引擎为自部署的 PaddleOCR 服务**（版面、文字、表格、印章一套齐全，Apache-2.0，中文与印章能力强，支持 CPU 与国产加速卡，官方提供服务化部署与 Docker 镜像）[5][6][7][9]；百炼 `qwen-vl-ocr` 作为云端识别器与低置信区域的「第二意见」[20]；Word 与文字型 PDF 仍在 JVM 内用 POI、PDFBox 取原生文字，不走 OCR。
6. **外购 OCR 产品按「解析引擎 SPI」接入**（ADR-061）。各家产品差异集中在：同步或异步、计费单位（页 / 次 / token）、坐标形式（四点、`[x,y,w,h]`、旋转矩形、归一化）、结果链接有效期、限流、数据留存承诺。适配器声明这些属性，平台统一做异步任务、结果转存、坐标换算、错误分类、按页计量、凭证（复用 ADR-042）、出网（EgressGuard）与数据去向过滤（ADR-040）。每个适配器必须通过同一套一致性测试才能上线。
7. **成本不是选型的决定因素**。按每天 10 份、每份 30 页估算每月约 9,000 页：阿里云文档解析（大模型版）增强链路 0.04 元/页，每月约 360 元（还有每月 3,000 页免费额度）[18][19]；腾讯云多模态文档解析 0.08 元/页约 720 元 [25]。决定因素是**坐标与证据可定位、印章与手写处理、数据留存承诺、私有化可用性**。
8. **排期**：M3 只做两件小事（后端约 2.5 人日，由 M3 缓冲吸收）：Word 自动编号与表格、修订的正确处理；文档层输出按契约 v1 的核心子集落地，避免 M4 返工。完整的解析服务、PaddleOCR 引擎、外购适配框架与参考适配器、特殊元素、安全与评测放 M4（后端约 27、前端约 7 人日），M4 预计再延长约 2 周，写 M4-00 时与 RAG 调研的增量一起核算。

## 1. 问题分解：合同文档的难点

| 难点 | 合同里的典型表现 | 解析要求 |
| --- | --- | --- |
| 条款编号 | 「第二十二条」「4.1.1」「（三）」混排；Word 里多数是自动编号 | 编号必须以渲染后的文字出现，才能建条款树（M3-03 第 2 节） |
| 表格 | 租金递增表、费用明细、免租期表；跨页；合并单元格；扫描件里的无框表 | 按单元格输出，带行列与合并信息；跨页续表要能接上 |
| 空白填写位 | 「【　】」「____」「（　）」，手写补填 | 不能丢；手写补填的内容要单独标记 |
| 印章 | 圆形公章、合同专用章、骑缝章；盖在文字上 | 识别印章本身（存在、文字、位置），并标出被遮挡的正文 |
| 手写 | 签名、日期、金额、手写修改 | 标记为手写，低可信，涉及金额日期的一律人工复核 |
| 扫描与拍照 | 倾斜、旋转、阴影、曲面、低分辨率、多张照片拼成一份合同 | 方向校正、纠偏、按页排序 |
| 混合 PDF | 有文字层但部分页是扫描插页；扫描件被二次 OCR 加了文字层 | 逐页判断文字层是否可信 |
| Word 特性 | 修订痕迹、批注、页眉页脚、文本框、域 | 定义修订采纳规则；页眉页脚不进正文 |
| 格式 | docx、doc、wps、pdf、jpg/png/tiff、多页 TIFF、手机 HEIC、国产版式文档 OFD | 统一规范化入口 |
| 安全 | 白色字体、极小字号、PDF 不可见文字层与图像不一致 | 隐藏内容检测；文字层与图像一致性抽检 |

## 2. 技术路线

### 2.1 三条路线

| 路线 | 做法 | 优点 | 风险 | 代表 |
| --- | --- | --- | --- | --- |
| 传统流水线 | 版面检测 → 文字检测识别 → 表格结构 → 规则组装 | 每一步可解释，有坐标与置信度，不会编造内容 | 模块多；复杂版面、无框表格较弱 | PP-StructureV3 [10]、Docling 默认流水线 [12] |
| 两阶段 VLM | 先版面（检测 + 阅读顺序），再把区域裁剪后交给小型 VLM 识别 | 精度最高；仍有区域坐标；VLM 只看局部，幻觉空间小 | 需要 GPU 才有吞吐；VLM 仍可能在区域内出错 | PaddleOCR-VL（PP-DocLayoutV3 + 0.9B VLM）[7][8]、MinerU2.5（同一个 1.2B 模型做两阶段）[1] |
| 端到端 VLM | 整页图片直接生成 Markdown 或 DocTags | 架构最简单 | 结构性幻觉、漏行重复；坐标不稳定或没有 | DeepSeek-OCR 2 [17]、Granite-Docling [13]、通用大模型 |

**判断**：合同证据要求「每个取值能定位到原文、改一个数字的引文被拒」（DOC-03），所以**以流水线或两阶段 VLM 为主**；端到端 VLM 只在没有更好选择时做兜底，且其输出必须标来源 `VLM` 并降低可信度。

### 2.2 公开评测（OmniDocBench）

OmniDocBench 是目前最常引用的文档解析评测，覆盖文字、公式、表格、阅读顺序。注意 v1.5 与 v1.6 两个版本的分数不可直接比较。

| GLM-OCR | 0.9B | 94.60 | 95.22 | [15]、[8]（经摘要） |
| PaddleOCR-VL-1.5 | 0.9B | 94.50 | 94.93 | [5]、[8]（经摘要） |
| MinerU2.5 | 1.2B | 90.67 | 93.04 | [1]、[8]（经摘要） |

- **PaddleOCR 最贴合合同场景**：中文强、印章流水线现成、坐标齐全、许可干净、支持国产硬件（私有化客户常见要求）、有官方服务化部署，不需要团队写 Python 业务代码。

- **Docling** 许可最宽松、格式最广、数据模型（body / furniture、来源、bbox）设计得最好，Tioka 的契约 v1 参考了它的结构；但中文合同与印章能力没有公开证据。列为备选引擎，Office 格式兜底可用。
- **Unstructured** 开源部分能力有限，不建议。

## 5. 解析输出的数据模型

调研了三种公开的结构化输出，供定义 Tioka 契约参考：

| 方案 | 结构 | 可借鉴 |
| --- | --- | --- |
| DoclingDocument [12] | 内容列表（texts、tables、pictures、key_value_items）+ 两棵树：body（正文，子节点顺序即阅读顺序）与 furniture（页眉页脚）；条目用 JSON 指针互相引用；带来源（页、bbox） | 正文与「家具」分开；阅读顺序由树决定；内容与结构分离 |
| PaddleOCR 结果 JSON [7][10] | 版面块（类别、分数、坐标，可选矩形 / 四边形 / 多边形）；OCR 行（文字、分数、多边形）；表格单元格坐标；印章（多边形、文字） | 每个块都有分数与坐标；印章是一等对象 |
| TextIn [24] | 页 → 内容项（类型、四点坐标、分数、文字）；结构化列表（文本块、标题子类型）；可选字符级坐标；阅读顺序还原 | 字符级坐标对引文高亮有用 |

Tioka 的契约 `tioka.parse/v1` 取三者之长（ADR-060 第 3 节）：块是扁平数组按阅读顺序排列，用 `parentId` 表示层级；`role` 区分正文与页眉页脚；坐标统一为页内 0〜1 归一化；每个块带来源、引擎与置信度；表格单元格、印章、勾选框是一等对象；Markdown 只作为派生视图。

## 6. 采购外部 OCR 产品要对接的差异

| 差异点 | 各家情况 | 平台统一处理 |
| --- | --- | --- |
| 调用模式 | 同步（TextIn、读光、qwen-vl-ocr）、异步提交加轮询（百度）、部分支持回调 | 平台统一成异步任务；只做轮询，不开放回调入口（避免新增入站暴露面） |
| 输入方式 | 二进制、Base64、URL（百度大文件必须 URL）| 不给外部发对象存储公网链接；大文件按页拆分后上传；确需 URL 的引擎只用短期签名链接并记审计 |
| 坐标 | 四点像素、`[x,y,w,h]`、旋转矩形、归一化 | 适配器换算为页内 0〜1 归一化；页尺寸以平台自己渲染的页图为准 |
| 结果获取 | 直接返回、结果链接（百度 30 天有效） | 拿到即转存对象存储，原始结果按文档保留期保存 |
| 计费 | 按页、按次、按 token、并发买断 | 适配器声明计费单位与单价，平台按调用记用量与估算成本 |
| 限流 | QPS 2〜5（百度）、可购买 QPS 叠加包（腾讯） | 按引擎实例令牌桶（CON-SDK） |
| 错误 | 各家错误码不同；有的失败也计费 [25] | 适配器把错误归为可重试、额度用尽、输入非法、鉴权失败、不支持五类 |
| 鉴权 | AK/SK 签名、API Key 换 token、请求头 app-id + secret、IP 白名单 | 凭证走 ADR-042（多 Key、有效期提醒、轮换）；出网走 EgressGuard，固定出口 IP 写入部署手册 |
| 数据留存 | 公开页面均未说明 | 引擎实例必须声明留存与训练条款，未声明的不能处理 `CONFIDENTIAL` 文档 |
| 版本 | 云端模型随时升级 | 引擎实例记录供应商声明的版本；结果变化由夜间评测发现 |

## 7. 与 Tioka 现有设计和代码的对照

### 7.1 现状

| 位置 | 内容 |
| --- | --- |
| 代码 `knowledge-biz/.../parse/DocumentParser` | PDF 用 PDFBox `PDFTextStripper` 取整份纯文本；DOCX 用 POI 取段落文字并拼接；HTML、Markdown 用正则去标签；返回一个字符串 |
| ADR-018 | 知识库解析为 `DocumentParser` SPI，输出带标题层级的段落；OCR、图片、Excel 留给 M4（KNW-09） |
| ADR-036、M3-03 第 2〜3 节 | 文档层 `doc_document` / `doc_page` / `doc_unit` / `doc_clause`；解析器按 MIME 分 docx（POI）、doc（LibreOffice 转换）、pdf（PDFBox）、图片（OCR）；字符密度低于阈值的 PDF 页走 OCR；OCR 是 Model Hub 能力 `ocr`（`BailianOcrAdapter`）；文字层与 OCR 按 IoU 合并；OCR 置信度低于 0.8 的取值置「待复核」；正则识别条款编号、空白填写位、签章区 |
| M3-00 Q6 | OCR 用哪个模型未定，W28 前用 3 份扫描件试跑 |
| M3-06 第 2 节 | 通用连接器 SDK：规格、凭证、游标、限流、健康、出网 |
| ADR-024、ADR-042 | 模型绑定、路由、凭证管理 |
| ADR-040 | 数据标签与去向许可 |

### 7.2 差距

| # | 差距 | 影响 | 建议 |
| --- | --- | --- | --- |
| G1 | POI 的段落 `getText` 不包含自动编号的渲染文字（编号定义在 numbering 部件里，需要按级别和格式计算）。M3-03 的 `ClauseTreeBuilder` 靠正则识别「第X条」，自动编号的 Word 合同建不出条款树 | **M3 P0 场景直接受影响**；开工前用样本确认 | M3 内补编号渲染（ADR-060 第 2.2 节） |
| G2 | Word 表格、页眉页脚、文本框、修订、批注的处理未定义；现有代码只取段落 | 租金表丢失；修订稿的删除内容可能混进正文 | M3 内补表格与修订采纳规则 |
| G3 | 文字型 PDF 只取文字层，没有版面分析（多栏、页眉页脚、表格） | 「以版面块为单元」做不到；表格单元格切不出 | M4 用版面模型处理所有 PDF 页，文字取自文字层 |
| G4 | 扫描页只有行级 OCR，没有版面、表格结构、阅读顺序 | 扫描件的费用表无法按单元格切分，M3-03 的切分规则落空 | M4 引入版面 + 表格引擎 |
| G5 | 印章只作为「OCR 独有的行」追加；没有印章对象；被印章遮挡的正文没有标记 | 「是否盖章」这类审查要点没有证据；遮挡处识别错误无提示 | 印章作为一等块；遮挡标记 |
| G6 | 手写内容不区分 | 手写金额、日期是高风险取值 | 手写标记，金额日期一律待复核 |
| G7 | 合并规则「配对上的行用文字层」默认文字层可信 | 文字层可能被篡改或是劣质二次 OCR，与页面图像不一致 | 文字层与图像一致性抽检；隐藏文字检测 |
| G8 | 知识库 `DocumentParser` 与文档层 `ParserRouter` 两套实现，没有共同输出契约 | 重复建设；RAG 切块无法利用表格与层级 | 统一为文档解析服务与契约 v1 |
| G9 | 外部 OCR 只有 `BailianOcrAdapter`，挂在 Model Hub 的模型绑定下；按页计费、异步、非模型类产品无处安放 | 采购的产品无法接入；成本统计缺失 | 解析引擎 SPI（ADR-061） |
| G10 | 识别率只有「10 组样本、条款路径 ≥ 95%」一个指标 | 换引擎、引擎升级时无法判断好坏 | 解析评测集与回归（ADR-062） |
| G11 | 格式只覆盖 docx、doc、pdf、图片；没有 OFD、wps、多页 TIFF、HEIC；拍照件没有纠偏 | 部分客户合同进不来 | 规范化阶段统一处理；OFD 等放 M4 之后 |
| G12 | Q6（OCR 模型）未定 | DOC-02 开工受阻 | 建议直接定 `qwen-vl-ocr` 稳定版（第 9 节） |
| G13 | 解析不可信文件没有资源限制与隔离（压缩炸弹、XXE、畸形 PDF） | 单个恶意文件拖垮服务 | 预检限额；引擎进程隔离 |

## 8. 方案选项

### 选项 P：解析的组织方式

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| P1 | 维持现状：知识库与文档层各自解析 | 重复建设；契约不统一；不推荐 |
| **P2（推荐）** | 新建文档解析服务模块，一条流水线、一份契约 `tioka.parse/v1`；文档层与知识库都消费它 | 一次建设两处受益；RAG 线程可直接按契约设计切块 |
| P3 | 解析做成 Flow 节点，由各场景自己编排 | 灵活，但每个场景都要重新拼流水线，质量口径不一 |

### 选项 Q：默认解析引擎

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| **Q1（推荐）** | 自部署 PaddleOCR 服务（版面、OCR、表格、印章）为默认；百炼 `qwen-vl-ocr` 作云端识别器与第二意见；Word、文字型 PDF 的文字在 JVM 内取 | 私有化客户可用；印章齐全；许可干净；本部署允许云端，两者互为备份 |
| Q2 | 纯云端：阿里云文档解析（大模型版）或百度文档解析 | 最省运维；但 `SECRET` 文档与不允许出网的私有化客户无法使用 |
| Q3 | 自部署 MinerU | 精度同级；无印章；附加许可条款需法务确认 |
| Q4 | 端到端 VLM（qwen-vl-ocr 文档解析任务或通用视觉大模型直接出 Markdown） | 最简单；坐标与幻觉问题不满足证据要求 |

### 选项 R：外购 OCR 产品的接入位置

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| R1 | 全部作为 Model Hub 的模型绑定 | 路由、配额、审计现成；但这些产品不是模型，按页计费、异步任务、坐标结果都不适合 token 计量与对话路由 |
| R2 | 全部作为通用连接器 | 凭证、限流、健康现成；但缺少数据去向过滤与成本统计 |
| **R3（推荐）** | 新增「文档解析引擎」SPI（ADR-026 的第十类 SPI）：适配器沿用连接器 SDK 的规格、凭证、限流、健康、出网约定，经插件宿主加载；VLM 类识别器（qwen-vl-ocr 等）仍是 Model Hub 绑定，由「模型引擎」适配器经 ModelGateway 调用；去向过滤与计量由解析服务统一做 | 各取所长；Model Hub 不被非模型产品污染 |

### 选项 S：VLM 输出的使用边界

| 选项 | 做法 | 评价 |
| --- | --- | --- |
| **S1（推荐）** | VLM 只做区域识别与低置信区域复核；结果标来源 `VLM`；数字与日期类区域在两个识别来源不一致时标「待复核」 | 利用 VLM 精度，同时守住证据要求 |
| S2 | VLM 端到端为主，传统 OCR 兜底 | 幻觉风险落到合同取值上 |

### 推荐组合与分期

P2 + Q1 + R3 + S1。

| 阶段 | 内容 |
| --- | --- |
| M3（随 DOC-01、DOC-02） | Word 自动编号渲染、表格、修订采纳；文档层输出按契约 v1 核心子集；Q6 定为 `qwen-vl-ocr` 稳定版；`BailianOcrAdapter` 保留在 Model Hub |
| M4 | 文档解析服务模块与流水线；引擎 SPI、解析方案与路由；PaddleOCR 引擎；外购适配框架与阿里云参考适配器；印章、手写、勾选框与跨页合并；安全；评测集；前端引擎管理页与解析结果查看器 |
| M4 之后 | 百度、腾讯、TextIn 适配器；OFD、HEIC、拍照纠偏；MinerU、Docling 备选引擎；评测报告页 |

## 9. 推荐方案要点

1. **一个服务、一份契约**（ADR-060）。流水线九个阶段；输出 `tioka.parse/v1`；按「文件哈希 + 解析方案版本 + 空间」缓存；发 `tioka.docparse.document_parsed.v1` 事件；文档层 `doc_unit` 与知识库切块都由契约派生。
2. **解析方案（Profile）**。按页类型和所需能力为每类页配置主引擎、第二意见引擎与降级链，是 ADR-041 的版本化配置；本部署默认方案为「标准-云可用」，私有化默认方案为「标准-私有」。
3. **引擎四类**：进程内（POI、PDFBox、LibreOffice）、自部署服务（PaddleOCR、MinerU、Docling）、云 API（外购产品）、模型（经 ModelGateway 的 VLM）。
4. **外购适配**（ADR-061）：清单声明能力、调用模式、限制、计费、坐标形式、去向属性；平台统一异步任务、转存、换算、计量、凭证、出网、去向过滤；一致性测试套件准入；采购评估清单。
5. **质量、特殊元素与安全**（ADR-062）：合同金标集与回归；印章、手写、勾选框、签名、遮挡；文字层一致性与隐藏文字；资源限制与隔离；低置信与手写金额日期一律人工复核。
