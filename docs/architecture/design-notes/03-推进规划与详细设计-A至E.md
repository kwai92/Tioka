## 摘要

建议分五个阶段推进：先用约 4 周做 **M0 地基加固**（测试变绿、鉴权、Runtime 内核、去单机假设），再按 M1 到 M4 逐步加厚。按 2 到 3 名后端 + 1 名前端估算，到 M4「可私有化交付」约需 9 到 10 个月。

规划依据两份前置文档：[差距分析](https://claude.ai/artifact/SAJrvKthNMeZJjsPeqJ1sm)（main 分支 fb27c4e 的现状）和[预期目标](https://claude.ai/artifact/2BjtRBWUmacrsMfd5jtMjA)（十层预期与 M1–M4 验收场景）。本文把预期拆成带编号的工作项，并给 P0 涉及的三个模块写详细设计。

规划遵循四条原则：

- **地基先于功能**。鉴权、异步 Runtime、多实例会改动几乎所有实体和接口签名，越晚做越贵，所以排在任何功能加厚之前。
- **一个内核、一套治理**。所有入口（Chat、Flow、Orchestration、IM）都经同一个 Runtime 和 Model Hub，配额和审计只在这两个入口各接一次。
- **完成度以自动化验收为准**。每个里程碑用一条「关闭 mock、双实例、开启鉴权」的端到端用例判定，进 CI，不再用文档勾选。
- **假实现先下线**。6 个对外暴露的假 API 在 M0 返回 501 或删除，做真时再上线。

工期是按工作量粗估，未考虑团队实际人数和并行度，需要你确认人力后再校准。

## 分阶段推进计划

五个阶段按顺序推进，只有 M3 可以在 M2 后半段并行启动。每个阶段末尾有一道闸门：验收用例在 CI 里通过才进入下一阶段。周次以启动周为 W1。

> 原文此处有一张嵌入图「推进路线图 · 5 个阶段，5 道闸门」，归档时未导出。

M3 在 M2 后半段并行启动，因为它只依赖 M1 的 Runtime 协议和 Model Hub 收口，只有数据源增量同步要等 M2 的 MQ。

1. **M0 地基加固（W1–W4）**。修红测试并做数据隔离；CI 加前端构建；认证拦截 + 请求级 Principal + 实体 owner/workspace 归属；Runtime 按会话加锁、Turn/Part 入表、多步工具循环；引入 Redis 并把 SSE 与 cancel 跨实例化；下线假实现 API。
   - 闸门 G0：`mvn test` 与前端构建全绿；未登录请求全部 401；双实例下一个需要 3 次工具的任务自动完成，另一实例可以 cancel。
2. **M1 安全可用的单内核（W5–W12）**。OIDC 登录（Keycloak）、角色权限点与资源级权限；Runtime 异步 Turn、可恢复、审批挂起；Model Hub 轮次冻结、自动故障接力、限流重试；配额与审计接入 Runtime 和 ModelRouter 入口；全仓模型调用收口到 Model Hub。
   - 闸门 G1：Keycloak 登录 → 选已发布 Agent → 真实模型多步调用 MCP 工具 → 双实例流式与取消正常 → 用量计入空间配额 → 审计可查。对外口径：可做企业 PoC。
3. **M2 人机协作闭环（W13–W22）**。RocketMQ + outbox；Orchestration 派工器、规则引擎、Attention 挂起续跑、定时；飞书入站事件与卡片回调；Part 协议对齐 AG-UI；审批台、轨迹视图、工作台。
   - 闸门 G2：飞书事件触发 Agent → 飞书卡片审批 → 续跑 → 结果回写，中途重启服务不丢任务，多 worker 不重复领取。
4. **M3 构建者工具链（W19–W30）**。Knowledge 真 embedding 默认化、结构切块、Rerank、3 类数据源增量同步、评测进 CI；Flow 节点走 Runtime、汇合调度修复、自定义节点、发布为 API/工具/MCP；Chat 编辑重试、真分叉、记忆注入。
   - 闸门 G3：上传文档后引用问答召回率达基线；Studio 建流 → 发布为工具 → Agent 调用 → 用量计入该 Agent 配额。
5. **M4 企业完备（W31–W42）**。SCIM 与组织同步、资产发布审批、工具调用策略引擎、OTel、容器沙箱代码解释器、子 Agent、上下文压缩、钉钉/企微、Helm 与空气隔离安装包。
   - 闸门 G4：离线环境一键安装；普通成员越权操作被拒并留审计；代码解释器在沙箱内运行。

**关键依赖**：M2 的挂起续跑依赖 M1 的异步 Turn 和审批挂起；M3 的 Flow Agent 节点依赖 M1 的 Runtime 协议，数据源增量同步依赖 M2 的 MQ；M4 的策略引擎依赖 M1 的权限模型和审计管道。

**与仓库现有 R0–R6 计划的关系**：`33-差距收口与后续推进计划.md` 中的 R2–R5（各域功能保真）整体后移到 M3；建议把本文定为新的权威计划，旧文档标注为已取代。

## 十层目标拆解

## 关键模块详细设计

本轮先设计 M0/M1 的三个地基模块：身份与权限、Runtime 内核、模型调用收口与配额审计。它们覆盖了 40 个 P0 中的 25 个，设计 D、E 是 M3 的 Knowledge 和 Flow，建立在前三份定下的 Principal、Runtime 协议和 ModelGateway 之上。其余业务能力的设计 F–N 见 详细设计 F–N。现有技术栈保持不变：Spring Boot 3.2、Java 17、MyBatis-Plus 3.5、PostgreSQL、Redis 7、RocketMQ 5（ADR-008）。

### 设计 A：身份、租户与权限

覆盖 FND-01〜05、FND-07、GOV-01、CHT-01。核心决定是：**每个请求和每个后台任务都携带一个不可变的 `Principal`**，数据隔离在持久层自动生效，资源权限在应用层显式校验。

**请求链路**

1. `SecurityFilterChain`（Spring Security 6）识别凭证：本地登录的不透明 token、OIDC 的 JWT、服务账号的 API Key。
2. 从 `X-Workspace-Id` 请求头取当前空间，校验成员关系；缺省取用户默认空间。
3. 组装 `Principal`（含角色展开后的权限点），写入 `PrincipalHolder` 与现有 `TenantContext`。
4. `@RequirePermission` 做功能权限；`ResourceGuard` 做资源权限（是否可编辑这个 Agent）。
5. MyBatis-Plus 的租户拦截器自动为所有业务表加 `tenant_id` 和 `workspace_id` 条件。

未登录白名单只有：登录/刷新、OIDC 回调、健康检查、IM 平台回调（后者用平台签名校验）。

**接口**

```java
public record Principal(
    String tenantId, String userId, String workspaceId,
    PrincipalType type,            // USER, SERVICE, SYSTEM
    Set<String> roles,
    Set<String> permissions,       // 展开后的权限点，如 agent:write
    String authMethod) {}          // password, oidc, api_key

public interface PrincipalHolder {
    Principal current();                         // 无则抛 401
    <T> T runAs(Principal p, Supplier<T> body);  // 后台任务恢复身份
}

@Target(METHOD) @Retention(RUNTIME)
public @interface RequirePermission { String[] value(); }

public interface ResourceGuard {
    void check(String resourceType, String resourceId, AccessLevel level); // VIEW, USE, EDIT, OWNER
    Set<String> visibleIds(String resourceType, AccessLevel level);        // 列表过滤
}
```

异步任务（Runtime Turn、编排 Run、知识 ingest）在创建时把 `Principal` 序列化到任务行的 `run_as_json` 字段，worker 执行前用 `runAs` 恢复。这是审计归属和配额计费在异步路径上成立的前提。

**权限模型**

权限点格式为 `资源:动作`，内置五个角色，租户可自定义角色。资源级共享（如把一个 Agent 分享给某人可用）走 ACL 表，替代现有 `agent_share`。

| 角色 | 范围 | 典型权限 |
| --- | --- | --- |
| tenant\_admin | 租户 | 全部，含成员、角色、模型供应商、审计查询 |
| workspace\_admin | 空间 | 空间成员、配额、资产发布审批 |
| builder | 空间 | agent/flow/kb/skill/mcp 的 read、write、publish |
| member | 空间 | chat:use、使用已发布资产、管理自己的会话 |
| viewer | 空间 | 只读 |

### 设计 B：Runtime 内核

覆盖 RT-01〜08、HCI-02。核心决定是改成 **thread / turn / item 三级模型（对齐 Codex app-server），Turn 异步执行、按会话串行、先入库再推送**。任何实例都能接收请求、执行 Turn、提供流式订阅，实例之间只通过 PostgreSQL 和 Redis 协作。

> 原文此处有一张嵌入图「Runtime 内核架构 · 无状态实例 + 共享存储」，归档时未导出。

PostgreSQL 是事实来源，Redis 只负责分发、推送和互斥；Redis 数据丢失时可以从数据库重建队列和流。

**状态机**

Turn 状态：`QUEUED → RUNNING → COMPLETED | FAILED | CANCELLED`；`RUNNING ⇄ WAITING_APPROVAL`；租约过期进入 `INTERRUPTED`，由回收器决定重试或失败。同一会话同时最多一个 RUNNING 的 Turn，后续消息按序排队。

**执行循环**（RT-03）

```text
for step in 1..maxSteps (默认 20):
    检查 cancel / steer 信号
    selection = modelGateway.select(sessionId, turnId)      // 同一 Turn 内冻结
    result    = modelGateway.chat(ctx, messages, tools, onDelta)
                // delta 只发 Redis Stream；完整消息作为 item 入库
    若无 toolCalls: Turn → COMPLETED，结束
    对每个 toolCall（最多 4 个并行）:
        decision = approvalPolicy.evaluate(principal, tool, args)
        若需审批: 写 runtime_approval，Turn → WAITING_APPROVAL，释放锁，返回
        out = toolGateway.call(ctx, tool, args, timeout)        // 工具网关写审计
        写 tool_result item
达到 maxSteps: 写 status item，Turn → COMPLETED(reason=max_steps)
```

**并发与多实例**（RT-01、RT-04、RT-05）

| 问题 | 现状 | 设计 |
| --- | --- | --- |
| 会话互斥 | `append` 上全局 `synchronized` | Redis 锁 `rt:lock:{sessionId}`，TTL 30 秒、每 10 秒续期；写库带 `lease_version` 条件，旧 worker 的写入会失败 |
| Turn 分发 | HTTP 线程内同步执行 | Redis Stream `rt:turns` + 消费组，各实例的有界线程池消费 |
| 流式推送 | SSE emitter 存在 JVM Map | item 先入库再写 `rt:events:{sessionId}`；任意实例的 SSE 用 `XREAD` 订阅，`Last-Event-ID` 之前的部分从数据库补 |
| 取消与插话 | 只改本机内存 | 写 `rt:signal:{turnId}`，执行循环在每步之间和每个 delta 之间检查 |
| 崩溃恢复 | 内存态丢失 | 回收器扫 `lease_until < now()` 的 Turn：最后一个 item 是用户输入或工具结果则重新入队；有未返回的工具调用则补一条「结果丢失」的 tool\_result 后再入队，不重放工具 |

Turn 分发用 Redis Stream 而不是 RocketMQ，是因为它延迟低且 M0 就要用；RocketMQ 在 M2 引入后只承担跨域业务事件。

### 设计 C：模型调用收口、配额与审计

覆盖 MH-01、MH-02、MH-04、MH-05、GOV-02、GOV-03、CON-01，并顺带解决 KNW-01 和 FLW-02。核心决定是：**全平台只有三个治理卡点**——`ModelGateway`（所有模型调用）、`RuntimeApi.startTurn`（所有执行）、`ToolGateway`（所有工具调用）。配额、限流、用量、审计都只在这三处实现一次。

**ModelGateway**（取代对外暴露的 `LlmClientApi`）

```java
public interface ModelGateway {
    ChatResult chat(ModelCallContext ctx, ChatRequest req, Consumer<StreamDelta> onDelta);
    EmbeddingResult embed(ModelCallContext ctx, EmbeddingRequest req);
    RerankResult rerank(ModelCallContext ctx, RerankRequest req);
}

                        String agentId, String routingPlanId,
                        String purpose) {}   // chat / flow / embedding / rerank / decision
```

一次调用的内部顺序：

1. 选模：同一 `(sessionId, turnId)` 命中冻结则复用，否则按路由计划决策并写冻结（MH-01）。新用户消息即新 Turn，自然重新决策。
2. 配额预检：按空间和 Agent 检查本周期 token 余量，不足则抛 `QUOTA_EXCEEDED`。
3. 限流：按 binding 的 RPM/TPM 令牌桶（Redis Lua），短时排队而不是立即报错。
4. 调用：可重试错误（429、5xx、超时）指数退避重试 2 次；仍失败则切到路由计划中的下一个 binding，最多接力 2 次，冻结记录同步更新，并写一条 `FailoverEvent` 到 Turn 时间线（MH-02）。耗尽时显式失败。
5. 记账：写 `model_usage`，扣减配额计数（MH-05）。

`OpenAiCompatibleClient` 降为 model-biz 内部类。ArchUnit 规则：除 model-biz 外，任何模块不得依赖模型 HTTP 客户端；Flow 的 LLM/Agent/Embedding 节点和 Knowledge 的嵌入都改为调 `ModelGateway`（MH-04）。

### 设计 D：Knowledge 入库、检索与数据源

覆盖 KNW-01〜08。核心决定是：**入库改为异步任务 + 版本切换，检索改为「权限过滤 → 混合召回 → Rerank → 父块扩展」四段，所有模型调用走 ModelGateway**。现有问题对应：默认 HashEmbedding、固定 200 字切块、同步 ingest 无事务、每次检索写 citation、无权限过滤。

**入库流水线**（KNW-03、KNW-05）

1. **登记**：上传或数据源变更只写 `kb_document` 和一条 `kb_ingest_job`，立即返回。按 `content_hash` 去重，内容未变则跳过。
2. **解析**：`DocumentParser` SPI 按格式选择实现（现有 PDF、DOCX，补 Markdown、HTML；OCR、图片、Excel 留给 M4），输出带标题层级的结构化段落。
3. **切块**：按标题切出父块（一个小节，上限 2000 字），父块内再切子块（约 400 token，重叠 50）；表格和代码块整块保留。策略按知识库可配。
4. **向量化**：批量调 `ModelGateway.embed`（purpose=embedding），用量计入知识库所属空间。
5. **索引与切换**：新版本分块写入时带 `doc_version`，全部成功后在一个事务内把 `kb_document.active_version` 切到新版本并删除旧版本，检索永远看不到半条数据。

各阶段由任务表驱动，失败可按阶段重试（最多 3 次）。M2 之前用数据库轮询派发任务，M2 后改由 RocketMQ 触发，任务表不变。

**检索链路**（KNW-02、KNW-04、KNW-08）

| 步骤 | 做法 |
| --- | --- |
| 权限过滤 | 用 `ResourceGuard.visibleIds("kb", USE)` 得到可见知识库，作为 SQL 条件下推，而不是召回后再过滤 |
| 混合召回 | 向量（pgvector HNSW）与关键词（PostgreSQL 全文索引）各取 50 条子块，RRF 融合（k=60，沿用现有实现） |
| Rerank | 前 50 条调 `ModelGateway.rerank` 取 topK；知识库未绑定 rerank 模型时跳过 |
| 父块扩展 | 返回子块用于引用定位，父块正文用于给模型上下文，同一父块只返回一次 |
| 引用 | 检索不再写 `kb_citation`；引用以 `chunkId@docVersion` 作为稳定引用号，由 Runtime 在回答实际采用时写成 citation item |

中文关键词检索需要 PostgreSQL 分词扩展（如 zhparser）。私有化环境装不了扩展时，退化为应用层分词后写入 `tsvector`，索引结构不变。


### 设计 E：Flow 执行引擎与发布

覆盖 FLW-01〜07。核心决定是：**把内存里按「波次」跑完的 DAG，改成状态落库、事件驱动的节点调度器**。这样汇合节点、人工节点挂起、Agent 节点长时间运行、进程重启后续跑，都用同一套机制解决。引擎复用 Runtime 的 worker 基础设施（Redis Stream 分发、租约、`run_as` 恢复身份）。

**节点状态与调度规则**

节点状态：`PENDING → READY → RUNNING → SUCCEEDED | FAILED | SKIPPED`，另有 `WAITING`（等审批或等 Agent Turn）。调度器在任一节点到达终态时重新计算下游：

- Branch 节点完成后，未选中的出边标记为「已跳过」；一个节点的入边全部被跳过时，它自己变成 SKIPPED 并继续向下传播。
- 汇合节点在所有入边都「已解决」（上游成功或被跳过）且至少一条来自成功节点时变成 READY。这就修复了现在「入度归不到 0，汇合节点永不执行」的问题（FLW-01）。节点可配 `joinMode`：`ALL`（默认）或 `ANY`（任一上游成功即执行）。
- 单个 Run 并发节点数上限 4；节点失败按配置重试，仍失败则 Run 失败，除非该节点配了 `continueOnError`。
- Loop 节点把循环体当作子图，每轮生成独立的 node run（`iteration` 字段区分），最大轮数必填。

**挂起与续跑**（FLW-03、FLW-04）

| 节点 | 执行方式 | 唤醒条件 |
| --- | --- | --- |
| HumanCard / Approval | 写一条 `runtime_approval`，节点进入 WAITING，释放 worker | 审批提交（Web 审批台或飞书卡片）调 `decideApproval` |
| Agent | 调 `RuntimeApi.startTurn`（origin=flow，originRef=节点运行 ID），节点进入 WAITING | 收到该 Turn 的 `turn.completed` 或 `turn.failed` |
| LLM / Embedding | 同步调 `ModelGateway`（purpose=flow） | — |
| Retrieve | 调 `KnowledgeSearchApi.search` | — |
| MCP / HTTP | 经 `ToolGateway`，统一鉴权与审计 | — |

等待不占线程，状态全在数据库，所以服务重启不会丢失等待中的 Run。Flow 里的人工节点和 Orchestration 的 Attention 共用同一张审批表和同一个审批台。

**类型化的图与节点 SPI**（FLW-05）

现在图和节点配置都是 `Map<String, Object>`。改为显式类型，发布时做完整校验（除 Loop 子图外无环、端口类型匹配、必填配置齐全、凭证引用存在）。

**发布**（FLW-06）

一个已发布版本可以有多个发布形态，取代现有只支持工具形态的 `flow_tool_pub`。输入输出 Schema 从图的 Input/Output 节点自动生成。

## 设计定案：执行中最容易偏差的 15 处

审查设计 A–E 后，发现 1 处矛盾和 14 处留白。留白的地方不同开发者会做出不同选择，所以在这里统一定案；实现时以本表为准，改动需走下一节的变更流程。第 1 处矛盾已在设计 B 的表结构里改正。

| # | 涉及 | 问题 | 定案 |
| --- | --- | --- | --- |
| 1 | B、E、ORC | **矛盾**：`runtime_approval` 原先 `turn_id` 必填，但 Flow 人工节点和编排 Attention 没有 Turn | 改为通用审批表：`subject_type` + `subject_id`（turn / flow\_node\_run / orch\_run），`kind` 区分工具审批与卡片。审批提交后发 `approval.decided` 事件，由各 subject 的处理器负责续跑 |
| 2 | B、C | 流式已经输出一半时主模型故障，故障接力会不会产生重复文字 | 首个 delta 发出前可以直接切备用；已发出 delta 后，本步 item 标记作废并发 `item.discarded`，整步用备用模型重跑。前端收到 discarded 即移除该 item |
| 3 | B | 断线续传时 delta 不入库，怎么补 | 断点 item 已完成：从库补完整 item。仍在流式：从 Redis Stream 补该 item 的全部 delta。Stream 保留到 Turn 结束后 10 分钟、上限 1 万条，过期则全部从库补。客户端按 item id 幂等渲染 |
| 4 | B | 会话锁续期失败时 worker 怎么做 | 立即停止该 Turn 的一切写入并放弃，由回收器接管；不尝试重新拿锁继续。所有 Turn 与 item 写入在同一事务内校验 `lease_version` |
| 5 | B | 同一会话正在运行时又来一条消息 | 默认排队（FIFO，最多 5 条，超出返回 429）。想插话用 steer，插话内容在下一次模型调用前作为用户 item 注入 |
| 6 | A、B | 异步任务运行中用户权限被收回 | `run_as` 只存身份，不存权限集。每个 Turn 开始和每次工具调用前重新加载权限（缓存 60 秒）；用户被禁用则进行中的 Turn 在下一步取消 |
| 7 | C | 配额预检要不要估算本次 token | 不估算。预检只看「已用 < 上限」；单次调用允许超出，照常记账，下一次被拒。并发配额以 Turn 计，`WAITING_APPROVAL` 不占并发 |
| 8 | C | 业务回滚时审计会不会一起丢 | 成功操作的审计与业务同事务；DENIED 和 ERROR 审计用独立事务（`REQUIRES_NEW`），不随业务回滚；工具调用审计在调用返回后单独写 |
| 9 | 全局 | ID 格式与列宽不一致（32 与 64 混用） | 新表主键统一 ULID（26 字符，列宽 `VARCHAR(32)`）；引用其他表的外键列统一 `VARCHAR(64)` 以兼容旧 ID；禁止截断 UUID |
| 10 | 全局 | 时间与时区 | 时间列一律 `TIMESTAMPTZ`，按 UTC 存；API 用带时区的 ISO-8601 |
| 11 | E | Flow 的 Agent 节点用哪个 Runtime 会话 | 每个节点运行新建一个 thread（Loop 的每轮也各自新建），thread 元数据记录 runId 与 nodeId；不复用 Chat 会话 |
| 12 | D | 文档切换版本时，引用了旧版本的回答怎么办 | 旧版本分块在切换后 5 分钟再删；之后引用解析失败时显示「来源已更新」，不报错 |
| 13 | 全局 | 删除语义 | 业务实体软删（沿用 `deleted` 列）；`runtime_item`、`model_usage`、`audit_event` 只增不改不删，按保留策略归档 |
| 14 | 全局 | 错误码与 HTTP 状态 | 沿用 `ApiResponse` 与 `ErrorCode`；新增错误码统一在 framework 登记：`UNAUTHENTICATED`→401、`FORBIDDEN`→403、`STALE_REVISION`→409、`QUOTA_EXCEEDED`→429、`LEASE_LOST` 仅内部使用 |
| 15 | 全局 | 事件命名与版本 | Runtime 的 SSE 事件用小写点分（`item.completed`）；跨域 MQ 事件用 `tioka.{domain}.{event}.v1`，payload 带 `schemaVersion`，不兼容变更必须升版本号 |

## 防偏差机制

文字设计本身拦不住偏差。建议把设计变成**仓库里的契约文件和 CI 里会失败的检查**，靠机器守，而不是靠人记。

1. **设计入库，只留一份权威**。设计 A–E 和上表定案转成 `docs/architecture/adr/` 下的 ADR，每份设计一篇、定案逐条编号。本文和飞书版只用于阅读。之后改设计只能通过修改 ADR 的 PR。
2. **契约先行**。每份设计开工前，先提一个只含契约的 PR：`-api` 模块的接口与 record、Flyway 迁移脚本、事件 JSON Schema、错误码。契约合并后，实现 PR 不得修改契约文件；用 CODEOWNERS 让契约目录必须由你审批。
3. **可执行的架构守护**。在 CI 里用 ArchUnit 强制：
   - 除 model-biz 外，任何模块不得依赖模型 HTTP 客户端（守住设计 C）。
   - 所有 Controller 方法必须带 `@RequirePermission` 或 `@PublicApi`（守住设计 A）。
   - `tioka-server` 只依赖各域 `-api`；应用层禁止 `synchronized` 与 `new ObjectMapper()`（守住设计 B 和 ENG-05）。
   - Chat、Flow、Orchestration 只能通过 `RuntimeApi` 执行 Agent（守住「一个内核」）。
4. **契约测试套件**。把状态机写成表驱动的测试：Turn 状态转换、幂等、租约失效；审批的创建、提交、过期；Flow 调度的分支、汇合、跳过传播、Loop。实现怎么改都要过这些用例。
5. **验收用例先写**。每个阶段开始时先把闸门（G0–G4）的端到端用例写好并让它们处于失败状态，阶段结束以它们变绿为准。
6. **可追溯与对账**。PR 模板必填工作项编号和对应 ADR；与设计不一致的 PR 必须同时修改 ADR。每两周做一次设计对账，抽查已合并代码是否符合 ADR。

这六条里，第 1、2、3 条应在 M0 第一周完成，否则 M0 的大规模改动会在没有契约的情况下开始。建议新增工作项 ENG-08（ADR 入库）、ENG-09（M0 契约 PR）、ENG-10（ArchUnit 守护规则），均为 M0、P0。
