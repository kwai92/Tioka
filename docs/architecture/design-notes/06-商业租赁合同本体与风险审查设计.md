## 结论摘要

设计的中心是你们的《租赁合同模型》（规格 v2.3）：每份合同建一次带证据、可确认、有版本的模型，风险审查、租金结构化、信息提取、执行预警、权益预警都只读模型。风险审查是第一个落地场景，它把文档层、建模、模型查询、要点判定、结论闭环这些共享能力建起来。

业务系统新建，它是唯一事实来源（已确认的模型、要点与阈值、修订案例、正反例、审查结论、处理流程）。Tioka 负责建模、审查、通知和评测，两边只通过通用连接器 SDK 的一个业务插件 `biz.lease` 打交道，Tioka 不直连业务库。

关键决定有六条：

1.  **平台与领域包分开**：按脑图的划界，Tioka 新增「业务本体」平台能力（模型定义资产、`@model.build`、模型查询与覆盖）；对象类型、词表、Prompt、校验、折叠属于租赁领域包；LAS 投影暂不做。

2.  **审查在模型上判定**：110 个要点中 D 类 70 个用 CEL 确定性判定，H 16 个规则加大模型复核，J 24 个交给大模型；结论只用四态，必备 56 个由平台校验必须有结论。

3.  **多智能体用在两处**：建模时大量并行的抽取 Agent，审查时主审 Agent 自主委派判定与复核 Agent，复核用另一个模型家族（百炼与 DeepSeek 各占一个）。

4.  **一切先落草稿**：模型和审查结论都以草稿写入业务系统，确认、定稿、退回都由人在业务系统完成。

5.  **通知走适配器**：飞书、钉钉、企业微信、邮件、短信实现同一个 `NotificationChannel` 接口；链接只带 reviewId，不带令牌，业务系统自己登录和鉴权。

6.  **处理结果回流**：法务逐条采纳、修改、驳回都回传 Tioka，成为评测数据、修订案例和经验条目。

按现有 34 号计划，这个场景最早在 M3 末以「影子模式」试点；完整的自主多智能体要等子 Agent（RT-12）和业务连接器（CON-07），二者目前都排在 M4，建议提前到 M3。

## 合同本体

本体直接采用你们的《租赁合同模型》（规格 v2.3，2026-10-13）：每份合同只建一次模型，与任务无关、带证据、可人工确认、有版本，下游任务只读模型。本节只说 Tioka 怎么承载它，不重复模型内容；本文其余部分都以这份规格的术语为准。

### 实例归属与版本（已定：业务系统为准）

- **已确认版本存在新建的业务系统**。脑图划给平台的「实例存储与版本」和「确认界面」，按这个决定落在业务系统里；Tioka 保留草稿和只读投影。

- **Tioka 负责建模**：跑 `@model.build` 十步，校验通过后经连接器写成业务系统里的草稿版本；人工在业务系统里只看与上一版本的差异并确认（D24 仍待你们确认）。

- **确认即事件**：业务系统发 `contract.model.confirmed`，Tioka 刷新投影并触发脑图里的「下游订阅」：折叠、投影、审查重跑。下游结果都记模型版本。

- **折叠引擎属于领域包**：确定性代码，在 Tioka 插件宿主（ADR-026）里运行；租约状态是派生数据，写回业务系统，随时可以重算。

## 场景与角色

第一个场景是**签约前的商务风险审查**：招商或业务人员在业务系统提交一份商业租赁合同（新签、续签、补充协议），系统自动审出商务风险，法务在业务系统里逐条处理。它审的是租金、免租期、递增、保证金、提前解约、转租、续租、违约责任、装修与交付等商务条款，不替代法务对法律效力的判断。

| 角色         | 在这个场景里做什么                                                                    | 在哪里做                                                  |
|--------------|---------------------------------------------------------------------------------------|-----------------------------------------------------------|
| 业务经办人   | 提交合同、收到退回意见后修改再提交                                                    | 业务系统                                                  |
| 法务（全体） | 收到通知，逐条采纳、修改或驳回风险，定稿审查意见；也可在对话里随时上传合同让 Agent 审 | 业务系统为主，Tioka 对话与飞书为辅                        |
| 法务负责人   | 维护规则库、审核修订案例与正反例、看质量与价值报表、决定自治级别                      | 业务系统（规则与案例），Tioka Studio（Agent、评测、看板） |
| 业务系统     | 合同、规则库、修订案例、正反例、审查结果、处理流程的唯一事实来源                      | 新建                                                      |
| Tioka        | 本体抽取、多智能体审查、草稿结果写回、通知、评测与审计                                | Tioka                                                     |

**成功标准**（建议值，需与法务负责人确认）：高风险项漏报率低于 5%；每份合同从提交到通知不超过 10 分钟；法务对 Agent 意见的采纳率逐月上升；每条风险都能点回合同原文、所依据的规则版本和参考案例。

## 多智能体审查链路

审查分两段：先建模（`@model.build`），再在模型上判定 110 个要点。多智能体只用在需要大模型的部分；D 类 70 个要点（含必备 39 个）在模型上确定性判定，不进模型。判定只读模型，需要原文时按证据引用定位，不重新召回，这是脑图的约束。

### 一份合同从提交到通知

1.  **受理**：业务系统发 `lease.contract.submitted`，编排建工单和 Run（`subject_key = lease:{门店编码}:{合同号}:v{版本}`，串行；新版本取消旧版本未完成的 Run）。

2.  **建模**：按脑图十步跑「单份审查」用法。确定性步骤（文档层、金额事实预抽、校验）是工具；「逐对象抽属性」和「逐条款抽陈述」按对象、按条款并行，每个子任务是一次抽取 Agent 运行。补充协议从同门店已确认的模型取封闭集合。

3.  **定范围**：`@model.coverage` 给出 19 个主题的有 / 无 / 空白 / 不适用，按要点的适用条件筛出本份合同要判的要点，必备 56 个一个不能少。

4.  **判定**：D 类用 `rule.evaluate` 在模型上求 CEL；H 类先规则预判、再由判定 Agent 对照证据复核；J 类按主题分组交给判定 Agent，读模型陈述、证据原文和修订案例、正反例。

5.  **复核**：复核 Agent 用另一个模型家族，只看「不满足」和全部 H / J 结论：引文是否真实存在、对等配对是否比对、结论与正反例是否一致。退回的要点定向重判，最多 2 轮。

6.  **落库与通知**：模型草稿和审查结论草稿写入业务系统，再通知法务。回执校验器发现必备要点没有结论时拒绝结束，把缺口还给主审 Agent。

### Agent 角色

| Agent                    | 做什么                                         | 模型           |
|--------------------------|------------------------------------------------|----------------|
| 主审 Agent               | 编排两段、处理异常、决定重抽、重判或问人、汇总 | 主力模型       |
| 抽取 Agent（大量并行）   | 逐对象按画像抽属性组，逐条款按主题模板抽陈述   | 性价比模型     |
| 判定 Agent（按主题分组） | H 类复核、J 类判断，写理由和修改建议           | 主力模型       |
| 复核 Agent               | 独立复核不满足与 H / J 结论                    | 另一个模型家族 |

主审 Agent 的自主决策集中在三类情况：必备要点依赖的取值是「待复核」或低置信时，选择针对该对象重抽、按「缺失」上报并标注，还是用 `orch.receipt(ask)` 问经办法务；修改声明指向的对象找不到时，用 `@entity.read` 去读同门店的其他合同；J 类要点证据不足时，决定是否多查修订案例。步数、token 预算、委派深度、重判轮数都有上限。

### 容量

每天 10 份左右，每月约 200–300 份。容量不是问题，每份合同可以花几分钟、几十次模型调用，取准确而不取快。用规则级配额（`gov_quota.scope_type = rule`）给每份合同定 token 预算即可。

### 从 M3 到 M4 的过渡

建模本来就是固定流程，用 Flow 实现即可；审查段在子 Agent（RT-12）就绪前也先用 Flow（D → H/J 分组 → 复核 → 提交）。RT-12 就绪后，审查段换成主审 Agent 自主委派，判定 Agent、结论结构和评测集都不变。

## 业务系统集成

业务系统新建，建议与 Tioka 同栈（Java 17、Vue 3、PostgreSQL），并接同一个 Keycloak。它持有：已确认的模型实例与版本、模型确认界面、审查要点与阈值、修订案例与正反例、审查结论与处理流程、租约状态。Tioka 与它只经一个连接器插件 `biz.lease` 对接（ADR-029 第 23 条的通用连接器 SDK），不直连它的数据库。业务系统和 Tioka 由同一个团队开发。LAS 暂不对接。

### 三类对接

| 方向              | 内容                                                                                                                                                                         | 机制                                                                                                                                   |
|-------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|
| 业务 → Tioka 事件 | `lease.contract.submitted`、`contract.model.confirmed`、`lease.review.feedback`（逐条处理结果）、`lease.performance.*`（预警场景用）                                         | CON-07 入站，接口调用（HMAC + 时间戳验签）和 MQ 消息两种入口都支持，不关心触发方，映射出 `attrs` 与 `subject_key`，调 `OrchApi.ingest` |
| Tioka → 业务 工具 | `getContract`、`getContractFiles`、`getStoreModels`（同门店已确认模型）、`getCheckpoints`（要点与阈值，带版本）、`proposeModelDraft`、`submitReviewDraft`、`writeLeaseState` | CON-07 出站：OpenAPI 生成 `biz.lease.*` 工具，注册进 ToolGateway，统一审计，写操作带幂等键                                             |
| 业务 → Tioka 知识 | 修订案例、正反例、要点说明                                                                                                                                                   | `DataSourceConnector`（HTTP/REST）增量同步，带 `aclPrincipals`                                                                         |

### 业务数据怎么用

- **审查要点与阈值**：要点 = 主题 + 适用条件 + 检查方式（D / H / J）+ 是否必备。D 类的参数规则存 CEL，品牌红线等阈值单独配置。两者都版本化，审查时冻结版本并写进结论。

- **修订案例**：「原条款 → 修订后条款 → 理由」，按主题和要点打元数据，用 `metadataFilter` 召回。判定 Agent 用它写修改建议；脑图里 10 组样本租约的修订处也是「不满足」的参考答案。

- **正反例**：同一要点下可接受与不可接受的写法，既是 H / J 判定的证据，也是评测集种子。

- **审查结论落库**：`submitReviewDraft(runId, contractKey, modelVersion, checkpointVersion, findings[])` 写入草稿，返回 `reviewId` 用于深链。副作用等级 REVERSIBLE，可被新版本替换，不需要逐次人审。

### 新建业务系统的最小功能

1.  合同受理与文件管理（Word、PDF、图片），按门店维护合同链。

2.  模型确认界面：只显示与上一版本的差异，空白、低置信度、必备主题优先；每个值可以点回原文高亮。

3.  要点与阈值、修订案例、正反例的维护（法务负责人）。

4.  审查单：逐条采纳 / 修改 / 驳回，定稿或退回，处理结果经 webhook 回传。

5.  租约状态与台账视图（后续场景用）。

6.  上表的 API 与 webhook，审查单详情页支持 `/review/{reviewId}` 直接打开。

如果业务系统和 Tioka 由同一个团队开发，要控制第 2 项的工作量：确认界面是脑图划给平台的能力，可以做成 Tioka 的 Vue 组件嵌入业务系统，数据仍写业务库。

## 通知与卡片跳转

审查结束时主审 Agent 交回执 `notice`，编排按规则配置的接收人和渠道投递同一张与渠道无关的卡片（`ImMessage`）。卡片上只放摘要和入口，处理动作全部发生在业务系统。

### 接收人与渠道

所有渠道实现同一个适配器接口 `NotificationChannel`，按能力分两级：交互渠道能发互动卡片、接按钮回调；单向渠道只发摘要和链接。第一期只做飞书和邮件，其余渠道后续按同一接口添加。

| 渠道           | 能力 | 形态                    | 现状                                  |
|----------------|------|-------------------------|---------------------------------------|
| 飞书           | 交互 | 互动卡片，可更新状态    | M2 CON-02/03 已设计                   |
| 钉钉、企业微信 | 交互 | 互动卡片                | CON-06 原在 M4，PR #3 已推到 M4 之后 |
| Tioka 站内     | 交互 | thread 里的 `card` item | ADR-028 已有                          |
| 邮件           | 单向 | HTML 摘要 + 链接        | 新增（SMTP）                          |
| 短信           | 单向 | 一行摘要 + 短链         | 新增（客户短信网关）                  |

``` java
public interface NotificationChannel {
    String channel();                       // feishu / dingtalk / wecom / email / sms / custom:{name}
    ChannelCapabilities capabilities();     // interactive, supportsUpdate, maxLength
    DeliveryRef send(Recipient to, Notice notice);   // Notice 与渠道无关：标题、摘要、要点、链接、按钮
    default void update(DeliveryRef ref, Notice notice) {}
}
```

- IM 适配器同时实现 ADR-021 的 `ImChannelAdapter` 和这个接口，客户自研渠道按同一接口以插件 jar 接入。单向渠道上的按钮自动降级为链接。

- 接收人来自业务事件的 `attrs.assignee` 和业务线对应的法务组，渠道按用户偏好选；交互渠道发送失败或用户未绑定时，降级到邮件。

- 公司外的人（没有平台账号）只能收邮件或短信，内容只有摘要和链接，不含合同正文。

- 超过 SLA（建议 1 个工作日）未处理的，由编排定时器发升级提醒。

### 卡片内容

- 标题：合同名称、承租方、铺位；整体风险等级。

- 正文：高 / 中 / 低风险数量，前 3 条高风险的一句话理由，「需法务重点关注」的条数。

- 按钮：**去业务系统处理**（深链）、**在对话里追问**（打开本次审查的 Tioka thread）、**转给同事**。

- 处理后更新：业务系统发来 `lease.review.feedback` 时，用 `ImChannelAdapter.update` 把卡片改成「已由某人定稿」，避免群里重复处理。

### 深链与登录

- 链接形如 `https://lease.example.com/review/{reviewId}?src=tioka&n={notifyId}`：**不带任何令牌**（与 ADR-029 第 32 条「URL 中不出现令牌」一致），`notifyId` 只用于统计点击和审计。

- 业务系统与 Tioka 接同一个 Keycloak，飞书内打开时走飞书免登或 OIDC 静默登录；业务系统自己校验「这个人能否处理这份审查单」，不信任链接本身。

- 「在对话里追问」打开的 thread 已经带有合同模型和全部结论，法务可以问「为什么这条不满足」「给我一个更稳妥的写法」。追问以法务本人身份运行，按他们自己的权限检索。

### 反向：业务系统内嵌对话

法务大部分时间在业务系统里工作，建议在审查单详情页嵌入 Tioka 的对话面板，点某条 Finding 就能在侧栏追问。这需要可嵌入的对话组件或对外 Agents API（CHT-07，M3），属于缺口。

## 权限、授权书、审计、人审与自治阶梯

核心原则是：**Agent 看到的不超过它替谁干活的那个法务能看到的，能做的不超过授权书写明的**。

### 谁能用

- 建一个「法务」空间，审查 Agent 发布在里面，用 `sys_resource_acl` 把 USE 授给法务部的组；组成员由 SCIM / 组织同步自动维护（FND-09），入职即可用，离职即收回。

- 法务负责人拿 EDIT / OWNER：改 Agent、看评测、调自治级别。发布走 ADR-025 资产发布审批，并触发 EVO-06 回归门禁。

### 以谁的身份运行

| 入口                            | 身份                                         | 数据可见范围                         |
|---------------------------------|----------------------------------------------|--------------------------------------|
| 业务事件触发（origin=orch）     | 服务账号 `sa-lease-review`，**代表**经办法务 | 服务账号权限 ∩ 授权书 ∩ 经办法务权限 |
| 法务在对话里上传（origin=chat） | 法务本人                                     | 法务本人权限 ∩ 授权书                |
| 卡片「追问」                    | 点击的法务本人                               | 同上                                 |

第一行的「代表」是关键。如果只用服务账号，它能检索到所有业务线的修订案例，引用可能泄露给无权看的法务。现在 `run_as` 只存一个 Principal，需要加 `on_behalf_of`，这正是数字员工 D0「有效权限 = 委托人 ∩ 授权书 ∩ 空间策略」的落点。

### 授权书（D0，编译为 Cedar）

- 允许：读合同与文件、读规则 / 案例 / 正反例、写审查草稿、提交待确认事实、发通知。

- 禁止：定稿、退回、修改合同文本、对外发送合同全文、调用白名单以外的模型平台。

- 负责人：法务负责人。负责人离职时 Agent 自动暂停，等待移交。

- 模型：白名单为百炼与 DeepSeek 等平台；主力与复核分属两个模型家族。合同发往这两个平台已获同意，不脱敏。

### 审计与决策档案

三个治理卡点（ModelGateway、startTurn、ToolGateway）已经把每次模型调用、每次工具调用写进 `audit_event`，GOV-09 的哈希链防篡改。本场景再补一个「决策档案」：每条 Finding 能一键还原「原文位置 + 规则版本 + 案例 + Agent 版本 + 模型 + Turn 轨迹」，并支持用同样输入重放。这是数字员工 D4（原定 M4 之后）的最小版。

### 人审的三个位置

1.  **运行中提问**：附件缺失、类型无法判断、关键事实抽取置信度低时，`orch.receipt(ask)` 发卡片给经办法务，答完在同一 thread 续跑（HCI-05）。

2.  **结果处理**：逐条采纳 / 修改 / 驳回在业务系统完成，Tioka 不重复做处理流程。

3.  **事实确认**：合同模型在业务系统里只看差异确认（D24）；只有已确认的版本进入折叠、租金结构化和预警。

### 自治阶梯（D2）

| 级别    | 审查场景里的含义                                 | 晋升条件（建议）                  |
|---------|--------------------------------------------------|-----------------------------------|
| L0 影子 | Agent 与人工审查并行，结果不给法务看，只拿来对比 | 试点起点                          |
| L1 建议 | 草稿进业务系统，法务全量处理                     | 影子期 200 份以上，高风险召回达标 |
| L2 分流 | 标准模板且无中高风险的合同走快通道，法务抽检     | L1 连续 3 个月无高风险漏报        |
| L3 以上 | 不开放：定稿永远由人做                           | —                                 |

自治级别按「Agent × 动作类」记，出现一例高风险漏报就自动降一级并通知法务负责人。表中数字是建议值。

## 评测与价值账本

评测分两层，沿用脑图的定义：模型层看建模准不准，任务层看审查结论准不准。标准答案来自已确认的模型和法务的定稿结论，所以评测集会随使用自动变大。

### 数据集（按 ADR-031 `eval_dataset` 版本化）

- **金标准起步**：脑图里的 10 组样本租约（业主原稿标注模型，修订处作为「不满足」参考答案）。标注分工见文末「脑图待确认项的评估」。

- **正反例集**：每个反例是一条「必须判为不满足」的用例，每个正例是一条「不应误报」的用例。

- **线上回流**：模型确认时人工修正的值、审查单上的驳回和法务补出的不满足项，进「待标注」队列，确认后入回归集。按每天 10 份，一个月可以积累约 200 份。

### 指标与评估器

| 层     | 指标                             | 评估器                                               | 用途                               |
|--------|----------------------------------|------------------------------------------------------|------------------------------------|
| 模型层 | 对象、属性、陈述的准确率与召回率 | 逐字段比对已确认模型                                 | 建模版本发布门禁                   |
| 模型层 | 主题覆盖率、证据绑定率           | 规则评估器                                           | 防漏抽、防无据取值                 |
| 审查   | 「不满足」召回率                 | 按 `checkpointId` 对齐标准答案                       | 头号指标，发布门禁与自治晋升都看它 |
| 审查   | 四态一致率                       | 同上                                                 | 整体质量                           |
| 审查   | 必备要点有结论的比例             | 规则评估器                                           | 必须 100%                          |
| 审查   | 引文真实率                       | 引文逐字对得上证据单元                               | 防幻觉                             |
| 审查   | 修改建议质量                     | LLM-as-a-Judge，对照修订案例，按月与法务人工打分校准 | 参考                               |
| 线上   | 采纳率、耗时、成本               | 线上反馈与轨迹                                       | 价值账本                           |

### 回归门禁

除了 Agent / Skill / Prompt 发版（EVO-06），**要点与阈值发版、模型定义发版也要触发回归**：要点在业务系统里变，审查结果就会变；模型定义变了，按脑图约束派生层要重算。这要求实验变量里能放「要点版本」和「模型定义版本」，是一个缺口。

### 价值账本（D3）

- 基线：从业务系统历史数据算出「人工审一份合同的平均时长」和「从提交到给出意见的等待时长」。

- 每份合同记：Agent 耗时与成本、法务在业务系统处理耗时（业务系统回传）、采纳条数、漏报条数。

- 月报给法务负责人：节省人时、周转缩短、风险拦截数、每份合同模型成本。合同本体让「风险拦截」可以继续追踪到履约期：审查时被采纳的修改，日后是否真的避免了损失。

## 后续场景如何复用

五个场景都只读合同模型或租约状态，区别在触发方式、读哪一层和新增什么。审查与预警输出同一种结论，走同一条写回、通知、处理、反馈链路。

| 场景         | 触发                                                    | 读什么                                             | 新增什么                                                               | 产出             |
|--------------|---------------------------------------------------------|----------------------------------------------------|------------------------------------------------------------------------|------------------|
| 风险审查     | `lease.contract.submitted`                              | 单份模型（草稿即可）                               | 要点与阈值                                                             | 审查结论草稿     |
| 租金结构化   | `contract.model.confirmed`                              | 已确认模型 + 折叠后的租约状态                      | 租金台账投影（LAS 对接暂不做）                                         | 租金台账草稿     |
| 信息提取     | 按需                                                    | 基础字段视图 + 字段模板（模型路径 / CEL / 回原文） | 字段模板                                                               | 值 + 状态 + 证据 |
| 执行风险预警 | 租约状态时间轴到期（编排定时器）；`lease.performance.*` | 租约状态 + 履约事件                                | 履约事件接入、预警规则：欠租、递增未执行、押金余额不足、续租通知期临近 | 预警结论         |
| 权益受损预警 | 履约事件、新合同确认、定时扫描                          | 租约状态 + 权利与后果陈述 + 跨门店查询             | 跨合同规则：对方违约未主张、解约条件已成就未行使、主张期限将尽         | 权益结论         |

三点影响今天的设计：

1.  **履约事件是脑图之外的新输入**。租约状态现在是「合同约定了什么」，两类预警还需要「实际发生了什么」。建议在租约状态旁加一条实际时间轴（收款、开票、催缴、通知、押金变动），以 MQ 消息或接口调用进入，统一映射成 \`lease.performance.\*\` 事件，不关心触发方是谁。

2.  **预警以规则为主**。它们要定期扫全部门店，不应该每条都跑模型；编排的「研判 Agent」前置（ADR-020）只对命中的候选开 Run。

3.  **结论带 `scenario` 和生命周期**。同一个问题可能在审查时被接受、在履约时变成预警，业务系统要能把它们串起来。

## 暴露的平台缺口

这个场景暴露了 14 个缺口（第 11 项已定不做），前 8 个不补就做不出来。最大的是 Tioka 没有「业务本体」这一层：Knowledge 管文档和分块，不管带类型、带状态、带证据、带时间的业务事实。你们的脑图已经把这一层的平台部分定义清楚了，可以直接作为新 ADR 的输入。百炼、DeepSeek 都是 OpenAI 兼容接口，接入 Model Hub 不算缺口。

|-----|------------------------|---------------------------------------------------|---------------------------------------------------------------------------------------------------------------|------------|

## 落地节奏与待确认问题

建议分四步，每步以评测结果而不是功能清单作为闸门。

1.  **准备（与 M1–M2 并行）**：新建业务系统的接口契约、确认界面与要点管理；把规格 v2.3 落成领域包 v1（模型定义、校验、折叠）；D 类要点写成 CEL；用 10 组样本租约做金标准。业务系统与 Tioka 是同一个团队，34 号计划的 M3 要重排：业务系统只做最小功能，确认界面做成 Tioka 组件一次开发两处使用。

2.  **影子试点（M3 末，L0）**：文档层与 OCR、`@model.build` Flow、`rule.evaluate`、`biz.lease`、飞书与邮件通知。按每天 10 份，约 1 个月放满 200 份影子样本。闸门：不满足召回率、引文真实率达标，必备要点覆盖 100%。

3.  **建议模式（M4，L1）**：主审 Agent 自主委派（RT-12）、Charter 与代表身份、短信 / 钉钉 / 企微、嵌入组件、价值月报；同时上线租金结构化（先出台账，不对接 LAS）和信息提取。RT-12 已由多智能体设计提前到 M3，如果按时就绪，主审 Agent 可以并入第 2 步。
