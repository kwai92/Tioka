## 降级阶梯行为（§7.1）

`finalizeFinalMode` 以 `OutputContract.fallback` 有序步骤驱动，每步 `status` item 发 `output.fallback.{step}` 进度；足迹写 `producedBy.fallbackSteps`：

| 步骤 | M3 行为 | 足迹标记 |
| --- | --- | --- |
| `REPAIR` | 调 `repair`（见下）；截断跳过、拒答/过滤不修复并写 `guardrail.checked`、空输出原样重试一次 | `repair:exhausted` / `repair:early_stop` / `repair:token_budget` / `repair:disabled` / `repair:skipped_truncated` / `repair:skipped_refused` / `repair:skipped_content_filtered` |
| `SWITCH_MODE` | M3 无「更严生成方式」杠杆 → 跳过 | `switch_mode:skipped` |
| `SWITCH_MODEL` | M3 无候选切换（故障接力在 Model Hub，阶梯内不重复） → 跳过 | `switch_model:no_eligible_model` |
| `DECOMPOSE` | 归 SCH-12 → 跳过 | `decompose:deferred` |
| `FALLBACK_VALUE` | 调 `applyFallbackValues`；覆盖不全 → 保留原评估 | `fallback_value:applied` / `:uncovered` / `:no_declaration` / `:no_candidate` / `:still_invalid` |
| `HUMAN` | `createHumanTask`；接线则 `HUMAN_PENDING` + Turn 挂起并 return；未接线 → 记 `human:unavailable` 继续 | `human` / `human:unavailable` |
| `FAIL` | 终局失败 | `fail` |

- 每步只在 `ev` 尚不可交付时执行（`deliverable()` 命中即 `break`）；末步须终局（发布期 `FALLBACK_TERMINAL_REQUIRED` 守护）。
- 结局：`deliverable()` → `COMPLETED`；否则 `COMPLETED(errorCode=output_invalid)`。

## 修复分类与早停（§6）

`repair` 按 `ReasonCode` 分类：

- **`TRUNCATED`**：不按格式错误修复（重生成格式修不好截断），记 `repair:skipped_truncated` 直接进下一档。
- **`REFUSED` / `CONTENT_FILTERED`**：不修复不追问，写 `guardrail.checked`（FLAG，含 `reasonCode`）供审计，直接进下一档（如换模型）。
- **`EMPTY`**：原样重试一次（`maxRounds=min(1, maxRepair)`，不追加错误清单）。
- **其余**：把候选输出与错误清单（只给错误不给答案，以 user MESSAGE 承载）交回模型，同 `StructuredDemand`（同方言同生成方式）。
- 约束：`maxRepair`（缺省 2）轮 + `maxRepairTokens`（首次输出 completionTokens × 2，先到为准）；**早停**——错误集合（pointer+code+message）与上一轮完全相同立即停（`repair:early_stop`）。

## 兜底值（§7.3）

`applyFallbackValues`：候选须为对象 → `schemas.fallbackDeclarations(schemaRef)` 非空 → **全部错误路径都被 `x-tioka-fallback` 声明覆盖**（`FallbackDeclaration.covers`）才可用；否则 `fallback_value:uncovered` 保留原评估。覆盖则 `setPointer` 把候选对象上这些字段替换为 Schema 声明值，重跑第 5〜8 步（`complete`）：通过 → 结局 `VALID_WITH_UNKNOWN` + `unknownPaths`（兜底路径并入）；`fallback_value:still_invalid` 则保留原评估。**平台永不填「看起来合理」的默认值**——只取 Schema 声明的未知/待复核状态。

## 人工补录（§7.4）

- **生成**：`finalizeFinalMode` 走 `HUMAN` 步（或 `resumePending` 校验不通过）→ `HumanTaskSuspendService.create` 事务内插任务（`kind=data.complete`、`status=PENDING`、预填 `lastCandidate`、`pending_pointers` 为出错字段清单）+ 写 `data.complete` card item + Turn → `WAITING_APPROVAL`（`TurnRunner` 见该状态即释放锁与配额、不写终态）；`OutputStage` 写 `outcome=HUMAN_PENDING`（`valid=false`、`payload=null`，不交付部分对象）+ `humanTaskId`，并 return `awaitingHuman`。
- **提交**：`HumanTaskSubmitService.submit` 置 `SUBMITTED`（同结果幂等）并将原 Turn `requeueFromWaitingApproval` + `afterCommit` 入队。
- **续跑**：`AgentLoop.run` 首行短接 `OutputStage.resumePending`——`humanTasks.takeSubmitted(ctx)` 命中已提交任务 → 以 `evaluate`（第 1〜8 步）校验 `answerJson`：通过 → 写 `outcome=VALID`、`producedBy.human=提交人` 的 data item 并收口；不通过（人也会填错）→ 按原错误清单与候选**再次生成补录任务**、Turn 再次挂起。
- **超时**：`HumanTaskExpirer` 每分钟把到期任务置 `EXPIRED` 并把 Turn 置 `FAILED(HUMAN_TIMEOUT)`（缺省 72 小时，见偏差 3）。

## CONTENT_FILTERED 可达化（§5 第 1 步 / §6）

原 `DefaultModelGateway.invokeChat` 在 `content_filter` 时抛 `BizException(MODEL_ERROR, ...)`，使 `CONTENT_FILTERED` 结局在链路中不可达。本批删除该抛异常分支，改由 `ProviderClient` 的 `finishReason` 透传 → `OutputStage.rawOf` 置 `RawModelOutput(..., filtered=true)` → 评估为 `FAILED(CONTENT_FILTERED)`，且**不进入修复**（`repair:skipped_content_filtered`）并写 `guardrail.checked`。

## Flow 三端口（ADR-043 修订）

- 端口表：声明输出契约的节点改用 `in` / `valid` / `pending` / `failed` 四端口（`pending` 对应 `HUMAN_PENDING`，`failed` 对应 `FAILED`）。
- 发布校验 `checkOutcomePorts`：`failed` 端口须有连线，或 `config.onOutcomeFailure=fail_fast`（失败时终止并通知），否则 `OUTCOME_FAILED_PORT_MISSING` 拒绝发布。

## 迁移

`runtime_human_task`（V233，双份逐字一致：`tioka-server/src/main/resources/db/migration/` 与 `docs/contracts/db/`）：

- 主键 `id`；`workspace_id`（**带空间列，不进 `PersistenceProperties.workspaceScopeExemptTables`**，ScopeLine deny-by-default 下按空间过滤）。
- `subject_type` 限 `turn`/`flow_node_run`/`orch_run`；`subject_id`/`thread_id`/`turn_id`/`item_id`。
- `kind` 缺省 `data.complete`；`schema_ref`；`candidate_json`（`lastCandidate` 预填，不可消费）；`pending_pointers`（出错字段 JSON Pointer 数组）；`answer_json`（人提交数据）。
- `status` 限 `PENDING`/`SUBMITTED`/`EXPIRED`/`CANCELLED`；`decided_by`/`decided_at`/`expires_at`。
- 索引：`idx_human_task_subject (subject_type, subject_id)`、`idx_human_task_pending (workspace_id, status, create_at) WHERE status='PENDING'`、`idx_human_task_expiry (expires_at) WHERE status='PENDING'`。

## 偏差清单

1. **JSON Pointer 归一（本批关键修复）**：SCH-02/SCH-03 起 `OutputValidator` 直接 `message.getInstanceLocation().toString()` 取错误位置，返回 networknt 的 **JsonPath 形态**（`$.conclusion`、`$.evidence[0].quote`）；平台其余错误来源（证据、引用、规则）均产 **JSON Pointer**（§1.2 口径）。本批改用 `loc.getPathType().convertToJsonPointer(loc.toString())`，把 SCHEMA 错误统一为 `/conclusion`。**根因**：原口径不一致使 §7.3 兜底值的 `FallbackDeclaration.covers("/conclusion")` 永远匹配不到 `$.conclusion`，兜底值恒 `fallback_value:uncovered`（`OutputStageIT.fallbackValueYieldsValidWithUnknown` 首跑即暴露）。修复后 `$.conclusion`→`/conclusion`、`$.evidence[0].quote`→`/evidence/0/quote` 经实证（scratch 程序 + javap 验证 networknt 1.5.3 `JsonNodePath`）。`ToolCallPipeline` 等其它同库用法不受影响（各取所需）。
2. **阶梯步骤在 M3 的杠杆缺失**：`SWITCH_MODE`（无更严生成方式）、`SWITCH_MODEL`（阶梯内无候选切换；故障接力属 Model Hub 职责，不在 OutputStage 重复）按「跳过」记录（`switch_mode:skipped` / `switch_model:no_eligible_model`）；`DECOMPOSE` 归 **SCH-12**（`decompose:deferred`）。三者均不改变结局，仅留足迹，符合 §7.1「没有杠杆则跳过」。
3. **人工补录最小版口径**：
   - **超时以 72 小时近似「3 个工作日」**：ADR-066 §7.4 要求 3 个工作日，工作日历由 Foundation BAS-18 提供；本批按 `tioka.runtime.human-task-timeout-hours`（缺省 72）近似，BAS-18 接线后改口径。
   - **超时扫描复用 `@Scheduled`**：与 `SubAgentReaper` 等既有清扫范式一致，间隔可配（`tioka.runtime.human-task-expirer-interval-ms`，缺省 60s）。
   - **提交幂等**：任务已 `SUBMITTED` 时 `submit` 直接返回（同结果幂等），非 `PENDING` 抛 `CONFLICT`。
   - **校验落点**：提交时**不校验**答案，只置 `SUBMITTED` + 重新入队；第 3〜8 步校验由续跑后的 `resumePending` 承接（`evaluate` 含第 1〜4 步 process，比「第 3〜8 步」更全，口径取齐全链）。
   - **`HUMAN` 步未接线降级**：`HumanTaskPort` 为 null（如 `OutputStage` 7 参构造）时 `createHumanTask` 返回 null，记 `human:unavailable` 继续走后续步骤（末步 `FAIL` 兜底），不静默吞掉。
4. **`content_filter` 由抛异常改透传**：原 `DefaultModelGateway` 抛 `BizException(MODEL_ERROR, "内容安全拦截（content_filter）")`，使 §1.1 的 `CONTENT_FILTERED` 结局不可达、`rawOf.filtered` 为死路径。本批删除该分支（`SCH-07 遗留` 中登记的该项由此收口）。
5. **降级阶梯发布校验落点**：`FALLBACK_TERMINAL_REQUIRED` 加在既有 `OutputContractPublishCheck`（过 `schemaRef`/严格档后），不改发布主流程；`FallbackStep` 枚举与 `OutputContract` 第 8 组件随 agent-api 一起加，7 参兼容构造器保证既有 AgentSpec 零改动。
6. **Flow 端口校验为「新增」而非「改造」**：`checkOutcomePorts` 与四端口表按 ADR-043「修订」节实现；`fail_fast` 为 `failed` 端口的替代出口（继续沿用 FLW-10 的 DSL 校验骨架）。
7. **`resumePending` 契约前置判断**：先判 `contractOf`（非结构化 Agent 直接跳过），避免每次 Turn 都查补录任务表；`humanTasks==null` 时同样短路，保证未接线环境行为不变。
8. **`SubmittedCompletion` 位置**：record 必须内嵌于 `LoopPorts.HumanTaskPort` 接口内（`LoopPorts.HumanTaskPort.SubmittedCompletion`）；本批实现中一度误置顶层致 `HumanTaskSuspendService`/`OutputStage` 编译失败，已归位。
