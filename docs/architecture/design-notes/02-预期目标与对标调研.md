## 结论

Tioka 的预期目标是：**一套可私有化部署的企业 Agent 平台，用户在 Web 和飞书里与 Agent 协作，开发者用 Flow 和知识库构建 Agent，平台统一负责执行、选模、接入和治理。** 十层中每一层的「预期」，以对标产品在 2026 年已公开交付的能力为下限。

调研后的三个判断：

- **对标产品的基线已经很高。** 例如 LibreChat 已内置 SSO/LDAP/二步验证、角色权限管理、子 Agent、沙箱代码解释器和可恢复流式；Langflow 既是 MCP 客户端也是 MCP 服务端。Tioka 如果要「能力并集」，就不能只做演示切片。
- **差异化不在单层功能，而在「一个内核、一套治理」。** 对标产品各自独立：Chat、Flow、知识库各有自己的执行器和模型调用。Tioka 的价值在于所有入口都走同一个 Runtime、同一个 Model Hub、同一套身份、配额和审计。这是当前代码最缺的部分。
- **「达到预期」需要可验证的标准。** 建议每层用「关闭 mock、多实例部署、开启鉴权」的自动化验收来判定，而不是文档勾选。

下文按三组给出每层的预期能力和验收标准，最后是分阶段里程碑。「对标事实」来自公开文档，「预期」是我据此给 Tioka 定的目标，可以直接在文档里改。

## 交互与应用层：HCI、Chat、Flow、Knowledge

这四层的预期是「对标产品能做的，Tioka 都能做，而且都跑在统一的 Runtime 和治理之上」。对标事实列只列公开文档中确认过的能力。

| 层 | 对标已交付（公开事实） | Tioka 预期目标 | 验收标准 | 当前代码 |
| --- | --- | --- | --- | --- |
| HCI | AG-UI 协议：可取消/恢复的流式、声明式生成式 UI、共享状态、思考步骤、前端工具调用、中途中断审批、子 Agent、steering；LibreChat Artifacts（React/HTML/SVG/Mermaid） | Part 协议对齐 AG-UI 事件模型；卡片可提交并唤醒挂起的 Run；工作台、审批台、轨迹视图、产物中心；同一张卡片在 Web 和飞书两端渲染 | 断网重连后流式从断点继续；审批卡片提交后原 Run 继续执行；全部 Part 类型有渲染与快照测试 | D1：PartRenderer + 11 个联调页；卡片不唤醒执行 |
| Chat | LibreChat：Agent 可共享、MCP、Skills、子 Agent、沙箱代码解释器、定时对话、联网搜索带引用、用户记忆、文件对话、OCR、可恢复流、分叉、只读分享链接、项目、导入导出、Agents API | 以上能力全部具备；会话归属用户与空间；记忆注入上下文；分叉是独立 Runtime 分支；对外提供 Agents API | 用真实模型完成「上传文件 → 多步工具 → 引用回答 → 分叉 → 分享」端到端用例；两个用户互相看不到对方会话 | D1：同步发送、fork 共用 session、记忆不注入、无归属 |
| Flow | Langflow：可视化编辑、Playground、单组件运行、API 发布并支持运行时参数覆盖、自定义 Python 组件、同时是 MCP 客户端和服务端（Flow 作为工具、文件作为资源）；1.13 增加审计日志与并发编辑检查 | Flow 的每个模型和 Agent 节点都经 Runtime + Model Hub；自定义节点插件；发布为 API、Agent 工具、MCP 工具三种形态；人工节点能挂起并续跑 | 「Studio 建流 → 发布为工具 → Agent 调用 → 用量记入该 Agent 的配额」全链路非 mock；分支后汇合节点正确执行 | D1+：DAG 有，Agent 节点是单次 LLM，绕过 Model Hub |
| Knowledge | WeKnora v0.8：10+ 格式解析（含图片、Excel、XMind）、BM25 + 向量 + 可选 GraphRAG + Rerank、父子分块、ReAct Agent、可编辑 Wiki 带版本回滚、飞书/钉钉/语雀/Notion/GitLab 等数据源、MCP 对外、召回率和 BLEU/ROUGE 评测、10 种 IM 问答通道 | 解析、混合检索 + Rerank、分块编辑、Wiki、引用溯源、至少 3 类数据源增量同步、评测集、对外 MCP；嵌入模型经 Model Hub；知识库按空间授权 | 公开评测集上召回率有基线并进 CI；飞书文档修改后自动同步；无权限用户检索不到受限文档 | D1+：混合检索有，默认假向量、无 Rerank、一类数据源 |

## 执行与模型层：Orchestration、Runtime、Model Hub

这三层是 Tioka 的内核，预期标准最硬：对标产品在这里已经把「会话隔离、可恢复、轮次级决策」做成了默认行为。

| 层 | 对标已交付（公开事实） | Tioka 预期目标 | 验收标准 | 当前代码 |
| --- | --- | --- | --- | --- |
| Runtime | Codex harness：thread / turn 模型，一个 turn 内多次「模型调用 + 工具执行」迭代；工具执行前按审批策略拦截；OS 级沙箱；超阈值自动上下文压缩；app-server 协议让宿主应用创建线程、启动 turn、收事件、处理审批。AgentCore：每会话独立 microVM，执行最长 8 小时，支持 MCP 与 A2A | 多步 Agent 循环（最大步数、并行工具）；Turn/Step/Item 事件入库可重建；审批挂起与续跑；容器级沙箱执行代码和 Skill；上下文压缩；子 Agent；异步长任务；对外提供类 app-server 协议供 Chat / Flow / Orch / IM 共用 | 杀掉进程后会话从库恢复；两个实例间 cancel 与流式正常；100 个并发会话互不阻塞；一个需要 3 次工具的任务自动完成 | D1：一轮工具、全局锁、内存状态、无沙箱 |
| Model Hub | HiRoute（higress-group，Apache-2.0，v0.3.1）：固定 / 难度 / 自定义分支 / 免费优先四种路由；决策模型（Jev）结合任务难度与上一阶段胜任度评分；同一 turn 内工具续写继承决策，新用户消息重新决策；有界故障接力，耗尽时显式失败；按会话展示实际模型、用量、成本。LiteLLM：重试与指数退避、冷却、按 TPM/RPM 限流、延迟 / 成本 / 负载路由策略、会话亲和 | 四种路由模式 + 可插拔决策模型；轮次级冻结；自动故障接力；限流、重试、冷却；成本按会话 / Agent / 空间归集；全平台所有模型调用（含 Embedding）都经过本层 | 主模型故障时自动切到备用且有时间线记录；第二条消息可以重新选模；全仓除 Model Hub 外无直连模型的代码（ArchUnit 守护） | D1：会话级冻结、关键词难度、failover 无调用方 |
| Orchestration | LangGraph：checkpointer 持久化线程状态，用于人工介入、时间旅行和容错，生产用 Postgres。WeKnora：Redis 任务队列 + 分阶段 worker 池。autoloop / dsh-superagent 未找到公开资料，按项目内设计文档 S2 理解 | 事件 → 规则 → 工单 → Run → 派工给 Runtime 的完整闭环；规则条件表达式与灰度；Run 状态持久化可恢复；Attention 挂起→审批→续跑；定时与延时；跳数熔断；基于 MQ 的至少一次投递 | 飞书事件触发 → Agent 执行 → 卡片审批 → 续跑 → 结果回写飞书，中途重启服务不丢任务；多 worker 不重复领取 | D1−：只创建 Run，无派工、无 MQ |

## 接入与治理层：Connector、Foundation、Governance

这三层决定 Tioka 能不能进企业。对标产品的企业版把 SSO、SCIM、细粒度 RBAC、审计对接 SIEM、租户配额当作基本门槛，而 Tioka 这三层目前最薄。

| 层 | 对标已交付（公开事实） | Tioka 预期目标 | 验收标准 | 当前代码 |
| --- | --- | --- | --- | --- |
| Connector | AgentCore Gateway：把 API / 函数 / 服务转为 MCP 工具，语义选工具，访问控制到参数级。WeKnora：飞书 / 企微 / 钉钉等 10 种 IM 问答通道，MCP 支持 stdio / SSE / HTTP 与 OAuth2。Langflow：MCP 客户端 + 服务端 | MCP 客户端与服务端（含 OAuth）；工具网关统一鉴权、限流、审计；飞书入站事件 + 出站消息 + 卡片回调完整闭环，再复制到钉钉与企微；业务系统 Webhook 与 REST 转 MCP | 在飞书里 @Agent 发起对话并点击卡片审批；越权工具调用被网关拒绝并写审计 | D1：只有出站消息，无入站 |
| Foundation | Dify Enterprise：SAML / OIDC SSO、细到工作流级的 RBAC、SCIM 开通、会话策略、VPC / 私有化 / 空气隔离部署（Helm、Terraform）、自带密钥加密。LibreChat：SSO、LDAP、二步验证、Passkey、用户 / 组 / 角色 / 权限管理后台。AgentCore Identity：对接 Okta / Entra ID 等，工作负载身份与令牌保管库 | OIDC / SAML / LDAP 登录；SCIM 同步用户与组织；角色 + 权限点 + 资源级权限；服务账号与 API Key；代用户调用外部系统的令牌保管；Helm 部署与空气隔离安装包 | 用 Keycloak 登录；未登录请求全部 401；普通成员无法修改他人的 Agent；离线环境一键安装 | D0：无鉴权拦截、无 RBAC |
| Governance | AgentCore：Cedar 策略拦截每次工具调用；Registry 发布审批流程；Evaluations 按会话 / trace / span 评估；OpenTelemetry 观测。Dify Enterprise：防篡改审计日志推送 SIEM、按调用 trace、PII 脱敏、租户级配额与计费 | 空间与租户隔离；资产目录 + 发布审批（Agent / MCP / Skill / Flow / 模型）；工具调用策略引擎；全链路 OTel trace；按空间的 Token 与并发配额生效；不可篡改审计；内容安全钩子；多环境 | 超配额请求被拒；每一次写操作和工具调用在审计中可查；未审批的资产无法被会话使用 | D0：配额与审计有接口但未接入 |

## 里程碑

建议把预期拆成四个顺序里程碑，每个里程碑用一条「关闭 mock 的端到端场景」验收。当前代码处在 M1 之前。

| 里程碑 | 范围 | 验收场景 | 达成后对外口径 |
| --- | --- | --- | --- |
| M1 安全可用的单内核 | Foundation 鉴权与 RBAC；Runtime 多步循环、持久化、按会话并发；Model Hub 轮次冻结与自动故障接力；配额与审计接入主链路 | Keycloak 登录 → 选已发布 Agent → 真实模型多步调用 MCP 工具 → 双实例部署下流式与取消正常 → 用量计入空间配额 → 审计可查 | 可以做企业 PoC |
| M2 人机协作闭环 | Orchestration 派工与挂起续跑；MQ；飞书入站与卡片回调；审批台与轨迹视图；Part 协议对齐 AG-UI | 飞书事件触发 Agent → 飞书卡片审批 → 续跑 → 结果回写，中途重启服务不丢任务 | 可以在飞书里落地业务流程 |
| M3 构建者工具链 | Knowledge 对齐 WeKnora 主链（解析矩阵、混合检索 + Rerank、3 类数据源、评测进 CI）；Flow 节点走 Runtime，发布为 API / 工具 / MCP | 上传文档 → 引用问答召回率达基线；Studio 建流 → 发布为工具 → Agent 调用 | 开发者能自助搭建 Agent 应用 |
| M4 企业完备 | SCIM、资产发布审批、工具调用策略引擎、OTel 观测、沙箱代码解释器、子 Agent、钉钉 / 企微、Helm 与空气隔离安装包 | 离线环境一键安装；普通成员越权操作被拒并留审计；代码解释器在沙箱内运行 | 可以私有化交付 |

这与仓库现有的 R0 到 R6 计划的主要区别是：把鉴权、多实例和 Runtime 内核提到最前（M1），而不是在各业务域功能做真之后再补。
