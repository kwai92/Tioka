## 结论速览

**多智能体**：不新造执行引擎。把 ADR-027 的 `agent.delegate` 升级为「团队」：主管 Agent 产出一张类型化任务图，派工器把就绪任务作为子 Turn 并行跑，子 Agent 只交结构化产物到共享黑板，冲突走有轮数上限的仲裁，仲裁不下就转人审。一切等待沿用「挂起 Turn、事件唤醒」。

**权限**：核心一条，**权限只随委派收窄，永不放大**。每个 Turn 携带一份委派授予（DelegationGrant），子授予 = 父授予 ∩ 子 Agent 绑定 ∩ 子授权书 ∩ 任务声明的收窄。数据权限分四层（空间 → 资源 ACL → 文档 ACL → 行/字段），再加一条随产物流动的数据标签，管住模型选择和对外输出。

**与 PR #3 的分工**：Charter 回答「这个 Agent 平时能做什么、做多大」，本设计回答「一条委派链上，这一次能做什么、能看什么」。本设计不新增策略引擎，Cedar 仍是唯一的决策点；只在 ADR-032 上做两处增补（授权书增加「可下放的动作类别」，Cedar context 增加委派链），其余都是新增，不改 ADR-032〜035 已定的条款。

| 已有定案                                         | 本设计怎么用                                           | 改动                                           |
|--------------------------------------------------|--------------------------------------------------------|------------------------------------------------|
| ADR-016 Turn / ADR-027 子 Agent、`WAITING_CHILD` | 团队的子任务就是子 Turn                                | 深度、并行数改为由 TeamSpec 配置，平台上限不变 |
| ADR-020 编排、`orch_mandate`、回执               | 团队可作为编排派工的目标；换名义只能经 `emit` 开新工单 | 无                                             |
| ADR-023 AgentSpec、AST-02 发布校验               | 新增 TeamSpec（Agent 类型 = 团队），发布校验扩展到成员 | 增补                                           |

## 一、自主决策多智能体怎么建

自主决策落在四个动作上：规划、分派、协商、汇总。前三个由模型决定做什么，平台决定能不能做、做到哪里为止。这是全文的分界线：**模型可以自主选择路径，但路径上的每一步都在平台计算的边界内**。

### 四种协作拓扑，只做一种引擎

| 拓扑                       | 适用                                   | 在 Tioka 里怎么实现                                                |
|----------------------------|----------------------------------------|--------------------------------------------------------------------|
| 主管-专家（默认）          | 任务可拆、子问题不确定，如合同风险审查 | TeamSpec + 任务图 + 黑板（本节）                                   |
| 制作-复核（maker-checker） | 输出要质量门槛，如报告、改价           | 任务图里的 `verify` 节点，复核者是另一个 Agent 或 ADR-031 评测规则 |
| 固定流水线                 | 步骤确定、要可视化编辑                 | 直接用 Flow（ADR-019），Agent 节点计一层委派                       |
| 事件接力                   | 跨部门、跨名义、跨天的协作             | 编排回执 `emit` 派生新事件与新工单（ADR-020）                      |

去中心的「群聊式」自由对话不做：轮次不可控、责任不可归属、成本不可预算，与企业审计要求相冲突。协商改为黑板上的结构化冲突与仲裁。

### TeamSpec：团队是一种 Agent

团队作为 `AgentSpec.profile.type = TEAM` 发布，和普通 Agent 一样有版本、ACL、授权书、自治等级。用户和编排看到的是一个 Agent，内部是一组角色。

``` java
public record TeamSpec(
    String leadAgentVersionId,            // 主管：负责规划、重规划、汇总
    List<Role> roles,                     // 可用专家
    PlanPolicy plan,                      // 模板计划 / 自由规划、是否需要计划审批
    List<ArtifactType> artifactTypes,     // 黑板上允许的产物类型，引用 ADR-037 结构化产物的 Schema
    NegotiationPolicy negotiation,        // 冲突规则、仲裁者、最多轮数（默认 2）
    TeamBudget budget,                    // token、成本、墙钟、最多任务数
    Limits limits) {}                     // 深度≤ 3、并行≤ 8（平台上限）

public record Role(String code, String agentVersionId,      // 已发布专家，或
                   String templateVersionId,                // 临时子 Agent 的模板（见第二章）
                   List<String> consumes, List<String> produces,  // 产物类型
                   int maxInstances) {}
```

### 四个动作

1.  **规划**：主管的第一个 Turn 调内置工具 `team.plan`，交出任务图（DAG）。每个节点写明角色、输入产物、期望产物类型、任务授予的收窄（第二部分）、预算份额。平台校验：角色在 TeamSpec 内、无环、预算之和不超团队预算、产物类型已声明。校验失败则打回重写，最多 2 次（与 ADR-020 回执重写同一机制）。选择模板计划时，主管只能填参数、不能改结构。

2.  **分派**：`TeamDispatcher` 把入度为 0 的节点作为子 Turn 投到 `rt:turns`，主管 Turn 进入 `WAITING_CHILD`。任务行在 PostgreSQL，任何实例都能接着派，满足双实例闸门。

3.  **协商**：子 Agent 只能用 `team.publish(type, payload, evidence)` 往黑板写结构化产物。同一主键（如同一条款 ID）上出现矛盾结论时，平台生成冲突记录，派给仲裁者（主管或指定角色）。仲裁者可要求双方补证一轮，超过轮数上限则转人审。

4.  **汇总**：全部叶子完成后唤醒主管，主管从黑板生成最终结果，每条结论必须引用产物 ID；引用不存在的产物时校验失败。配了 `verify` 的，汇总先经复核者再交付。

重规划是自主决策的关键：任一节点失败、产物不达标或新产物揭示新问题时，主管被唤醒，可以增删未开始的节点。每次规划和重规划写一条 `team_decision`，带理由与前后 diff，进 why 时间线。单个团队 Run 最多重规划 3 次。

``` sql
CREATE TABLE team_task (id VARCHAR(32) PRIMARY KEY, team_run_id VARCHAR(32) NOT NULL, role_code VARCHAR(64) NOT NULL,
  depends_on_json TEXT, inputs_json TEXT, expected_type VARCHAR(64), grant_narrow_json TEXT, spec_json TEXT,
  budget_tokens INT, status VARCHAR(16) NOT NULL,      -- PENDING / READY / RUNNING / DONE / FAILED / SKIPPED / CANCELLED
  thread_id VARCHAR(64), attempts INT NOT NULL DEFAULT 0, plan_rev INT NOT NULL);
CREATE TABLE team_artifact (id VARCHAR(32) PRIMARY KEY, team_run_id VARCHAR(32) NOT NULL, task_id VARCHAR(32),
  type VARCHAR(64) NOT NULL, subject_key VARCHAR(255), payload_json TEXT NOT NULL, evidence_json TEXT,
  data_label VARCHAR(8) NOT NULL, author_agent VARCHAR(64) NOT NULL, create_at TIMESTAMPTZ NOT NULL DEFAULT now());
CREATE TABLE team_conflict (id VARCHAR(32) PRIMARY KEY, team_run_id VARCHAR(32) NOT NULL, subject_key VARCHAR(255),
  artifact_ids_json TEXT NOT NULL, round INT NOT NULL, status VARCHAR(16) NOT NULL, resolution_json TEXT);
CREATE TABLE team_decision (team_run_id VARCHAR(32), seq INT, kind VARCHAR(16) NOT NULL,  -- PLAN / REPLAN / ARBITRATE / ESCALATE
  reason TEXT, diff_json TEXT, at TIMESTAMPTZ NOT NULL, PRIMARY KEY (team_run_id, seq));
```

## 二、子 Agent 的生成、回收、失败与人审

子 Agent 有两种来源，权限规则不同。关键限制是：**主管可以生成提示词，但不能生成能力**。

| 来源         | 谁定义                           | 主管能改什么                                      | 权限上限                        |
|--------------|----------------------------------|---------------------------------------------------|---------------------------------|
| 已发布专家   | 构建者发布，走 AST-02 与发布审批 | 只能传任务与输入                                  | 该专家版本的 AgentSpec 与授权书 |
| 临时子 Agent | 从已发布「子 Agent 模板」派生    | 指令可生成；工具、Skill、知识库只能在模板内取子集 | 模板 ∩ 父授予                   |

临时子 Agent 不进资产库、不可被别人使用，其派生规格写在 `team_task.spec_json` 里并算哈希，审计可以还原。模板自己要有授权书，子 Agent 的动作类别和自治等级沿用模板的，这样 ADR-034 的晋级证据按模板积累，不会因为每次生成新 Agent 而清零。

### 生命周期

``` text
PLANNED ──就绪──▶ SPAWNED（建子 thread、签发子授予、划拨预算）──▶ RUNNING ⇄ WAITING_APPROVAL
   │                                                                  │
   └──重规划删除──▶ SKIPPED                     DONE / FAILED / CANCELLED ──▶ REAPED
```

回收（REAPED）在子任务进入终态时同事务完成：子授予标记失效（之后任何用它的工具调用都拒）；未用完的预算退回团队；子 thread 的沙箱立即释放（不等 15 分钟空闲），工作盘中被引用的文件提升为团队产物，其余按 7 天保留期清理；未决审批一并关闭。父 Turn 取消时级联取消（ADR-027 已定）。

### 失败处理

| 失败                            | 谁处理        | 动作                                                              |
|---------------------------------|---------------|-------------------------------------------------------------------|
| 工具报错、超时                  | 子 Agent 自己 | 按工具重试策略，写 item                                           |
| 子任务 FAILED 或产物不合 schema | 派工器        | 同角色重试 1 次（可换路由计划），仍失败唤醒主管重规划             |
| 预算耗尽                        | 平台          | 取消未完成子任务，主管用已有产物交部分结果，并发 `ask` 问是否追加 |
| 已对外产生副作用后中断          | 人            | 进入 `UNCERTAIN`（ADR-020），可撤销的按 ADR-033 一键撤销          |
| 冲突超轮数                      | 人            | 仲裁卡片，展示双方产物与证据，人选一方或写结论                    |
| 重规划超 3 次                   | 人            | 团队 Run 停下，结局 FAILED，卡片说明卡在哪                        |

### 人审放在哪

人审不另造，全部用通用审批表和 ADR-034 的等级判定，只新增两种 subject_type：

- **计划审批**（`team_plan`）：团队的「规划」动作类别处于 L1 时，任务图先给人看再开跑；L2 及以上只在计划超模板或预算超 50% 时审。

- **仲裁**（`team_conflict`）：见上表。

- 子 Agent 自己的写操作，按它各自动作类别的等级审，审批卡片标明委派链（「合同审查团队 → 财务条款专家」）。四眼原则对链上发起人生效。

## 三、权限模型：委派链与授予收窄

多智能体的权限风险只有一个根源：一个权限大的 Agent 被一个权限小的人或 Agent 指使，或者被数据里的文字指使（提示注入）。解法是能力衰减：权限只从配置和人的审批里来，沿委派链只减不增，模型输出和工具结果里的任何文字都不改变授予。

### 三个问题分开回答

| 问题                   | 载体                                                                                                                                                      | 在链上怎么变                                                                                                 |
|------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------|
| 以谁的名义（身份）     | `根 Principal：发起人或服务账号（ADR-032 actingAs）；服务账号模式另带 on_behalf_of（代表哪位经办人，与合同审查设计一致），此时根权限 = 服务账号 ∩ 经办人` | **全链不变**。子 Agent 不能中途换成服务账号；确需换名义，只能经编排 `emit` 开新工单，生成新的 `orch_mandate` |
| 经过哪些 Agent（链）   | `DelegationChain`：根 → 主管 → 子 → 孙                                                                                                                    | 每委派一次追加一节，深度≤ 3                                                                                  |
| 这一次能做什么（授予） | `DelegationGrant`，存在子 thread 上                                                                                                                       | 只能取交集                                                                                                   |

### DelegationGrant

``` java
public record DelegationGrant(
    String grantId, String parentGrantId,          // 根授予的 parent 为空
    String rootPrincipalRef,                       // run_as，只存身份不存权限集（定案 6）
    List<ChainHop> chain,                          // agentVersionId + taskId
    Set<String> tools,                             // 工具名（含 MCP、flow.*、内置）
    Set<String> actionClasses,                     // 可用的写动作类别
    Set<String> skillVersionIds,
    Map<String, Set<String>> resources,            // kb / dataset / mcp / flow → ID 集合
    Map<String, Object> scope,                     // 参数范围，如 {"contractId":["HT-2026-031"]}
    String maxDataLabel,                           // 能读的最高数据标签（第四章）
    Set<String> egressHosts,
    Budget budget, Instant expiresAt, String hash) {}
```

签发规则（`GrantService.narrow`，委派时同事务写入）：

``` text
子.tools          = 父.tools ∩ 子 AgentSpec.tools ∩ task.narrow.tools
子.actionClasses  = 父.actionClasses ∩ 父授权书.delegable ∩ 子授权书.actionClasses
子.resources      = 父.resources ∩ 子 AgentSpec 绑定 ∩ task.narrow.resources
子.scope          = 父.scope ∧ task.narrow.scope            -- 只能加条件
子.maxDataLabel   = min(父, 子 AgentSpec.dataClearance)
子.budget         ≤ 父.budget 剩余额，划拨即冻结
子.expiresAt      ≤ 父.expiresAt
```

校验不靠自觉：`narrow` 只接受集合、区间、枚举三种可证明收窄的形式，输出不是输入的子集就拒绝签发。权限的实时性仍靠定案 6：根身份的权限每次工具调用前重新加载（60 秒缓存），授予是在它之上的再收窄，所以根用户被收权后整条链同时失效。

### 有效权限公式：把 ADR-032 从单个 Agent 推广到链

``` text
有效权限(调用) = 根身份权限                    -- ADR-032 不变
              ∩ 执行者授权书（完整）            -- ADR-032 不变
              ∩ 链上每个祖先的禁区与可下放类别   -- 新增
              ∩ 委派授予                      -- 新增
              ∩ 空间策略（Cedar）              -- ADR-025 不变
```

为什么祖先只看「禁区 + 可下放」：主管常常自己只读、把写操作派给专家，如果要求主管授权书也含该写类别，就等于给主管开写权限，反而扩大攻击面。所以对 ADR-032 的增补是：`Charter` 加一个字段 `delegable: List<String>`（可交给下属的动作类别），缺省为空，即不配置就不能下放任何写操作。

### 在 Cedar 里怎么表达

不加引擎，只给 ADR-025 / ADR-032 的 context 加三个属性：`context.chain`（链上 agentVersionId 集合）、`context.depth`、`context.grantScope`。`CharterCompiler` 编译禁区时把 `context.agentVersion == X` 改为 `context.chain.contains(X)`，祖先的禁区就自动约束整条链；额度类策略仍只对执行者生效。空间管理员可以写链级策略，例如：

``` cedar
@id("space:no-irreversible-below-depth-1")
@effect("ESCALATE")
forbid (principal, action, resource)
when { context.depth >= 2 && resource.reversibility == "IRREVERSIBLE" };
```

含义是：孙子层级的 Agent 做不可撤销的事，一律要人批。

### 对外系统看到的是谁

- DELEGATED：MCP 与业务系统都用根用户在 TokenVault 里的令牌（FND-08），子 Agent 没有自己的凭证。外部系统自己的行级权限因此天然生效。

- SERVICE：用服务账号凭证，外部系统看不到细分，所以行级权限必须在 Tioka 的连接器层补上（第四章）。

- 对 Tioka 自己的下游服务（对外 MCP、Agents API），可用 Keycloak 的 Token Exchange（RFC 8693）换出带 `act` 声明的缩权令牌，标明「用户 A 经 Agent X」。放 M4，P2。

## 四、数据权限：四层过滤加一条标签

数据权限在取数时生效（看不到就不会泄露），数据标签在取数之后生效（看到了就管住它去哪）。多智能体比单 Agent 多出来的风险在后者：一个子 Agent 合法读到的敏感数据，经黑板传给另一个子 Agent，再被发到群里或公有云模型。

### 四层取数过滤

| 层          | 粒度                             | 机制                                              | 出处                         |
|-------------|----------------------------------|---------------------------------------------------|------------------------------|
| L1 空间     | 空间整体                         | MyBatis-Plus 拦截器自动加 `workspace_id`          | ADR-015，不变                |
| L2 资源     | 知识库、数据集、MCP Server、Flow | `ResourceGuard` USE ∩ 授予 `resources`            | ADR-015 + 本设计             |
| L3 文档     | 知识库内单篇文档                 | `aclPrincipals` 与知识库权限取交集，SQL 下推      | ADR-018 / ADR-029 #23，不变 |
| L4 行与字段 | 业务数据的行、列                 | 数据集策略：行谓词 + 列掩码，在连接器数据平面执行 | 新增                         |

L4 的对象是「数据集」：通用连接器（JDBC、HTTP/REST、业务插件如 `biz.lease`）把一张表、一个视图或一个查询接口登记为数据集，声明列和列的密级。Agent 不写 SQL 直连业务库，只调 `data.query(dataset, filter, columns)` 或业务插件的查询工具。

``` java
public record DatasetPolicy(String datasetId, int version,
    List<RowRule> rows,          // 多条取并集；一条也不命中 = 一行都看不到
    List<ColumnRule> columns) {} // 未列出的列按列密级的缺省掩码
record RowRule(String when,      // CEL，只引用 principal 属性（部门、区域、角色）
               String predicate) {}  // CEL 子集，引用行列，编译为 SQL WHERE 或 API 过滤参数
record ColumnRule(String column, String when, Mask mask) {}
enum Mask { NONE, PARTIAL, HASH, NULLIFY, DROP }
```

示例：`when: principal.roles.contains("lease_legal")`，`predicate: row.region in principal.attrs.regions`；承租方银行账号 `PARTIAL`，只有 `finance` 角色是 `NONE`。

- 执行点在连接器 SDK：JDBC 类把谓词编译进外层 `SELECT … FROM (原查询) t WHERE …`，参数化绑定；API 类优先映射为过滤参数，不支持的在插件内后过滤（记一条「后过滤」事实，提示性能）。列掩码在结果离开插件前完成，模型拿到的就是掩码后的值。

- 为什么用 CEL 不用 Cedar：Cedar 输出是允许/拒绝，给不出「哪些行」；它的部分求值可以产出残差，但 cedar-java 里仍是实验特性。CEL 已用于编排条件（ADR-020）和合同规则，少一种语言。Cedar 仍管「能不能查这个数据集」，CEL 只管「查到哪些行列」。

- 委派时只能再加条件：授予的 `scope` 与行谓词 AND 合并，如主管把「只看合同 HT-2026-031 的账单」下放给规则判定 Agent。

- DELEGATED 模式下外部系统自己也会过滤；数据集策略仍然执行，是外部系统权限粗糙时的兜底。

### 数据标签：看到之后管住去向

密级四档：`PUBLIC < INTERNAL < CONFIDENTIAL < SECRET`。标签来自数据集列密级、知识库或文档密级、MCP Server 的配置、上传文件的空间缺省值。规则只有三条：

1.  只升不降：每个工具结果 item 带 `dataLabel`；Turn 的标签取已读内容的最高值；子 Agent 产物继承其 Turn 的标签写上黑板；主管读了该产物，自己的标签也升上去。压缩摘要、记忆、经验条目都继承来源标签。

2.  读取要许可：授予的 `maxDataLabel` 低于产物标签时，子 Agent 读不到该产物（黑板也是一个执行点）。

3.  对外要许可：模型调用、IM 消息、邮件、外部 MCP、写工具参数，每个去向都有许可密级。Turn 标签高于去向许可时：模型调用改用允许该密级的路由计划（如只允许私有化模型）；消息类去向先经 ContentSafetyHook 脱敏，脱敏后仍超则拒绝或转审批。

第 3 条与差异化方向 D4「数据分级路由」是同一件事，这里只做其中「按密级选可用模型」的最小部分。

### 共享记忆是最容易漏的口子

Agent 级经验（ADR-031）是跨用户共享的。审查 A 用户合同时学到的「经验」如果带着具体金额，就会在 B 用户的会话里出现。规定：经验只接受 `INTERNAL` 及以下的内容；来源为更高密级的候选经验先经脱敏和人工审核；用户记忆只属于本人，子 Agent 不读根用户以外的记忆。

## 五、Skills、MCP、Workflow 的绑定权限

三类能力统一过三道门：**发布时**（绑得上吗）、**委派时**（传得下去吗）、**调用时**（这一次能用吗）。它们都不是身份，只是「被 Agent 使用的能力」，调用时的身份永远是委派链的根。

| 门                    | Skill                                                                                                    | MCP 工具                                                                                | Workflow（Flow 发布）                                                                                                   |
|-----------------------|----------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------|
| 发布时（AST-02 扩展） | 版本已签名；清单声明的工具、主机、路径、最高数据标签 ⊆ Agent 的 ToolSet、沙箱策略与 dataClearance        | 发布者对 Server 有 USE；引用不可变快照号 + 工具白名单；非只读工具必须归入授权书动作类别 | 发布时自动算出 `requiredCapabilities` = 全部节点工具、知识库、数据集、子 Agent 的并集；绑定到 Agent 时要求 ⊆ Agent 绑定 |
| 委派时                | `skillVersionIds` 取交集；子 Agent 不继承父的 always Skill 文本                                          | 工具名取交集；Server 的代用户令牌仍属根用户                                             | Flow 里的 Agent 节点计一层委派，占深度与预算                                                                            |
| 调用时                | `skill.load` 只能加载授予内的版本；脚本只在沙箱内跑，出网 = Skill 主机 ∩ 沙箱白名单 ∩ 授予 `egressHosts` | ToolGateway 全管线（下一章）；Server 熔断时从工具列表移除；结果按 Server 密级打标签     | `flow.{name}` 以**调用方的授予**运行，不用 API Key 的服务账号；每个节点的工具调用都进 ToolGateway                       |

### 三个容易做错的地方

1.  **Skill 不能「带来」工具**。Skill 的清单是上限声明，不是授权。SKILL.md 里写「调用 xxx」不会让 xxx 出现在工具列表里。这也是防提示注入的前提：文本只能影响模型选择，选择范围由授予决定。

2.  **Flow 不能成为提权通道**。ADR-019 里 API 形态以 API Key 的服务账号运行、Agent 工具形态以 Turn Principal 运行，这是对的；本设计补一条：Agent 工具形态把整份授予（含链、标签、预算）带进 Flow Run，Flow 内部的每次模型与工具调用都用它，`requiredCapabilities` 超出授予时直接拒，而不是跑到半途失败。

3.  **MCP 工具的自述不可信**。`readOnlyHint` 只用于给管理员提示缺省值（ADR-033 已定），工具描述与结果全部当作不可信数据进上下文；快照刷新后工具描述或 schema 变了，已发布 Agent 仍用旧快照，要用新的必须重新发布并过审批。

### 编排规则也是一种绑定

编排规则绑定服务账号与 Agent（ADR-020），派工时的根授予 = 服务账号角色 ∩ 经办人（on_behalf_of） ∩ Agent 授权书 ∩ `orch_mandate.scope_json`。规则上的 `emits` 白名单就是「这个团队可以把哪些事转给别的部门」的授权。

## 六、执行点与审计

全平台只有九个执行点，其中五个已在既有 ADR 里，四个是本设计新增。任何新功能都必须走其中一个，不允许绕过（ArchUnit 检查：只有连接器包能引用 JDBC 数据源与 EgressClient）。

| #  | 执行点                         | 检查什么                                                                                                          | 状态            |
|-----|--------------------------------|-------------------------------------------------------------------------------------------------------------------|-----------------|
| P1  | API 入口                       | 登录、空间成员、`@RequirePermission`                                                                              | ADR-015         |
| P2  | `startTurn`                    | Agent 已发布、ACL USE、授权书 ACTIVE、配额                                                                        | ADR-016/025/032 |
| P3  | `agent.delegate` / `team.plan` | 角色在 TeamSpec 内、深度、并行、预算、`GrantService.narrow`                                                       | **新增**        |
| P4  | ToolGateway `prepare`          | 在 ADR-033 的 12 步里插入第 2.5 步「授予校验」：工具、资源 ID、scope 参数、授予未失效；第 9 步 Cedar context 加链 | 增补            |
| P5  | 连接器数据平面                 | 数据集策略（行、列）、结果打标签                                                                                  | **新增**        |
| P6  | 知识检索                       | 知识库 ACL ∩ 文档 ACL ∩ 授予 `resources` ∩ `maxDataLabel`                                                         | 增补            |
| P7  | ModelGateway                   | Turn 标签 → 可用路由计划                                                                                          | 增补            |
| P8  | 对外去向                       | IM、邮件、外部 MCP 的密级许可 + ContentSafetyHook                                                                 | 增补            |
| P9  | 黑板读写                       | 产物类型已声明、schema、读取方密级许可                                                                            | **新增**        |

执行点只读快照和授予，不读模型输出。所以即使一个子 Agent 被工具结果里的文字「说服」了，它能做的事也不会变多。

### 审计：每条记录都能还原整条链

`audit_event` 加五个字段，哈希链与外送（GOV-09）不变：

``` sql
ALTER TABLE audit_event ADD COLUMN root_principal VARCHAR(64);   -- 以谁的名义
ALTER TABLE audit_event ADD COLUMN on_behalf_of VARCHAR(64);     -- 代表谁
ALTER TABLE audit_event ADD COLUMN chain_json TEXT;              -- [agentVersionId, taskId] 列表
ALTER TABLE audit_event ADD COLUMN grant_id VARCHAR(32);
ALTER TABLE audit_event ADD COLUMN data_label VARCHAR(16);
```

- 拒绝记录写明是哪个执行点、哪一步、命中哪条策略 `@id` 或数据集策略版本。

- 行级过滤不记行内容，只记策略版本、返回行数、被掩码的列名。

- OTel trace：团队 Run 一个根 span，每个子任务一个子 span，轨迹视图按任务图展开，点进任意子 thread。

- why 时间线：`team_decision`（规划、重规划、仲裁、升级）与 `orch_fact` 合并展示，回答「为什么去问了这个专家、为什么没问那个」。

- 权限回答页：管理端输入「用户 + Agent + 工具/数据集」，给出有效权限及每一层的裁剪原因。这是运维和审计问得最多的问题。

## 七、贯穿示例：商业租赁合同风险审查

角色与流程完全沿用[合同审查设计](https://claude.ai/artifact/PxdZR5xfAkyauCJ7AUQfAd)：主审 Agent 委派合同解析、规则判定（按六个条款组并行）、复核三类专家，必审检查点覆盖率由回执校验器程序兜底。本节只补它没展开的两件事：团队怎么配，授予怎么一路收窄。

**团队配置**：发布一个 TEAM 类型的「租赁合同审查」，用模板计划（解析 → 六组判定 → 复核 → 定向重审），主审可以追加检查点节点、不能删必审节点。产物类型引用 ADR-037 的 Finding 与本体事实 Schema。冲突规则：同一检查点上「规则判定」与「复核」结论不同，仲裁者是主审，最多 2 轮，仍不一致标「需法务重点关注」。复核角色绑定另一模型家族的路由计划。

**根授予**（业务事件触发）：服务账号 `sa-lease-review`，on_behalf_of = 经办法务张三，scope = `{contractId: HT-2026-031, version: 3}`，maxDataLabel = CONFIDENTIAL，路由只允许私有化模型。

| 角色         | 工具（∩ 父）                                                                  | 数据范围                                    | 写动作类别                                                                 |
|--------------|-------------------------------------------------------------------------------|---------------------------------------------|----------------------------------------------------------------------------|
| 主审         | 全部只读工具、`agent.delegate`、`biz.lease.submitReviewDraft`、`orch.receipt` | 本合同 + 张三可见的案例库                   | `lease.review_draft`（REVERSIBLE，L2）；`delegable = [lease.fact_propose]` |
| 合同解析     | 文档解析、模板比对、`ontology.propose`                                        | 本合同文件与标准模板                        | `lease.fact_propose`（从主审下放）                                         |
| 规则判定 × 6 | `rule.evaluate`、`kb.search`                                                  | 本组条款；案例库加 `clauseType = 本组` 过滤 | 无                                                                         |
| 复核         | `ontology.get`、`citation.verify`、`kb.search`                                | 全部 Finding 与本体事实                     | 无                                                                         |

这样安排后可以证明几件事：

- 规则判定 Agent 即使被合同正文里的「请忽略违约条款」误导，也没有任何写工具；漏判的检查点会被回执校验器拦下。

- 任何角色都读不到张三无权看的业务线案例，因为根权限已与张三取交集。

- 「定稿」「对外发送合同全文」在主审授权书的禁区里，编译为 `context.chain.contains(主审)`，整个团队都做不了。

- 整个 Run 的标签是 CONFIDENTIAL，飞书卡片只带摘要与深链，正文经 ContentSafetyHook 去掉金额与账号。

- 张三离职或被移出法务组：60 秒内根权限重载，整条链的后续工具调用被拒，Run 转给法务组其他人重新发起。
