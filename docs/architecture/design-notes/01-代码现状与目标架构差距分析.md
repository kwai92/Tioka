## 结论摘要

Tioka 目前是「设计文档覆盖十层，代码只撑起四层的演示骨架」：约 1.17 万行 Java 主代码 + 3 千行前端，对应约 9 千行设计文档。Runtime、Model Hub、Knowledge、Flow 有能跑的切片；Foundation 和 Governance 两层基本不存在；Orchestration 只有数据表没有执行引擎。

仓库自带的 `33-差距收口` 和 `depth-gap-inventory` 已经承认了大部分功能缺口（mock 默认开、哈希向量、节点语义浅等），但漏掉了下面几个更底层、影响架构方向的问题：

1. **全站没有鉴权**。除 `/api/system/auth/me` 外，所有接口匿名可调；没有角色、没有 RBAC、没有权限注解或拦截器；默认账号 admin/admin123，密码用无盐 SHA-256，token 不过期。「企业级」「治理平台」的前提目前为零。
2. **Runtime 不是 Agent 循环，也不能水平扩展**。工具调用只支持一轮（调完工具后续写时传入空工具列表）；`append` 在整个 Service 上加了 `synchronized`，所有会话串行执行；会话状态和 SSE 连接都放在 JVM 内存 Map 里。
3. **Model Hub 的「同轮冻结」实际是「整会话冻结」**，难度路由只对第一条消息生效；故障接力没有任何代码调用；Flow 的 LLM/Agent 节点直接读节点配置里的 baseUrl 和 model，完全绕过 Model Hub。
4. **编排层只有表，没有引擎**。事件 → 规则（三种 if 分支）→ 写一条 Run 记录，然后就没有人把 Run 派给 Runtime 执行；全仓 MQ 生产/消费为 0。
5. **工程信号不可信**。main 分支 `mvn test` 当前是红的（`OrchAttentionTest` 依赖测试执行顺序），而文档写的是 BUILD SUCCESS；Chat、Connector、Skill、Infra 四个模块 0 测试；配额、审计服务写了但业务代码从不调用；多项 W5 能力是假实现（GraphRAG 返回写死数据、代码解释器返回 `code.hashCode()`）。

**判断**：按项目主题定义的「企业级套件 + 运行中台 + 治理平台」，现状大约在「单机 Demo」阶段。建议先补 Foundation 鉴权和 Runtime 内核这两个地基，再继续加厚上层功能，具体顺序见最后一节。

## 十层架构逐层对照

十层里没有一层达到「关掉 mock 后主路径符合设计」（D2），最弱的是 Foundation 和 Governance。深度沿用仓库自己的定义：D0 空壳 · D1 可串通切片（允许 mock）· D2 保真路径 · D3 可验收。表中按差距从大到小排序。

| 层 | 对标 | 现状深度 | 已有 | 关键缺口（代码证据） |
| --- | --- | --- | --- | --- |
| Foundation | IAM/SCIM + RuoYi + AgentCore | D0 | 用户名密码登录、mock OIDC、SecretStore AES、SPI 接口 7 个 | 无任何鉴权拦截（无 Filter / Interceptor / SecurityFilterChain）；无角色与 RBAC；无组织架构；SCIM 只是把 JSON 存进一张表；SPI 实现多为 Noop；AirGap 判断用 `url.contains("localhost")`，可被 `?localhost` 绕过 |
| Governance | AgentCore | D0 | Quota 表与接口、FileAuditSink、资产目录接口 | `QuotaService.acquire/consumeTokens` 在业务代码中零调用，配额不生效；审计只有运维接口读，业务不写；无租户、无多环境、无内容安全（Noop）；workspaceId 在 Chat 里写死 `ws_default` |
| Orchestration | autoloop / superagent | D1− | 事件幂等、规则版本、Run 租约、Attention、why 日志 | 规则只有 ignore / create_run / open_attention 三个 if；Run 创建后无人派给 Runtime；无 MQ；`ingestEvent`/`claim` 是单机 `synchronized`；定时与 later 只有 API |
| Connector | dsh-feishu + WeKnora 数据源 | D1 | 飞书 IM 发消息、飞书文档同步、钉钉/企微 Webhook、MCP 客户端与出口 Server | 只有出站，没有 IM 入站回调（用户在飞书里无法对话或点卡片续办）；数据源仅飞书一类；模块 0 测试 |
| Chat | LibreChat | D1 | 会话、消息、卡片提交、fork、记忆表 | `send` 在 HTTP 请求内同步跑完整轮；消息与 Runtime parts 双份存储；fork 复用同一个 runtime session，不是真分支；长期记忆写了但不注入模型；无编辑/重试/分享/提示词库；会话无归属用户 |
| HCI | LibreChat 壳 + 飞书卡片 + IDE 轨迹 | D1 | 11 个页面、PartRenderer、Vue Flow Studio、TS + Pinia + Element Plus | 整个前端 3k 行；没有工作台、产物中心、知识台、轨迹视图；Observability 页 61 行；CI 不构建前端 |
| Runtime | Codex / DeepSeek harness | D1 | 流式接口、ToolGateway + Grant 校验、Steer/Cancel、Skill 注入、工作区目录 | 工具只跑一轮，不是多步循环；全局 `synchronized`；状态在内存且不回收；parts 以整块 JSON 存会话行；无沙箱、无审批挂起、无上下文压缩、无 SubAgent 执行（`SubAgentPolicy` 只有深度校验） |
| Model Hub | HiRoute | D1 | Provider/Binding/RoutingPlan、发布、OpenAI 兼容流式客户端、用量事件 | 冻结是会话级而非轮次级；难度路由是「含“复杂”或长度 >500」；无决策模型；failover 仅能手工 HTTP 触发；无重试限流；Flow 绕过本层；`lastRoutes` 在内存 |
| Flow | Langflow | D1+ | 拓扑调度、Branch、有界并行、14 种节点执行器、发布、Studio | Agent 节点只是一次 LLM 调用（system 提示词是 "agent"），不走 Runtime；Branch 后的汇合节点因入度归不到 0 而永不执行；HumanCard 不中断下游；无自定义节点机制 |
| Knowledge | WeKnora | D1+ | PDF/DOCX 解析、关键词 + 向量 RRF 融合、citation、pgvector 路径、评测接口 | 默认 HashEmbedding（假向量）；固定 200 字切块；无 Rerank、无 OCR；每次检索都写 citation 表；GraphRAG 返回写死结果；Wiki 只是再 ingest 一次 |

对照依据：项目主题中的十层表（与 `docs/architecture/systems/S0-体系总览与边界.md` 一致），代码为 main 分支 fb27c4e。

## 架构与横切问题

这些问题不属于某一层，但决定了上面每一层能不能「加厚」而不是「重写」。仓库自审文档大多把它们列为 P3 或未提及，我的判断是其中前三项应该是 P0。

1. **安全模型缺位（P0）**。没有请求级用户上下文，所以也就没法做数据权限、审计归属和配额计费。这不是补一个 Filter 就能解决的：会话、Agent、知识库、Flow 等实体都没有 owner 或 workspace 的校验。越晚补，要改的实体越多。
2. **单机内存状态（P0）**。Runtime 的 `hot` 会话表、SSE emitter 表、路由的 `lastRoutes`、编排的 `synchronized` 都假设只有一个进程。两个实例时，SSE 会连到没有这个会话的实例、cancel 只在本机生效、两个 worker 可能抢到同一个 Run。这与 S8/S9 的「HA、私有化、客户自备中间件」直接冲突。
3. **Runtime 是同步请求模型（P0）**。一轮对话在 HTTP 线程里跑完，全局锁让第二个用户等第一个用户的 LLM 返回。对标 Codex harness 需要的是：异步 Turn 任务 + 按 session 加锁 + 事件日志（Turn/Step/Part 表）+ 可恢复。当前 `partsJson` 整块 blob 的存法也会随会话变长而每轮全量重写。
4. **没有异步骨干**。S0 规定「生命周期走 MQ」，实际只有 `*MqTopics` 常量类，生产消费为 0；跨域全靠 Spring 进程内事件。编排层、数据源同步、IM 续办都卡在这里。
5. **事务边界几乎不存在**。全仓只有 1 处 `@Transactional`。Agent 发布、知识 ingest（文档 + 分块 + 向量）、Chat 的用户消息 + 助手消息都是多步写入，中途失败会留下半条数据。
6. **模块边界有渗漏**。`agent-api` 与 `mcp-api` 互相依赖（文档 `module-dependencies.md` 自己也画了这个环）；`tioka-server` 的 `OpsFacadeController`、`AssetCatalogController` 直接 import 各域的 `application` 和 `infrastructure` 实现类（如 `FileAuditSink`），绕过了 `-api` 契约，而 ArchUnit 只管 biz 之间。
7. **分层原则未执行**。「Runtime 经 S10 取模」是 S0 的硬边界，但 Flow 的 LLM/Agent/Embedding 节点和 Knowledge 的 Embedding 各自直连模型；Flow 也不经 Runtime。结果是路由、成本、配额只覆盖 Chat 一条路径。

## 代码质量、测试与过程

最大的过程问题是文档和完成度标签跑在代码前面，导致「绿」不代表能用。

**测试**

- 我在 main 上跑 `mvn test`：构建失败。`OrchAttentionTest` 期望 claim 到自己刚创建的 Run，实际拿到了另一个测试留在共享 H2 里的 Run。测试之间没有数据隔离，结果取决于执行顺序。
- 316 个主源文件对应 38 个测试类；Chat、Connector、Skill、Infra 为 0。服务端的 `GateRegressionSuite` 和 `GoldenPathE2E` 都在 mock 下跑，证明的是接口能串通。
- CI 只跑 Maven，不构建、不测试前端。

**假实现对外暴露为 API**（建议先下线或显式标为未实现，而不是继续保留）

| 类 | 宣称能力 | 实际行为 |
| --- | --- | --- |
| `GraphRagService` | 图谱检索 | 返回一条写死的 `entity-related` |
| `CodeInterpreterService` | 代码解释器 | 不执行，`stdout` 是 `"executed:" + code.hashCode()` |
| `AutomationJobService` | 自动化任务 | 写库后状态直接为 COMPLETED |
| `ChatDensityService.fork` | 会话分支 | 复制消息，但与原会话共用 runtime session |
| `SubAgentPolicy` | 子 Agent / Team | 只有深度和白名单校验，无执行 |
| `DifficultyRouter` | 难度分流 / 决策模型 | 关键词「复杂 / hard」或长度 >500 |

**编码层面**

- 大量 `Map<String, Object>` 当领域对象传递（Flow 图、规则动作、Part payload），类型系统帮不上忙。
- 异常被吞：JSON 解析失败静默返回空列表或默认动作 `create_run`，底层数据损坏时不会报错。
- 每个 Service 自己 `new ObjectMapper()`，ID 用 UUID 截 8–10 位，量大时有碰撞风险。
- 密码用无盐 SHA-256；本地环境 SecretStore 缺 master key 时回退到开发密钥。

**过程**

- 仓库只有 1 个 commit；所有设计、评审、签字文档都标注 2026-11-05，里面的「委员会全票 APPROVE」是多个 AI Agent 互审，没有人工签字。文档量（约 9 千行）接近后端代码量。
- `docs/architecture` 与 `feishu-docs/Tioka` 是两份手工同步的镜像，已经出现行数不一致（如 40-BA 181 行 vs 221 行）。
- 33 号文档 §1.1 的体量数字（biz 约 4.8k 行、14 个测试类）已过时，而 §17 又把 R1–R5 标成了已推进，同一天内反复修正完成度口径。

## 建议优先级

建议把仓库 33 号计划里的 R2–R5（各域功能保真）整体后移，先做下面的 P0 地基。理由是：鉴权、多实例、异步 Runtime 这三件事会改动几乎所有实体和接口签名，在功能加厚之后再做成本会成倍上升。

**P0：地基（不做完不建议对外演示为企业级）**

1. 修复 main 的红测试，给集成测试加数据隔离；CI 加入前端构建。
2. Foundation 鉴权：统一认证拦截 + 请求级 `Principal`（userId、workspaceId、roles）；角色与权限点模型；核心实体加 owner/workspace 并校验；密码改 bcrypt，token 加过期，去掉默认 admin 密码。
3. Runtime 内核重做：多步工具循环（带最大步数）、按 session 加锁替代全局锁、Turn 异步执行、Turn/Part 入表替代 blob、状态可从库恢复。
4. 去除单机假设：SSE 投递与 cancel 信号走共享中间件（Redis 或 MQ），编排 claim 改用数据库行锁。选定 MQ 并落地至少一条 outbox → broker → consumer 链路。
5. 下线或显式标注假实现 API（上表 6 项），避免演示时被当成真能力。

**P1：把主链路做真**

1. Model Hub：冻结改为 turn 级；failover 接入 Runtime 的异常路径；Flow、Knowledge 的模型调用全部改走 ModelRouter，用量统一上报。
2. Governance：在 ModelRouter / Runtime 入口调用配额；在写操作统一写审计；核心多步写入加事务。
3. Orchestration：实现 Run → Runtime 的派工器和 Attention 挂起/续跑，规则从三个 if 改为可配置条件 + 动作。
4. Connector：飞书事件回调入站（消息 + 卡片回传），打通「IM 里对话 + 人审续办」。
5. Flow：Agent 节点走 Runtime，修复 Branch 后汇合节点不执行的调度 bug。

**P2：功能密度**

- Knowledge：真 embedding 默认化、按结构切块、Rerank、第二/三类数据源。
- Chat/HCI：编辑重试、真分支、记忆注入、工作台与轨迹视图。
- Runtime：沙箱、上下文压缩、SubAgent 执行。
- 文档：只保留一份权威源，完成度标签以自动化的非 mock 验收结果为准。
