## 设计 F：Orchestration 编排

覆盖 ORC-01〜07 与 S2 的全部能力簇。核心决定是：**编排只做「事件 → 规则 → 工单 → Run」的调度和记账，执行一律交给 Runtime，人审一律用通用审批表**。S2 中的 Mandate、Eval 准入、交付流水线不另造引擎，而是用服务账号权限、前置决策 Turn、Flow 发布来组合实现。

### 主链路

1. **事件接入**：外部经 Connector 验签后调 `OrchApi.ingest`，内部模块通过 outbox 发事件。幂等键必填（来源 + 外部 ID），重复事件直接返回已有结果。
2. **规则匹配**：取该事件类型的已发布规则版本，用 CEL 求值条件。按 S0 硬边界「事件正文不决定路由和权限」，**条件只能引用信封字段和 Connector 映射出的可信属性 `attrs`**，不能读原始正文。
3. **归单**：按 `subject_key` 找到或创建工单（WorkItem）。规则声明并发模式：`serial`（同一工单串行排队）、`merge`（运行中来的新事件合并为下一次 Run 的输入）、`parallel`。
4. **派工**：写 Run 与 outbox 同事务；派工器消费 `tioka.orch.run.created.v1`，调 `RuntimeApi.createThread` + `startTurn`（origin=orch，run\_as=规则的服务账号）。
5. **回执**：编排发起的 Turn 自动挂上内置工具 `orch.receipt`，Agent 用它交回结构化结果：`resolve`（完成）、`ask`（发起人审）、`notice`（通知）、`later`（延时再跑）、`emit`（派生新事件，hops+1）。Turn 结束却没有回执，按 `resolve` 处理并记一条告警事实。
6. **人审**：`ask` 写通用审批（subject\_type=orch\_run，kind=card），经审批台和 IM 同时投递；答复后用答案作为新输入在同一 thread 上开下一个 Turn。超时按规则配置升级给指定角色，或采用默认答案。

### Run 状态机

`PENDING → DISPATCHED → RUNNING ⇄ WAITING_ATTENTION → SUCCEEDED | FAILED | CANCELLED`。Turn 被中断且已有工具对外产生副作用时进入 `UNCERTAIN`，只能由人在审批台判定重跑或关闭，系统不自动重试。迟到的 Turn 结果（Run 已取消）只记事实，不改状态。

### 规则版本与灰度

规则版本不可变。灰度按 `hash(subject_key) % 100 < canary_percent` 分流到候选版本，同一工单始终命中同一版本。候选版本求值报错时回落到稳定版本并告警（即 S2 的「坏规则保旧版」）。

### 定时与延时（ORC-06）

统一一张 `orch_timer` 表，取代现有 `LaterTriggerService`。各实例每 5 秒用 `FOR UPDATE SKIP LOCKED` 取到期定时器，触发即发一条事件。cron 按规则声明的时区计算；错过的触发默认只补最近一次（`LATEST_ONLY`），可配 `ALL` 或 `SKIP`。

### 熔断（ORC-07）

- hops 超过 8 的事件丢弃并告警，防止事件环。
- 同一规则连续 5 次 Run 失败则自动暂停规则。
- 预算熔断复用配额：规则是配额的一种作用对象（`gov_quota.scope_type = rule`）。
- 消费失败 3 次的消息进死信表，管理端可重放。

### Mandate、Eval 与交付流水线的落法

| S2 能力 | 实现方式 |
| --- | --- |
| Mandate 授权 | 每条规则绑定一个服务账号（FND-06），其角色、可用工具、审批策略、配额就是 Mandate。撤销或收窄即时生效（定案 6） |
| Eval 准入 | 规则可配一个前置「研判 Agent」，先跑一个只读 Turn，其回执为 `resolve(skip)` 时不创建正式 Run |
| 交付流水线 | 审查→CI→合并→发布类长任务建成 Flow，规则动作直接调用 Flow 发布（origin=orch） |
| 订阅扇出 | 一个事件可命中多条规则，各自生成 Run；不另设订阅实体 |
| SLA 与值班 | M4 之后：审批超时升级链 + 值班日历表，接口留在审批超时处理器上 |

## 设计 G：Connector、IM 与 MCP 管理

覆盖 CON-02〜07 与 S6、S12。核心决定有三条：**所有出网请求只能经 Connector 的 `EgressClient`**（白名单、超时、审计一处实现）；**IM 只是 Chat 和审批的另一个入口**，不自己跑 Agent；**MCP 工具和业务系统工具都注册进 ToolGateway**，和内置工具受同一套权限、审批、审计约束。

### IM 入站对话（CON-02）

1. 平台回调打到 `POST /api/connector/im/{channel}/{bindingId}/events`（白名单接口，只靠平台签名鉴权）。验签解密、按平台事件 ID 去重，**3 秒内先应答**，再异步处理。
2. 外部用户按 `sys_external_identity` 映射到平台用户。未绑定的用户收到一条带绑定链接的回复，不执行任何操作。
3. 群聊只响应 @机器人的消息；私聊全部响应。IM 会话（群 + 话题）映射到一个 Chat 会话，默认使用绑定上配置的 Agent。
4. 调 Chat 发送（origin=im），订阅 Turn 事件，把回答渲染为流式卡片：更新节流为每秒一次，结束时写入完整内容和引用。

### 卡片回调与审批（CON-03）

审批卡片里的按钮携带 `approvalId` 和一个签名令牌（对 approvalId、接收人、过期时间做 HMAC），防止伪造。回调时把点击人映射为平台用户，校验其是否有权审批，再以该用户身份调 `decideApproval`，并把卡片更新为「已由某人处理」。同一审批在 Web 和 IM 任一端处理后，另一端同步更新。

### IM 渠道 SPI（CON-06）

### 业务系统接入（CON-07）

- **入站**：每个业务绑定配置签名方式（HMAC 头 + 时间戳，允许偏差 5 分钟防重放）和字段映射（JSONPath → `attrs`、`subject_key`），映射后调 `OrchApi.ingest`。只有映射出的字段算可信属性。
- **出站**：上传 OpenAPI 描述，勾选要暴露的操作，生成 `biz.{system}.{operation}` 工具注册进 ToolGateway。写操作默认需要审批。

### MCP 管理（S12、CON-05）

| 项 | 定案 |
| --- | --- |
| 传输 | Streamable HTTP 为主，兼容旧 SSE；stdio 只在私有化部署中由管理员启用，进程跑在沙箱里 |
| 认证 | none / bearer / OAuth。需要代用户授权的 Server，用户令牌存在令牌保管（设计 L） |
| 工具发现 | 接入和手动刷新时拉 `tools/list`，存为不可变快照；Agent 版本引用快照号，工具变化不会悄悄改变已发布 Agent 的行为 |
| 命名 | 暴露给模型的工具名为 `{serverSlug}__{tool}`，避免跨 Server 重名 |
| 健康 | 每 60 秒握手探活，连续 3 次失败熔断 5 分钟；熔断期间该 Server 的工具从模型的工具列表中移除 |
| 授权 | 两层：空间成员对 Server 有 USE 权限才能在 Agent 上绑定；绑定写入 Agent 版本快照，只允许快照里的工具 |

## 设计 H：Chat 对话

覆盖 CHT-02〜07 与 S3。核心决定是：**消息内容只存在 Runtime 的 item 里，Chat 只管会话组织和分支关系**。当前 `chat_message` 与 Runtime parts 双份存储的问题由此消除；分叉、编辑、重新生成都归结为 Runtime 的 thread fork。

### 会话、分支与消息

- 一个会话由若干分支组成，每个分支对应一个 Runtime thread，会话记录当前激活的分支。
- **fork 不复制数据**：新 thread 记录 `parent_thread_id` 和 `fork_seq`，读取时拼接父 thread 中 `seq ≤ fork_seq` 的 item 与自身 item。
- **编辑用户消息** = 在该消息之前 fork，再以新文本开 Turn；**重新生成** = 在该回答对应的用户消息之后 fork，重跑同一输入；**继续** = 在同一 thread 上开新 Turn。每次操作都产生新分支，前端按分支树展示「第 2/3 版」。
- **发送**：`POST /api/chat/conversations/{id}/messages`，请求带 `clientMsgId`、文本、附件引用，返回 turnId 与事件流地址（CHT-02）。停止即 `interrupt`。
- **Agent 版本**：会话创建时按 Agent 配置选择「钦死版本」或「跟随最新」，每个 Turn 记录实际使用的版本。

### 附件与文件对话

上传走预签名直传对象存储，前端确认后生成 `file_ref`（仓库 ADR-014 D4）；发送时 Runtime 把文件物化到会话工作盘。图片直接作为多模态输入；文档在 20 页以内抽取文本放入上下文，超过则索引进一个会话专属的隐藏知识库（设计 D 的流水线），由 Agent 用检索工具读取。会话删除时一并清理。

### 长期记忆（CHT-05）

- **抽取**：Turn 完成后异步调一次模型（purpose=memory），从本轮对话中提取值得记住的用户偏好或事实，与已有记忆去重合并。
- **注入**：Turn 开始时按与当前问题的向量相似度取前若干条，放入系统提示的独立段落，上限 1000 token。
- **控制**：用户可以查看、编辑、删除单条记忆，或整体关闭；临时（无痕）会话不抽取也不注入。管理员可按空间关闭记忆功能。

## 设计 I：Agent 与 Skill 资产管理

覆盖 S11、S13，新增工作项 AST-01〜06。核心决定是：**Agent 的一切配置收成一个类型化的 `AgentSpec` 文档，发布即冻结为不可变快照**。现在散落在 `agent_version`、`mcp_grant`、`agent_sandbox`、`agent_share` 里的绑定关系合并进快照或 ACL，Runtime 只认快照，不再临时查各张绑定表。

### AgentSpec（AST-01）


快照里只存引用 ID，不存密钥。草稿可反复修改（乐观锁），发布时生成新版本号和内容哈希。

### 发布校验（AST-02）

发布前必须全部通过，任一失败则不能发布：

1. 引用的路由计划已发布；MCP 快照存在且 Server 未熔断；Flow 发布与知识库存在。
2. **发布者本人对每一个引用都有 USE 权限**，防止借 Agent 绕过权限。
3. Skill 版本已签名（租户策略要求时），且 Skill 声明的权限是 Agent 沙箱策略的子集。
4. 空间开启了发布审批时，版本进入 `PENDING_APPROVAL`，审批通过才生效（设计 K）。

回滚 = 把已发布指针指向旧版本；diff = 两个快照的 JSON 差异。发布、停用、回滚都发 `tioka.agent.*.v1` 事件，ToolGateway 和 Chat 缓存据此刷新。

### 共享、克隆与市场（AST-03、AST-04）

- 共享统一走 `sys_resource_acl`：USE 可对话使用，EDIT 可改草稿，OWNER 可发布和授权。跨空间共享默认关闭。
- 克隆 = 把某个版本的快照复制成自己名下的新草稿，发布时重新校验权限。
- 市场与模板共用一张上架表，上架走资产审批。模板只能克隆，不能直接使用。

## 设计 J：Model Hub 供应商、路由与决策

覆盖 MH-03、MH-06、MH-07 与 S10，是设计 C 中 `ModelGateway` 「选模」一步的展开。核心决定是：**路由计划也是类型化、可版本化的快照，决策逻辑是可插拔的 `RoutingDecider`**。现有关键词难度判断降级为内置的启发式决策器，不再冠名「决策模型」。

### 模型目录

| 实体 | 内容 |
| --- | --- |
| ProviderConnection | 协议（OpenAI 兼容、Anthropic、Azure OpenAI、Ollama 等）、Base URL、密钥引用、健康状态；出网走 EgressClient |
| ModelBinding | 某供应商上的一个可调用模型：用途（general / decision / embedding / rerank）、能力（工具调用、视觉、JSON、上下文长度）、单价、RPM/TPM 上限、启停 |
| LogicalModel | 可选的产品侧名称，把多个供应商的同一模型收拢展示 |

### 路由计划

```java
public record RoutingPlanSpec(
    int schemaVersion,
    RoutingMode mode,                       // FIXED / DIFFICULTY / BRANCH / FREE_FIRST
    Map<String, List<String>> groups,       // 组名 → 有序的 bindingId 候选
    Map<String, String> categoryToGroup,    // BRANCH 模式：任务类别 → 组
    DecisionConfig decision,                // deciderId、决策 binding、超时、超时时的兜底组
    EscalationPolicy escalation,            // 常规组耗尽是否升主力组；主力组耗尽即失败
    boolean preferPreviousInGroup) {}       // 同组时优先沿用上一模型

public interface RoutingDecider {            // 决策器 SPI
    String id();                              // heuristic / llm / http:{name}
    Decision decide(DecisionInput input);
}
record DecisionInput(String userText, String previousGroup, Double previousCompetence, Map<String, Object> hints) {}
record Decision(String category, Difficulty difficulty, double confidence, String reason) {}
```

内置三种决策器：启发式（现有 `DifficultyRouter` 搬入）、大模型决策（用决策 binding 以固定提示词输出 JSON，经 `ModelGateway` purpose=decision）、外部 HTTP（客户自有决策服务）。HiRoute 的 Jev 决策模型可作为外部 HTTP 决策器接入。

### 一次选模

1. 只在 Turn 开始时决策；同一 Turn 内的工具续写沿用冻结（设计 C）。上下文压缩后允许重新决策。
2. FIXED 模式不调决策器。其他模式调决策器得到类别和难度，映射到组；决策超时（默认 1.5 秒）或失败时走兜底组，并在时间线记录原因。
3. 组内按候选顺序过滤：未启用、熔断中、缺少本 Turn 所需能力（有工具则需工具调用，有图片则需视觉）的跳过。新组与上一 Turn 同组时优先沿用上一模型。
4. FREE\_FIRST：先试免费组，失败后按计划升到主力组或直接失败。
5. 每一步（决策、选中、沿用、接力）写一条路由事件，构成会话路由时间线。

### 限流、重试与冷却（MH-03）

binding 级 RPM/TPM 令牌桶放 Redis；取不到令牌时最多等待 2 秒，仍不足则视为该候选不可用、走下一个。一分钟内失败率超过 50%（至少 10 次调用）的 binding 进入冷却 60 秒。重试和接力次数见设计 C。

### 发布与生效

路由计划有草稿和不可变版本。发布校验：候选都存在且启用、需要决策器的模式已配决策 binding、阈值合法。**Agent 引用的是计划 ID，计划发布新版本对所有 Agent 立即生效**，这是集中路由的意义；时间线记录每次使用的计划版本，出问题可一键回滚。管理员可为调试在会话上钦死某个 binding，强制审计。

### 胜任度与成本（MH-07）

Turn 结束后可选地用决策 binding 给本轮回答打 0–1 分，结果存表并作为下一次决策的输入。M3 先只记录不参与决策，观察一段时间再开启。成本在写用量时按 binding 单价计算，每天汇总到日报表供看板和导出。

## 设计 K：Governance 余项

覆盖 GOV-06〜11（GOV-05 成本归集已在设计 J）。核心决定是：**治理能力全部挂在已有的卡点和表上，不新增执行路径**。发布审批复用通用审批表，策略引擎挂在 ToolGateway，内容安全挂在 Runtime 的输入输出处，多环境复用空间。

### 资产发布审批（GOV-06）

- 空间按资产类型配置是否需要审批和审批角色。类型包括 Agent、Skill、Flow 发布、MCP Server、路由计划、市场上架。
- 发布时版本进入 `PENDING_APPROVAL`，写一条通用审批（subject\_type=asset\_version），审批人在审批台看到与上一版本的 diff。
- **执行侧只认 PUBLISHED 版本**：Runtime 创建 thread 时、ToolGateway 解析工具时都校验状态，满足验收「未审批的资产无法被会话使用」。

### 工具调用策略引擎（GOV-07）

选用 Cedar（`cedar-java`，进程内求值，不需要额外部署服务）。ToolGateway 在权限检查之后、审批判定之前求值：

| Cedar 要素 | 取值 |
| --- | --- |
| principal | 用户或服务账号，带角色与部门属性 |
| action | 工具名，如 `Action::"biz.erp.createOrder"` |
| resource | 工具及其参数中声明为可策略化的字段（如金额、目标路径） |
| context | Agent、空间、会话来源（web / im / orch）、时间 |

结果三种：允许、拒绝、转人工审批。RBAC 是基线，策略只能收紧不能放宽。策略按租户和空间版本化，新策略先在「仅记录」模式跑一段时间，确认误拦率后再切换到「强制」。每次拒绝都写审计，带命中的策略 ID。`cedar-java` 依赖本地库，需确认目标部署架构（x86 / ARM）都有可用构建。

### 可观测（GOV-08）

- 用 OpenTelemetry SDK，span 层级：HTTP 请求 → Turn → Step → 模型调用 / 工具调用；Flow 的节点运行、编排 Run 作为独立 trace 并链接到它们触发的 Turn。
- span 属性只带 ID、模型、token 数、耗时、结果；**默认不带提示词和工具参数正文**，需要时按空间开启并经内容安全脱敏。
- 指标走 Micrometer → Prometheus：Turn 耗时与排队长度、模型错误率、工具错误率、配额拒绝数、outbox 积压。
- 用 OTLP 导出到客户的采集器；Helm chart 可选带一套默认后端。自建的 `trace_span` 表废弃。`audit_event` 和 `model_usage` 都记录 traceId，可互相跳转。

### 审计防篡改与外送（GOV-09）

写审计时不算哈希，避免写入串行化。一个封印任务每分钟按 ID 顺序为新记录计算 `hash = sha256(prev_hash + 规范化后的记录)`，每个租户一条链，并把每批的末尾哈希写入封印表（可同时外送到 SIEM，作为外部锚点）。提供校验接口重算整条链。外送经 `AuditSinkAdapter`（syslog、HTTP、Kafka），从 outbox 投递，客户 SIEM 不可用时不影响业务。

### 内容安全（GOV-10）

`ContentSafetyHook` SPI 挂在三个点：用户输入进入 Turn 前、模型输出 item 完成时、工具参数发往外部系统前。动作：放行、脱敏、拦截。流式输出无法事前审查，所以在 item 完成时检查，命中拦截则发 `item.discarded` 并替换为提示（与定案 2 同一机制）。内置正则 PII 脱敏（身份证、手机号、银行卡、邮箱），客户自有审核服务以适配器接入。

### 多环境（GOV-11）

**环境就是带标签的空间**：空间增加 `env`（dev / staging / prod）和「晋升到哪个空间」。晋升 = 把某个资产版本的快照复制到目标空间，按名称重新绑定引用（路由计划、MCP、知识库），绑定不到则拒绝，并走目标空间的发布审批。这样不用在每张业务表加环境字段。

## 设计 L：Foundation 余项

覆盖 FND-08〜11 与 S9 的其余部分。核心决定是：**身份和组织以客户 IdP 为准，Tioka 只存映射和授权**；本地账号只保留应急管理员，生产可关闭。外部系统的用户令牌、客户自有的密钥库和中间件，都通过适配器接入。

### 外部身份映射

`sys_external_identity` 统一记录「外部身份 → 平台用户」：OIDC subject、SCIM externalId、飞书 open\_id / union\_id、钉钉 userId 等。绑定方式两种：管理员配置「按工号或已验证邮箱自动关联」；否则用户在 IM 里点绑定链接，用该 IM 的 OAuth 登录证明身份后关联。**不允许仅凭名字匹配**。

### 组织同步（FND-09）

- Tioka 作为 SCIM 2.0 服务方提供 `/scim/v2/Users`、`/scim/v2/Groups`，由 Keycloak、Entra ID、Okta 推送；不支持 SCIM 的来源（飞书通讯录、LDAP、客户 HR 接口）由 `OrgDirectoryAdapter` 定时拉取。
- 部门作为有层级的组存储。管理员配置「组 → 空间角色」映射规则，成员变更后角色自动计算。手工授予的角色单独标记，同步不会覆盖。
- **离职处理**：用户被停用时，吊销登录令牌和代用户令牌、取消进行中的 Turn（定案 6）；其名下的资产转交给空间管理员待处理队列，已发布的资产继续可用。

### 登录方式（FND-10）

OIDC 在 M1（设计 A）；SAML 2.0 用 Spring Security SAML2，LDAP 用绑定认证，都在 M4；CAS 等其他协议由 `IdentityProviderAdapter` 接入。所有方式最终都产生同一种平台令牌和 `Principal`。

### 代用户令牌保管（FND-08）

```java
public interface TokenVault {
    TokenResult get(String userId, String provider, Set<String> scopes);  // 过期自动刷新
    String authorizationUrl(String userId, String provider, Set<String> scopes, String returnTo);
    void revokeAll(String userId);
}
sealed interface TokenResult {
    record Granted(String accessToken, Instant expiresAt) implements TokenResult {}
    record AuthorizationRequired(String url) implements TokenResult {}
}
```

工具拿到 `AuthorizationRequired` 时，把授权链接作为工具结果返回，前端渲染成「去授权」按钮，而不是改用应用身份。刷新时按 (用户, 提供方) 加锁，避免并发刷新使 refresh token 失效。

### 密钥与加密

采用信封加密：每个租户一把数据密钥，由主密钥加密保存；主密钥来自 `SecretStoreAdapter`（本地密钥文件、HashiCorp Vault、客户 KMS）。**生产环境缺少主密钥时直接启动失败**，去掉现在回退到开发密钥的行为。代用户令牌、供应商 API Key、各类回调密钥都用同一套。主密钥轮换只需重新加密数据密钥。

### 适配器与插件

S9 列出的九类 SPI（身份、组织、IM、业务系统、审计外送、通知、密钥、对象存储、工作盘）统一由插件宿主加载：从插件目录读取 jar，用独立类加载器隔离，校验签名和所声明的 SPI 版本，不兼容则拒绝加载。各类适配器实例的配置存在登记表里，密钥只存引用。

### 部署形态（FND-11）

| 项 | 定案 |
| --- | --- |
| 进程角色 | 一个镜像，用 `tioka.roles` 启用角色：`api`（HTTP 与 SSE）、`worker`（Turn、Flow 节点、入库任务、MQ 消费）、`scheduler`（outbox 中继、定时器、回收器、审计封印，靠 Redis 锁保证只有一个实例在跑）。小部署一个进程全开 |
| 中间件 | PostgreSQL（含 pgvector）、Redis、RocketMQ、MinIO 均可用客户自备的；Redis key 与 MQ topic 支持前缀，可与客户其他系统共用 |
| 数据库变更 | 全部改用 Flyway 迁移脚本，废弃手工维护的 `schema.sql`；启动时由拿到锁的实例执行迁移 |
| Helm | 按角色拆分 Deployment，api 与 worker 各自水平扩容；中间件与 Keycloak 为可选子 chart |
| 空气隔离 | 安装包含全部镜像的 tar、chart、校验和、安装与升级脚本、离线的 embedding 与 rerank 模型镜像（可选）；安装脚本先做环境自检 |
| Docker Compose | 用于演示和小团队，与 Helm 共用同一套配置项 |

## 设计 M：Runtime 余项

覆盖 RT-09〜12 与 S1 中的沙箱、代码执行、子 Agent、上下文压缩、后台 Job。核心决定是：**所有长时间等待都用「挂起 Turn、释放 worker、事件唤醒」这一种机制**，和审批挂起一致。因此设计 B 的 Turn 状态机增加一个 `WAITING_CHILD`（等子 Agent 或后台 Job），这是对设计 B 的正式修订。

### 沙箱（RT-11）

```java
public interface SandboxProvider {                 // docker / k8s；微虚拟机后端可后续接入
    SandboxHandle acquire(SandboxSpec spec);
    ExecResult exec(SandboxHandle handle, ExecRequest request);
    void release(SandboxHandle handle);
}
record SandboxSpec(String threadId, String image, int cpuMilli, int memoryMb, Duration maxLifetime,
                   NetworkPolicy network,          // NONE / ALLOWLIST(hosts)
                   List<Mount> mounts) {}          // 会话工作盘挂到 /workspace
```

| 项 | 定案 |
| --- | --- |
| 后端 | 开发与 Compose 用 Docker；Helm 部署用 Kubernetes Pod，集群支持时使用 gVisor 运行时 |
| 生命周期 | 每个 thread 最多一个沙箱，第一次执行时创建；空闲 15 分钟回收，最长存活 8 小时；回收后工作盘保留，下次执行重新挂载 |
| 工作盘 | 按 ADR-014 的 uploads / skills / scratch / artifacts 目录，存在共享卷上；不同 thread 互不可见 |
| 网络 | 默认无网络；允许联网时只能经 Tioka 的出口代理，受 Agent 沙箱策略与 Skill 权限交集的白名单限制 |
| 镜像 | 内置 Python 数据分析镜像和 Node 镜像；离线安装包一并携带 |
| 底线 | 沙箱未启用的部署中，代码执行与脚本类工具一律不可用，绝不在应用进程内执行 |

### 代码执行工具

`code.run(language, code)` 在沙箱内运行，返回 stdout / stderr（各截断到 20KB）和退出码；写到 `/workspace/artifacts` 的文件自动变成 `file_ref` item 供下载。取代现在返回 `code.hashCode()` 的假实现。`shell.exec` 只对沙箱策略为 full 的 Agent 开放；交互式终端放在 M4 之后。

### 后台 Job 与长任务（RT-09）

- 工具可以把长命令转为后台 Job：立即返回 jobId，Job 在沙箱里继续跑。Agent 可选择等待（Turn 进入 `WAITING_CHILD`）或继续做别的。
- Job 结束发事件：等待中的 Turn 被唤醒并拿到结果；已结束的 Turn 则按 Agent 配置在同一 thread 开一个新 Turn（origin=job）或仅通知用户。
- 默认时限：工具调用 120 秒（最大 30 分钟），单个 Turn 2 小时，Job 8 小时。取代现在写库即完成的 `AutomationJobService`。

### 子 Agent（RT-12）

1. 内置工具 `agent.delegate(agentId, task, context)`，只能委派 AgentSpec 里 `subAgents` 允许的 Agent。
2. 创建子 thread（记录父 Turn 和深度），用同一个 Principal 开子 Turn；父 Turn 进入 `WAITING_CHILD`，不占 worker。
3. 深度默认上限 2，同一步最多并行委派 3 个；子 Turn 的 token 计入父 Turn 的预算，超出则子 Turn 被取消。
4. 子 Turn 完成后，其最终回答作为委派工具的结果回到父 Turn，轨迹视图可点进子 thread。父 Turn 被取消时级联取消子 Turn。

S1 的 Agent Team（任务板与角色协作）建立在委派之上，放在 M4 之后单独设计。

### 上下文组装与压缩（RT-10）

**组装顺序固定**，各模块不得自行插入：平台安全指令 → Agent 指令 → always Skill → auto Skill 索引 → 用户记忆 → 知识自动检索结果 → 压缩摘要 → 历史 item → 本轮输入。

每个 item 入库时记录 token 数。每次调模型前估算总量，超过所选模型上下文的 75% 就压缩：保留最近 3 个 Turn，更早的内容经 `ModelGateway`（purpose=compaction）摘要成一个压缩 item，原始 item 仍保留供界面展示。单个工具结果超过 8000 token 时，全文写入工作盘，提示里只放开头部分和文件路径。压缩后允许重新选模（设计 J）。

## 设计 N：HCI 前端架构与各工作台

覆盖 HCI-03〜08。核心决定是：**前端只认一种流协议（Runtime 事件 + item 类型），所有工作台复用同一套渲染组件**，不再按页面各写一套流解析。

### 前端架构

| 项 | 定案 |
| --- | --- |
| 框架 | 保留现有 React + TypeScript + Vite，单一应用按路由分区：/chat、/studio、/console、/admin |
| 接口类型 | 后端 OpenAPI 生成 TS 客户端（CI 校验生成物无差异），禁止手写请求类型 |
| 状态 | 服务端数据用 TanStack Query；流状态用每个 thread 一个 store，由事件归并得出 |
| 鉴权 | OIDC 授权码 + PKCE，access token 只在内存，刷新走后端会话 Cookie |
| 权限显隐 | 登录后拉取 `/me/permissions`，菜单与按钮按权限码隐藏；后端仍做最终校验 |
| 国际化 | 中英双语，文案统一放 i18n 资源 |

### 流协议（与设计 B 一致）

前端通过 SSE 订阅 `/threads/{id}/events`，断线用 Last-Event-ID 续传。事件只有 `turn.*`、`item.*`、`approval.*` 三族；item 类型固定为 message、reasoning、tool\_call、tool\_result、file\_ref、citation、card、compaction、child\_thread、error。新增类型必须先改契约（事件 schema），前端遇到未知类型显示通用占位，不报错。对外的 AG-UI 兼容是在网关做协议转换，不影响内部协议。

### 共享组件

- **ItemRenderer**：按 item 类型渲染，所有工作台共用。
- **ApprovalCard**：工具审批与卡片表单（kind=tool/card），支持批准、拒绝、修改参数后批准。
- **TrajectoryView**：按 Turn 展开 item 时间线，显示模型、token、耗时、引用来源，可钻入子 thread。
- **CitationPanel**：知识引用的原文片段与文档跳转（按用户 ACL 再校验）。

### 各工作台

| 工作台 | 主要页面 | 依赖后端 |
| --- | --- | --- |
| 对话（HCI-03） | 会话列表、分支、文件上传、Agent 选择、记忆管理、分享 | 设计 B、H |
| 审批中心（HCI-04） | 待我审批、我发起的、按 Agent 与风险筛选、批量处理 | runtime\_approval |
| 轨迹与调试（HCI-05） | Turn 时间线、重放、对比两次运行、导出 | runtime\_item、model\_usage |
| Studio（HCI-06） | Agent 编辑与试运行、Skill 管理、Flow 画布、路由方案、发布与评测 | 设计 E、I、J |
| 知识控制台（HCI-07） | 知识库、数据源同步、文档状态、检索调试、评测集 | 设计 D |
| 管理控制台（HCI-08） | 成员与组、角色、资源授权、模型与配额、审计查询、渠道接入、编排规则 | 设计 A、C、F、G、K、L |

### 质量约束

- 每个工作台有 Playwright E2E，跑在真实后端（门禁 G2 起）。
- 首屏 JS 不超过 300KB（gzip），Studio 与 Flow 画布按路由懒加载。
- 可访问性：键盘可操作，审批与表单符合 WCAG AA 对比度。
- 现有按页面手写的 SSE 解析和 mock 数据在 HCI-03 完成后删除。
