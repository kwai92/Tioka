## 结论

建议把 Tioka 从「又一个 Agent 搭建平台」改定位为**企业数字员工的上岗、授权、执行、问责、经营平台**：企业怎么管一个人，Tioka 就怎么管一个 Agent。现有 ADR-015〜031 已经把对话、知识、Flow、编排、评测这些「积木」补齐了，但 Dify、Coze、AgentCore、Agent 365 都有同样的积木，客户没有理由选我们。

真正让 CIO 签字的是三个问题：**它出错了能不能兜住、它能不能逐步放手、它到底省了多少钱**。对应推荐三个方向优先做：

1. **可撤销执行**：每个写操作都有「预演、确认、提交、撤销」，Agent 做错的事能一键回滚。
2. **自治阶梯与影子上岗**：Agent 像新员工一样从影子跟岗到独立上岗，升级和降级都由线上证据自动驱动。
3. **价值账本**：每次运行都算出省了多少工时、花了多少钱、质量如何，形成每个数字员工的经营报表。

这三个方向共用一份轻量的「数字员工档案与授权书」作为骨架。其余两个方向（决策档案与监管回放、工作机会雷达）建议放到 M4 之后。这三项都挂在已有的 Runtime、ToolGateway、审批和评测上，不新开执行路径，估算在现有 M0〜M4 上增加约 95 人日。

## 为什么现有设计不够

现有设计的问题不是缺能力，而是**每一层都在对标别人的强项**：Chat 对标 LibreChat、Flow 对标 Langflow、治理对标 AgentCore。对标的上限是「和它们一样好」，而且这些产品还在往前跑。

2025 年 12 月 AWS 给 [AgentCore 加了 Policy（Cedar）和 Evaluations](https://aws.amazon.com/blogs/aws/amazon-bedrock-agentcore-adds-quality-evaluations-and-policy-controls-for-deploying-trusted-ai-agents/)，微软的 [Agent 365](https://learn.microsoft.com/ga-ie/microsoft-agent-365/overview) 把 Agent 注册表和 Agent 身份做成了控制面。Tioka 的 ADR-025（Cedar 策略）和 ADR-031（评测飞轮）做完，也只是追平这条基线。

企业从试点走到规模化时，卡住的往往是下面六件事，而现有设计对它们只有零散的支撑：

| 企业的卡点 | 买单人的原话 | 现有设计的支撑 | 缺口 |
| --- | --- | --- | --- |
| 写操作不敢放 | 「它要是把订单改错了怎么办」 | 审批卡、Cedar 拦截 | 只有「拦」和「放」，没有预演、影响面和撤销 |
| 人审成了瓶颈 | 「每一步都要人点，那还不如人自己做」 | 审批策略静态配置 | 放权不会随证据变化，只能全审或全放 |
| 说不清 ROI | 「今年花了 200 万算力，省了什么」 | 成本归集（GOV-05）、质量分 | 只有成本侧，没有价值侧 |
| 出事无人负责 | 「这是谁让它做的」 | Agent 有 owner 字段 | 没有职责边界和授权额度 |
| 审计与监管质询 | 「三个月后能说清它当时为什么这么判吗」 | 审计哈希链、轨迹 | 轨迹可看不可重放，引用的知识版本未封存 |
| 不知道该做哪些 Agent | 「业务部门提不出需求」 | 无 | 完全空白 |

私有化、单租户、中国企业这三个约束反而是优势：它们让「授权书、岗位职责、绩效考核」这套中国企业内控本来就熟悉的语言可以直接搬到 Agent 上，这是海外产品不会做的。

## 六个候选方向

六个方向是一条生命周期上的六个环节，任何一个都能单独交付；全部做完时，它们互相供数。编号沿用下文推荐组合的叫法。

撤销会把 Agent 的自治等级降一级，账本里的价值数据反过来决定下一批该做哪些 Agent。

### D0 数字员工档案与授权书（骨架）

**惊艳点**：每个上线的 Agent 都有一份和员工一样的档案：岗位、直属负责人、授权额度、禁区、KPI、复核周期。负责人离职时，Agent 自动暂停并发起交接。

- **授权书（Mandate）**按动作类别写额度：单笔金额上限、日累计、单次影响记录数、可触达的客户范围。授权书发布时**编译成 Cedar 策略**，直接复用 ADR-025 的求值点，不引入第二套策略引擎。
- **有效权限 = 委托人权限 ∩ 授权书 ∩ 空间策略**。Agent 以用户名义做事时永远不超过这个用户；以服务账号做事时不超过授权书。
- **四眼原则**：授权书可以声明某类动作必须由委托人以外的第二人审批。
- **挂接**：Foundation 的组织同步（FND）提供负责人状态；AgentSpec（ADR-023）加 `mandate` 段；Governance 的发布审批（GOV-06）对授权书做 diff 审批。

### D1 可撤销执行：动作契约与变更单

**惊艳点**：Agent 改了 ERP 里的 12 条订单，负责人在飞书卡片上点「撤销本次」，12 条按逆序恢复。现在的平台只能在执行前「拦」，没有一家能在执行后「收」。

- **副作用等级**：工具在连接器 SDK 里声明 `READ`、`REVERSIBLE`（有撤销接口）、`COMPENSABLE`（有冲销类补偿动作）、`IRREVERSIBLE`（发邮件、付款）。未声明的写工具按 `IRREVERSIBLE` 处理。
- **三个钩子**：连接器 SDK 的写工具实现 `preview()`、`apply()`、`compensate()`。`preview()` 返回结构化的变更单：哪些对象、字段从什么变成什么、金额合计。
- **执行路径**：意图 → 预演（生成变更单）→ 按自治等级决定自动提交或送审 → 提交 → 回执。一个 Turn 或编排 Run 内的写操作组成一个 saga，撤销窗口内可整体回滚。
- **爆炸半径**：单次运行的影响记录数和金额累计超过授权书额度时，剩余步骤自动转审批。
- **挂接**：ToolGateway 在 Cedar 求值之后加预演步；Runtime 加 `change_set` item 类型（ADR-016）；审批卡展示变更单 diff（M2-03/04）；补偿走 outbox（M2-01）保证至少一次。

### D2 自治阶梯与影子上岗

**惊艳点**：新 Agent 先「跟岗」两周，和人同时处理同一批工单但不执行，产出一份上岗报告；之后按线上证据一级级放权，出事自动降级。人审从「永久瓶颈」变成「有证据地逐步退出」。

| 等级 | 名称 | 行为 |
| --- | --- | --- |
| L0 | 影子 | 只产出建议和变更单，不执行，与人工实际处理比对 |
| L1 | 逐步审 | 每个写操作都送审 |
| L2 | 按风险审 | 低风险自动提交，高风险送审 |
| L3 | 事后抽检 | 先执行，按比例抽检，撤销窗口内可回滚 |
| L4 | 自主 | 只在异常和超额度时上报 |

- 等级按 **Agent × 动作类别**设置。同一个 Agent 可以查询类 L4、改价类 L1。
- **晋级**：样本数、审批「原样通过率」、撤销率、线上评测分都达标，并以置信区间下界判断，系统生成「转正申请」由负责人确认，不自动越级。
- **降级**：撤销、驳回、事故单触发后立即降一级并通知负责人，不等人确认。
- **挂接**：影子运行是编排 Run 的一种来源（ADR-020，`origin=shadow`）；证据来自 ADR-031 的线上评测和审批记录；等级决定 ADR-025 的审批判定；被人改过的审批自动回流为回归数据集。

### D3 价值账本

**惊艳点**：CIO 每月收到一份「数字员工经营报表」：每个 Agent 干了多少件事、省了多少工时、花了多少钱、人接手率多少，这是续费和扩容的直接依据。

- **人工基线**：每个任务类型登记人工平均耗时、人力单价、错误率。优先取 D2 影子期实测，其次手填并标注「估算」。
- **每次运行一条账**：节省工时 = 基线 − 人的参与时长（审批停留、修改、接手）；成本 = 模型 + 工具 + 平台分摊；质量 = 评测分、撤销、投诉。
- **防虚报**：只有「完成且未被撤销」的运行计入节省；基线修改留审计。
- **挂接**：GOV-05 成本归集和 `model_usage` 给成本侧；ADR-031 的 `eval_result` 给质量侧；编排 Run 和 Turn 的结局给产出侧；HCI 新增一个经营看板。

### D4 决策档案与监管回放

**惊艳点**：审计员问「三个月前它为什么拒了这笔报销」，系统能按当时的知识版本、策略版本、模型响应原样重放，还能用新版 Agent 重算一遍做对比。

- 有副作用的决策封存一份档案：输入、引用的知识切片及版本哈希、命中的策略版本、模型与路由版本、提示词版本、审批人、变更单，档案哈希入 GOV-09 审计链。
- 知识与输入带密级标签，Model Hub 按密级只路由到合规模型（例如机密数据只走本地部署）。
- **挂接**：ADR-016 轨迹、ADR-018 知识版本、ADR-024 路由、GOV-09 封印任务。金融、国企、医药客户的强卖点，但大部分客户第一年不会用到回放。

### D5 工作机会雷达与 SOP 编译

**惊艳点**：不等业务部门提需求。Tioka 经授权扫描飞书审批、工单和群聊，列出「最值得交给 Agent 的 20 件事」及估算价值；选中一件，从 SOP 文档和历史样本生成 Agent 草稿、回归数据集和建议授权书，直接进入 L0 影子上岗。

- **挂接**：Connector 数据源、Knowledge 入库、ADR-023 资产、D2 影子。
- **风险**：隐私审批重、聚类质量不确定、工作量大，适合作为 M4 之后的第二增长引擎。

## 推荐组合与路线图影响

推荐做 D0 + D1 + D2 + D3，合称「可信放权」，在现有 M2〜M4 里加约 95 人日；D4、D5 放到 M4 之后。四项都依赖已在计划里的审批、outbox 和评测，所以 M0、M1 不变。

| 方向 | 估算（人日） | 落在 | 依赖的现有工作项 | 新闸门验收 |
| --- | --- | --- | --- | --- |
| D1 可撤销执行：副作用等级、预演、变更单卡片 | 20 | M2 | CON-03、HCI-05、ORC-02 | G2：飞书卡片展示变更单后才提交 |
| D1 可撤销执行：补偿、saga、撤销本次、爆炸半径 | 15 | M3 | D1 第一段、ORC-07 | G3：撤销一次 5 步写操作，业务桩数据全部复原 |
| D0 档案与授权书，编译为 Cedar | 15 | M3 | GOV-07 从 M4 提前到 M3、FND 组织同步 | G3：超额度动作转审批；负责人停用后 Agent 暂停 |
| D2 自治等级 L1〜L4 与自动降级 | 10 | M3 | D0、D1、HCI-05 | G3：一次撤销触发降级 |
| D2 影子上岗与晋级申请 | 15 | M4 | EVO-01〜03、ORC-03 | G4：影子 Run 不产生任何写操作，并产出上岗报告 |
| D3 价值账本与经营看板 | 20 | M4 | GOV-05、EVO-01、D2 | G4：看板数字可从账本明细逐条复算 |

容量上，3 后端加 1 前端的团队已经排满，这 95 人日需要从 M3、M4 里腾出来。候选的延后项是 CON-06（钉钉、企微）、CON-07（OpenAPI 转 MCP）、GOV-11（多环境）和 HCI-08 的工作台部分。它们都是对标补齐型的项，延后不影响卖点；确切的人日对账在你选定方向后做。

对前端的影响最大的是三个新画面：变更单 diff 卡片（飞书卡片和 Web 审批台共用）、数字员工档案页、经营看板。其余都是在已设计的画面上加字段。

## 需要你决定的事

1. **选哪些方向深化**。推荐 D0〜D3；如果首批客户是金融或国企，D4 应提前；如果更看重拉新客户，D5 的演示效果最好。
2. **是否接受为此延后部分对标项**（CON-06、CON-07、GOV-11、HCI-08 工作台），以及把 GOV-07 Cedar 从 M4 提前到 M3。
3. **对外叫法**。「数字员工」在国内客户里容易懂，但也容易被联想成 RPA；备选是「可信放权」。

你选定后，下一步是为选中的方向写 ADR（编号从 ADR-032 开始）、接口与数据模型、对 34 号计划和 M2 施工设计的修订，按 ADR-030 的变更流程提 PR。
