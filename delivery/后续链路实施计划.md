> 本文是 **G6 阶段主理人集成交付物**，与同批《一致性矩阵与冲突裁决》配套。它把 G3 §4.5 冻结的 L1 至 L10 链路优先级，结合 G4 方案 A 裁决与 G5 部署 / 安全实证，收敛为 **G6 通过后可直接进入的分批实施规格**。

## 3. P0 四条链路实施规格

### 3.1 L1 Runtime 状态落库与按 thread_id 会话加锁

**现状实证（G4 已推翻 G3 §2.5「无 checkpoint 表」旧快照，属时差，不是待开发项）**

| 能力 | 实证出处 |
| --- | --- |
| Runtime 状态已落库 | `V101__m0_runtime_kernel.sql` 建 `runtime_turn` / `runtime_item` / `runtime_approval` |
| 遗留字段清理与回填 | `V105__m0_drop_legacy_runtime.sql` 删除 `parts_json`；`V104__BackfillRuntimeItems.java` Java 回填 |
| 恢复计数与审批索引 | `V114__m1_runtime_recovery_approval.sql` 加 `recover_count` 与 `WAITING_APPROVAL` 索引 |
| session 更名 thread | `V128__rename_runtime_session_to_thread.sql` |
| 数据库行锁 | `RuntimeTurnMapper.xml:54` 的 `SELECT 1 FROM runtime_thread WHERE id = #{threadId} FOR UPDATE` |
| Redis 会话锁 | `RedisThreadLock.java:15` 的 `rt:lock:{threadId}` 加 `setIfAbsent` 加 TTL |
| 事件重放 | `ThreadEventsService.java:79` 的 `listAfterSeq(threadId, afterSeq, 500)` 四步重放 |

**真实缺口（L1 的待实现部分）**

| 编号 | 缺口 | 影响 |
| --- | --- | --- |
| L1-G01 | `StreamPump.subs` 与 `readPositions` 仍为 JVM 内存订阅态 | 进程重启后订阅游标丢失，无法水平扩展 |
| L1-G02 | `MemoryItemSink.streaming` 仍为内存态 | 流式增量项不落库，重启不可恢复 |
| L1-G03 | `SignalBus.local` 仍为本地信号 | 多实例下信号不可达 |
| L1-G04 | EventStream TTL 导致长时断线丢事件窗口 | 超过窗口的 `Last-Event-ID` 无法重放 |

**实施步骤（方案 A 复用补链，逐字遵循用户裁决）**

1. 以既有 `runtime_turn` / `runtime_item` / `runtime_approval` 为权威状态，**不新建独立 checkpoint 表、不新增 Flyway 迁移**。
2. 把 `StreamPump.subs` 与 `readPositions` 的订阅态外置到 Redis Stream，`MemoryItemSink.streaming` 的增量项写入既有 `runtime_item`，`SignalBus.local` 改为经 Redis Stream 发布订阅；复用现仓已有的 Redis 7，不引入新中间件（O7）。
3. 固化 `EventId` 单调游标与 `Last-Event-ID` 幂等；**状态快照重放的幂等键取 `threadId 加 EventId.seq`**，与 `Last-Event-ID` 共用同一 EventId 游标（G4 系统设计已冻结该取值，不重复发起中间确认）。
4. EventStream TTL 窗口与 `runtime_item` 权威重放源做衔接：TTL 内走 Stream 增量，超出窗口回落到 `listAfterSeq` 的数据库重放；不承诺无限期事件保留，窗口数值待 U 系列取证后回填。
5. 与 L4 共用同一 Turn 状态机，不新增第二套状态机。

**验收标准**：进程重启后状态可恢复；同 thread 并发串行化（数据库行锁加 Redis 锁双证）；契约测试绿；`Last-Event-ID` 重放幂等可证；不新增任何 Flyway 迁移文件。

### 3.2 L2 六个假实现 API 下线或替换

**现状**：G3 §4.5 要求「V6 待按 D7 §01 表名逐类检索确认，本报告不假设其已下线」；G4 UserStory 返工已写入 `RESERVED` 与「已下线」等实证结论，说明部分假实现已收口，但**六类逐类结论尚未形成一份可检索清单**。

**实施步骤**

1. 按 `design-notes/01` 登记的六类假实现表名逐类 `Grep` 检索，逐类输出「仍存在 / 已下线 / 已替换」三态结论与代码路径。
2. 对「仍存在」的类别，按 34 号四原则给出下线或替换方案；替换须复用既有真实实现，不新增中间件、不新增数据表。
3. 对「已下线」的类别，登记 `RESERVED` 或等价留痕证据，避免回归。
4. 输出清单交 G6 后首批验收，不在本轮改代码。

**验收标准**：六类逐类结论可检索、可复核；无未经登记的默认假实现继续承接生产流量。

### 3.3 L3 MQ 生产 / 消费 / 幂等三点核验与补链

**现状实证（G4 代码级三点齐备，但 X13 冻结定性不改判）**

| 点 | 实证出处 |
| --- | --- |
| 生产 | `OutboxEventPublisher.java` 实现 `EventPublisher`；`V130__m2_outbox.sql` 已建 `sys_outbox` |
| 消费 | `RocketMqConsumerBootstrap.java` 注册 `MessageListenerOrderly`；6 个 Consumer |
| 幂等 | `IdempotentDeliveryService`、`sys_consumed` 复合主键、`sys_dead_letter`；`V130` 三表齐备 |

**实施步骤**

1. 按域实测三点，逐点标注「已证实 / 未证实 / 待补」并给出按域实测入口；不把「类存在」当作「运行时闭环成立」。
2. 对「待补」项给出补链入口，**不新建 outbox 迁移**（`V130` 已建三表，方案 A 复用）。
3. 运行时端到端闭环取证转 U-01 与 V7；按 X13 冻结定性，本阶段**不改判** BA-05 / S0-02 / SEC-14 / DEP-14。
4. 与 L1 的 `EventId` 单调游标共用同一幂等语义，避免两套游标。

**验收标准**：三点核验表可逐条追溯；至少一次投递下不重复执行业务；X13 定性维持「缺失 / 闭环未证实」。

### 3.4 L4 SSE 事件续传与审批挂起恢复

**现状实证**：`ThreadEventsService.java:79` 已有 `listAfterSeq(threadId, afterSeq, 500)` 四步重放；`V114` 已加 `recover_count` 与 `WAITING_APPROVAL` 索引；`runtime_approval` 表已存在。

**实施步骤**

1. 把 `Last-Event-ID` 头与 `after` 查询参数统一收敛到 L1 冻结的 `EventId` 单调游标，重放幂等键取 `threadId 加 EventId.seq`。
2. 审批挂起恢复复用 `WAITING_APPROVAL` 状态与 `recover_count`，**审批跨多次不新开 Turn**；与 L1 共用同一 Turn 状态机。
3. 断线重连按「TTL 内 Stream 增量 → 超出窗口回落 `listAfterSeq` 数据库重放」两段式执行，与 L1-G04 衔接。
4. 不新增独立状态快照表、不新增迁移。

**验收标准**：事件 id 单调递增；状态快照重放幂等；审批跨多次不新开 Turn；契约测试绿。

### 3.5 P0 批次内建议顺序（供 G6 审核确认，非冻结裁决）

| 批次 | 内容 | 理由 |
| --- | --- | --- |
| 批次 1 | L1 先行，L4 紧随 | 二者共用同一 Turn 状态机与 EventId 游标，先立地基再接续传 |
| 批次 2 | L2 与 L3 可并行 | L2 是清单核验与下线，L3 是三点核验与补链，互不阻塞；L3 的幂等语义复用批次 1 的游标 |

每批次退出须同时满足：契约测试绿、Gate 冒烟通过、四态判定不因实现被改判、不新增 Flyway 迁移、不改 `deploy/compose.yml`。
